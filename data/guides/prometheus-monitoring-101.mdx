Prometheus monitoring has become the go-to choice for DevOps teams and site reliability engineers looking for a reliable, open-source solution. Whether you're just getting started with Prometheus 101 concepts or looking to improve your existing setup, this Prometheus monitoring guide covers everything from core architecture to hands-on configuration. By the end of this Prometheus tutorial, you'll know how to use Prometheus effectively for system and application monitoring.

## What is Prometheus Monitoring?

Prometheus is an open-source monitoring and alerting toolkit built for reliability and scalability. It's widely used to track performance metrics in systems and applications, offering a time-series data collection and analysis solution that fits modern infrastructure.

Developed by SoundCloud in 2012, Prometheus was created to address the need for robust monitoring in dynamic, cloud-native environments. It became open-source in 2015 and is now maintained by the Cloud Native Computing Foundation (CNCF). Today, Prometheus monitoring is the backbone of observability for many organizations running containers and microservices.

### Key Features of Prometheus

Some of the key features that make the Prometheus monitoring tool a popular choice include:

1. **Multi-Dimensional Data Model:**
Prometheus stores time-series data using a multi-dimensional model. Each metric is uniquely identified by its name and labels (key-value pairs), making it easy to filter and analyze data across various dimensions.
2. **Flexible Query Language (PromQL):**
Prometheus uses PromQL (Prometheus Query Language), a powerful query language for selecting, aggregating, and manipulating time-series data. PromQL enables complex queries for detailed insights and performance analysis.
3. **Autonomous Server Nodes:**
Prometheus operates with autonomous server nodes, meaning each node collects and stores its own data independently. This decentralized setup enhances scalability and ensures fault tolerance, removing the need for a centralized database.

<Figure src="/img/guides/2025/02/prometheus-monitoring-101-image.webp" alt="Key Features of Prometheus" caption="Key Features of Prometheus" />

Unlike traditional monitoring systems like [Nagios](/comparisons/nagios-alternatives/) or [Zabbix](/comparisons/zabbix-alternatives/), Prometheus is optimized for dynamic environments, particularly in cloud-native architectures. Prometheus uses a pull-based model for data collection, in contrast to the push-based methods used by many other systems. This gives Prometheus flexibility in monitoring services that are constantly changing, making it a powerful tool for modern infrastructure.

### Where is Prometheus Used?

Prometheus monitoring works well across a wide range of use cases:

- **Server & Cloud Monitoring:** Track resource usage like CPU, memory, and network activity.
- **Application Monitoring:** [Monitor APIs](/docs/application-monitoring/api-monitoring/), database performance, and response times.
- **Kubernetes & Microservices:** Automatically detect and track containerized applications.
- **Business Insights:** Measure website traffic, transactions, and system availability.

### Where is Prometheus Not Used?

Prometheus is great for time-series monitoring but not ideal for:

- **Log Management:** Designed for numerical metrics, not raw logs. Use [SigNoz](https://signoz.io/), [ELK Stack](/blog/elk-alternative-open-source/) or [Loki](/blog/loki-alternatives/) instead.
- **Long-Term Storage:** Data retention is limited; Thanos or Cortex is needed for historical analysis.
- **Tracing Requests:** Lacks [distributed tracing](/distributed-tracing/); Jaeger or SigNoz with [OpenTelemetry](/opentelemetry/) are better options.
- **Real-Time Streaming:** Works on intervals, not real-time events. Use Kafka or Flink for that.

Prometheus is best paired with other tools for a complete [observability stack](/guides/observability-stack/).

## How Does Prometheus Work?

Understanding how Prometheus monitoring operates under the hood is essential before diving into configuration. Prometheus has a straightforward yet powerful architecture designed for monitoring dynamic and large-scale systems.

### Pull-Based Model

Prometheus uses a pull-based approach, where it actively scrapes Prometheus metrics from target services (like applications and servers) over HTTP at regular intervals.

### Data Scraping Process and Intervals

Metrics are scraped from configured endpoints, with intervals (default 15 seconds) that can be adjusted based on needs.

For Prometheus to pull metrics from a target, the target must expose a specific HTTP endpoint, typically at the `/metrics` path. The HTTP endpoints follow the format; `hostaddress/metrics`. This endpoint provides the current state of the target in a plain text format that Prometheus can understand.

<Figure src="/img/guides/2025/02/prometheus-monitoring-101-how-does-prometheus-work-Untitled201.webp" alt="Metrics displayed from an HTTP endpoint (localhost:8080/metrics)" caption="Metrics displayed from an HTTP endpoint (localhost:8080/metrics)" />

Collected data is stored in a Time Series Database (TSDB), where each time series is identified by a metric name and labels. Data is efficiently compressed for fast storage and retrieval.

Prometheus uses PromQL, a powerful query language, for querying, filtering, and analyzing time-series data to gain insights, create alerts, and generate reports.

### Core Components of Prometheus

Prometheus comprises several key components that work together to create a comprehensive Prometheus monitoring solution.

<Figure src="/img/guides/2025/02/prometheus-monitoring-101-image%201.webp" alt="Prometheus architecture" caption="Prometheus architecture" />

1. **Prometheus Server**

    **Purpose:** This is the core of the Prometheus ecosystem, responsible for scraping, storing, and serving Prometheus metrics.

    **Components:**

    - **Data Retriever:** Pulls metrics from monitored targets at defined intervals using a pull-based model.
    - **Time Series Database (TSDB):** Stores metrics as time series data, optimized for high performance and efficient storage.
    - **HTTP Server:** Serves data to users and external tools via PromQL (Prometheus Query Language).
2. **Service Discovery**

    **Purpose:** Dynamically discover targets to monitor without manual intervention. This eliminates the need for static configurations, making Prometheus adaptable to scaling and dynamic infrastructure changes.

    **Tools Supported:**

    - **Kubernetes:** For monitoring containers, pods, and clusters.
    - **Consul:** For service discovery in dynamic environments.

    <Figure src="/img/guides/2025/02/prometheus-monitoring-101-image%202.webp" alt="Prometheus service discovery" caption="Prometheus service discovery" />

3. **Exporters**

    **Purpose:** Exporters act as intermediaries that enable Prometheus to monitor systems, services, or applications that do not natively expose Prometheus metrics in a compatible format. They collect data from these sources, transform it into a Prometheus-readable format, and expose the metrics for scraping.

    **Each exporter exposes an HTTP endpoint that Prometheus scrapes for metrics.**

4. **Alertmanager**

    **Purpose:** Handles alerts generated by Prometheus, manages their lifecycle, and routes them to the appropriate channels.

    **Features:**

    - Deduplication, grouping, and routing of alerts.
    - Integration with notification systems like:
        - **Email:** Sends email notifications for alerts.
        - **Slack:** Sends alerts to Slack channels.
        - **PagerDuty:** Handles incident response workflows.

    Alerts are configured in [Prometheus rules](/guides/what-is-a-prometheus-rule/) and pushed to [Alertmanager](/docs/manage/administrator-guide/configuration/alertmanager/) when triggered.

5. **Visualization Tools**

    **Purpose:** Enables users to analyze Prometheus metrics and visualize trends.

    **Options:**

    - **Prometheus Web UI:** Built-in interface for basic exploration and querying.
    - **Grafana:** Advanced dashboards with rich visualizations.
    - **SigNoz:** Combines [observability and monitoring](/blog/observability-vs-monitoring/), focusing on end-to-end tracking.
    - **PromLens:** Simplifies PromQL query building and exploration.

    [Grafana](/grafana-alternative/) is the most popular tool for dashboarding, but SigNoz provides deeper observability integrations.

6. **Remote Storage (Optional)**

    **Purpose:** Extends Prometheus monitoring for long-term storage or external analytics.

    **Features:**

    - Forwarding scraped metrics to external systems (e.g., AWS S3, Thanos, Cortex).
    - Enables scalability for long-term historical data.

    This feature is useful for environments where retaining Prometheus metrics for extended periods is critical.

7. **Pushgateway (Optional)**

    **Purpose:** Collects metrics from short-lived jobs (e.g., batch jobs) that cannot be scraped directly by Prometheus.

    **Usage:** Jobs push their metrics to [Pushgateway](/guides/prometheus-pushgateway/), which exposes them for Prometheus to scrape. It is also used in environments with transient workloads, such as [CI/CD pipelines](/blog/cicd-observability-with-opentelemetry/).

8. **Query Language (PromQL)**

    **Purpose:** PromQL is the query language used to retrieve and analyze metrics data from the Prometheus TSDB.

    **PromQL allows for flexible querying with features like filtering, aggregation, and mathematical operations to extract actionable insights.**

    Example of a PromQL query:

    <Figure src="/img/guides/2025/02/prometheus-monitoring-101-how-does-prometheus-work-Untitled203.webp" alt="PromQL query" caption="PromQL query" />

    This query checks the status of targets (Prometheus, [node_exporter](/guides/prometheus-node-exporter/), cadvisor, or mysqld_exporter) and returns whether they are up (1) or down (0).

9. **Scrape Targets**

    **Purpose:** Endpoints that expose Prometheus metrics for scraping.

    **Types of Scrape Targets:**

    - **Applications:** Custom or pre-built applications that expose metrics directly through an HTTP endpoint (e.g., `/metrics`).
    - **Infrastructure Components:** Such as Linux hosts, Docker containers, Kubernetes pods, and other system-level entities.
    - **Third-Party Exporters:** Services that bridge the gap between Prometheus and non-native systems by exposing metrics on behalf of those systems.

    [Targets](/guides/what-is-prometheus-target/) are defined in the Prometheus configuration file or dynamically discovered via service discovery.

## Setting Up Prometheus: A Quick Start Guide

This section of the Prometheus tutorial walks you through setting up Prometheus monitoring on a Linux system. If you're following along as a Prometheus 101 exercise, this is where things get hands-on.

1. Download the latest Prometheus release:

    ```bash
    wget <https://github.com/prometheus/prometheus/releases/download/v2.30.3/prometheus-2.30.3.linux-amd64.tar.gz>
    ```

2. Extract the archive:

    ```bash
    tar xvfz prometheus-*.tar.gz
    cd prometheus-*    
    ```

3. Create a basic configuration file named `prometheus.yml`:

    ```yaml:prometheus.yml
    global:
      scrape_interval: 15s
    
    scrape_configs:
      - job_name: 'prometheus'
        static_configs:
          - targets: ['localhost:9090']
    ```

4. Start Prometheus:

    ```bash
    ./prometheus --config.file=prometheus.yml    
    ```

Prometheus is now running and accessible at `http://localhost:9090`. You can verify it's working by navigating to the web UI and running a simple PromQL query like `up` to check target health.

## Understanding Prometheus Metrics and Data Model

Prometheus metrics are the foundation of everything the Prometheus monitoring tool does. Understanding how Prometheus organizes its data is key to writing useful queries and building effective dashboards. Here's a breakdown of the metric types and data model:

### Types of Prometheus Metrics

1. Counter:
    - A counter is a metric that only increases over time, representing a cumulative value. Common use cases include tracking the number of requests or errors.
    - Example: `http_requests_total` (number of HTTP requests processed).
2. Gauge:
    - A gauge represents a value that can go up or down, such as temperature or memory usage.
    - Example: `memory_usage_bytes` (memory usage in bytes).
3. Histogram:
    - A histogram samples observations (usually durations or sizes) and counts them in configurable buckets. It also provides summary statistics like the sum and count of observations.
    - Example: `http_request_duration_seconds` (histogram of request durations in seconds).
4. Summary:
    - A summary is similar to a histogram but also provides quantiles (e.g., 95th percentile) for a set of observations. It is typically used for tracking latencies or response times.
    - Example: `http_request_duration_seconds_sum` (total request duration) and `http_request_duration_seconds_count` (count of requests).

### Labels and Dimensions in Prometheus

Labels are key-value pairs associated with a metric that help to identify and filter the data. They add dimensions to your Prometheus metrics, enabling fine-grained queries.

Example:

```bash
http_requests_total{method="GET", status="200"}
```

Labels help create a multi-dimensional data model that allows efficient aggregation and filtering.

### Naming Conventions for Prometheus Metrics

Adopting consistent naming conventions is crucial for readability and maintainability. Here's how to structure Prometheus metrics and labels effectively:

- Metric Name: It should be clear, concise, and represent what the metric measures. Conventionally, metric names are in lowercase, and underscores are used to separate words.

    Example: `http_requests_total` (total number of HTTP requests).

- Label Names: Label names should describe the dimensions they represent. Use short but meaningful names to identify specific characteristics and avoid using [high-cardinality](/blog/high-cardinality-data/) labels (e.g., user IDs or timestamps) to maintain efficiency.

    Example: `method` (GET, POST) or `status` (200, 404).

### Prometheus Best Practices for Creating and Organizing Metrics

Following Prometheus best practices when creating and organizing metrics makes the difference between a useful monitoring setup and a noisy one.

1. Use Descriptive Names: Choose metric names that clearly describe what they measure and avoid overly generic names.
2. Leverage Labels for Granularity: Use labels to capture different dimensions (e.g., method, status code) but avoid using [high cardinality](https://signoz.io/blog/high-cardinality-data/) labels that could increase storage and query complexity.
3. Be Consistent with Naming: Stick to a consistent naming pattern for your metrics, labels, and units (e.g., `seconds` for durations, `bytes` for sizes).
4. Avoid Too Many Metrics: Only create Prometheus metrics that provide value for monitoring and troubleshooting. Too many metrics can make the system harder to manage.
5. Use Histograms and Summaries Wisely: Choose between histograms and summaries based on the use case. Histograms are typically better for large-scale aggregations, while summaries are more useful for precise quantile calculations.

## Querying Prometheus Data with PromQL

[PromQL](/guides/promql-cheat-sheet/) (Prometheus Query Language) is what makes Prometheus monitoring so powerful. It allows you to retrieve, filter, and manipulate time-series data stored in Prometheus. If you're learning how to use Prometheus, mastering PromQL is the single most important skill.

### Basic PromQL Syntax and Operators

- Metric Name: The name of the metric you want to query (e.g., `http_requests_total`).
- Labels: You can filter metrics by label values using curly braces `{}` (e.g., `http_requests_total{status="200"}`).
- Operators: PromQL supports various operators in filtering and comparing metrics.
    - Comparison operators: `=`, `!=`, `>`, `<`, `>=`, `<=`.
    - Arithmetic operators: `+`, `-`, `*`,`/`, `%` for operations on time-series data.
    - Logical operators: `and`, `or`, `unless` for combining or excluding series.
    - Aggregation operators: `sum`, `avg`, `min`, `max`, `count`, etc.

Example: To query all HTTP requests with a status code of 200:

```bash
http_requests_total{status="200"}
```

### Common PromQL Query Patterns and Prometheus Examples

Here are some PromQL patterns you'll use regularly in Prometheus monitoring:

1. Rate of Change: Calculate the rate of change for a counter metric (e.g., requests per second).

    ```bash
    rate(http_requests_total[5m])    
    ```

    This returns the per-second rate of HTTP requests over the last 5 minutes.

2. Aggregation: Aggregate data by a label, such as the total requests per HTTP method.

    ```bash
    sum(http_requests_total) by (method)
    ```

    This sums the `http_requests_total` metric and groups it by the `method` label (e.g., GET, POST).

3. Filtering by Time Range: Query Prometheus metrics over a specific time range (e.g., the last 1 hour).

    ```bash
    http_requests_total{status="200"}[1h]
    ```

    This returns the `http_requests_total` metric for status "200" over the last hour.

### Using PromQL Functions for Aggregation and Analysis

PromQL includes a variety of functions that allow for complex aggregation and analysis of Prometheus metrics:

1. `avg()`: Calculate the average value of a metric.

    ```bash
    avg(http_request_duration_seconds)
    ```

2. `max()`: Find the maximum value of a metric.

    ```bash
    max(http_request_duration_seconds)
    ```

3. `count()`: Count the number of time-series for a given metric.

    ```bash
    count(http_requests_total)
    ```

4. `rate()`: Calculate the rate of increase for counters (used for time-series data that only increases, like HTTP request counts).

    ```bash
    rate(http_requests_total[1m])
    ```

### Tips for Writing Efficient PromQL Queries

These PromQL tips reflect Prometheus best practices that experienced operators rely on daily:

1. Limit the Range: Use time ranges effectively in queries. For example, use `rate()` or `avg()` with short ranges like `[5m]` or `[1h]` to reduce computation time.
2. Use `rate()` for Counters: For counter metrics (e.g., requests, errors), always use `rate()` or `irate()` to avoid returning raw, increasing values.
3. Avoid High Cardinality Labels: High cardinality (many unique values) in labels (e.g., user IDs, instance IDs) can cause performance issues. Try to avoid using such labels in aggregation or as part of groupings.
4. Filter Early: Filter out unnecessary time series early in your PromQL queries using specific label filters to minimize the data Prometheus needs to process.
5. Use Aggregation Wisely: When using aggregation operators like `sum()`, `avg()`, or `count()`, make sure you're aggregating across the appropriate labels to avoid returning overly granular data.

1. Keep Dashboards Focused: Group related Prometheus metrics into panels to avoid clutter.

3. Set Thresholds: Define thresholds to highlight critical values (e.g., red for high error rates).
4. Leverage Annotations: Add event markers (e.g., deployments or outages) to correlate data with incidents.
5. Optimize Panel Queries: Avoid overly complex PromQL queries that could slow down your dashboard. Use shorter time ranges or caching when possible.

## Alerting with Prometheus

[Prometheus alerting](/guides/how-do-i-add-alerts-to-prometheus/) lets you proactively identify system issues by setting up thresholds and notifying you when Prometheus metrics cross those thresholds. Here's a breakdown of how to get started and optimize alerting.

### Configuring Alerting Rules in Prometheus

Prometheus uses alerting rules defined in the `prometheus.yml` configuration file to trigger alerts based on conditions. Here's how to use Prometheus alerting rules:

1. Define Alerting Rules:
Add an `alerting` section in the `prometheus.yml` file or include a separate rules file:

    ```yaml:prometheus.yml
    rule_files:
      - "alerts.yml"    
    ```

2. Example Alerting Rule:
In `alerts.yml`, define an alert for high CPU usage:

    ```yaml:alerts.yml
    groups:
      - name: cpu_alerts
        rules:
          - alert: HighCPUUsage
            expr: avg(rate(node_cpu_seconds_total{mode!="idle"}[5m])) > 0.8
            for: 2m
            labels:
              severity: critical
            annotations:
              summary: "High CPU usage detected"
              description: "The average CPU usage is above 80% for the last 2 minutes."
    ```

    - `expr`: PromQL expression to evaluate.
    - `for`: How long must the condition persist before firing an alert?
    - `labels`: Metadata for categorizing alerts (e.g., severity).
    - `annotations`: Add context for the alert, like a summary and description.
3. Apply Configuration: Restart the Prometheus server to apply the changes.

<Figure src="/img/guides/2025/02/prometheus-monitoring-101-image%206.webp" alt="Setting Alerts in Prometheus" caption="Setting Alerts in Prometheus" />

### Understanding Alert States and Labels

1. Alert States:
    - Pending: The condition has been met but not for the required duration.
    - Firing: The alert is active and will trigger notifications.
    - Resolved: The condition is no longer met.

    <Figure src="/img/guides/2025/02/prometheus-monitoring-101-image%207.webp" alt="Alert States" caption="Alert States" />

2. Labels:
    - Labels help identify and group alerts.
    - Example: `severity: critical` can be used to route high-priority alerts to specific channels.

    <Figure src="/img/guides/2025/02/prometheus-monitoring-101-image%208.webp" alt="Alert Labels" caption="Alert Labels" />

Alertmanager is used to handle notifications triggered by Prometheus alerts. It supports routing, deduplication, and silencing.

### Prometheus Best Practices for Creating Meaningful Alerts

These Prometheus best practices for alerting will help you avoid alert fatigue and focus on what actually matters:

1. Define Clear Alert Thresholds:
    - Use thresholds that represent real issues, avoiding false positives.
    - Example: Set disk usage alerts at 90%, not 70%.
2. Categorize Alerts by Severity:
    - Use labels like `severity: critical` or `severity: warning` to prioritize responses.
3. Add Context to Alerts:
    - Include meaningful summaries and descriptions in `annotations`.
    - Example: Specify affected systems or recommended actions.
4. Avoid Overlapping Alerts:
    - Ensure alerts are distinct and don't create noise for the same issue.
5. Test Alerts Regularly:
    - Use tools like the Prometheus web UI or PromQL queries to simulate alert conditions.
6. Integrate with Incident Management Tools:
    - Route alerts to tools like PagerDuty, Opsgenie, or Slack for streamlined handling.

## Scaling Prometheus for Production Environments

Scaling Prometheus monitoring effectively ensures it can handle the demands of large-scale, high-traffic systems. Here are key strategies from this Prometheus monitoring guide:

### 1. Federation for Large-Scale Deployments

- Use Prometheus Federation to split metrics collection across multiple Prometheus servers.
- Parent servers aggregate high-level Prometheus metrics from child servers, reducing the load on any single instance.
- Ideal for multi-cluster or region-specific setups.

### 2. Long-Term Storage Solutions

- Prometheus's built-in storage is not designed for long-term retention. Use remote write integrations with tools like:
    - Thanos: Adds long-term storage and global querying.
    - Cortex or VictoriaMetrics: Scalable solutions for high availability and extended data retention.

### 3. High Availability Setups

- Run multiple Prometheus instances with identical configurations to ensure fault tolerance.
- Use a load balancer or alert deduplication via Alertmanager to handle overlaps.

### 4. Performance Tuning and Optimization

- Limit the scrape interval for non-critical Prometheus metrics to reduce overhead.
- Use efficient PromQL queries and avoid heavy computations on large datasets.
- Leverage sharding by dividing targets among multiple Prometheus instances.

## Prometheus Exporters

Prometheus exporters enable you to gather Prometheus metrics from various systems, applications, and environments, making Prometheus monitoring more versatile and comprehensive.

### Overview of Common Exporters

- `node_exporter`: Collects system metrics like CPU, memory, and disk usage.
- `blackbox_exporter`: Tracks the availability and performance of network endpoints using HTTP, TCP, DNS, and ICMP.
- Database Exporters: Prometheus examples include `postgres_exporter` for PostgreSQL and `mysqld_exporter` for MySQL.
- Custom Exporters: For applications or services without native Prometheus support.

Exporters are typically lightweight applications that expose metrics to Prometheus.

### Custom Exporters

If no existing exporter meets your requirements, you can create custom exporters tailored to your applications. Custom exporters expose Prometheus metrics in the text-based format, which allows Prometheus to scrape and store them effectively.

### Prometheus Best Practices for Using Exporters

- Choose Verified Exporters: Use community-supported or official exporters for critical systems.
- Reduce Noise: Disable unnecessary Prometheus metrics to focus on relevant data and minimize storage usage.
- Ensure Reliability: Monitor exporters themselves to avoid missing key metrics during downtime.
- Keep Exporters Updated: Use the latest versions to benefit from performance improvements and fixes.

## FAQs

### What is Prometheus monitoring and how does it differ from other tools?

Prometheus monitoring is an open-source approach to collecting time-series metrics using a pull-based model. Unlike push-based monitoring tools like Nagios or Zabbix, Prometheus actively scrapes targets over HTTP, making it better suited for dynamic, cloud-native environments. Its multi-dimensional data model and PromQL query language give it an edge over traditional alternatives.

### How does Prometheus handle high-cardinality data?

Prometheus can struggle with high-cardinality data. Prometheus best practices include limiting label combinations and using recording rules to pre-aggregate data. Keeping cardinality under control is one of the most important things to get right when learning how to use Prometheus at scale.

### Can Prometheus be used for logging as well as metrics?

No. Prometheus logging is not supported—Prometheus is built specifically for numerical time-series metrics. For logging, consider complementary tools like Loki or use a comprehensive solution like SigNoz that handles both metrics and logs natively.

### What are the limitations of Prometheus, and how can they be addressed?

Prometheus has limitations in long-term storage and high-cardinality data handling. These can be addressed through remote storage solutions (Thanos, Cortex) and careful metric design. For teams that need metrics, logs, and traces in one place, SigNoz offers a more complete alternative to running Prometheus monitoring alongside multiple separate tools.
