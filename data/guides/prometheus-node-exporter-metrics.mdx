Prometheus Node Exporter collects host-level metrics such as CPU time, available memory, disk activity, and network traffic. Prometheus scrapes these metrics so you can query them and set up alerts when a host needs attention.

This guide takes you through that setup, then shows how to tune collectors, add custom metrics, and configure common host alerts. You’ll also see how to send Node Exporter metrics to [SigNoz Cloud](https://signoz.io/) using [OpenTelemetry](https://signoz.io/opentelemetry/).

## Prerequisites

- **Prometheus** - A monitoring and alerting toolkit that collects and stores metrics as time series data. Download and install Prometheus from the <a href="https://prometheus.io/download/" rel="noopener noreferrer nofollow" target="_blank">official website</a>.


## Install & Run the Prometheus Node Exporter

The easiest way to install Node Exporter is to download the precompiled binary from the Prometheus <a href="https://prometheus.io/download/#node_exporter" rel="noopener noreferrer nofollow" target="_blank">official downloads page</a>. The tarball contains a single static executable that can be extracted and run directly on any Linux/Unix-based system.

If you prefer not to leave the terminal, you can also use the following commands to download and extract Node Exporter:

```bash
# Download the latest version (adjust version number, OS, and ARCH).
wget https://github.com/prometheus/node_exporter/releases/download/v<VERSION>/node_exporter-<VERSION>.<OS>-<ARCH>.tar.gz

# Extract binary
tar xvfz node_exporter-<VERSION>.<OS>-<ARCH>.tar.gz

# Change directory to the extracted folder
cd node_exporter-<VERSION>.<OS>-<ARCH>

# Start the node exporter
./node_exporter
```

## Configure Prometheus to Scrape Node Exporter

Prometheus reads all scrape targets from its main configuration file: `prometheus.yml`. If you don’t already have one, you can create it now and update it with the below configs.

<KeyPointCallout title="Do you already have a prometheus.yml file?" defaultCollapsed="true">

Do not replace your existing `prometheus.yml` with the example shown below. Overwriting it will remove your current Prometheus settings, which is not intended.

Instead, simply add the Node Exporter configuration block under the `scrape_configs` section and set the appropriate `static_configs` target.

</KeyPointCallout>

```yaml
global:
  # How frequently Prometheus scrapes all targets unless overridden
  scrape_interval: 15s

scrape_configs:
  # === Scrape Node Exporter Metrics ===
  - job_name: 'node' # A name to identify this scrape job
    static_configs:
      - targets: ['localhost:9100']
        # Node Exporter exposes metrics on port 9100 by default
        # Replace 'localhost' with the server IP if scraping remotely
```

<KeyPointCallout title="Breakdown of Prometheus.yml file" defaultCollapsed="true">

`global` : Defines default settings that apply to all scrape jobs unless a job overrides them.

`scrape_interval: 15s`: Tells Prometheus to collect metrics from each target every 15 seconds.

`scrape_configs`: This section defines what Prometheus should scrape. Each entry under scrape_configs is a scrape job (a logical group of targets).

`static_configs`: Tells Prometheus, "These targets are manually defined and fixed."

</KeyPointCallout>

Once your `prometheus.yml` file is updated, start Prometheus using the command below:

```bash
prometheus --config.file=./prometheus.yml --web.enable-lifecycle
```

This will load your scrape targets. Now that Prometheus is running, let’s move on to visualizing the metrics using the Prometheus Expression Browser.

## Check the Metrics in Prometheus

Open `http://localhost:9090/targets` and check that the `node` target is `UP`. You can also run:

```promql

```

A value of `1` confirms the scrape succeeded. To explore the CPU metrics, enter the following query in the Prometheus expression browser and switch to the graph view:

This shows the fraction of time each CPU core spent in system mode over the last minute.

## Limitations of Default Node Exporter Configurations

Node Exporter enables many collectors by default. Start with these defaults, then review which metrics your dashboards and alerts actually use before changing the collector set.

Common issues teams run into:

- **Metric noise:** Unused metrics increase storage and query costs.
- **Resource overhead:** Unnecessary collectors add CPU and I/O overhead on hosts.
- **Alert fatigue:** Alerting on raw metrics without context leads to false positives.
- **Lack of ownership:** Teams collect metrics they don’t know what to do with.

In production, every metric should serve a purpose (dashboards, alerts, or capacity planning). This brings us to the next critical step: **Configuring Node Exporter Collectors**. By enabling only the collectors you actually need, you ensure that the metrics you ingest are intentional, meaningful, and aligned with real operational goals.

## Configuring Node Exporter Collectors

Collectors determine which categories of system metrics Node Exporter exposes, such as CPU, memory, disks, networking, thermal sensors, filesystem stats, etc.

Node Exporter ships numerous collectors, most of which are enabled by default. You can explore the complete list of collectors and the metrics they expose in the <a href="https://github.com/prometheus/node_exporter" rel="noopener noreferrer nofollow" target="_blank">Official Node Exporter GitHub repository</a>. 

Stop the exporter before restarting it with a different set of collectors. You can control them using these startup flags:

- `--collector.<name>`: enable a collector
- `--no-collector.<name>`: disable a default collector
- `--collector.disable-defaults`: start with nothing and enable only what you need

**For Example**

Enable the processes collector (disabled by default)
    
    ```bash
    ./node_exporter --collector.processes
    ```
    
Disable the entropy collector
    
    ```bash
    ./node_exporter --no-collector.entropy
    ```
    
Minimal mode: enable only CPU and memory collectors:
    
    ```bash
    ./node_exporter \
      --collector.disable-defaults \
      --collector.cpu \
      --collector.meminfo
    ```
    

After configuring collectors, you can verify changes by re-running:

```bash
curl http://localhost:9100/metrics
```

By now, you’ve seen how Node Exporter collectors control which categories of metrics are exposed from a host. Tuning collectors helps reduce noise and overhead, but it still leaves one crucial question unanswered: **"Which metrics should you actually care about?"**

## Explore Most Common Node Exporter Metrics

Even with a minimal set of collectors enabled, Node Exporter exposes hundreds of host-level metrics, but only a subset is essential for day-to-day monitoring and alerting. In production, the goal isn’t to understand every metric Node Exporter exposes. The goal is to identify a small, reliable set of signals that helps better understand the host state.

Below are some of the most essential metric families you’ll use when building dashboards or defining alerting rules.
| Category        | Metric                                                                 | Description |
|-----------------|------------------------------------------------------------------------|-------------|
| CPU Metrics     | `node_cpu_seconds_total`                                                | Total CPU time spent in different modes (idle, user, system, iowait, etc.). |
| Memory Metrics  | `node_memory_MemAvailable_bytes`, `node_memory_MemTotal_bytes`          | Used for memory utilization and low-memory alerts. |
| Disk Metrics    | `node_filesystem_avail_bytes`, `node_filesystem_size_bytes`             | Used for disk-space-low alerts and capacity monitoring. |
| Disk I/O        | `node_disk_io_time_seconds_total`                                       | Time the device has spent handling I/O. Useful for monitoring disk activity. |
| Network Metrics | `node_network_receive_bytes_total`                                      | Total number of bytes received over the network interface. |
| Network Metrics | `node_network_transmit_bytes_total`                                     | Total number of bytes transmitted (sent) over the network interface. |
| System Load     | `node_load1`, `node_load5`, `node_load15`                                | Load averages over 1, 5, and 15 minutes, including runnable tasks and tasks in uninterruptible sleep on Linux. |

## When Built-In Metrics Aren’t Enough

The metrics we’ve covered so far represent the core health signals of a Linux host. For most infrastructure teams, CPU, memory, disk, and network metrics form the backbone of reliable host monitoring.

However, real-world systems often have environment-specific conditions that generic exporters can’t capture.

Examples include:

- Repeated failed SSH login attempts
- Status of backup jobs or cron tasks
- Disk cleanup scripts that must run successfully
- Presence (or absence) of critical files
- Custom health checks tied to your organization’s operational logic

These signals are just as important as CPU or memory usage, but they don’t exist as built-in Node Exporter metrics. This is where custom host metrics come into play.

## Expose Custom Host Metrics

Node Exporter doesn’t try to anticipate every possible operational requirement. Instead, it provides a simple and powerful extension mechanism: the textfile collector. It is a custom collector you can use to expose your own metrics by writing them to `.prom` files.

**Step 1**: Create a directory

```bash
sudo mkdir -p /var/lib/node_exporter/textfile_collector
```

**Step 2**: Start Node Exporter with the textfile collector

```bash
./node_exporter \
  --collector.textfile \
  --collector.textfile.directory=/var/lib/node_exporter/textfile_collector
```

**Step 3**: Create a custom metric file in the directory we created in step 1

```bash
echo "custom_failed_ssh_logins_total $(grep -c 'Failed password' /var/log/auth.log)" \
  > /var/lib/node_exporter/textfile_collector/ssh_failures.prom
```

**Step 4**: Verify Metrics

```bash
curl http://localhost:9100/metrics | grep custom_failed
```

## Setting Up Most Common Node Exporter Alerting Rules

To monitor Linux hosts effectively using Node Exporter, SRE teams rely on four fundamental indicators of system health. These are a host-level adaptation of Google’s “Golden Signals” for services. Each signal maps directly to a PromQL alerting rule that Prometheus can evaluate.

1. **CPU Usage (Saturation)**: High CPU usage indicates saturation, leading to slow application performance or request queuing.
2. **Memory Usage (Saturation):** Memory pressure can cause swapping, OOM kills, or severe application slowdowns.
3. **Disk I/O Saturation (Saturation)**: When disks are saturated, read/write operations slow down, and applications may stall.
4. **Filesystem Fullness (Errors / Saturation):** Running out of disk space can cause service outages, failed writes, or database corruption.

Let’s set up these alerting rules.

**Step 1:** Create a directory for the alert rules alongside `prometheus.yml`.

```bash
mkdir -p rules
```

**Step 2:** Save the following rules as `rules/node_alerts.yml`.

```yaml:node_alerts.yml
groups:
  - name: node_exporter_alerts
    rules:
      # CPU
      - alert: HighCPUUsage
        # Triggers when average non-idle CPU usage exceeds 85% across all cores.
        expr: (100 - avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m]) * 100)) > 85
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "High CPU usage on {{ $labels.instance }}"

      # Memory
      - alert: HighMemoryUsage
        # Triggers when available memory drops below 15% of total memory.
        expr: (node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes)
              / node_memory_MemTotal_bytes > 0.85
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "High memory usage on {{ $labels.instance }}"

      # Sustained disk activity
      - alert: DiskIOSaturation
        # Triggers when disk spends more than 80% of time handling I/O operations.
        expr: rate(node_disk_io_time_seconds_total[5m]) > 0.80
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "Sustained disk activity on {{ $labels.instance }}"

      # Disk Fullness
      - alert: DiskSpaceLow
        # Triggers when available disk space falls below 10% on any real filesystem.
        expr: node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}
              / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"} < 0.10
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "Low disk space on {{ $labels.instance }}"
```
<KeyPointCallout defaultCollapsed="true" title="Alert Rule File: Technical Breakdown">

`alert`: Unique, stable name used by Prometheus and Alertmanager to identify, deduplicate, and track the alert.

`expr`: PromQL expression evaluated by Prometheus that defines the condition under which the alert should fire.

`labels`: Key–value metadata attached to the alert, used for routing, grouping, filtering, and ownership.

`severity`: Conventional label indicating alert urgency (for example **warning** or **critical**) and driving notification routing.

`annotations`: Human-readable context added to alerts, shown in notifications to help responders understand the issue.

`summary`: Short, one-line annotation that describes what is wrong and where, typically displayed as the alert title.

</KeyPointCallout>

Your Prometheus directory structure should now look like this:

```scss
.
  ├── prometheus.yml
  └── rules/
       └── node_alerts.yml
```

**Step 3:** Add the rule file to your existing `prometheus.yml` without removing its scrape jobs:

```yaml
rule_files:
  - 'rules/node_alerts.yml'
```

Check the rules and configuration before reloading Prometheus:

```bash
promtool check rules rules/node_alerts.yml
promtool check config prometheus.yml
```

Reload the running process using your service manager or a `SIGHUP` signal. For the rule lifecycle and notification setup, see our [Prometheus rules guide](https://signoz.io/guides/what-is-a-prometheus-rule/).

## Send Node Exporter Metrics to SigNoz Cloud

Once you have checked the metrics in Prometheus, you can also send them to SigNoz Cloud for dashboards alongside application metrics, logs, and traces. The [OpenTelemetry Collector](https://signoz.io/blog/opentelemetry-collector-complete-guide/) provides two ways to collect host metrics, depending on whether you want to keep Node Exporter.

### Scrape Node Exporter with the Prometheus Receiver

If Node Exporter is already running, configure the OpenTelemetry Collector's Prometheus receiver to scrape its `/metrics` endpoint. Add the host and port, such as `localhost:9100`, as a scrape target and enable the receiver in the metrics pipeline. The Collector then forwards the metrics to SigNoz through its configured exporter.

Open *Metrics Explorer* in *SigNoz Cloud* and search for a metric such as `node_cpu_seconds_total` to confirm that data is arriving.

<Figure src="/img/guides/2025/12/prometheus-node-exporter-metrics.webp" alt="Metrics tab in SigNoz Cloud with node_ metrics" caption="Metrics tab in SigNoz Cloud with node_ metrics" />

Follow the [SigNoz Prometheus receiver guide](https://signoz.io/docs/userguide/prometheus-metrics/) for the full configuration.

### Collect Host Metrics without Node Exporter

If you prefer to collect host metrics directly through OpenTelemetry, use the `hostmetrics` receiver instead. It collects CPU, memory, disk, and network metrics without a separate Node Exporter process.

This receiver uses different metric names, so the Node Exporter queries and alert rules in this guide will need adapting. Follow the [SigNoz host metrics guide](https://signoz.io/docs/infrastructure-monitoring/user-guides/hostmetrics/) to configure it and check the hosts view.

<Figure src="/img/guides/2025/12/prometheus-node-exporter-infrastructure.webp" alt="Host Level Metrics Visualized in SigNoz Cloud Dashboard" caption="Host Level Metrics Visualized in SigNoz Cloud Dashboard" />

## Conclusion

You now have a Node Exporter setup that exposes host metrics, a Prometheus scrape job to collect them, and examples for tuning collectors and configuring alerts. You can keep this Prometheus setup or use the OpenTelemetry Collector to send Node Exporter metrics to SigNoz.

By being intentional about what you collect and alert on, Node Exporter becomes a reliable signal for host health rather than a source of metric sprawl and alert fatigue.
