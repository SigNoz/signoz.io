Python logging helps you understand what your application is doing at runtime. It is built into the Python standard library and gives you a consistent way to record diagnostics, warnings, errors, and operational events without scattering `print()` statements throughout your code.

As an application grows, logging becomes essential for debugging, incident response, performance analysis, and auditing. A good logging setup also makes it much easier to route logs to files, terminals, or centralized platforms for monitoring and alerting.

## What is Python logging and why is it important?

Python’s `logging` module provides a flexible event-logging framework for applications and libraries. Compared with `print()`, it gives you:

1. **Severity levels** so you can separate debug noise from important production issues.
2. **Consistent formatting** with timestamps, logger names, and contextual fields.
3. **Multiple destinations** such as the console, files, syslog, email, or queues.
4. **Centralized configuration** so application behavior can change by environment without rewriting logging calls.

Logging is especially useful for:

- **Debugging**: understand control flow and inspect failures.
- **Operations**: surface warnings, errors, and service health signals.
- **Performance analysis**: record timings and bottlenecks.
- **Security and audit trails**: capture important user or system events.
- **Centralized observability**: ship logs to tools that help you search, correlate, and alert on them.

## Getting started with Python logging

Start with the standard pattern: create a module-level logger and configure logging once in your application entry point.

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
)

logger = logging.getLogger(__name__)

logger.info("Application started")
```

This is enough for many small scripts. For larger applications, move configuration into a dedicated function or a `dictConfig()` block so environment-specific settings are easier to manage.

### Logging levels

Python defines six pre-defined levels. In day-to-day application code, the five severity levels below `NOTSET` are the ones you will use most often.

| Level | Typical use |
| --- | --- |
| `NOTSET` | Delegate level handling to ancestors or handle everything on a handler |
| `DEBUG` | Detailed diagnostic information |
| `INFO` | Normal application events |
| `WARNING` | Something unexpected happened, but the application can continue |
| `ERROR` | An operation failed |
| `CRITICAL` | A severe failure that may prevent the program from continuing |

## Core building blocks of the logging module

Python logging revolves around four main concepts: loggers, handlers, formatters, and filters.

### Loggers

A logger is the object your code calls to emit messages.

```python
import logging

logger = logging.getLogger(__name__)
logger.info("Fetching data")
```

Logger names are hierarchical and usually mirror your module structure. For example, `my_app.api` is a child of `my_app`. That hierarchy matters because log records can **propagate** upward to *ancestor* handlers.

A good default is:

- create one logger per module with `logging.getLogger(__name__)`
- configure handlers centrally in the application
- avoid attaching handlers to many child loggers unless you intentionally disable propagation

### Handlers

Handlers decide **where** log records go.

Common built-in handlers include:

- `StreamHandler` for console output
- `FileHandler` for writing to a file
- `RotatingFileHandler` for size-based rotation
- `TimedRotatingFileHandler` for time-based rotation
- `SysLogHandler` for syslog
- `SMTPHandler` for email alerts
- `QueueHandler` and `QueueListener` for queue-based, high-throughput logging

Here is a simple logger that writes to both the console and a file:

```python
import logging

logger = logging.getLogger("my_app")
logger.setLevel(logging.DEBUG)

console_handler = logging.StreamHandler()
file_handler = logging.FileHandler("app.log", encoding="utf-8")

logger.addHandler(console_handler)
logger.addHandler(file_handler)
```

### Formatters

Formatters control the layout of each log entry.

```python
import logging

formatter = logging.Formatter(
    "%(asctime)s - %(name)s - %(levelname)s - %(message)s"
)
```

You can attach the same formatter to multiple handlers:

```python
console_handler.setFormatter(formatter)
file_handler.setFormatter(formatter)
```

If you want more context, add fields such as `%(funcName)s`, `%(filename)s`, or `%(lineno)d`.

### Filters

Filters give you fine-grained control over which records are emitted.

```python
import logging

class SpecificFilter(logging.Filter):
    def filter(self, record):
        return "specific" in record.getMessage()

logger = logging.getLogger("my_app")
logger.setLevel(logging.DEBUG)

handler = logging.StreamHandler()
handler.addFilter(SpecificFilter())
logger.addHandler(handler)

logger.info("This message contains a specific keyword")
logger.info("This message will be filtered out")
```

Filters are useful when you want to drop noisy events, route only certain records to a handler, or add custom logic before records are emitted.

## Recommended configuration patterns

`basicConfig()` is a good starting point, but production applications usually benefit from centralized configuration.

### Use `dictConfig()` for larger applications

`dictConfig()` makes it easier to define handlers, formatters, levels, and logger policies in one place.

```python
import logging.config
from logging.handlers import RotatingFileHandler

LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "standard": {
            "format": "%(asctime)s %(levelname)s %(name)s %(message)s"
        }
    },
    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "formatter": "standard",
            "level": "INFO",
        },
        "file": {
            "class": "logging.handlers.RotatingFileHandler",
            "formatter": "standard",
            "level": "DEBUG",
            "filename": "app.log",
            "maxBytes": 5_000_000,
            "backupCount": 5,
            "encoding": "utf-8",
        },
    },
    "root": {
        "level": "INFO",
        "handlers": ["console", "file"],
    },
}

logging.config.dictConfig(LOGGING)
logger = logging.getLogger(__name__)
```

### Configure by environment

Development and production usually need different verbosity.

```python
import logging
import os

logger = logging.getLogger(__name__)

env = os.getenv("APP_ENV", "development")

if env == "development":
    logging.basicConfig(level=logging.DEBUG)
else:
    logging.basicConfig(level=logging.WARNING)
```

In development, verbose logs help you debug quickly. In production, a higher threshold reduces noise and storage overhead.

### Applications and libraries should configure logging differently

Applications should configure handlers and levels. Libraries usually should **not** add real output handlers of their own. Instead, library authors typically attach a `NullHandler` and let the application decide what to do with those records.

```python
import logging

logger = logging.getLogger(__name__)
logger.addHandler(logging.NullHandler())
```

### Avoid duplicate log lines

Duplicate records are often caused by attaching handlers to both a child logger and one of its ancestors while leaving propagation enabled.

As a rule of thumb:

- attach handlers high in the logger hierarchy, often on the root logger
- let child loggers propagate upward
- set `propagate = False` only when you intentionally want a logger to stop bubbling records upward

## Structured logging and contextual data

Plain-text logs are easy to read, but structured logs are easier to query and analyze in log platforms.

### Adding contextual fields with `extra`

```python
import logging

logging.basicConfig(
    format="%(asctime)s %(levelname)s %(name)s %(clientip)s %(user)s %(message)s"
)

logger = logging.getLogger("auth")
logger.info(
    "Login succeeded",
    extra={"clientip": "192.168.0.10", "user": "alice"},
)
```

Use `extra` carefully: if your formatter expects a field and it is missing, formatting will fail for that record.

### Using `LoggerAdapter` for repeated context

If you need to attach the same contextual fields repeatedly, `LoggerAdapter` is cleaner than passing `extra` on every call.

```python
import logging

base_logger = logging.getLogger("payments")
logger = logging.LoggerAdapter(base_logger, {"service": "checkout"})

logger.info("Charge created")
```

### Emitting JSON logs with the standard library

You do not need a third-party package just to start emitting JSON.

```python
import json
import logging

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {
            "timestamp": self.formatTime(record, self.datefmt),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
        }

        for field in ("service", "request_id", "user_id"):
            if hasattr(record, field):
                payload[field] = getattr(record, field)

        if record.exc_info:
            payload["exception"] = self.formatException(record.exc_info)

        return json.dumps(payload)

handler = logging.StreamHandler()
handler.setFormatter(JsonFormatter())

logger = logging.getLogger("api")
logger.addHandler(handler)
logger.setLevel(logging.INFO)

logger.info("Request handled", extra={"request_id": "req-123"})
```

## Logging exceptions, performance, and concurrency

### Log exceptions with stack traces

Inside an exception handler, `logger.exception()` is usually the clearest option because it logs at `ERROR` level and includes exception information automatically.

```python
import logging

logger = logging.getLogger(__name__)

def divide(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        logger.exception("Division failed")
        raise
```

### Avoid unnecessary work in hot paths

When logging inside performance-sensitive code paths:

- use the right log level
- avoid generating very verbose messages in production
- prefer parameterized logging calls so message formatting happens only if the record is emitted
- guard expensive debug-only work with `isEnabledFor()`

```python
import logging

logger = logging.getLogger(__name__)

user_id = 42
logger.info("User %s logged in", user_id)

if logger.isEnabledFor(logging.DEBUG):
    expensive_payload = {"items": list(range(1000))}
    logger.debug("Payload details: %s", expensive_payload)
```

### High-throughput applications: use queue-based logging

Python’s logging module is thread-safe, but slow handlers can still become a bottleneck. For high-throughput services, queue-based logging is the built-in way to move handler work off the request or worker thread.

```python
import logging
import logging.handlers
import queue

log_queue = queue.Queue()

queue_handler = logging.handlers.QueueHandler(log_queue)
stream_handler = logging.StreamHandler()
listener = logging.handlers.QueueListener(log_queue, stream_handler)

logger = logging.getLogger("worker")
logger.setLevel(logging.INFO)
logger.addHandler(queue_handler)

listener.start()
try:
    logger.info("Processing started")
finally:
    listener.stop()
```

This pattern is preferable to relying on a non-existent `logging.handlers.AsyncHandler`.

### Multi-threaded and multi-process logging

The logging module is designed to be thread-safe. That said, multi-process logging needs more care. If multiple processes write to the same file, use an approach designed for that scenario, such as a queue-based listener process or an external log collector.

## Troubleshooting common logging issues

### No logs are appearing

Check these first:

- the logger level
- the handler level
- whether the handler is attached
- whether propagation has been disabled unexpectedly

### You are seeing duplicate log lines

This usually means the same record is being handled multiple times. Common causes include:

- a handler attached to both a child logger and an ancestor logger
- repeated configuration during application startup
- calling `basicConfig()` or your setup function more than once unintentionally

### Custom fields are missing from the output

If you use `extra`, your formatter must include those fields. Also make sure every matching log call supplies the required keys.

### Log files have encoding problems

Specify an encoding on file-based handlers:

```python
handler = logging.FileHandler("app.log", encoding="utf-8")
```

### Log files grow without bound

Use `RotatingFileHandler` or `TimedRotatingFileHandler`, or ship logs to a centralized platform with retention controls.

## Key takeaways

- Python’s standard `logging` module is flexible enough for most applications.
- Start with `getLogger(__name__)` and centralized configuration.
- Use handlers to control destinations and formatters to control output.
- Prefer `dictConfig()` for larger applications.
- Use `QueueHandler` and `QueueListener` for high-throughput logging.
- Avoid duplicate handlers and accidental propagation mistakes.
- Structured logs and centralized observability tools make logs far more useful in production.

## FAQs

### What is logging in Python?

Logging in Python is the process of recording runtime events using the standard-library `logging` module so you can debug, monitor, and audit application behavior.

### How do I set up logging in a Python script?

For a simple script:

```python
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)
logger.info("Hello from logging")
```

### What are the different logging levels in Python?

The pre-defined levels are `NOTSET`, `DEBUG`, `INFO`, `WARNING`, `ERROR`, and `CRITICAL`.

### Can I log to multiple destinations at the same time?

Yes. Add multiple handlers to the same logger or configure them centrally with `dictConfig()`.

### How do I add custom fields to my log messages?

Use `extra` for per-call fields or `LoggerAdapter` when you want to reuse the same context across many log calls.

### What is a good production logging baseline?

A practical baseline is:

- module-level loggers created with `getLogger(__name__)`
- centralized configuration with `dictConfig()`
- structured logs where possible
- rotation or centralized log shipping
- redaction of sensitive data before logs leave the process
