A Prometheus target is an endpoint or resource that exposes metrics for collection. These targets serve as the primary data sources for [Prometheus monitoring](https://signoz.io/guides/what-is-prometheus-for-monitoring/), allowing it to gather valuable information about your systems and applications.

Prometheus targets come in various forms, including:

- Applications instrumented with Prometheus client libraries
- Servers exposing system-level metrics
- Databases offering performance statistics
- Third-party systems with Prometheus-compatible metric endpoints

This guide explains how Prometheus discovers targets, how to configure their metrics endpoints, and how to add labels that identify each service or host. It also covers authentication, custom HTTP headers, and troubleshooting failed scrapes.

## How Prometheus Discovers Targets

Prometheus needs a list of targets to scrape. You can define this list in two ways:

- **Static configuration:** Add target addresses under `static_configs` in `prometheus.yml`. Use this when you have a small set of targets whose addresses rarely change.
- **Service discovery:** Prometheus gets target addresses from Kubernetes, DNS, cloud APIs, or YAML/JSON files. With file-based discovery, it watches the files for changes and updates valid target entries without requiring a reload of `prometheus.yml`.

## How to configure Prometheus targets

To configure a target, you need an endpoint that exposes metrics and a scrape job that points to it. After adding the job, validate the configuration and reload Prometheus to apply it. If your application already serves metrics, you can [skip to the scrape job configuration](#configure-the-scrape-job) and use its address instead.

### Expose a metrics endpoint for your target

A target identifies where Prometheus should scrape. The metrics endpoint is the HTTP URL it requests, such as `http://localhost:8000/metrics`. The hostname and port go in `targets`, while `metrics_path` selects the URL path and defaults to `/metrics`.

If your application does not expose metrics yet, add a Prometheus client library. This Python example counts completed iterations of a demo task and exposes the counter over HTTP. In a real application, increment the counter after the operation you want to measure completes.

Create a virtual environment and install the library. These commands use a macOS or Linux shell:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install prometheus-client
```

Save the following as `metrics_demo.py`:

```python
import time
from prometheus_client import Counter, start_http_server

completed_tasks = Counter('demo_tasks_completed_total', 'Total completed demo tasks')

if __name__ == '__main__':
    start_http_server(8000, addr='127.0.0.1')
    while True:
        time.sleep(1)
        completed_tasks.inc()
```

Run `python3 metrics_demo.py`, then check the endpoint in another terminal:

```bash
curl -fsS http://127.0.0.1:8000/metrics
```

Among the library's output, look for lines such as these. The counter value increases while the process runs; your value will depend on when you request it.

```text
# HELP demo_tasks_completed_total Total completed demo tasks
# TYPE demo_tasks_completed_total counter
demo_tasks_completed_total 5.0
```

`HELP` describes the metric, `TYPE` identifies it as a counter, and the final line contains its name and value. Client libraries handle the exposition format for you. The <a href="https://prometheus.github.io/client_python/" target="_blank" rel="noopener noreferrer nofollow">official Python client guide</a> provides more instrumentation examples.

### Configure the scrape job

Open `prometheus.yml` and add this job under `scrape_configs`. If that key already exists, append the job to its list rather than adding another `scrape_configs` key:

```yaml
scrape_configs:
  - job_name: 'python-demo'
    scrape_interval: 15s
    metrics_path: /metrics
    static_configs:
      - targets: ['127.0.0.1:8000']
```

This example assumes Prometheus runs directly on the same host as the Python process. Inside a container, `127.0.0.1` refers to that container, so use an address reachable from Prometheus and configure the application's listening address accordingly. The demo binds to loopback for local use. `scrape_interval: 15s` sets this job's interval explicitly; `metrics_path` defaults to `/metrics`.

### Validate, reload, and check the target

Check the configuration before applying it:

```bash
promtool check config prometheus.yml
```

If the check passes, reload Prometheus by sending `SIGHUP` to its process. If you started Prometheus with `--web.enable-lifecycle`, you can instead reload it over HTTP:

```bash
curl -fsS -X POST http://localhost:9090/-/reload
```

Use your Prometheus address and authentication settings if they differ. The reload endpoint is disabled without that flag. Restarting Prometheus also loads the configuration, but a reload avoids a restart.

Open the target health page and query `up{job="python-demo"}`. A value of `1` means the scrape succeeded; `0` means it failed. Then query `demo_tasks_completed_total{job="python-demo"}` to confirm that the demo metric is available.

### Scrape targets that require authentication or custom headers

Some metrics endpoints require a token, an API key, or a tenant header before they return data. Configure these request settings in the target's scrape job. Prometheus supports custom headers directly through `http_headers`.

For example, this job scrapes an HTTPS endpoint that expects a tenant ID and an API key:

```yaml
scrape_configs:
  - job_name: 'protected-app'
    scheme: https
    metrics_path: /metrics
    http_headers:
      X-Tenant-ID:
        values: ['team-a']
      X-API-Key:
        files: ['/etc/prometheus/secrets/metrics-api-key']
    static_configs:
      - targets: ['app.example.com:443']
```

Replace the example hostname, header names, and tenant ID with those required by your endpoint. Create the API key file at the specified path and make it readable by the Prometheus process. If Prometheus runs in a container, mount the file at that path inside the container. These headers apply to every target in this scrape job; use separate jobs when targets require different credentials.

Use `values` for non-sensitive headers and `files` to read credentials from a separate file. Inline sensitive values can use `secrets`, which hides them on the configuration page, but they remain in the YAML file. Keep credentials out of version control and use HTTPS when sending them.

For HTTP Basic authentication, use `basic_auth` with `username` and `password_file`. For a bearer token, use `authorization` with `type: Bearer` and `credentials_file`; the file should contain the token without the `Bearer` prefix. Use these authentication settings instead of adding an `Authorization` header under `http_headers`. See the <a href="https://prometheus.io/docs/prometheus/latest/configuration/configuration/#http_config" target="_blank" rel="noopener noreferrer nofollow">Prometheus HTTP configuration reference</a> for the supported options and restrictions.

Validate and reload the configuration as shown above, then check the target health page. For a `401` or `403` response, verify the credentials, required header names, and permission to access the metrics endpoint.

### Restrict access to metrics endpoints

Metrics can expose internal service names and operational data. Keep production endpoints on private networks and restrict access to the Prometheus scrapers using firewall rules or Kubernetes NetworkPolicies. Avoid credentials, personal data, and unbounded values such as user IDs in metric labels.

Enforce authentication and TLS at the application, exporter, or a reverse proxy that protects it. The scrape-job settings above supply credentials to that endpoint; they do not turn on authentication at the endpoint itself. If the endpoint requires mutual TLS, configure `tls_config` with the appropriate `ca_file`, `cert_file`, and `key_file`. Keep certificate verification enabled. See the <a href="https://prometheus.io/docs/operating/security/" target="_blank" rel="noopener noreferrer nofollow">Prometheus security model</a> for endpoint access guidance.

### Add target-specific labels

Target labels describe where metrics came from, such as their environment, service, or region. For static targets, add a `labels` map to each group in `static_configs`:

```yaml
scrape_configs:
  - job_name: 'api-server'
    static_configs:
      - targets: ['api-1.example.com:8080']
        labels:
          environment: 'production'
          service: 'api'
          region: 'us-west-2'
      - targets: ['api-staging.example.com:8080']
        labels:
          environment: 'staging'
          service: 'api'
          region: 'us-west-2'
```

Labels in a group apply to every target in that group's `targets` list. Use separate groups when their label values differ. After validating and reloading the configuration, inspect the labels on the target health page. Query `up{job="api-server", environment="production"}` to select the production target.

If a scraped metric already has a label with the same name, the default `honor_labels: false` setting keeps the configured target label and renames the conflicting scraped label with an `exported_` prefix. With `honor_labels: true`, the scraped label wins. Check for collisions before adding labels such as `service` or changing `instance`.

For service-discovered targets, use `relabel_configs` to copy discovery metadata into labels you want to keep. For example, add these rules to an existing Kubernetes pod scrape job:

```yaml
relabel_configs:
  - source_labels: [__meta_kubernetes_namespace]
    target_label: namespace
  - source_labels: [__meta_kubernetes_pod_name]
    target_label: pod
```

These rules assume the job already uses `kubernetes_sd_configs` with `role: pod` and has the required API permissions and target selection rules. Discovery labels beginning with `__meta_` are temporary; copying their values to ordinary labels makes them available in queries after target relabeling.

Target relabeling runs before scraping. It differs from `metric_relabel_configs`, which processes scraped samples, and from PromQL's `label_replace()`, which changes query results. Choose stable label values and avoid high-cardinality values such as request IDs. Our [Prometheus labels guide](https://signoz.io/guides/what-are-prometheus-labels/) explains label selection in more detail.

### Use a hostname as the instance label

By default, `instance` contains the target's host and port. The host can already be a DNS name; it is not always an IP address. To use a readable name while scraping an IP address, supply a hostname label and copy it to `instance`:

```yaml
scrape_configs:
  - job_name: 'node-exporter'
    static_configs:
      - targets: ['192.0.2.10:9100']
        labels:
          hostname: 'worker-01'
      - targets: ['192.0.2.11:9100']
        labels:
          hostname: 'worker-02'
    relabel_configs:
      - source_labels: [hostname]
        regex: '(.+)'
        target_label: instance
```

Here, Prometheus still scrapes `192.0.2.10:9100`, but stores its metrics with `instance="worker-01"` and `hostname="worker-01"`. The rule changes `instance` without changing `__address__`, which determines the network destination. The regex skips empty hostname values. Replace the example IPs with your actual targets.

You can also set `instance` directly under `labels` for a static target. Copying a separate hostname label is useful when the same rule needs to work across a changing target inventory. For file-based discovery, put the target-to-hostname mappings in a file such as `/etc/prometheus/targets/nodes.yml`:

```yaml
- targets: ['192.0.2.10:9100']
  labels:
    hostname: 'worker-01'
- targets: ['192.0.2.11:9100']
  labels:
    hostname: 'worker-02'
```

Replace the job's `static_configs` with the following and keep the `relabel_configs` rule above:

```yaml
file_sd_configs:
  - files: ['/etc/prometheus/targets/nodes.yml']
```

Prometheus detects changes to the discovery file. The file supplies the hostname mapping; relabeling does not perform reverse DNS lookups.

Keep `instance` unique within each job, especially when several exporters run on one host. Retain a port or another distinguishing value when needed. Changing label values creates new time series for future scrapes; it does not rename historical data. Review dashboards and alerts that match the old instance values. To keep existing selectors working, leave `instance` unchanged and query or group by the separate `hostname` label instead.

## Troubleshooting Prometheus target issues

Start with the target health page and its last scrape error. Test connectivity from the host or container running Prometheus, since an endpoint reachable from your laptop may not be reachable from the scraper.

| Symptom | What to check |
| --- | --- |
| Target missing from the scrape list | Confirm the job loaded, service discovery returned the target, and target relabeling did not drop it. |
| `up` is `0` or the target is DOWN | Read the scrape error to identify the connection, authentication, TLS, or response-format problem. |
| Connection refused or DNS error | Check the address, port, listening interface, DNS resolution, and network access. |
| `404` response | Check `metrics_path` and confirm the endpoint exists. |
| `401` or `403` response | Check credentials, required headers, and endpoint permissions. |
| TLS certificate error | Check the certificate hostname, trusted CA, expiry, and any required client certificate. |
| Scrape timeout | Check endpoint response time and network latency. Review `scrape_timeout`, which cannot exceed `scrape_interval`. |
| Response parsing error | Confirm the endpoint returns supported metrics rather than JSON or an HTML login page, and sends the appropriate `Content-Type`. |
| Scrape succeeds but a counter stays unchanged | Confirm the instrumented operation is running and increments the counter. |

`up = 1` confirms a successful scrape, not the health of every part of the application. An absent `up` series can mean the target is no longer discovered or was dropped; it is different from a failed scrape returning `up = 0`. For response-format details, see the <a href="https://prometheus.io/docs/instrumenting/exposition_formats/" target="_blank" rel="noopener noreferrer nofollow">supported exposition formats</a>.

## FAQs

### What's the difference between a Prometheus target and an exporter?

A target is the endpoint Prometheus scrapes. An exporter is a program that collects metrics from another system and exposes them at an endpoint Prometheus can scrape. Applications with built-in Prometheus instrumentation can expose targets without a separate exporter.

### How often does Prometheus scrape targets by default?

The built-in default for `scrape_interval` is one minute. Example configurations often explicitly set it to `15s`. A job inherits the global interval unless it sets its own, so check both the `global` and job-level configuration.

### Can Prometheus automatically discover new targets in a Kubernetes cluster?

Yes. Configure `kubernetes_sd_configs` with the appropriate discovery role and Kubernetes API permissions. Use target relabeling to select the endpoints and ports you want to scrape.

### How many targets can a single Prometheus instance handle?

There is no fixed target limit that fits every deployment. Capacity depends on active time series, samples per scrape, scrape frequency, query load, and CPU, memory, and storage resources. Measure those factors under your workload before adding capacity.
