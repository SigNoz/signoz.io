## Overview

SigNoz reads exceptions from the traces your services already send. Your instrumentation records an exception as an `exception` span event, and SigNoz collects those events into a dedicated **Exceptions** view that groups them by service, exception type, and message.

Every exception carries the span and trace IDs of the request it came from, so you can move from a row in the list to the flame graph of the failing request.

With the Exceptions view you can:

- Browse the exception types your services hit, with count, first seen, and last seen.
- Filter by deployment environment, service, host, or Kubernetes cluster, namespace, deployment, and pod.
- Read the full stack trace for any occurrence.
- Open the trace that produced the exception to inspect the failing span and what ran before and after it.
- Step through individual occurrences of the same exception group.
- [Alert on exceptions](https://signoz.io/docs/alerts-management/exceptions-based-alerts/) when a new type shows up or a known one spikes.

## How to View Exceptions?

Open **Exceptions** from the left navigation. The list shows one row per exception group with its type, message, occurrence count, first seen, last seen, and the application that reported it. Sort by exception type, count, first seen, last seen, or application. Narrow the time range from the picker at the top, and use the filter sidebar or the search bar to scope the list to a service, environment, host, or Kubernetes workload.

To follow an exception into the request that caused it:

1. Click an exception type to open its detail page. You get the stack trace, the identifiers that tie the exception back to its origin (`spanID`, `traceID`, `serviceName`, and `groupID`), and **Older** and **Newer** buttons to step through other occurrences in the same group.

   <Figure
       src="/img/docs/exception-detail-1.webp"
       alt="Exception detail page showing stack trace and span attributes"
       caption="Exception detail page with stack trace and span attributes"

2. Click **See the error in trace graph** to open the full trace. The flame graph and waterfall show the failing span in the context of the whole request, and the span details panel gives you the span's own attributes, events, and correlated logs. The exception detail page does not carry those attributes, so open the trace when you need them.

## What counts as an exception

SigNoz builds the Exceptions view from span events. Log records do not feed it. SigNoz treats a span event as an exception when its name is `exception` or ends in `.exception`, which covers the current OpenTelemetry conventions:

- `exception`
- `http.client.request.exception` and `http.server.request.exception`
- `db.client.operation.exception`
- `rpc.client.call.exception` and `rpc.server.call.exception`

From each event SigNoz stores `exception.type`, `exception.message`, `exception.stacktrace`, and `exception.escaped`. Type and message fill the list columns and decide grouping, so record at least one of them. OpenTelemetry has deprecated `exception.escaped`, so treat it as legacy data rather than something to set on new instrumentation.

<Admonition type="info">
OpenTelemetry is <a href="https://opentelemetry.io/blog/2026/deprecating-span-events/" target="_blank" rel="noopener noreferrer nofollow">deprecating the span-event exception APIs</a> in favor of the Logs API. No action is needed today: existing `recordException` calls stay valid and span events remain the default. The migration runs per instrumentation library, not across an SDK. A library that has adopted the `OTEL_SEMCONV_EXCEPTION_SIGNAL_OPT_IN` opt-in emits log records instead of span events when you set it to `logs`, and those exceptions will not appear in the Exceptions view. Libraries that have not adopted it ignore the variable, and `recordException` calls in your own code stay span events either way. Set `logs/dup` to emit both while you migrate.
</Admonition>

## Recording exceptions

Instrumentation libraries record an exception event when an exception escapes the operation they wrap, so an auto-instrumented Python, Java, Ruby, or JavaScript app reports its unhandled exceptions without any code changes. Record an exception yourself when it marks a failed operation that no library captured, such as an error you catch at a request boundary and turn into a 500 response. OpenTelemetry <a href="https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-spans/" target="_blank" rel="noopener noreferrer nofollow">no longer recommends recording exceptions</a> that you catch and recover from inside the span, since they add noise to the Exceptions view and to any alerts built on it.

To record an exception, get the current span from the tracer and call `recordException()` or its language equivalent. That call adds the span event and leaves the span status alone, so set the status to error separately when the exception means the operation failed.

Examples for each language:

### Record Exceptions in Java:

```java
// Get the current span from the tracer
Span span = Span.current();

// recordException converts a Throwable into a span event.
span.recordException(new RuntimeException("Something went wrong"));

// Set the status of the span to error
span.setStatus(StatusCode.ERROR, "Something bad happened!");
```

### Record Exceptions in Golang:

```go
import "go.opentelemetry.io/otel/codes"

// Get the current span from the tracer
span := trace.SpanFromContext(ctx)

// RecordError converts an error into a span event.
span.RecordError(err)

// Mark span as failed.
span.SetStatus(codes.Error, "internal error")
```

### Record Exceptions in Python:

```python
# Get the current span from the tracer
from opentelemetry import trace
from opentelemetry.trace.status import Status, StatusCode

span = trace.get_current_span()

# record_exception converts the exception into a span event. 
exception = Exception("Something went wrong")
span.record_exception(exception)

# Update the span status to failed.
span.set_status(Status(StatusCode.ERROR, "internal error"))
```

### Record Exceptions in JavaScript:

```javascript
// import relevant opentelemetry functions
const { trace, SpanStatusCode } = require("@opentelemetry/api");

// Get the current span from the tracer
const span = trace.getActiveSpan();
// Create a new sample error
err = new Error("This is a sample error");
// recordException converts the error into a span event. 
span.recordException(err);
// Update the span status to failed.
span.setStatus({ code: SpanStatusCode.ERROR, message: String(err) });
```

### Record Exceptions in .NET:

OpenTelemetry .NET provides several options to report Exceptions in Activity. It varies from the most basic option of setting Status, to fully recording the Exception itself to activity. Follow the <a href="https://github.com/open-telemetry/opentelemetry-dotnet/blob/main/docs/trace/reporting-exceptions/README.md" target="_blank" rel="noopener noreferrer nofollow">OpenTelemetry .NET documentation</a> to learn more.

Below is one such example:

```csharp
using (var activity = MyActivitySource.StartActivity("Foo"))
{
    try
    {
        Func();
    }
    catch (SomeException ex)
    {
        activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
        activity?.RecordException(ex);
    }
}
```

### Record Exceptions in Ruby:

```ruby
# Import otel sdk
require "opentelemetry/sdk"

# Get the current span from the tracer
span = OpenTelemetry::Trace.current_span

begin
  do_work
rescue StandardError => e
  # Record the exception and update the span status.
  span.record_exception(e)
  span.status = OpenTelemetry::Trace::Status.error(e.to_s)
end
```

### Record Exceptions in PHP:

```php
$span = $tracer->spanBuilder('process-order')->startSpan();
$scope = $span->activate();

try {
    doWork();
} catch (Throwable $t) {
    // Record the exception and update the span status.
    $span->recordException($t);
    $span->setStatus(StatusCode::STATUS_ERROR, $t->getMessage());
} finally {
    $scope->detach();
    $span->end();
}
```

## Grouping Exceptions

<Admonition type="note">
This section applies to Self-Host only. It configures the `otel-collector`'s `clickhousetraces` exporter directly, which SigNoz Cloud manages for you.
</Admonition>

By default, exceptions on **Exception List page** are grouped by service name, exception type
and exception message. This might result in high cardinality of exception groups, especially
if exception messages contains UUIDs or randomly generated IDs.

To reduce the cardinality of the exception grouping, set the `low_cardinal_exception_grouping`
to `true` in `clickhousetraces` exporter configuration. This will result in exception grouping
by name of service and exception type.

<Admonition type="info">
This new grouping strategy will only be applied to new data injected after new instance of
`otel-collector` with updated the environment variable.
</Admonition>

### Docker Standalone and Docker Swarm

To enable exception grouping, users can set `LOW_CARDINAL_EXCEPTION_GROUPING=true` as an
environment variable for otel collector service in `docker-compose.yaml`.

```yaml {4}
services:
  otel-collector:
    environment:
      - LOW_CARDINAL_EXCEPTION_GROUPING=true
```

### Kubernetes (Helm)

To enable exception grouping, include the following in `override-values.yaml`:

```yaml
otelCollector:
  lowCardinalityExceptionGrouping: true
```

To install or upgrade SigNoz release with the updated configurations in `override-values.yaml`:

```yaml
helm -n platform upgrade \
    --create-namespace --install \
    my-release signoz/signoz \
    -f override-values.yaml
```
