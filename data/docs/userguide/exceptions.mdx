## Overview

SigNoz reads exceptions from the traces your services already send. Your instrumentation records an exception as an `exception` span event, and SigNoz collects those events into a dedicated **Exceptions** view that groups them by service, exception type, and message.

Every exception carries the span and trace IDs of the request it came from, so you can move from a row in the list to the flame graph of the failing request. Nothing appears until your services send traces, so [instrument them first](https://signoz.io/docs/instrumentation/overview/) if you have not already.

With the Exceptions view you can:

- Browse the exception types your services hit, with count, first seen, and last seen.
- Filter by deployment environment, service, host, or Kubernetes cluster, namespace, deployment, and pod.
- Read the stack trace for any occurrence whose instrumentation recorded one.
- Open the trace that produced the exception to inspect the failing span and what ran before and after it.
- Step through individual occurrences of the same exception group.
- [Alert on exceptions](https://signoz.io/docs/alerts-management/exceptions-based-alerts/) when a new type shows up or a known one spikes.

## How to View Exceptions

Open **Exceptions** from the left navigation. The list shows one row per exception group with its type, message, occurrence count, first seen, last seen, and the application that reported it. Sort by exception type, count, first seen, last seen, or application. Narrow the time range from the picker at the top, and use the filter sidebar or the search bar to scope the list to a service, environment, host, or Kubernetes workload.

To follow an exception into the request that caused it:

1. Click an exception type to open its detail page. You get the stack trace when the instrumentation recorded one, the identifiers that tie the exception back to its origin (`spanID`, `traceID`, `serviceName`, and `groupID`), and **Older** and **Newer** buttons to step through other occurrences in the same group. OpenTelemetry treats `exception.stacktrace` as recommended rather than required, and some SDKs omit it by default, so the panel can be empty.

   <Figure

       caption="Exception detail page with the stack trace and the identifiers linking back to the span"

2. Click **See the error in trace graph** to open the full trace. The flame graph and waterfall show the failing span in the context of the whole request, and the span details panel gives you the span's own attributes, events, and correlated logs. The exception detail page does not carry those attributes, so open the trace when you need them.

## What Counts as an Exception

SigNoz builds the Exceptions view from span events. Log records do not feed it. A span event counts as an exception when its name is `exception` or ends in `.exception`.

In practice that means the `exception` event. It is the only name OpenTelemetry's <a href="https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-spans/" target="_blank" rel="noopener noreferrer nofollow">span convention</a> defines, and it is what every `recordException` call emits today. The `.exception` suffix names such as `http.server.request.exception` and `db.client.operation.exception` belong to the newer <a href="https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-logs/" target="_blank" rel="noopener noreferrer nofollow">log-based convention</a>, so a library that has adopted them emits log records and those do not reach the Exceptions view. SigNoz matches the suffix so that the events do land there whenever an SDK routes them back onto spans. That matching needs OTel Collector `v0.144.3` or newer, which shipped with SigNoz `v0.120.0`.

From the `exception` event SigNoz stores `exception.type`, `exception.message`, `exception.stacktrace`, and `exception.escaped`. Type and message fill the list columns and decide grouping, so record at least one of them. OpenTelemetry has deprecated `exception.escaped`, so treat it as legacy data rather than something to set on new instrumentation.

<Admonition type="info">
OpenTelemetry is <a href="https://opentelemetry.io/blog/2026/deprecating-span-events/" target="_blank" rel="noopener noreferrer nofollow">deprecating the span-event exception APIs</a> in favor of the Logs API. No action is needed today: existing `recordException` calls stay valid and span events remain the default. The migration runs per instrumentation library, not across an SDK. A library that has adopted the `OTEL_SEMCONV_EXCEPTION_SIGNAL_OPT_IN` opt-in emits log records instead of span events when you set it to `logs`, and those exceptions will not appear in the Exceptions view. Libraries that have not adopted it ignore the variable, and `recordException` calls in your own code stay span events either way. Set `logs/dup` to emit both while you migrate.
</Admonition>

## Recording Exceptions

Instrumentation libraries record an exception event when an exception escapes the operation they wrap, so once your services are instrumented they report unhandled exceptions with no extra code at the call site. Record an exception yourself when it marks a failed operation that no library captured, such as an error you catch at a request boundary and turn into a 500 response. OpenTelemetry <a href="https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-spans/" target="_blank" rel="noopener noreferrer nofollow">no longer recommends recording exceptions</a> that you catch and recover from inside the span, since they add noise to the Exceptions view and to any alerts built on it.

To record an exception, get the current span from the tracer and call `recordException()` or its language equivalent. That call adds the span event and leaves the span status alone, so set the status to error separately when the exception means the operation failed.

The Java, Go, Python, JavaScript, and Ruby examples read the span that instrumentation already made current in a request handler, so they must run inside an active span. Outside one, those APIs hand back a no-op span (`undefined` in JavaScript) and the exception goes nowhere. The .NET and PHP examples start their own span instead, so they stand alone as long as a tracer provider is configured.

Each example records the failure and then returns a server error rather than rethrowing. Let the exception escape instead and the surrounding instrumentation records it for you, in which case drop the manual `recordException` call to avoid two events for one failure.

### Record Exceptions in Java

```java
import io.opentelemetry.api.trace.Span;
import io.opentelemetry.api.trace.StatusCode;

void handleRequest() {
    // Get the current span from the tracer
    Span span = Span.current();

    try {
        doWork();
    } catch (Exception e) {
        // recordException converts the Throwable into a span event.
        span.recordException(e);
        // Mark the span as failed.
        span.setStatus(StatusCode.ERROR, e.getMessage());
        // Surface the failure to the caller.
        sendServerError();
    }
}
```

### Record Exceptions in Golang

```go
import (
	"context"

	"go.opentelemetry.io/otel/codes"
	"go.opentelemetry.io/otel/trace"
)

func handleRequest(ctx context.Context) {
	// Get the current span from the context
	span := trace.SpanFromContext(ctx)

	if err := doWork(); err != nil {
		// RecordError converts the error into a span event. Go omits
		// exception.stacktrace unless you pass WithStackTrace.
		span.RecordError(err, trace.WithStackTrace(true))
		// Mark the span as failed.
		span.SetStatus(codes.Error, err.Error())
		// Surface the failure to the caller.
		sendServerError()
	}
}
```

### Record Exceptions in Python

```python
from opentelemetry import trace
from opentelemetry.trace import Status, StatusCode


def handle_request():
    # Get the current span from the tracer
    span = trace.get_current_span()

    try:
        do_work()
    except Exception as e:
        # record_exception converts the exception into a span event.
        span.record_exception(e)
        # Mark the span as failed.
        span.set_status(Status(StatusCode.ERROR, str(e)))
        # Surface the failure to the caller.
        send_server_error()
```

### Record Exceptions in JavaScript

```javascript
// import relevant opentelemetry functions
const { trace, SpanStatusCode } = require("@opentelemetry/api");

function handleRequest() {
  // Get the current span from the tracer. It is undefined outside an active span.
  const span = trace.getActiveSpan();

  try {
    doWork();
  } catch (err) {
    // recordException converts the error into a span event.
    span?.recordException(err);
    // Mark the span as failed.
    span?.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
    // Surface the failure to the caller.
    sendServerError();
  }
}
```

### Record Exceptions in .NET

OpenTelemetry .NET offers several ways to report exceptions on an `Activity`, from setting the status alone to recording the full exception. The <a href="https://opentelemetry.io/docs/languages/dotnet/instrumentation/" target="_blank" rel="noopener noreferrer nofollow">OpenTelemetry .NET documentation</a> covers the rest:

```csharp
using System.Diagnostics;

using (var activity = MyActivitySource.StartActivity("Foo"))
{
    try
    {
        Func();
    }
    catch (SomeException ex)
    {
        activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
        activity?.AddException(ex);
        // Surface the failure to the caller.
        SendServerError();
    }
}
```

`AddException` needs .NET 9 or `System.Diagnostics.DiagnosticSource` 9.0.0 and later. On older versions, call `activity?.RecordException(ex)` from `OpenTelemetry.Api` instead. That extension method is marked obsolete in `OpenTelemetry.Api` 1.10.0 and later, where it forwards to `AddException`.

### Record Exceptions in Ruby

```ruby
# Import otel sdk
require "opentelemetry/sdk"

def handle_request
  # Get the current span from the tracer
  span = OpenTelemetry::Trace.current_span

  begin
    do_work
  rescue StandardError => e
    # Record the exception and update the span status.
    span.record_exception(e)
    span.status = OpenTelemetry::Trace::Status.error(e.to_s)
    # Surface the failure to the caller.
    send_server_error
  end
end
```

### Record Exceptions in PHP

```php
use OpenTelemetry\API\Trace\StatusCode;
use Throwable;

$span = $tracer->spanBuilder('process-order')->startSpan();
$scope = $span->activate();

try {
    doWork();
} catch (Throwable $t) {
    // Record the exception and update the span status.
    $span->recordException($t);
    $span->setStatus(StatusCode::STATUS_ERROR, $t->getMessage());
    // Surface the failure to the caller.
    sendServerError();
} finally {
    $scope->detach();
    $span->end();
}
```

## Grouping Exceptions

<Admonition type="note">
This section applies to Self-Host only. It sets an option on the `otel-collector`'s `clickhousetraces` exporter, and SigNoz Cloud runs a managed collector that you do not configure. Cloud users cannot change the grouping strategy today. Reach out to support if variable exception messages are splitting one problem across many groups.
</Admonition>

By default, SigNoz groups the exceptions in the list by service name, exception type, and exception message. Messages that embed UUIDs or randomly generated IDs split one underlying problem across many groups.

To group by service name and exception type only, set `low_cardinal_exception_grouping` to `true` in the `clickhousetraces` exporter configuration.

<Admonition type="info">
The new strategy applies only to data ingested after you restart `otel-collector` with the updated environment variable. Groups that already exist keep their original grouping.
</Admonition>

### Docker Standalone and Docker Swarm

Set `LOW_CARDINAL_EXCEPTION_GROUPING=true` as an environment variable on the otel-collector service in `docker-compose.yaml`.

```yaml {4}
services:
  otel-collector:
    environment:
      - LOW_CARDINAL_EXCEPTION_GROUPING=true
```

### Kubernetes (Helm)

Include the following in `override-values.yaml`:

```yaml
otelCollector:
  lowCardinalityExceptionGrouping: true
```

Then install or upgrade the SigNoz release with the updated `override-values.yaml`:

```bash
helm -n platform upgrade \
    --create-namespace --install \
    my-release signoz/signoz \
    -f override-values.yaml
```

## Troubleshooting
</ToggleHeading>

### The Exceptions List Is Empty

Work through these causes in order:

1. **No traces are reaching SigNoz.** Open [Traces](https://signoz.io/docs/userguide/traces/) and check whether any spans arrive in the same time range. If none do, fix ingestion first by following [Instrumentation overview](https://signoz.io/docs/instrumentation/overview/). Exceptions ride along with trace data, so nothing can appear until spans do.
2. **Spans arrive, but nothing records an exception.** Instrumentation libraries record only exceptions that escape the operation they wrap, so an application that catches everything internally reports none. Add a `recordException` call where the operation fails, as shown in [Recording Exceptions](#recording-exceptions).
3. **A filter or the time range hides them.** Clear the filter sidebar and the search bar, then widen the time range. The list is scoped to the selected window.

### Domain-Specific Exception Events Do Not Show Up

Names such as `db.client.operation.exception` and `http.server.request.exception` come from OpenTelemetry's log-based exception convention, so a library that has adopted them emits log records. The Exceptions view reads span events, so those never arrive. They show up only when your SDK routes the events back onto spans, and in that case the collector also has to be `v0.144.3` or newer to match the `.exception` suffix. Check the collector image tag in your `docker-compose.yaml` or Helm values.

### Exceptions Disappeared After Switching to Log-Based Exceptions

An instrumentation library running with `OTEL_SEMCONV_EXCEPTION_SIGNAL_OPT_IN=logs` emits log records instead of span events, and the Exceptions view reads span events only. Set the variable to `logs/dup` to emit both while you migrate.

### One Problem Splits Into Many Exception Groups

Exception messages that embed UUIDs, IDs, or other variable text produce a separate group per message. On Self-Host, switch to low-cardinality grouping as described in [Grouping Exceptions](#grouping-exceptions), which applies to newly ingested data only. On SigNoz Cloud the grouping strategy is not configurable, so contact support. Either way, dropping the variable part from the exception message at the source fixes it for both.
