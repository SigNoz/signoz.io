## Overview

High trace volume increases storage costs and can make it harder to find meaningful signals. You can control trace volume at two points in the pipeline: at the application (head sampling) or at the OpenTelemetry Collector (tail sampling or filtering).

<Admonition type="info">

- Your application is instrumented with an OpenTelemetry SDK
- You have access to the OpenTelemetry Collector configuration (`otel-collector-config.yaml`)

</Admonition>

## Steps

### Step 1: Choose your approach

| Approach | When to use |
|---|---|
| **Head sampling (at the application)** | You want a simple, stateless percentage-based drop applied before any data leaves your app |
| **Tail sampling (at the Collector)** | You need policy-based decisions (e.g., always keep error traces, drop healthy ones) after seeing the full trace |
| **Attribute dropping (at the Collector)** | You want to keep all traces but strip noisy or sensitive span attributes |
| **Span filtering (at the Collector)** | You want to drop specific individual spans based on name, status, or attributes |

---

### Step 2: Head sampling — at the application

Sampling decisions made here are called **head sampling** because the decision is made at the start of the trace.

**Option A — TraceIdRatioBased sampler**

Set these environment variables before starting your application:

```bash
OTEL_TRACES_SAMPLER="parentbased_traceidratio"
OTEL_TRACES_SAMPLER_ARG=0.001
```

`0.001` means 1 in every 1000 traces is sampled. See the [OTel TraceIdRatioBased spec](https://github.com/open-telemetry/opentelemetry-specification/blob/9758cdddee20c699b620aac1d7f777ccd490f252/specification/trace/sdk.md#traceidratiobased) for details.

**Option B — Custom sampler**

Implement the [`ShouldSample`](https://github.com/open-telemetry/opentelemetry-specification/blob/9758cdddee20c699b620aac1d7f777ccd490f252/specification/trace/sdk.md#shouldsample) method in the `Sampler` interface. Return one of:

| SamplingResult | Effect |
|---|---|
| `DROP` | Span is dropped |
| `RECORD_ONLY` | Span is recorded locally but not exported |
| `RECORD_AND_SAMPLE` | Span is recorded and exported |

Refer to your SDK's documentation for implementation details.

**Option C — Exclude specific routes**

Some instrumentations support an environment variable to exclude routes entirely:

```bash
OTEL_PYTHON_EXCLUDED_URLS="https://example.com/healthz"
```

Check your instrumentation library's documentation for the equivalent flag.

---

### Step 3: Tail sampling — at the Collector

Tail sampling decisions are made **after** the full trace has been collected. There are three sub-approaches:

**Option A — Drop specific span attributes**

Use the `attributes` or `resource` processor to delete noisy or sensitive fields before export.

```yaml
# Delete a span attribute
processors:
  attributes/drop_span_attributes:
    actions:
      - key: http.method
        action: delete

# Delete resource attributes
processors:
  resource/drop_span_resource_attributes:
    attributes:
      - key: process.runtime.description
        action: delete
      - key: telemetry.distro.name
        action: delete
      - key: process.executable.path
        action: delete
      - key: process.runtime.name
        action: delete
      - key: process.command_args
        action: delete
```

Add the processor to your traces pipeline:

```yaml
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [attributes/drop_span_attributes, batch]
      exporters: [otlp]
```

**Option B — Drop entire traces**

Use the **Probabilistic Sampling Processor** or **Tail Sampling Processor**:

- [Probabilistic Sampling Processor docs](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/probabilisticsamplerprocessor)
- [Tail Sampling Processor docs](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/tailsamplingprocessor)

**Option C — Drop individual spans with the Filter Processor**

<Admonition type="warning">
Dropping individual spans can create broken traces where child spans reference a missing parent. Prefer dropping entire traces when possible.
</Admonition>

Configure the filter processor to drop spans by name, status, span kind, or attributes:

```yaml
# Drop by span name
processors:
  filter/drop_spans_by_name:
    traces:
      span:
        - 'name == "test-span"'

# Drop by status
processors:
  filter/drop_spans_by_status:
    traces:
      span:
        - 'status.code == STATUS_CODE_OK'

# Drop by resource attribute (exact match)
processors:
  filter/drop_spans_by_resource:
    traces:
      span:
        - 'resource.attributes["k8s.pod.name"] == "test-pod"'

# Drop by resource attribute (regex)
processors:
  filter/drop_spans_by_resource_regex:
    traces:
      span:
        - 'IsMatch(resource.attributes["k8s.pod.name"], "test-pod-.*")'

# Drop by span attribute (exact match)
processors:
  filter/drop_spans_by_attribute:
    traces:
      span:
        - 'attributes["http.method"] == "GET"'

# Drop by span attribute (regex)
processors:
  filter/drop_spans_by_attribute_regex:
    traces:
      span:
        - 'IsMatch(attributes["http.method"], "GET|POST")'
```

Add the processor to your traces pipeline:

```yaml
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [filter/drop_spans_by_name, batch]
      exporters: [otlp]
```

See [Filter Processor docs](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/filterprocessor) for the full OTTL expression syntax.

## Verify

After applying your changes, restart the Collector (or your application for SDK-level changes) and check:

1. Go to **Traces** in SigNoz and confirm the expected reduction in span count.
2. For attribute dropping, open any trace and confirm the removed attributes no longer appear in the span details panel.
3. For span/trace drops, confirm the dropped traces no longer appear in the Traces Explorer.
