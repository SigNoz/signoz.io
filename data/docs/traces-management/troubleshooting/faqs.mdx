## Logs and traces

### I can't see related logs for a trace

**Cause:** Your logs do not include `trace_id` and `span_id`, so SigNoz cannot link them to the trace.

**Fix:**

<details>
<summary>Step-by-step resolution</summary>

1. If you are using an OpenTelemetry SDK, enable the logging bridge or log appender for your language. The SDK will inject `trace_id` and `span_id` automatically.
2. If you collect logs from files or via Kubernetes agents (FluentBit, FluentD), use a SigNoz log pipeline to extract `trace_id` and `span_id` from the log body. See [Parse Trace Information from Logs](https://signoz.io/docs/logs-pipelines/guides/trace/).

</details>

For the full guide, see [How to Correlate Traces and Logs](/docs/traces-management/guides/correlate-traces-and-logs).

## Services metrics

### My custom rate queries differ from the Services dashboard numbers

**Cause:** The Services dashboard filters to **top-level (entry-point) spans** only. A direct query on `signoz_calls_total` includes all spans — child and internal spans — resulting in higher values.

**Fix:**

<details>
<summary>Detailed explanation</summary>

When you query `signoz_calls_total` in the Metrics section with Rate and Sum functions, you get data from every span across all operations, including nested and internal child spans.

The Services dashboard applies an additional filter to show only **top-level operations** — the first span where a request enters each service. This is why the values are typically lower than a raw `signoz_calls_total` query.

To recreate the exact metrics shown in the Services dashboard, use the official [APM Metrics dashboard template](https://signoz.io/docs/dashboards/dashboard-templates/apm-metrics) as a reference for the correct query structure.

</details>

For the full explanation of how APM metrics are generated, see [APM Metrics reference](/docs/traces-management/guides/apm-metrics).

## Trace data issues

### I see "missing spans" in my traces

**Cause:** A span's parent span was not collected, so the child span has no parent to attach to.

**Common causes:**
- **Tail sampling** — the sampler kept some spans but dropped others, leaving orphaned children
- **Network issues** — spans dropped in transit between your app and the Collector, or between the Collector and SigNoz
- **Uninstrumented services** — a service in the call chain is not sending spans; downstream services reference a parent ID that was never collected

<Figure
  src="/img/docs/missing-spans-diagram.webp"
  alt="Diagram showing a normal trace with all spans present vs a trace with a missing span"
  caption="Normal trace vs trace with a missing span"
/>

<details>
<summary>How parent-child span relationships work</summary>

Every span carries a **Span ID** and a **Parent Span ID**. When service A calls service B, it passes its Span ID in the `traceparent` header; service B uses that as its Parent Span ID. A span is "missing" when no collected span matches a referenced Parent Span ID.

**Example:** If `Auth` fails to export its span (ID `def2`), the `Database` span that references `def2` as its parent will appear as a missing span.

Learn more: [How traces work in OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/traces/).

</details>

### I see gaps between spans in the waterfall

**Cause:** Code executed during that time is not instrumented. OpenTelemetry auto-instrumentation does not cover custom functions or methods by default.

**Fix:** Add [manual instrumentation](/docs/instrumentation/) to the untraced code paths.

### The trace duration in the list differs from the Trace Details view

**Cause:** The duration column in the Traces list shows the **root span duration**, not the total trace duration. If the root span returns before async child spans finish, the listed duration will be shorter than the full trace duration shown in Trace Details.

**Example:** A trace listed as **38.9 s** may show **1 min** in Trace Details because background jobs continued running after the root span returned.

This is expected behavior. To measure specific service-to-service latencies, see [querying for specific service latencies](https://signoz.io/docs/userguide/writing-clickhouse-traces-query/#querying-for-specific-service-latencies).
