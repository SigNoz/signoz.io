## Overview

Resource attributes attach contextual metadata to logs — such as `service.name`, `deployment.environment`, `host.name`, and Kubernetes labels. Setting them correctly enables filtering by service, grouping by environment, and correlating logs with traces in SigNoz.

Choose the approach that fits your setup: Collector-level (affects all logs), SDK-level (per-application control), environment variables (ideal for containers), or Kubernetes annotations.

:::info Prerequisites
- Logs are flowing into SigNoz.
- You have access to your OpenTelemetry Collector config or application code.
:::

## Approach 1: Collector level

Use collector-level processors when you want to stamp all incoming logs with the same attributes — regardless of which SDK or receiver generated them.

### Using the resource processor

The [resource processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/resourceprocessor) adds, modifies, or deletes resource attributes:

```yaml
processors:
  resource:
    attributes:
      - key: service.name
        value: 'my-log-service'
        action: upsert
      - key: deployment.environment
        value: 'production'
        action: insert
      - key: host.name
        from_attribute: 'hostname'
        action: upsert

service:
  pipelines:
    logs:
      receivers: [otlp]
      processors: [resource, batch]
      exporters: [otlp]
```

`action` values: `insert` (add if missing), `update` (overwrite if present), `upsert` (always write).

### Using the resource detection processor

The [resource detection processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/resourcedetectionprocessor/README.md) automatically detects host, OS, cloud provider, and Kubernetes metadata:

```yaml
processors:
  resourcedetection:
    detectors: [env, host, system, docker, k8snode]
    system:
      hostname_sources: ['os']
    timeout: 5s

service:
  pipelines:
    logs:
      receivers: [otlp]
      processors: [resourcedetection, batch]
      exporters: [otlp]
```

## Approach 2: SDK level

Set resource attributes in your application code when you need per-service control or want to include custom attributes that the collector cannot detect automatically.

<Tabs>
<TabItem value="nodejs" label="Node.js" default>

```javascript
import { Resource } from '@opentelemetry/resources'
import { SemanticResourceAttributes } from '@opentelemetry/semantic-conventions'
import { NodeSDK } from '@opentelemetry/sdk-node'
import { OTLPLogExporter } from '@opentelemetry/exporter-logs-otlp-http'

const resource = new Resource({
  [SemanticResourceAttributes.SERVICE_NAME]: 'my-log-service',
  [SemanticResourceAttributes.SERVICE_VERSION]: '1.0.0',
  [SemanticResourceAttributes.DEPLOYMENT_ENVIRONMENT]: 'production',
  'custom.team': 'backend-team',
  'custom.region': 'us-west-2',
})

const sdk = new NodeSDK({
  resource: resource,
  logRecordProcessor: new BatchLogRecordProcessor(
    new OTLPLogExporter({ url: 'http://localhost:4318/v1/logs' })
  ),
})

sdk.start()
```

</TabItem>
<TabItem value="python" label="Python">

```python
from opentelemetry.sdk.resources import Resource
from opentelemetry.semconv.resource import ResourceAttributes
from opentelemetry._logs import set_logger_provider
from opentelemetry.sdk._logs import LoggerProvider
from opentelemetry.sdk._logs.export import BatchLogRecordProcessor
from opentelemetry.exporter.otlp.proto.grpc._log_exporter import OTLPLogExporter

resource = Resource.create({
    ResourceAttributes.SERVICE_NAME: "my-log-service",
    ResourceAttributes.SERVICE_VERSION: "1.0.0",
    ResourceAttributes.DEPLOYMENT_ENVIRONMENT: "production",
    "custom.team": "backend-team",
    "custom.region": "us-west-2"
})

logger_provider = LoggerProvider(resource=resource)
set_logger_provider(logger_provider)

logger_provider.add_log_record_processor(
    BatchLogRecordProcessor(OTLPLogExporter(endpoint="http://localhost:4317"))
)
```

</TabItem>
<TabItem value="java" label="Java">

```java
import io.opentelemetry.sdk.resources.Resource;
import io.opentelemetry.semconv.resource.attributes.ResourceAttributes;

Resource resource = Resource.getDefault()
    .merge(Resource.builder()
        .put(ResourceAttributes.SERVICE_NAME, "my-log-service")
        .put(ResourceAttributes.SERVICE_VERSION, "1.0.0")
        .put(ResourceAttributes.DEPLOYMENT_ENVIRONMENT, "production")
        .put("custom.team", "backend-team")
        .put("custom.region", "us-west-2")
        .build());

SdkLoggerProvider loggerProvider = SdkLoggerProvider.builder()
    .setResource(resource)
    .addLogRecordProcessor(BatchLogRecordProcessor.builder(
        OtlpGrpcLogRecordExporter.builder()
            .setEndpoint("http://localhost:4317")
            .build())
        .build())
    .build();
```

</TabItem>
<TabItem value="dotnet" label=".NET">

```csharp
using OpenTelemetry.Resources;
using OpenTelemetry.Logs;

var loggerFactory = LoggerFactory.Create(builder =>
{
    builder.AddOpenTelemetry(options =>
    {
        options.SetResourceBuilder(ResourceBuilder.CreateDefault()
            .AddService("my-log-service", "1.0.0")
            .AddAttributes(new Dictionary<string, object>
            {
                ["deployment.environment"] = "production",
                ["custom.team"] = "backend-team",
                ["custom.region"] = "us-west-2"
            }));

        options.AddOtlpExporter(otlpOptions =>
        {
            otlpOptions.Endpoint = new Uri("http://localhost:4318/v1/logs");
        });
    });
});
```

## Approach 3: Environment variables

Use environment variables when you want to configure attributes at deploy time — ideal for containers and CI/CD pipelines. OpenTelemetry SDKs automatically pick up these variables:

```bash
# Set multiple attributes at once
export OTEL_RESOURCE_ATTRIBUTES="service.name=my-log-service,service.version=1.0.0,deployment.environment=production,custom.team=backend"

# Or set the service name separately
export OTEL_SERVICE_NAME="my-log-service"
```

## Approach 4: Kubernetes

<Tabs>
<TabItem value="k8s-infra-chart" label="K8s Infra Chart" default>

The [K8s infra chart](https://signoz.io/docs/collection-agents/k8s/k8s-infra/overview/) automatically sets many Kubernetes resource attributes (cluster name, namespace, pod name, deployment name). See the [chart values reference](https://github.com/SigNoz/charts/blob/main/charts/k8s-infra/README.md#values) for the complete list.

</TabItem>

<TabItem value="kubernetes-operator" label="Kubernetes Operator">

Use the [OpenTelemetry Operator](https://signoz.io/docs/tutorial/opentelemetry-operator-usage/) to automatically inject resource attributes into all pods in a namespace:

```yaml
apiVersion: opentelemetry.io/v1alpha1
kind: Instrumentation
metadata:
  name: my-instrumentation
  namespace: default
spec:
  resource:
    addK8sUIDAttributes: true
  resourceAttributes:
    deployment.environment: 'production'
    custom.team: 'backend-team'
  env:
    - name: OTEL_RESOURCE_ATTRIBUTES
      value: 'service.version=1.0.0'
```

Apply this to a specific deployment with an annotation:

```yaml
metadata:
  annotations:
    instrumentation.opentelemetry.io/inject-sdk: 'my-instrumentation'
```

</TabItem>
</Tabs>

## Verify

After applying your changes, generate a log and open **Logs → Logs Explorer** in SigNoz. Click any log line and check the **Resource Attributes** section in the detail drawer. Your configured attributes should appear there.
