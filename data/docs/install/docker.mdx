<HostingDecision />

This guide explains how to install SigNoz on Docker using Docker Compose. It runs all the components SigNoz requires on a single machine, making it the quickest way to get started with SigNoz.

<Admonition type="warning" title="Migrating from the install script or bundled Docker Compose?" defaultCollapsed="true">
The legacy install script (`install.sh`) and the Docker Compose files bundled under `deploy/` in the SigNoz repository are deprecated as of <a href="https://github.com/SigNoz/signoz/releases/tag/v0.130.0" target="_blank" rel="noopener noreferrer nofollow">SigNoz v0.130.0</a> and are no longer maintained or distributed. Foundry, documented below, is now the supported way to install and manage SigNoz, Docker Compose included.

If you have an existing install-script or Compose deployment, follow the <a href="https://github.com/SigNoz/signoz/blob/main/deploy/MIGRATION.md" target="_blank" rel="noopener noreferrer nofollow">migration guide</a> to move to Foundry without losing your data.
</Admonition>

## Prerequisites

- A Linux or macOS machine. On Microsoft Windows, use WSL 2 with Docker Engine installed inside WSL (see the note below).
- <a href="https://docs.docker.com/engine/install/" target="_blank" rel="noopener noreferrer nofollow">Docker Engine</a> 20.10+ (or Docker Desktop on macOS/Linux) with the <a href="https://docs.docker.com/compose/install/" target="_blank" rel="noopener noreferrer nofollow">Docker Compose</a> v2 plugin.
- At least 4GB of memory allocated to Docker.
- Open ports: `8080` (SigNoz UI), `4317` and `4318` (OTLP ingestion), and `8000` if you enable the MCP server.

<Admonition type="info" title="Running SigNoz on Windows (WSL 2)" defaultCollapsed="true">
On Windows, run everything inside a <a href="https://learn.microsoft.com/en-us/windows/wsl/install" target="_blank" rel="noopener noreferrer nofollow">WSL 2</a> distribution with Docker Engine installed natively in WSL, not Docker Desktop. ClickHouse Keeper has been reported to crash in a restart loop with segmentation faults (exit code 139) under Docker Desktop's virtualization layer on Windows.

1. Install Docker Engine inside your WSL distribution (for example, Ubuntu):

   ```bash
   curl -fsSL https://get.docker.com | sh
   ```

2. Allow your user to run Docker without sudo, then close and reopen the WSL shell:

   ```bash
   sudo usermod -aG docker $USER
   ```

   If `docker ps` fails with `Cannot connect to the Docker daemon`, start the daemon with `sudo service docker start` (needed on distributions without systemd enabled).

3. If Docker Desktop is installed, disable its WSL integration for the distribution (**Settings → Resources → WSL integration**) so `docker` inside WSL uses the native engine.

4. Follow the rest of this guide from the WSL shell.
</Admonition>

## Install SigNoz

<Admonition type="info" title="What is Foundry?" defaultCollapsed="true">
Foundry is an open-source CLI that runs your self-hosted observability stack as code. One declarative config provisions the infrastructure, installs the SigNoz backend, and sets up OpenTelemetry collection on bare metal, containers, or Kubernetes. Learn more about <a href="https://github.com/SigNoz/foundry" target="_blank" rel="noopener noreferrer nofollow">Foundry</a>.
</Admonition>

### Step 1: Install foundryctl

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
```

For manual install (Windows PowerShell, air-gapped, etc.) or PATH setup, see the <a href="https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md" target="_blank" rel="noopener noreferrer nofollow">foundry getting-started guide</a>.

### Step 2: Create casting.yaml

Create a casting file that targets Docker with `flavor: compose` and `mode: docker`:

```yaml
apiVersion: v1alpha1
kind: Installation
metadata:
  name: signoz
spec:
  deployment:
    flavor: compose
    mode: docker
```

For all configuration options, see the <a href="https://github.com/SigNoz/foundry/blob/main/docs/reference/casting-file.md" target="_blank" rel="noopener noreferrer nofollow">casting file reference</a> and the <a href="https://github.com/SigNoz/foundry/tree/main/docs/examples/docker/compose" target="_blank" rel="noopener noreferrer nofollow">Docker Compose example</a>.

### Step 3: Deploy

```bash
foundryctl cast -f casting.yaml
```

`cast` validates Docker, generates the Compose files into `pours/deployment/`, and starts the containers.

<Admonition type="tip" title="Skip cast and run docker compose directly" defaultCollapsed="true">
`cast` chains Foundry's three stages:

- `gauge` checks your environment
- `forge` renders the Compose files into `pours/` and writes `casting.yaml.lock`
- `cast` starts the stack

If you prefer to manage the containers yourself, render the files with `forge`, inspect them, and bring the stack up with Docker Compose:

```bash
foundryctl gauge -f casting.yaml   # validate prerequisites
foundryctl forge -f casting.yaml   # generate compose files
cd pours/deployment && docker compose up -d
```
</Admonition>

### Step 5: Enable the SigNoz MCP server (optional)

Foundry can also deploy the <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/mcp-server.md" target="_blank" rel="noopener noreferrer nofollow">SigNoz MCP server</a> alongside the stack so AI clients can query your telemetry. It is disabled by default.

1. Add an `mcp` block under `spec` in `casting.yaml`:

   ```yaml
   apiVersion: v1alpha1
   kind: Installation
   metadata:
     name: signoz
   spec:
     deployment:
       flavor: compose
       mode: docker
     mcp:
       spec:
         enabled: true
   ```

2. Re-run cast to add the `signoz-mcp` service on port `8000`:

   ```bash
   foundryctl cast -f casting.yaml
   ```

   Verify it is live:

   ```bash
   curl -fsS localhost:8000/livez && echo " OK"
   ```

3. Create an API key from a [service account](https://signoz.io/docs/manage/administrator-guide/iam/service-accounts/) (**Settings → Service Accounts**, requires **Admin** role).

4. Add the server to your AI client. For example, with Claude Code:

   ```bash
   claude mcp add --scope user --transport http signoz http://localhost:8000/mcp \
     --header "SIGNOZ-API-KEY: <your-api-key>"
   ```

   - `<your-api-key>`: the key from step 3

   To confirm the connection, run `/mcp` inside Claude Code and check that the `signoz` server is listed as connected.

For other clients and example workflows, see [SigNoz MCP Server](https://signoz.io/docs/ai/signoz-mcp-server/) and [AI use cases](https://signoz.io/docs/ai/use-cases/).

## Customize the installation

Every change follows the same loop: update `casting.yaml`, then re-run `foundryctl cast` to apply it.

- **Component settings** (image, replicas, environment): set them in the component's `spec`. For example, to pin SigNoz to a specific release, set its image to a version tag:

  ```yaml
  spec:
    signoz:
      spec:
        image: signoz/signoz:v0.128.0
  ```

- **Anything Foundry does not model** (memory limits, networks, volumes): add <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/patches.md" target="_blank" rel="noopener noreferrer nofollow">patches</a> under `spec.patches`. Do not edit the generated files in `pours/` by hand, since forge overwrites them.

## Troubleshooting
</ToggleHeading>

### foundryctl fails

Re-run the failing command with `--debug` for verbose logs.

### A container is unhealthy or the UI does not load

Check the component's logs using the generated Compose file:

```bash
docker compose -f pours/deployment/compose.yaml logs -f signoz-signoz-0
```

### Containers keep restarting

Increase the memory allocated to Docker. SigNoz needs at least 4GB.

### clickhouse-keeper keeps restarting with exit code 139 on Windows

Exit code 139 is a segmentation fault. ClickHouse Keeper segfaults under Docker Desktop's virtualization layer on Windows. Run the stack with native Docker Engine inside WSL 2 instead, as described in [Prerequisites](#prerequisites).
