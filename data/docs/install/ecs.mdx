This guide explains how to install SigNoz on AWS Elastic Container Service (ECS) with the EC2 launch type, on infrastructure that Foundry provisions or on an existing cluster.

## Prerequisites

- An AWS account, with credentials that can create the resources listed in the tab you follow.
- Terraform and the AWS CLI installed on the same machine. Terraform reads the same credentials as the AWS CLI.
- Enough capacity for SigNoz. For sizing, see [resource planning](https://signoz.io/docs/setup/capacity-planning/community/resources-planning/).

## Install SigNoz

<Admonition type="info" title="What is Foundry?" defaultCollapsed="true">
Foundry is an open-source CLI that runs your self-hosted observability stack as code. One declarative config provisions the infrastructure, installs the SigNoz backend, and sets up OpenTelemetry collection on bare metal, containers, or Kubernetes. Learn more about <a href="https://github.com/SigNoz/foundry" target="_blank" rel="noopener noreferrer nofollow">Foundry</a>.
</Admonition>

### Step 1: Install foundryctl

Run this on the machine where you run Terraform:

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
```

For manual install (Windows PowerShell, air-gapped, etc.) or PATH setup, see the <a href="https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md" target="_blank" rel="noopener noreferrer nofollow">foundry getting-started guide</a>.

### Step 2: Create casting.yaml

Create a file named `casting.yaml`. It describes the infrastructure, named `foundry`:

```yaml minimap
apiVersion: v1alpha1
kind: Infrastructure
metadata:
  name: foundry
  annotations:
    foundry.signoz.io/ecs-region: <aws-region>
spec:
  deployment:
    platform: aws
    mode: ecs
    flavor: terraform
  resource:
    spec:
      config:
        data:
          resource.yaml: |
            networking:
              networkCIDR: 10.0.0.0/16
              subnets:
                private-a:
                  type: private
                  zone: <availability-zone>
                  cidr: 10.0.0.0/19
                public-a:
                  type: public
                  zone: <availability-zone>
                  cidr: 10.0.96.0/22
```

**Verify these values:**

- `<aws-region>`: The AWS region to create the infrastructure in, for example `us-east-1`.
- `<availability-zone>`: An Availability Zone of that region, for example `us-east-1a`.
- `networkCIDR` and each subnet's `cidr`: Change them if they overlap a network you connect to.

The defaults are development sizes; production sizing is under Customize the installation.

<Admonition type="info" title="What Foundry creates" defaultCollapsed="true">
Foundry creates everything SigNoz needs in your AWS account, then installs SigNoz on it:

- A VPC with one private and one public subnet, an internet gateway, and a NAT gateway for the private subnet.
- An ECS cluster, `foundry-cls`.
- Three instances for ClickHouse, ClickHouse Keeper and PostgreSQL (`c5.large`, 30 GB root disk, a 50 GB gp3 data volume each at `/var/lib/foundry`).
- One instance in an autoscaling group for SigNoz and the ingester (`t3.medium`, 30 GB root disk).
- An IAM role for the instances and one security group that allows traffic between them.
- For SigNoz itself: one ECS service per component, a task role and an execution role, a Cloud Map namespace `signoz-installation.local`, and the component configuration in AWS AppConfig.

Your AWS credentials need permission to create these.
</Admonition>

`metadata.name` names everything Foundry creates; the ECS cluster is `foundry-cls`.

For all options, see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/infrastructure.md" target="_blank" rel="noopener noreferrer nofollow">Infrastructure</a> and the <a href="https://github.com/SigNoz/foundry/tree/main/docs/examples/infrastructure/aws/ecs/terraform" target="_blank" rel="noopener noreferrer nofollow">ECS infrastructure example</a>.

<Admonition type="info" title="Store Terraform state in S3" defaultCollapsed="true">
The infrastructure's Terraform state starts in `pours/infrastructure/terraform.tfstate`. To keep it in an S3 bucket, add this under the Infrastructure document's `spec` before the first cast:

```yaml
spec:
  patches:
    - target: infrastructure/backend.tf.json
      operations:
        - op: replace
          path: /terraform/backend
          value:
            s3:
              bucket: <state-bucket>
              key: foundry/infrastructure.tfstate
              region: <state-bucket-region>
```

**Verify these values:**

- `<state-bucket>`: An existing S3 bucket. Your AWS credentials need `s3:ListBucket`, `s3:GetObject` and `s3:PutObject` on it.
- `<state-bucket-region>`: The AWS region of that bucket, for example `us-east-1`.

`key` is the path of the state file inside the bucket.
</Admonition>

### Step 3: Create the infrastructure

Run this from the directory that contains `casting.yaml`:

```bash
foundryctl cast -f casting.yaml
```

This creates the infrastructure with Terraform in `pours/infrastructure/`. Run the same command again after editing `casting.yaml` to apply the change.

<Admonition type="tip" title="Run Terraform yourself" defaultCollapsed="true">
To run Terraform directly, generate the files and apply them:

```bash
foundryctl forge -f casting.yaml   # writes pours/infrastructure/
cd pours/infrastructure
terraform init
terraform plan -out=tfplan
terraform apply tfplan
```
</Admonition>

Check that the instances have registered with the cluster. Run this with the AWS CLI:

```bash
aws ecs describe-clusters --clusters foundry-cls --region <aws-region> \
  --query 'clusters[0].registeredContainerInstancesCount'
```

**Verify these values:**

- `<aws-region>`: The region from `casting.yaml`.

Wait until the count reaches the number of instances before the next step:

```output
4
```

### Step 4: Add SigNoz to casting.yaml

Open `casting.yaml` and add the SigNoz installation below the infrastructure. The file now has two documents, separated by `---`:

```yaml minimap
apiVersion: v1alpha1
kind: Infrastructure
metadata:
  name: foundry
  annotations:
    foundry.signoz.io/ecs-region: <aws-region>
spec:
  deployment:
    platform: aws
    mode: ecs
    flavor: terraform
  resource:
    spec:
      config:
        data:
          resource.yaml: |
            networking:
              networkCIDR: 10.0.0.0/16
              subnets:
                private-a:
                  type: private
                  zone: <availability-zone>
                  cidr: 10.0.0.0/19
                public-a:
                  type: public
                  zone: <availability-zone>
                  cidr: 10.0.96.0/22
---
apiVersion: v1alpha1
kind: Installation
metadata:
  name: signoz
  annotations:
    foundry.signoz.io/ecs-region: <aws-region>
spec:
  deployment:
    platform: ecs
    mode: ec2
    flavor: terraform
  infrastructure:
    name: foundry
```

**Verify these values:**

- `<aws-region>`: The AWS region from Step 2, the same in both documents.
- `<availability-zone>`: The Availability Zone from Step 2.

<Admonition type="info" title="Use your own IAM roles" defaultCollapsed="true">
Foundry creates two IAM roles: `signoz-installation-iam-task` for the SigNoz tasks and `signoz-installation-iam-exec` for the ECS agent. To use an existing role for either one, add its annotation under `metadata.annotations`:

```yaml
metadata:
  annotations:
    foundry.signoz.io/ecs-task-role-arn: <task-role-arn>
    foundry.signoz.io/ecs-task-execution-role-arn: <task-execution-role-arn>
```

**Verify these values:**

- `<task-role-arn>`: The ARN of the role the SigNoz tasks assume. It must allow `appconfig:StartConfigurationSession` and `appconfig:GetLatestConfiguration`.
- `<task-execution-role-arn>`: The ARN of the role the ECS agent uses to pull images and start the tasks. The role Foundry creates carries the AWS managed policy `AmazonECSTaskExecutionRolePolicy`.
</Admonition>

`spec.infrastructure.name` must match the Infrastructure document's `metadata.name`. The installation's `metadata.name`, `signoz`, prefixes every ECS service and names the DNS namespace `signoz-installation.local`.

<Admonition type="info" title="Store Terraform state in S3" defaultCollapsed="true">
The installation's Terraform state starts in `pours/deployment/terraform.tfstate`. To keep it in an S3 bucket, add this under the Installation document's `spec` before the next cast:

```yaml
spec:
  patches:
    - target: deployment/backend.tf.json
      operations:
        - op: replace
          path: /terraform/backend
          value:
            s3:
              bucket: <state-bucket>
              key: signoz/deployment.tfstate
              region: <state-bucket-region>
```

**Verify these values:**

- `<state-bucket>`: An existing S3 bucket. Your AWS credentials need `s3:ListBucket`, `s3:GetObject` and `s3:PutObject` on it.
- `<state-bucket-region>`: The AWS region of that bucket, for example `us-east-1`.

Use a different `key` from the infrastructure's state.
</Admonition>

### Step 5: Deploy SigNoz

Run this from the directory that contains `casting.yaml`:

```bash
foundryctl cast -f casting.yaml
```

This checks the infrastructure for changes, then installs SigNoz with Terraform in `pours/deployment/`. Run the same command again after editing `casting.yaml` to apply the change.

<Admonition type="tip" title="Run Terraform yourself" defaultCollapsed="true">
To run Terraform directly, generate the files and apply them:

```bash
foundryctl forge -f casting.yaml   # writes pours/infrastructure/ and pours/deployment/
cd pours/infrastructure
terraform init
terraform plan -out=tfplan
terraform apply tfplan
cd ../deployment
terraform init
terraform plan -out=tfplan
terraform apply tfplan
```
</Admonition>

### Step 6: Verify the installation

Check that each SigNoz service runs its task. Run this with the AWS CLI:

```bash
aws ecs describe-services --cluster foundry-cls --region <aws-region> \
  --services signoz-telemetrykeeper-clickhousekeeper-0 signoz-telemetrystore-clickhouse-0-0 \
    signoz-metastore-postgres-0 signoz-signoz-0 signoz-ingester \
  --query 'services[].[serviceName,desiredCount,runningCount]' --output text
```

**Verify these values:**

- `<aws-region>`: The region from `casting.yaml`.

Each line shows the service name, the desired task count and the running task count. The output should look similar to the following:

```output
signoz-telemetrykeeper-clickhousekeeper-0    1    1
signoz-telemetrystore-clickhouse-0-0         1    1
signoz-metastore-postgres-0                  1    1
signoz-signoz-0                              1    1
signoz-ingester                              1    1
```

The counts can take a few minutes to match.

ECS runs SigNoz's health check, `/api/v1/health`, inside the task. Read its result with the AWS CLI:

```bash
aws ecs describe-tasks --cluster foundry-cls --region <aws-region> \
  --tasks $(aws ecs list-tasks --cluster foundry-cls --region <aws-region> --service-name signoz-signoz-0 --query 'taskArns[0]' --output text) \
  --query 'tasks[].healthStatus' --output text
```

The output is:

```output
HEALTHY
```

The status reads `UNKNOWN` until the first check passes. Failed checks in the first five minutes after the task starts do not count against it.

SigNoz is reachable at `http://signoz-0.signoz-installation.local:8080` from inside the VPC.

## Send data to SigNoz

Your applications send traces, metrics, and logs to the SigNoz ingester. Inside the VPC, the ingester listens at:

```bash
http://ingester.signoz-installation.local:4318
```

Use this address as the OTLP endpoint in your instrumentation, for example as the value of `OTEL_EXPORTER_OTLP_ENDPOINT`. For gRPC, use port `4317` instead.

The name resolves inside the VPC. The security group Foundry creates allows traffic between its members, so allow ports `4317` and `4318` from your applications. The `signoz` in `signoz-installation.local` is the installation's `metadata.name`. If you changed it, use yours.

For applications outside the VPC, see the [self-hosted ingestion guide](https://signoz.io/docs/ingestion/self-hosted/overview/).

## Customize the installation

Every change follows the same loop: edit `casting.yaml`, then run `foundryctl cast -f casting.yaml` again.

- **Component settings** (image, shards, replicas): set them in the Installation document's component `spec`. For example, to pin SigNoz to a specific release:

  ```yaml
  spec:
    signoz:
      spec:
        image: signoz/signoz:v0.144.0
  ```

  ClickHouse takes shard and replica counts, and ClickHouse Keeper takes a replica count under `spec.telemetrystore.spec.cluster` and `spec.telemetrykeeper.spec.cluster`. Each node runs as its own ECS service.

- **Infrastructure** (machine types, disks, node counts): override `resource.yaml` in the Infrastructure document. For production, the SigNoz capacity guide names the C5 family, `c5.4xlarge` and up, for ClickHouse, and the T3 family, `t3.xlarge` and up, for everything else:

  ```yaml minimap defaultCollapsed
  apiVersion: v1alpha1
  kind: Infrastructure
  metadata:
    name: foundry
    annotations:
      foundry.signoz.io/ecs-region: <aws-region>
  spec:
    deployment:
      platform: aws
      mode: ecs
      flavor: terraform
    resource:
      spec:
        config:
          data:
            resource.yaml: |
              networking:
                networkCIDR: 10.0.0.0/16
                subnets:
                  private-a:
                    type: private
                    zone: <availability-zone>
                    cidr: 10.0.0.0/19
                  public-a:
                    type: public
                    zone: <availability-zone>
                    cidr: 10.0.96.0/22
              instanceGroups:
                persistent:
                  machineType: c5.4xlarge
                  minSize: 3
                  maxSize: 3
                  dataVolume:
                    size: 500
                ephemeral:
                  machineType: t3.xlarge
                  minSize: 3
                  maxSize: 3
  ```

  Every `resource.yaml` field, with an example per section, is in <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/infrastructure.md#the-document" target="_blank" rel="noopener noreferrer nofollow">Infrastructure</a>; what happens to the data on each disk when you change a machine is under <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/infrastructure.md#disks" target="_blank" rel="noopener noreferrer nofollow">Disks</a>.

- **Platform settings** (CPU, memory): add <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/patches.md" target="_blank" rel="noopener noreferrer nofollow">patches</a> under a document's `spec.patches`, against its files in `pours/deployment/` for the Installation or `pours/infrastructure/` for the Infrastructure. For example, to give SigNoz 1024 CPU units, in the Installation document:

  ```yaml
  spec:
    patches:
      - target: deployment/signoz.tf.json
        operations:
          - op: replace
            path: /locals/containers_signoz_0/0/cpu
            value: 1024
  ```

  Run `foundryctl forge -f casting.yaml` from the directory that contains `casting.yaml` and read the generated file to find the path you need. Each run regenerates the files under `pours/`, so keep every change in `casting.yaml`.

## Troubleshooting
</ToggleHeading>

### foundryctl fails

Re-run the failing command with `--debug` for verbose logs.

### An instance never registers

List the instances that hold data. Run this with the AWS CLI:

```bash
aws ecs list-container-instances --cluster foundry-cls --region <aws-region> \
  --filter "attribute:foundry.signoz.io/storage == persistent"
```

**Verify these values:**

- `<aws-region>`: The region from `casting.yaml`.

Fewer than three entries means an instance has not mounted its data volume yet. See <a href="https://github.com/SigNoz/foundry/blob/main/docs/examples/infrastructure/aws/ecs/terraform/README.md#validate" target="_blank" rel="noopener noreferrer nofollow">Validate</a> and <a href="https://github.com/SigNoz/foundry/blob/main/docs/examples/infrastructure/aws/ecs/terraform/README.md#changing-the-infrastructure" target="_blank" rel="noopener noreferrer nofollow">Changing the infrastructure</a>.

### A service never reaches its desired count

Read the service's recent events. Run this with the AWS CLI:

```bash
aws ecs describe-services --cluster foundry-cls --region <aws-region> \
  --services <service-name> --query 'services[0].events[:5].message'
```

**Verify these values:**

- `<aws-region>`: The region from `casting.yaml`.
- `<service-name>`: A service name from Step 6, for example `signoz-signoz-0`.

The events say why ECS could not place or start the task. How each service is placed on the instances Foundry creates is in the <a href="https://github.com/SigNoz/foundry/blob/main/docs/examples/ecs/ec2/terraform/README.md#binding-to-provisioned-infrastructure" target="_blank" rel="noopener noreferrer nofollow">ECS installation example</a>.

For tasks that started and then stopped, list them and read why they stopped:

```bash
aws ecs list-tasks --cluster foundry-cls --region <aws-region> \
  --service-name <service-name> --desired-status STOPPED
aws ecs describe-tasks --cluster foundry-cls --region <aws-region> \
  --tasks <task-arn> --query 'tasks[].stoppedReason'
```

**Verify these values:**

- `<task-arn>`: A task ARN from the `list-tasks` output.

### Read container logs

The containers write their logs on the container instance with Docker's `json-file` log driver. Find the instance that runs a service's task. Run this with the AWS CLI:

```bash
TASK=$(aws ecs list-tasks --cluster foundry-cls --region <aws-region> --service-name <service-name> --query 'taskArns[0]' --output text)
INSTANCE=$(aws ecs describe-tasks --cluster foundry-cls --region <aws-region> --tasks "$TASK" --query 'tasks[0].containerInstanceArn' --output text)
aws ecs describe-container-instances --cluster foundry-cls --region <aws-region> --container-instances "$INSTANCE" --query 'containerInstances[0].ec2InstanceId' --output text
```

**Verify these values:**

- `<aws-region>`: The region from `casting.yaml`.
- `<service-name>`: A service name from Step 6, for example `signoz-signoz-0`.

Connect to that instance (for example with AWS Systems Manager Session Manager) and run this. The main container of each task carries its service's name:

```bash
sudo docker logs $(sudo docker ps -q --filter label=com.amazonaws.ecs.container-name=<service-name>)
```

### Removing SigNoz or the infrastructure

Remove SigNoz first, then the infrastructure. Run this from the directory that contains `casting.yaml`:

```bash
cd pours/deployment
terraform state rm aws_ec2_tag.claims
terraform destroy
cd ../infrastructure
terraform destroy
```

Destroying the infrastructure deletes the data volumes and their data. Why the `state rm` step is needed is under <a href="https://github.com/SigNoz/foundry/blob/main/docs/examples/ecs/ec2/terraform/README.md#teardown" target="_blank" rel="noopener noreferrer nofollow">Teardown</a>.

## Install SigNoz

<Admonition type="info" title="What is Foundry?" defaultCollapsed="true">
Foundry is an open-source CLI that runs your self-hosted observability stack as code. One declarative config provisions the infrastructure, installs the SigNoz backend, and sets up OpenTelemetry collection on bare metal, containers, or Kubernetes. Learn more about <a href="https://github.com/SigNoz/foundry" target="_blank" rel="noopener noreferrer nofollow">Foundry</a>.
</Admonition>

This path installs SigNoz on an ECS cluster you already run. You need:

- An ECS cluster with registered EC2 container instances.
- A VPC with private subnets that route outbound traffic through a NAT gateway or VPC endpoints.
- A security group for the SigNoz tasks that allows traffic between them (the ports are listed below).
- A durable volume mounted at `/var/lib/foundry` on the container instances. ClickHouse, ClickHouse Keeper and PostgreSQL store their data there. ECS can move a task to another instance, where it starts on that instance's copy of the directory; pin the stateful services with a placement constraint (see Step 2).

<Admonition type="info" title="Ports the SigNoz components use" defaultCollapsed="true">
| Component | Ports |
| --- | --- |
| ClickHouse Keeper | `9181` client, `9234` Raft |
| ClickHouse | `9000` native, `8123` HTTP, `9009` interserver, `9363` metrics |
| PostgreSQL | `5432` |
| SigNoz | `8080` UI and API, `4320` OpAMP |
| Ingester (OpenTelemetry Collector) | `4317` OTLP gRPC, `4318` OTLP HTTP |
</Admonition>

### Step 1: Install foundryctl

Run this on the machine where you run Terraform:

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
```

For manual install (Windows PowerShell, air-gapped, etc.) or PATH setup, see the <a href="https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md" target="_blank" rel="noopener noreferrer nofollow">foundry getting-started guide</a>.

### Step 2: Create casting.yaml

Create a file named `casting.yaml`. It describes the installation and names the AWS resources SigNoz runs on:

```yaml
apiVersion: v1alpha1
kind: Installation
metadata:
  name: signoz
  annotations:
    foundry.signoz.io/ecs-region: <aws-region>
    foundry.signoz.io/ecs-cluster-arn: <cluster-arn>
    foundry.signoz.io/ecs-vpc-id: <vpc-id>
    foundry.signoz.io/ecs-private-subnet-ids: <private-subnet-ids>
    foundry.signoz.io/ecs-security-group-ids: <security-group-ids>
spec:
  deployment:
    platform: ecs
    mode: ec2
    flavor: terraform
```

**Verify these values:**

- `<aws-region>`: The AWS region of your ECS cluster, for example `us-east-1`.
- `<cluster-arn>`: The ARN of your ECS cluster, for example `arn:aws:ecs:us-east-1:111122223333:cluster/observability`.
- `<vpc-id>`: The ID of the VPC your container instances run in, for example `vpc-0a1b2c3d4e5f67890`.
- `<private-subnet-ids>`: Comma-separated IDs of private subnets in the Availability Zones where your container instances run, for example `subnet-0a1b2c3d4e5f67890,subnet-0f9e8d7c6b5a43210`.
- `<security-group-ids>`: Comma-separated IDs of the security groups for the SigNoz tasks, for example `sg-0a1b2c3d4e5f67890`.

<Admonition type="info" title="Use your own IAM roles" defaultCollapsed="true">
Foundry creates two IAM roles: `signoz-installation-iam-task` for the SigNoz tasks and `signoz-installation-iam-exec` for the ECS agent. To use an existing role for either one, add its annotation under `metadata.annotations`:

```yaml

    foundry.signoz.io/ecs-task-role-arn: <task-role-arn>

```

**Verify these values:**

- `<task-role-arn>`: The ARN of the role the SigNoz tasks assume. It must allow `appconfig:StartConfigurationSession` and `appconfig:GetLatestConfiguration`.
- `<task-execution-role-arn>`: The ARN of the role the ECS agent uses to pull images and start the tasks. The role Foundry creates carries the AWS managed policy `AmazonECSTaskExecutionRolePolicy`.
</Admonition>

`metadata.name` prefixes every ECS service name and names the private DNS namespace the components use, `signoz-installation.local`.

<Admonition type="info" title="Pin the stateful services to their instances" defaultCollapsed="true">
ClickHouse, ClickHouse Keeper and PostgreSQL keep their data under `/var/lib/foundry` on the instance that runs them. To keep each one on its instance, add placement constraints to `casting.yaml` before the first deploy:

```yaml defaultCollapsed
spec:
  patches:
    - target: deployment/telemetrykeeper.tf.json
      operations:
        - op: add
          path: /resource/aws_ecs_service/telemetrykeeper_clickhousekeeper_0/placement_constraints
          value:
            - type: memberOf
              expression: ec2InstanceId == <keeper-instance-id>
    - target: deployment/telemetrystore.tf.json
      operations:
        - op: add
          path: /resource/aws_ecs_service/telemetrystore_clickhouse_0_0/placement_constraints
          value:
            - type: memberOf
              expression: ec2InstanceId == <clickhouse-instance-id>
    - target: deployment/metastore.tf.json
      operations:
        - op: add
          path: /resource/aws_ecs_service/metastore_postgres_0/placement_constraints
          value:
            - type: memberOf
              expression: ec2InstanceId == <postgres-instance-id>
```

**Verify these values:**

- `<keeper-instance-id>`: The ID of the container instance that runs ClickHouse Keeper, for example `i-0123456789abcdef0`.
- `<clickhouse-instance-id>`: The ID of the container instance that runs ClickHouse, for example `i-0123456789abcdef1`.
- `<postgres-instance-id>`: The ID of the container instance that runs PostgreSQL, for example `i-0123456789abcdef2`.

With more shards or replicas, each node's service gets its own constraint: `telemetrykeeper_clickhousekeeper_<replica>`, `telemetrystore_clickhouse_<shard>_<replica>` and `metastore_postgres_<replica>`.
</Admonition>

### Step 3: Deploy

Run this from the directory that contains `casting.yaml`:

```bash
foundryctl cast -f casting.yaml
```

This installs SigNoz with Terraform in `pours/deployment/`. Run the same command again after editing `casting.yaml` to apply the change.

<Admonition type="tip" title="Run Terraform yourself" defaultCollapsed="true">
To run Terraform directly, generate the files and apply them:

```bash
foundryctl forge -f casting.yaml   # writes pours/deployment/
cd pours/deployment
terraform init
terraform plan -out=tfplan
terraform apply tfplan
```
</Admonition>

### Step 4: Verify the installation

Check that each SigNoz service runs its task. Run this with the AWS CLI:

```bash
aws ecs describe-services --cluster <cluster-arn> --region <aws-region> \
  --services signoz-telemetrykeeper-clickhousekeeper-0 signoz-telemetrystore-clickhouse-0-0 \
    signoz-metastore-postgres-0 signoz-signoz-0 signoz-ingester \
  --query 'services[].[serviceName,desiredCount,runningCount]' --output text
```

**Verify these values:**

- `<cluster-arn>`: The cluster ARN from `casting.yaml`.
- `<aws-region>`: The region from `casting.yaml`.

Each line shows the service name, the desired task count and the running task count. The output should look similar to the following:

```output
signoz-telemetrykeeper-clickhousekeeper-0    1    1
signoz-telemetrystore-clickhouse-0-0         1    1
signoz-metastore-postgres-0                  1    1
signoz-signoz-0                              1    1
signoz-ingester                              1    1
```

The counts can take a few minutes to match. If you changed shard or replica counts, `aws ecs list-services --cluster <cluster-arn> --region <aws-region>` lists every service name.

ECS runs SigNoz's health check, `/api/v1/health`, inside the task. Read its result with the AWS CLI:

```bash
aws ecs describe-tasks --cluster <cluster-arn> --region <aws-region> \
  --tasks $(aws ecs list-tasks --cluster <cluster-arn> --region <aws-region> --service-name signoz-signoz-0 --query 'taskArns[0]' --output text) \
  --query 'tasks[].healthStatus' --output text
```

**Verify these values:**

- `<cluster-arn>`: The cluster ARN from `casting.yaml`.
- `<aws-region>`: The region from `casting.yaml`.

The output is:

```output
HEALTHY
```

The status reads `UNKNOWN` until the first check passes. Failed checks in the first five minutes after the task starts do not count against it.

SigNoz is reachable at `http://signoz-0.signoz-installation.local:8080` from inside the VPC. The `signoz` prefix follows `metadata.name`.

## Send data to SigNoz

Your applications send traces, metrics, and logs to the SigNoz ingester. Inside the VPC, the ingester listens at:

```bash
http://ingester.signoz-installation.local:4318
```

Use this address as the OTLP endpoint in your instrumentation, for example as the value of `OTEL_EXPORTER_OTLP_ENDPOINT`. For gRPC, use port `4317` instead.

The name resolves inside the VPC, and the security group must allow ports `4317` and `4318` from your applications. The `signoz` in `signoz-installation.local` is `metadata.name`. If you changed it, use yours.

For applications outside the VPC, see the [self-hosted ingestion guide](https://signoz.io/docs/ingestion/self-hosted/overview/).

## Customize the installation

Every change follows the same loop: edit `casting.yaml`, then run `foundryctl cast -f casting.yaml` again.

- **Component settings** (image, shards, replicas): set them in the component's `spec`. For example, to pin SigNoz to a specific release:

  ```yaml
  spec:
    signoz:
      spec:
        image: signoz/signoz:v0.144.0
  ```

  ClickHouse takes shard and replica counts, and ClickHouse Keeper takes a replica count:

  ```yaml
  spec:
    telemetrystore:
      spec:
        cluster:
          shards: 2
          replicas: 1
    telemetrykeeper:
      spec:
        cluster:
          replicas: 3
  ```

  Each node runs as its own ECS service. ClickHouse `replicas` counts the copies beside each shard, so this example runs four ClickHouse services, `signoz-telemetrystore-clickhouse-0-0` to `signoz-telemetrystore-clickhouse-1-1`, and three ClickHouse Keeper services. Keep the ClickHouse Keeper count odd.

- **Platform settings** (CPU, memory): add <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/patches.md" target="_blank" rel="noopener noreferrer nofollow">patches</a> under `spec.patches` against the component's file in `pours/deployment/`. For example, to give SigNoz 1024 CPU units:

  ```yaml
  spec:
    patches:
      - target: deployment/signoz.tf.json
        operations:
          - op: replace
            path: /locals/containers_signoz_0/0/cpu
            value: 1024
  ```

  Run `foundryctl forge -f casting.yaml` from the directory that contains `casting.yaml` and read the generated file to find the path you need. Each run regenerates the files under `pours/`, so keep every change in `casting.yaml`.

## Troubleshooting
</ToggleHeading>

### foundryctl fails

Re-run the failing command with `--debug` for verbose logs.

### Terraform rejects a variable or a subnet

A missing or malformed annotation stops `terraform plan` with a validation message, for example:

```output
subnet_ids must be a non-empty list of subnet IDs.
```

A subnet that assigns public IP addresses on launch stops the plan with a message that names it, for example:

```output
subnet subnet-0a1b2c3d4e5f67890 assigns public IPs on launch; tasks on the EC2 launch type take no public IP, so state private subnets with a NAT route or VPC endpoints.
```

Fix the annotation in `casting.yaml` and run `foundryctl cast -f casting.yaml` again. What each annotation names is under <a href="https://github.com/SigNoz/foundry/blob/main/docs/examples/ecs/ec2/terraform/README.md#annotations" target="_blank" rel="noopener noreferrer nofollow">Annotations</a>.

### A service never reaches its desired count

Read the service's recent events. Run this with the AWS CLI:

```bash
aws ecs describe-services --cluster <cluster-arn> --region <aws-region> \
  --services <service-name> --query 'services[0].events[:5].message'
```

**Verify these values:**

- `<cluster-arn>`: The cluster ARN from `casting.yaml`.
- `<aws-region>`: The region from `casting.yaml`.
- `<service-name>`: A service name from Step 4, for example `signoz-signoz-0`.

The events say why ECS could not place or start the task. Each SigNoz task takes its own elastic network interface on the instance, so small instance types fit only a few tasks. See <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-networking-awsvpc.html" target="_blank" rel="noopener noreferrer nofollow">task networking</a>.

For tasks that started and then stopped, list them and read why they stopped:

```bash
aws ecs list-tasks --cluster <cluster-arn> --region <aws-region> \
  --service-name <service-name> --desired-status STOPPED
aws ecs describe-tasks --cluster <cluster-arn> --region <aws-region> \
  --tasks <task-arn> --query 'tasks[].stoppedReason'
```

**Verify these values:**

- `<task-arn>`: A task ARN from the `list-tasks` output.

### Read container logs

The containers write their logs on the container instance with Docker's `json-file` log driver. Find the instance that runs a service's task. Run this with the AWS CLI:

```bash
TASK=$(aws ecs list-tasks --cluster <cluster-arn> --region <aws-region> --service-name <service-name> --query 'taskArns[0]' --output text)
INSTANCE=$(aws ecs describe-tasks --cluster <cluster-arn> --region <aws-region> --tasks "$TASK" --query 'tasks[0].containerInstanceArn' --output text)
aws ecs describe-container-instances --cluster <cluster-arn> --region <aws-region> --container-instances "$INSTANCE" --query 'containerInstances[0].ec2InstanceId' --output text
```

**Verify these values:**

- `<cluster-arn>`: The cluster ARN from `casting.yaml`.
- `<aws-region>`: The region from `casting.yaml`.
- `<service-name>`: A service name from Step 4, for example `signoz-signoz-0`.

Connect to that instance (for example with AWS Systems Manager Session Manager) and run this. The main container of each task carries its service's name:

```bash
sudo docker logs $(sudo docker ps -q --filter label=com.amazonaws.ecs.container-name=<service-name>)
```

### Removing SigNoz

Run this from the directory that contains `casting.yaml`:

```bash
cd pours/deployment && terraform destroy
```

This removes the services and everything else the Terraform created.
