SigNoz v0.145.0 stores every notification channel in the v2 config format. A migration runs once on startup and backfills existing channels, and the v1 channel API now rejects configurations the v2 format cannot represent. If you manage notification channels only through the UI, back up the Metastore, upgrade, then check the server logs for any channel the migration could not convert.

<Admonition type="warning" title="Some channels may not convert to the v2 format">
The migration backfills each channel from its stored receiver. A channel that v2 cannot represent, such as a Telegram or Pushover channel, one that bundles several notifiers, or one that uses an unsupported HTTP option, is left without a v2 spec and logged. These channels keep firing alerts, but they cannot be edited through the API until they are repaired or recreated. Back up the Metastore (SQLite or Postgres) before you upgrade.
</Admonition>

<Admonition type="info" title="The v1 channel API now rejects unsupported configs">
`POST /api/v1/channels` and `PUT /api/v1/channels/{id}` reject channel types, multi-notifier receivers, and HTTP options that have no v2 equivalent. If you call the v1 endpoints from scripts, see [What the v1 API now rejects](https://signoz.io/docs/alerts-management/migrate-notification-channel-api-v1-to-v2/#what-the-v1-api-now-rejects).
</Admonition>

## Upgrade self-hosted SigNoz

### Step 1: Back up your data

Notification channels live in the SigNoz Metastore alongside dashboards and alerts. Back up the Metastore before you start. If you are more than one release behind, check the [Upgrade Path Tool](https://signoz.io/upgrade-path/) for required stops before you move to v0.145.0.

### Step 2: Upgrade SigNoz

The channel migration runs once, automatically, when the server starts on the new version.

<Tabs entityName="installer">
<TabItem value="foundry" label="Foundry" default>

Upgrade <a href="https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md" target="_blank" rel="noopener noreferrer nofollow">foundryctl</a> to pick up the v0.145.0 defaults, then re-apply your existing `casting.yaml`:

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
foundryctl cast -f casting.yaml
```

If your <a href="https://github.com/SigNoz/foundry/blob/main/docs/reference/casting-file.md" target="_blank" rel="noopener noreferrer nofollow">casting.yaml</a> pins image versions, the new defaults will not override them (your config wins), so bump the SigNoz image pin to v0.145.0 yourself.

</TabItem>
<TabItem value="helm" label="Kubernetes (Helm chart)">

Update the <a href="https://github.com/SigNoz/charts" target="_blank" rel="noopener noreferrer nofollow">chart</a> and upgrade. Replace `<namespace>` and `<release-name>` with your own values:

```bash
helm repo update
helm -n <namespace> upgrade <release-name> signoz/signoz
```

`helm upgrade` takes the newest chart; add `--version 0.145.0` to pin the v0.145.0 chart.

</TabItem>
</Tabs>

For Docker or binary deployments, follow the [standard upgrade guide](https://signoz.io/docs/operate/migration/upgrade-standard/) and set the target version to v0.145.0.

### Step 3: Verify the upgrade

1. Pods and containers are healthy (`kubectl get pods -n <namespace>`, `docker compose ps`, or `systemctl status 'signoz-*'`).
2. SigNoz reports v0.145.0 under **Settings**.
3. Search the server logs for `leaving notification channel without a v2 spec`. Each entry names the `org_id` and `channel_id` of a channel the migration could not convert.

## Remediate flagged channels

A channel the migration left without a v2 spec still delivers alerts, but any edit through the API fails until it carries a v2 spec. Two options fix that:

- **Repair it.** `POST /api/v2/notification_channels/{id}/repair` rewrites a channel into the v2 format where the conversion is possible. See the [SigNoz API Reference](https://signoz.io/api-reference/) for the request and response schema.
- **Recreate it.** For a type v2 does not support (such as Telegram or Pushover), delete the channel and recreate it as a supported type. See [the v2 config table](https://signoz.io/docs/alerts-management/migrate-notification-channel-api-v1-to-v2/#the-config-for-each-kind) for the supported kinds.

For the full list of v1 restrictions and the v2 request schema, see [Migrate the Notification Channel API from v1 to v2](https://signoz.io/docs/alerts-management/migrate-notification-channel-api-v1-to-v2/).
