SigNoz v0.143.0 prepares the OTel collector for AI observability and moves login sessions to opaque tokens. Two things follow for self-hosted upgrades: the collector must run signoz-otel-collector v0.144.11 with two new processors in its traces pipeline, and every user signs in again once.

<Admonition type="info" title="What changed in v0.143" defaultCollapsed="true">
**Sessions**

The default session provider is now opaque tokens. JWT stays available by setting the provider and a secret.

**AI Observability**

You can now monitor your LLM and agent workloads in SigNoz. This release includes:

- **Overview**: tokens, cost, latency and errors across models, providers and agents.
- **Explorer**: query AI spans by model, provider, agent and tool, and filter by rolled-up totals such as tokens and cost.
- **Attribute mapping**: normalizes span attributes from different AI frameworks into the OpenTelemetry `gen_ai.*` keys, so one set of queries works across all of them.
- **Pricing**: set per-model prices and get cost on every LLM span.

**What changes for you**

Attribute mapping moves input and output messages from framework-specific attributes like `input.value` or `gen_ai.prompt` into the standard `gen_ai.input.messages` and `gen_ai.output.messages`. These are the biggest attributes on an LLM span, so we don't keep the original alongside the copy.

Keys that are moved:

- Into `gen_ai.input.messages`: `gen_ai.prompt`, `ai.prompt.messages`, `input.value`
- Into `gen_ai.output.messages`: `gen_ai.completion`, `ai.response.toolCalls`, `ai.response.text`, `output.value`, `final_result`

If your queries, saved views or alerts use the old keys, switch them to the standard ones. Spans that already use the standard keys are not affected.

Want to keep the original key too? Go to **AI Observability**, **Attribute Mapping** and change the operation from move to copy.

**Coming next**

- Trace detail with conversation threads
- Dashboards, alerts and saved views built on AI explorer queries

For the full release scope, see the <a href="https://github.com/SigNoz/signoz/releases/tag/v0.143.0" target="_blank" rel="noopener noreferrer nofollow">v0.143.0 release notes</a>.
</Admonition>

## Who needs to act

<Admonition type="info" title="AI observability needs two new collector processors" defaultCollapsed="true">
SigNoz now manages the `signozspanmapper` and `signozllmpricing` processors in your collector over OpAMP. It writes their contents, but it does not add them to the traces pipeline. If you run the default collector config from Foundry or the Helm chart, the new defaults carry them. If you maintain your own collector config, [add them yourself](#add-the-ai-observability-processors-to-a-custom-collector-config).
</Admonition>

<Admonition type="warning" title="JWT is no longer the default in v0.143.0" defaultCollapsed="true">

Before v0.143.0, JWT was the default, so a secret alone was enough. To keep JWT sessions, set both:

```bash
SIGNOZ_TOKENIZER_PROVIDER=jwt
SIGNOZ_TOKENIZER_JWT_SECRET=<your secret>
```

With the JWT provider and no secret, SigNoz refuses to start:

```text
jwt::secret must be set when provider is jwt, without a JWT secret, user sessions are vulnerable to tampering and unauthorized access
```

Users sign in again once after the switch. See [Keep the JWT session provider](#keep-the-jwt-session-provider) and the <a href="https://github.com/SigNoz/signoz/releases/tag/v0.143.0" target="_blank" rel="noopener noreferrer nofollow">v0.143.0 release notes</a>.

</Admonition>

| If you | Then |
| --- | --- |
| Run the default collector config | Nothing beyond the upgrade. Sign in again afterwards |
| Override the collector config or its traces pipeline | [Add the two processors](#add-the-ai-observability-processors-to-a-custom-collector-config) before or with the upgrade |
| Pin the collector image below v0.144.11 | Move it to v0.144.11, or stay on SigNoz v0.142.x until you can |
| Set `SIGNOZ_TOKENIZER_JWT_SECRET` or `SIGNOZ_JWT_SECRET` today | Your sessions move to opaque and the secret is ignored. To stay on JWT, add `SIGNOZ_TOKENIZER_PROVIDER=jwt` before you upgrade. See [Keep the JWT session provider](#keep-the-jwt-session-provider) |

## Upgrade self-hosted SigNoz

### Step 1: Back up your data

Pricing rules and attribute mappings live in the SigNoz Metastore (SQLite or Postgres) alongside dashboards and alerts. Back up the Metastore before you start. If you are more than one release behind, check the [Upgrade Path Tool](https://signoz.io/upgrade-path/) for required stops before you move to v0.143.0.

### Step 2: Upgrade SigNoz and the collector

Upgrade both together. SigNoz v0.143.0 requires signoz-otel-collector v0.144.11.

<Tabs entityName="installer">
<TabItem value="foundry" label="Foundry" default>

Upgrade <a href="https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md" target="_blank" rel="noopener noreferrer nofollow">foundryctl</a> to pick up the v0.143.0 collector config, then re-apply your existing `casting.yaml`.

<Admonition type="warning" title="Update the images before you run cast" defaultCollapsed="true">
`cast` applies the regenerated files but does not pull images. If your casting uses floating tags such as `latest`, refresh `signoz/signoz` and `signoz/signoz-otel-collector` on the host first so the restarted containers run v0.143.0 and v0.144.11. Otherwise the collector restarts on the old image with the new config.
</Admonition>

<Tabs entityName="foundry-platform">
<TabItem value="foundry-standard" label="Compose, Kubernetes, ECS" default>

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
foundryctl cast -f casting.yaml
```

`cast` regenerates the collector config with the two processors when the ingester image is `latest` or a version that ships them, and keeps the previous config for an older pin. If your <a href="https://github.com/SigNoz/foundry/blob/main/docs/reference/casting-file.md" target="_blank" rel="noopener noreferrer nofollow">casting.yaml</a> pins image versions, bump SigNoz to v0.143.0 and the collector to v0.144.11 yourself; `cast` refuses SigNoz v0.143.0 paired with a collector that cannot load the processors and tells you to move to v0.144.11.

If your casting sets `spec.config` on the ingester with its own traces `processors` list, that list replaces the generated one. [Add the two processors](#add-the-ai-observability-processors-to-a-custom-collector-config) to it.

</TabItem>
<TabItem value="foundry-swarm" label="Docker Swarm">

Swarm configs are immutable. `cast` cannot update the changed collector config in place, so `docker stack deploy` fails on the existing stack. Remove the stack first, then cast:

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
docker stack rm <stack-name>
foundryctl cast -f casting.yaml
```

The stack is named after `metadata.name` in your `casting.yaml`, which is `signoz` in the shipped example.

All services are down between `docker stack rm` and `foundryctl cast`. `docker stack rm` removes the services and the networks, so data on named volumes is kept.

</TabItem>
<TabItem value="foundry-systemd" label="systemd">

Foundry does not download binaries. Replace the SigNoz and collector binaries at the paths your casting states, then cast:

```bash
ARCH=$(uname -m | sed 's/x86_64/amd64/;s/aarch64/arm64/')

# defaults; your casting may set foundry.signoz.io/signoz-binary-path and foundry.signoz.io/ingester-binary-path
# extract the full SigNoz tarball: bin/, web/, templates/ and conf/ have to stay together
curl -fsSL "https://github.com/SigNoz/signoz/releases/download/v0.143.0/signoz_linux_${ARCH}.tar.gz" \
  | sudo tar -xz --strip-components=1 -C /opt/signoz

curl -fsSL "https://github.com/SigNoz/signoz-otel-collector/releases/download/v0.144.11/signoz-otel-collector_linux_${ARCH}.tar.gz" \
  | sudo tar -xz --strip-components=1 -C /opt/ingester

sudo foundryctl cast -f casting.yaml
```

`cast` regenerates the collector config, runs the migrations and reloads the units, but does not restart running services. Restart both so they pick up the new binaries and config:

```bash
sudo systemctl restart <name>-signoz.service <name>-ingester.service
```

`<name>` is `metadata.name` in your `casting.yaml`, which is `signoz` in the shipped example.

</TabItem>
</Tabs>

</TabItem>
<TabItem value="helm" label="Kubernetes (Helm chart)">

Update the <a href="https://github.com/SigNoz/charts" target="_blank" rel="noopener noreferrer nofollow">chart</a> and upgrade. Replace `<namespace>` and `<release-name>` with your own values:

```bash
helm repo update
helm -n <namespace> upgrade <release-name> signoz/signoz -f <your-values.yaml>
```

`helm upgrade` takes the newest chart; add `--version 0.143.0` to pin the v0.143.0 chart. The chart's default `otelCollector.config` carries both processors. Helm replaces lists instead of merging them, so if your values file sets `otelCollector.config.service.pipelines.traces.processors`, [add the two processors](#add-the-ai-observability-processors-to-a-custom-collector-config) to your list.

</TabItem>
</Tabs>

### Step 3: Verify the upgrade

1. SigNoz and the collector are healthy (`kubectl get pods -n <namespace>`, `docker compose ps`, `docker stack ps <stack-name>`, or `systemctl status 'signoz-*'`).
2. SigNoz reports v0.143.0 under **Settings**.
3. The collector log shows no `unknown type` error for `signozspanmapper` or `signozllmpricing`.

## Add the AI observability processors to a custom collector config

Add both processors under `processors`, exactly as below. SigNoz fills `groups` and `default_pricing.rules` over OpAMP, so leave them empty here.

```yaml
processors:
  signozspanmapper:
    groups: []
  signozllmpricing:
    attrs:
      model: gen_ai.request.model
      in: gen_ai.usage.input_tokens
      out: gen_ai.usage.output_tokens
      cache_read: gen_ai.usage.cache_read.input_tokens
      cache_write: gen_ai.usage.cache_creation.input_tokens
    default_pricing:
      rules: []
    output_attrs:
      in: signoz.gen_ai.usage.input_tokens.cost
      out: signoz.gen_ai.usage.output_tokens.cost
      cache_read: signoz.gen_ai.usage.cache_read.input_tokens.cost
      cache_write: signoz.gen_ai.usage.cache_write.input_tokens.cost
      total: signoz.gen_ai.usage.tokens.cost
```

Then add both to the traces pipeline, after `signozspanmetrics/delta` and before `batch`:

```yaml
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [signozspanmetrics/delta, signozspanmapper, signozllmpricing, batch]
      exporters: [clickhousetraces, metadataexporter, signozmeter]
```

A collector with the processors defined but missing from the pipeline starts fine; token costs and attribute mapping stay off until the pipeline entries are in place.

## Keep the JWT session provider

SigNoz v0.143.0 issues opaque session tokens by default. Before v0.143.0 JWT was the default, so a secret alone was enough. To stay on JWT, set both before you upgrade:

```bash
SIGNOZ_TOKENIZER_PROVIDER=jwt
SIGNOZ_TOKENIZER_JWT_SECRET=<your existing secret>
```

With the `jwt` provider and no secret, SigNoz refuses to start:

```text
jwt::secret must be set when provider is jwt, without a JWT secret, user sessions are vulnerable to tampering and unauthorized access
```

If you still use `SIGNOZ_JWT_SECRET`, rename it to `SIGNOZ_TOKENIZER_JWT_SECRET`. See [Configure the JWT Secret](https://signoz.io/docs/manage/administrator-guide/configuration/jwt-secret/) for details.
