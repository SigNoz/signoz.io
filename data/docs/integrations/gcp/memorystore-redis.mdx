The **Memorystore for Redis** integration brings instance metrics (uptime, CPU, memory, clients, cache hit ratio, keyspace, and command latency) into SigNoz, with a pre-built dashboard for the service.

Memorystore publishes its metrics to **Cloud Monitoring**, and SigNoz reads them through the OpenTelemetry Collector running in your GCP project.

<Admonition type="info">
This page covers **Memorystore for Redis** (the `redis.googleapis.com/*` metrics on `redis_instance` resources). Memorystore for Redis Cluster publishes a different metric set and is not covered here.
</Admonition>

## Prerequisites

Before configuring this service, complete the shared GCP integration setup:

- Your [GCP account is connected in SigNoz](https://signoz.io/docs/integrations/gcp/connect-gcp-account/), and the project running your Redis instances is in [**Projects to Monitor**](https://signoz.io/docs/integrations/gcp/manual-setup/#connection-fields).
- The [OpenTelemetry Collector is deployed and running](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/).
- The `signoz-integration` service account has `roles/monitoring.viewer` on the project that hosts the instances. See [Create a service account](https://signoz.io/docs/integrations/gcp/create-service-account/#step-3-grant-metrics-permission-on-each-monitored-project).
- The **Cloud Monitoring API** is enabled in that project. For logs, the **Cloud Logging API**, the **Pub/Sub API**, and a working [log pipeline](https://signoz.io/docs/integrations/gcp/collect-logs/) are also required.

## Step 1: Enable the service in SigNoz

1. In SigNoz, go to **Integrations** > **Google Cloud Platform**.
2. Select **GCP Memorystore for Redis** from the service list.
3. Toggle **Metric Collection** on to activate the pre-built dashboard.
4. Open the **Data Collected** tab and note the metrics listed there. These are the metrics the dashboard's panels query.

<Admonition type="warning">
Enabling the toggle does not start collection on its own. The metrics that reach SigNoz are exactly the ones in your Collector's `metrics_list`. If you skip a metric in step 2, its dashboard panel stays empty.
</Admonition>

## Step 2: Add the metrics to your Collector config

Open the `otel-collector-config.yaml` you created in [Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-1-prepare-the-collector-configuration) and add the Memorystore metric names to the `metrics_list` of the `googlecloudmonitoring` receiver for the project your instances run in:

```yaml:otel-collector-config.yaml
receivers:
  googlecloudmonitoring:
    project_id: "<monitored-project-id>"
    collection_interval: 300s   # 5 minutes; minimum is 60s
    metrics_list:
      # Availability
      - metric_name: "redis.googleapis.com/server/uptime"
      # Compute and memory
      - metric_name: "redis.googleapis.com/stats/cpu_utilization_main_thread"
      - metric_name: "redis.googleapis.com/stats/memory/usage_ratio"
      - metric_name: "redis.googleapis.com/stats/memory/system_memory_usage_ratio"
      # Clients
      - metric_name: "redis.googleapis.com/clients/connected"
      - metric_name: "redis.googleapis.com/clients/blocked"
      - metric_name: "redis.googleapis.com/stats/reject_connections_count"
      # Keyspace and cache effectiveness
      - metric_name: "redis.googleapis.com/keyspace/keys"
      - metric_name: "redis.googleapis.com/stats/cache_hit_ratio"
      # Commands
      - metric_name: "redis.googleapis.com/commands/calls"
      - metric_name: "redis.googleapis.com/commands/usec_per_call"

service:
  pipelines:
    metrics:
      receivers: [googlecloudmonitoring]
      processors: [memory_limiter, batch]
      exporters: [otlphttp]
```

**Verify these values:**

- `<monitored-project-id>`: The GCP project that hosts your Redis instances. It must be one of the entries in your **Projects to Monitor** list.

<Admonition type="info">
If your instances span several projects, add one **named** receiver per project (`googlecloudmonitoring/<name>`) and list them all in the metrics pipeline. See [Configure multiple projects](https://signoz.io/docs/integrations/gcp/collect-metrics/#step-3-configure-multiple-projects).
</Admonition>

## Step 3: Apply the configuration

The Collector loads its config from the `signoz-collector-config` secret, so a config change needs a new secret version and a redeploy:

1. Save your updated `otel-collector-config.yaml`.
2. Add a new secret version ([step 2 of Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-2-store-the-config-in-secret-manager)).
3. Redeploy the Cloud Run service ([step 3](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-3-deploy-to-cloud-run)).

## Step 4: Route Memorystore logs

<Admonition type="info">
Memorystore for Redis does **not** write Redis command or server logs to Cloud Logging. What it does emit is **audit logs** (administrative API calls on instances) and **maintenance logs** (maintenance windows and rollouts). Metrics are the primary signal for this service.
</Admonition>

If you want those log types in SigNoz, follow [Collect logs](https://signoz.io/docs/integrations/gcp/collect-logs/) to create the Pub/Sub topic and the push subscription. When you reach [step 4, Create a log sink](https://signoz.io/docs/integrations/gcp/collect-logs/#step-4-create-a-log-sink-per-monitored-project), use one of the filters below as the sink's **Build inclusion filter** value.

**Audit logs.** Memorystore audit logs use the `redis.googleapis.com` service and the `audited_resource` resource type. Enter this as the sink's inclusion filter:

```
resource.type="audited_resource"
resource.labels.service="redis.googleapis.com"
```

Admin Activity audit logs are always written and can't be disabled. Data Access audit logs are off by default, so you may need to enable them for the `redis.googleapis.com` service under **IAM & Admin → Audit Logs**. Pick the categories you want:

- **Admin Read**: API calls that read instance metadata or configuration, such as listing or describing instances.
- **Data Read**: API calls that read user-provided data.
- **Data Write**: API calls that write user-provided data.

Enabling Data Access audit logs increases Cloud Logging ingestion, which is billable. See <a href="https://docs.cloud.google.com/memorystore/docs/redis/audit-logs" target="_blank" rel="noopener noreferrer nofollow">Memorystore for Redis audit logging</a> for which methods fall into each category.

**Maintenance logs.** These are written to the shared maintenance log, so use this as the sink's **Build inclusion filter** value (same field as above) to narrow it to Redis activity types:

```
logName="projects/<monitored-project-id>/logs/maintenance.googleapis.com%2Factivity_log"
labels.activity_type_name=~"^CloudRedis"
```

See <a href="https://cloud.google.com/memorystore/docs/redis/view-maintenance-logs" target="_blank" rel="noopener noreferrer nofollow">View maintenance logs</a> for the individual activity type names.

<Admonition type="warning">
Add a matching **exclusion filter** on the project's `_Default` sink, or you pay to store the same logs in both Cloud Logging and SigNoz. See [Avoid duplicate log costs](https://signoz.io/docs/integrations/gcp/collect-logs/#step-6-avoid-duplicate-log-costs).
</Admonition>

## Validate

1. Wait one or two collection intervals (up to about 5 minutes with the default `300s`).
2. In SigNoz, go to **Dashboards** and open the Memorystore for Redis dashboard. Panels should start filling in.
3. To check a single metric, open **Metrics Explorer** and query `redis.googleapis.com/stats/memory/usage_ratio`.
4. For logs, open **Logs** and filter where `gcp.resource_type` = `audited_resource` and `gcp.label.service` = `redis.googleapis.com`.

## What's collected

<details>
<summary>Metrics</summary>

See the **Data Collected** tab in the SigNoz integration for the definitive list the dashboard uses, and the <a href="https://docs.cloud.google.com/monitoring/api/metrics_gcp_p_z#gcp-redis" target="_blank" rel="noopener noreferrer nofollow">GCP metrics list</a> for full definitions.

| Metric name | Unit | Type |
|-------------|------|------|
| `redis.googleapis.com/server/uptime` | Seconds | Gauge |
| `redis.googleapis.com/stats/cpu_utilization_main_thread` | Seconds | Sum |
| `redis.googleapis.com/stats/memory/usage_ratio` | None | Gauge |
| `redis.googleapis.com/stats/memory/system_memory_usage_ratio` | None | Gauge |
| `redis.googleapis.com/clients/connected` | Count | Gauge |
| `redis.googleapis.com/clients/blocked` | Count | Gauge |
| `redis.googleapis.com/stats/reject_connections_count` | Count | Sum |
| `redis.googleapis.com/keyspace/keys` | Count | Gauge |
| `redis.googleapis.com/stats/cache_hit_ratio` | None | Gauge |
| `redis.googleapis.com/commands/calls` | Count | Sum |
| `redis.googleapis.com/commands/usec_per_call` | Microseconds | Gauge |

</details>

<details>
<summary>Logs</summary>

Routed by the sink filter you set in step 4. Memorystore emits audit and maintenance logs only, not Redis command logs. In SigNoz, these log entries carry these resource and label attributes:

| Attribute | Description |
|-----------|--------------|
| `gcp.resource_type` | `audited_resource` for audit logs |
| `gcp.label.service` | `redis.googleapis.com` for audit logs |
| `gcp.project` | The project that owns the instance |

</details>

## Troubleshooting
</ToggleHeading>

**A dashboard panel is empty.** The metric backing that panel is missing from your `metrics_list`. Compare the **Data Collected** tab against your `otel-collector-config.yaml`, add what's missing, and repeat step 3.

**No Memorystore metrics at all.** Confirm the `signoz-integration` service account holds `roles/monitoring.viewer` on the project in `project_id`, and that the Cloud Monitoring API is enabled there. Then check the Cloud Run logs for `googlecloudmonitoring` receiver errors.

**Cache hit ratio looks wrong right after a restart.** The ratio is derived from counters that reset when the instance restarts. Check `server/uptime` before reading too much into a sudden change.

**No Redis query logs.** This is expected. Memorystore does not export command or slow-log entries to Cloud Logging. Use the keyspace and cache metrics above, or instrument the application's Redis client to get per-command visibility.

</details>
