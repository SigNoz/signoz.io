The **Compute Engine** integration brings VM instance metrics into SigNoz, with a pre-built dashboard for the service. With One-Click Integration, it also brings in your Compute Engine logs.

Compute Engine publishes its metrics to **Cloud Monitoring** and its logs to **Cloud Logging**. SigNoz reads them through the OpenTelemetry Collector running in your GCP project.

<Admonition type="info">
This page reads what Compute Engine already sends to Cloud Monitoring and Cloud Logging, so nothing gets installed on your VMs. If you want detailed host metrics and logs collected from inside each VM, see [Host Monitoring](https://signoz.io/docs/infrastructure-monitoring/host-monitoring/). The two approaches work well together.
</Admonition>

## One-Click Integration

SigNoz deploys and manages the Collector for you. You turn the service on in SigNoz, and the SigNoz agent sets up metrics and logs collection in the background. Collects **metrics and logs**.

### Prerequisites

- Your GCP project is connected with [One-Click Integration](https://signoz.io/docs/integrations/gcp/one-click-gcp-integrations/).
- Your VM instances run in that same project. The agent monitors only the project it's deployed in.

### Step 1: Turn on the service in SigNoz

1. In SigNoz, go to **Integrations** > **Google Cloud Platform**.
2. Select **GCP Compute Engine** from the service list.
3. Turn on **Metric Collection**, **Log Collection**, or both.
4. Click **Save**.

The agent picks up the change within about 30 seconds and updates the Collector and the log sink for you. There's no Collector config to edit.

### Step 2: Turn on the optional data in GCP

Most data starts flowing with no extra work. Two kinds of data need a setting on the GCP side first:

- **Memory panels.** GCP can't see inside a VM on its own, so memory metrics need help from the VM:
  - **% Memory Utilization via Ops Agent** needs the <a href="https://cloud.google.com/stackdriver/docs/solutions/agents/ops-agent" target="_blank" rel="noopener noreferrer nofollow">Ops Agent</a> installed on the VM.
  - **% Memory Utilization** and **Memory Used in Bytes** are only reported by GKE nodes and by VMs running Container-Optimized OS. GKE nodes report them by default. Standalone Container-Optimized OS VMs need <a href="https://cloud.google.com/container-optimized-os/docs/how-to/monitoring" target="_blank" rel="noopener noreferrer nofollow">health monitoring</a> turned on first: set the `google-monitoring-enabled` metadata key to `true` on the VM or project. It's off by default.
- **Logs from inside the VM**, such as syslog and application logs, also need the Ops Agent. Without it, SigNoz still collects the Compute Engine audit logs.

Skip this step if you only need CPU, disk, and network metrics and audit logs.

### Validate

1. Wait about 10 minutes for the first metrics to arrive.
2. In SigNoz, go to **Dashboards** and open **GCP Compute Engine Overview**. Panels should start filling in.
3. If you turned on **Log Collection**, open **Logs** in SigNoz and start with this filter to find your project's logs:

   ```text
   gcp.project = '<deployment-project-id>' AND gcp.resource_type = 'gce_instance'
   ```

   Log entries appear within a few minutes of the next VM change or, with the Ops Agent installed, the next log line from the VM. Audit logs for disks, firewall rules, and other Compute Engine resources use other resource types, so drop the `gcp.resource_type` part to see them too.

   **Verify these values:**

   - `<deployment-project-id>`: the GCP project you connected with One-Click Integration.

## Manual Setup

You run the OpenTelemetry Collector in your own GCP project and add Compute Engine metrics to its configuration. You control which metrics are pulled and how often. Collects **metrics only**.

Complete the [GCP integration setup](https://signoz.io/docs/integrations/gcp/manual-setup/) once, then follow the steps below for each project that hosts the VMs you want to monitor.

### Prerequisites

Before configuring this service, complete the shared GCP integration setup:

- Your [GCP account is connected in SigNoz](https://signoz.io/docs/integrations/gcp/connect-gcp-account/), and the project running your VMs is in [**Projects to Monitor**](https://signoz.io/docs/integrations/gcp/manual-setup/#connection-fields).
- The [OpenTelemetry Collector is deployed and running](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/).
- The `signoz-integration` service account has `roles/monitoring.viewer` on the project that hosts the VMs. See [Create a service account](https://signoz.io/docs/integrations/gcp/create-service-account/#step-3-grant-metrics-permission-on-each-monitored-project).
- The **Cloud Monitoring API** is enabled in that project.

### Step 1: Enable the service in SigNoz

1. In SigNoz, go to **Integrations** > **Google Cloud Platform**.
2. Select **GCP Compute Engine** from the service list.
3. Toggle **Metric Collection** on to activate the pre-built dashboard.
4. Open the **Data Collected** tab and note the metrics listed there. These are the metrics the dashboard's panels query.

<Admonition type="warning">
Enabling the toggle does not start collection on its own. The metrics that reach SigNoz are exactly the ones in your Collector's `metrics_list`. If you skip a metric in step 2, its dashboard panel stays empty.
</Admonition>

### Step 2: Add the metrics to your Collector config

Open the `otel-collector-config.yaml` you created in [Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-1-prepare-the-collector-configuration) and add the Compute Engine metric names to the `metrics_list` of the `googlecloudmonitoring` receiver for the project your VMs run in. Only the `metrics_list` shown below changes; leave the rest of the file as is:

```yaml:otel-collector-config.yaml defaultCollapsed
receivers:
  googlecloudmonitoring:
    project_id: "<monitored-project-id>"
    collection_interval: 300s   # 5 minutes; minimum is 60s
    metrics_list:
      # Uptime
      - metric_name: "compute.googleapis.com/instance/uptime_total"
      # CPU and memory
      - metric_name: "compute.googleapis.com/instance/cpu/utilization"
      - metric_name: "compute.googleapis.com/guest/memory/bytes_used"
      - metric_name: "compute.googleapis.com/guest/memory/percent_used"
      - metric_name: "agent.googleapis.com/memory/percent_used"
      # Disk
      - metric_name: "compute.googleapis.com/instance/disk/average_io_latency"
      - metric_name: "compute.googleapis.com/instance/disk/read_bytes_count"
      - metric_name: "compute.googleapis.com/instance/disk/write_bytes_count"
      - metric_name: "compute.googleapis.com/instance/disk/read_ops_count"
      - metric_name: "compute.googleapis.com/instance/disk/write_ops_count"
      - metric_name: "compute.googleapis.com/instance/disk/performance_status"
      # Network
      - metric_name: "compute.googleapis.com/instance/network/received_bytes_count"
      - metric_name: "compute.googleapis.com/instance/network/sent_bytes_count"
      - metric_name: "compute.googleapis.com/instance/network/received_packets_count"
      - metric_name: "compute.googleapis.com/instance/network/sent_packets_count"
      - metric_name: "compute.googleapis.com/firewall/dropped_packets_count"
```

**Verify these values:**

- `<monitored-project-id>`: The GCP project that hosts your VMs. It must be one of the entries in your **Projects to Monitor** list.

<Admonition type="info">
If your VMs span several projects, add one **named** receiver per project (`googlecloudmonitoring/<name>`) and list them all in the metrics pipeline. See [Configure multiple projects](https://signoz.io/docs/integrations/gcp/collect-metrics/#step-3-configure-multiple-projects).
</Admonition>

The memory metrics need help from the VM: `agent.googleapis.com/memory/percent_used` needs the <a href="https://cloud.google.com/stackdriver/docs/solutions/agents/ops-agent" target="_blank" rel="noopener noreferrer nofollow">Ops Agent</a>, and the two `guest/memory/` metrics are only reported by GKE nodes and by Container-Optimized OS VMs with <a href="https://cloud.google.com/container-optimized-os/docs/how-to/monitoring" target="_blank" rel="noopener noreferrer nofollow">health monitoring</a> turned on (`google-monitoring-enabled=true`). Drop the ones your VMs don't report.

The receiver polls every metric in the list once per `collection_interval`, and the Monitoring API bills per read call, so keep the list to the metrics your dashboards and alerts actually use. See [Cost and tuning](https://signoz.io/docs/integrations/gcp/collect-metrics/#cost-and-tuning).

### Step 3: Apply the configuration

The Collector loads its config from the `signoz-collector-config` secret, so a config change needs a new secret version and a redeploy:

1. Save your updated `otel-collector-config.yaml`.
2. Add a new secret version ([step 2 of Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-2-store-the-config-in-secret-manager)).
3. Redeploy the Cloud Run service ([step 3](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-3-deploy-to-cloud-run)).

### Validate

1. Wait one or two collection intervals (up to about 5 minutes with the default `300s`).
2. In SigNoz, go to **Dashboards** and open the **GCP Compute Engine Overview** dashboard. Panels should start filling in.
3. To check a single metric, open **Metrics Explorer** and query `compute.googleapis.com/instance/cpu/utilization`.

## What's collected

The **GCP Compute Engine Overview** dashboard has 16 panels. An **Uptime total** table sits at the top, followed by three sections:

- **CPU & Memory:** % CPU Utilization, % Memory Utilization, % Memory Utilization via Ops Agent, Memory Used in Bytes.
- **Disk:** Disk average latency, Disk performance status, Disk Read Throughput, Disk Write Throughput, Disk Read IOPS, Disk Write IOPS.
- **Network:** Received traffic, Sent traffic, Received packets, Sent packets, Dropped packets.

Two variables scope the panels: **project_id** and **instance_id**.

<details>
<summary>Logs (One-Click Integration only)</summary>

With **Log Collection** turned on, SigNoz collects these logs for your VMs:

| Log | What it contains | GCP setup needed |
| --- | --- | --- |
| Admin Activity audit logs | Changes to Compute Engine resources, such as creating, starting, stopping, or deleting a VM, and changes to disks and firewall rules | None. GCP always writes these. |
| System Event audit logs | Actions Google takes on your VMs, such as live migration, host maintenance, and preemption | None. GCP always writes these. |
| Data Access audit logs | Reads of Compute Engine resources, such as getting or listing VMs | Turn on <a href="https://cloud.google.com/logging/docs/audit/configure-data-access" target="_blank" rel="noopener noreferrer nofollow">Data Access audit logs</a> for Compute Engine |
| VM logs | Logs written inside the VM, such as syslog and application logs | Install the <a href="https://cloud.google.com/stackdriver/docs/solutions/agents/ops-agent" target="_blank" rel="noopener noreferrer nofollow">Ops Agent</a> on the VM |

<Admonition type="info">
The audit log part of the filter matches every Compute Engine resource in the project, not only VMs. With Data Access audit logs turned on, routine list and get calls can add a lot of log volume.
</Admonition>

SigNoz uses this log sink filter:

```text
resource.type="gce_instance" OR protoPayload.serviceName="compute.googleapis.com"
```

## Troubleshooting
</ToggleHeading>

**Memory panels are empty.** These panels need help from inside the VM. **% Memory Utilization via Ops Agent** needs the Ops Agent installed. **% Memory Utilization** and **Memory Used in Bytes** only report for GKE nodes and for Container-Optimized OS VMs. On a standalone Container-Optimized OS VM, confirm <a href="https://cloud.google.com/container-optimized-os/docs/how-to/monitoring" target="_blank" rel="noopener noreferrer nofollow">health monitoring</a> is on by checking that the `google-monitoring-enabled` metadata key is `true`. CPU, disk, and network panels work without either.

**No logs after turning on Log Collection (One-Click).** Audit logs only appear when a VM or other Compute Engine resource changes, so a quiet project may show nothing at first. For logs from inside the VM, confirm the Ops Agent is installed and running. Open **Logs Explorer** in the GCP Console and filter on `resource.type="gce_instance"` to see what GCP has written.

**No metrics at all (One-Click).** Confirm the VMs run in the project the agent is deployed in, and that **Metric Collection** is on and saved. See the [One-Click troubleshooting](https://signoz.io/docs/integrations/gcp/one-click-gcp-integrations/#troubleshooting) for agent and Collector checks.

**A dashboard panel is empty (Manual).** The metric backing that panel is missing from your `metrics_list`. Compare the **Data Collected** tab against your `otel-collector-config.yaml`, add what's missing, and repeat step 3.

**No Compute Engine metrics at all (Manual).** Confirm the `signoz-integration` service account holds `roles/monitoring.viewer` on the project in `project_id`, and that the Cloud Monitoring API is enabled there. Then check the Cloud Run logs for `googlecloudmonitoring` receiver errors.

**Dropped packets stays at zero.** That's the healthy state. The panel only shows incoming packets that a firewall rule dropped.
