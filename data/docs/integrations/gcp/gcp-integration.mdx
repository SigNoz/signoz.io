The **SigNoz GCP Integration** brings metrics and logs from your Google Cloud services into SigNoz, with pre-built dashboards for supported services. You connect a GCP account in the SigNoz UI, deploy an OpenTelemetry Collector inside your own GCP project, and point it at SigNoz.

This first release uses a **manual flow**: you create and own the GCP resources (a service account, an OpenTelemetry Collector, and, for logs, a Pub/Sub topic and a log sink). SigNoz guides you through each resource with the docs in this section.

<Admonition type="info">
The GCP integration is available on **SigNoz Cloud**. Traces are **not** part of this integration. Send traces by [instrumenting your applications](https://signoz.io/docs/instrumentation/) directly.
</Admonition>

## How it works

GCP does not PUSH telemetry to third parties, so SigNoz collects it with an OpenTelemetry Collector that runs **inside your GCP project**:

- **Metrics** live in **Cloud Monitoring** and are pulled through the Monitoring API. The Collector's <a href="https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver/googlecloudmonitoringreceiver" target="_blank" rel="noopener noreferrer nofollow">`googlecloudmonitoring`</a> receiver scrapes them on an interval and exports them to SigNoz over OTLP.
- **Logs** are written to **Cloud Logging**. A **log sink** routes the logs you care about to a **Pub/Sub topic**, and a Pub/Sub **push subscription** delivers them to the Collector, which exports them to SigNoz over OTLP.

The Collector must run in your environment because Pub/Sub push subscriptions authenticate only with a GCP service account (they cannot attach a SigNoz ingestion key), so pushing straight to the SigNoz gateway is not possible. Keeping the Collector inside your project also keeps the pipeline within GCP's trust boundary.

<Admonition type="info">
These guides use **Cloud Run** for the Collector because it is the quickest managed option, but it is **not required**. You can run the Collector on any compute you prefer (a Compute Engine VM, GKE, or an existing Kubernetes cluster) as long as its endpoint is reachable by the Pub/Sub push subscription. The metrics receiver works anywhere it can authenticate to the Monitoring API.
</Admonition>

## The four connection fields

When you connect a GCP account in SigNoz (step 2), you provide four values. They anchor the rest of the setup, so keep them handy: every guide in this section refers back to them.

| Field | What it means | Where it's used later |
| --- | --- | --- |
| **Account Name** | A label you choose to uniquely identify this integration in SigNoz. GCP projects are globally unique and need not sit under an organization, so there is no automatic account ID as with AWS or Azure. Use your organization ID, billing account, or an environment name (for example, `production` or `my-org`). | Identifies the connected account in the SigNoz UI. It does not name any GCP resource. |
| **Deployment Project ID** | The GCP project where you deploy the **OpenTelemetry Collector** (Cloud Run) and, for logs, the **Pub/Sub topic** and **push subscription**. | The project you build resources in during steps 3 and 5. When a monitored project differs from this one, you reference this project ID in fully-qualified resource names (for example, the Pub/Sub topic path). |
| **Deployment Region** | The GCP region where the Cloud Run Collector runs. Selected from a dropdown; a single region. | The `--region` for the Cloud Run service in step 3. |
| **Projects to Monitor** | The list of project IDs whose metrics and logs you want in SigNoz. It may include the Deployment Project ID and any number of other projects. | One `googlecloudmonitoring` receiver block per project (step 4) and one log sink per project (step 5). |

<Admonition type="info">
Throughout these guides, `<deployment-project-id>`, `<deployment-region>`, and `<monitored-project-id>` refer to the values you enter in these fields. Substitute your own values wherever you see them.
</Admonition>

## Costs to expect

The manual flow runs resources in your GCP project, so the cost is billed to you, not SigNoz. Plan for:

- **Cloud Run (Collector):** roughly **~$110/month** for a Collector sized at 2 vCPU and 4 GiB running continuously. This is a comfortable default; if you ingest low volumes, you can pick a smaller configuration (for example, 1 vCPU and 1–2 GiB) to lower the cost. Size it to your throughput and scale up only if the Collector shows memory pressure or dropped data. See <a href="https://cloud.google.com/run#pricing" target="_blank" rel="noopener noreferrer nofollow">Cloud Run pricing</a>.
- **Pub/Sub (logs):** **$40 per TiB** of throughput. See <a href="https://cloud.google.com/pubsub/pricing" target="_blank" rel="noopener noreferrer nofollow">Pub/Sub pricing</a>.
- **Monitoring API (metrics):** **$0.01 per 1,000 read calls**, with the first 1 million read calls free per billing account each month. Write calls are free. See <a href="https://cloud.google.com/stackdriver/pricing" target="_blank" rel="noopener noreferrer nofollow">Cloud Monitoring pricing</a>.

<Admonition type="warning">
**Avoid paying twice for logs.** Every service already sends logs to GCP's built-in `_Default` sink. A second sink for SigNoz means the same logs are stored twice. Add an **exclusion filter** on the `_Default` sink for the services you monitor through SigNoz. See [Collect logs](https://signoz.io/docs/integrations/gcp/collect-logs/#avoid-duplicate-log-costs).
</Admonition>
