The **Cloud SQL for PostgreSQL** integration brings instance metrics into SigNoz, with a pre-built dashboard for the service. With One-Click Integration, it also brings in your PostgreSQL logs.

Cloud SQL publishes its metrics to **Cloud Monitoring** and its logs to **Cloud Logging**. SigNoz reads them through the OpenTelemetry Collector running in your GCP project.

## One-Click Integration

SigNoz deploys and manages the Collector for you. You turn the service on in SigNoz, and the SigNoz agent sets up metrics and logs collection in the background. Collects **metrics and logs**.

### Prerequisites

- Your GCP project is connected with [One-Click Integration](https://signoz.io/docs/integrations/gcp/one-click-gcp-integrations/).
- Your Cloud SQL for PostgreSQL instances run in that same project. The agent monitors only the project it's deployed in.

### Step 1: Turn on the service in SigNoz

1. In SigNoz, go to **Integrations** > **Google Cloud Platform**.
2. Select **GCP Cloud SQL for PostgreSQL** from the service list.
3. Turn on **Metric Collection**, **Log Collection**, or both.
4. Click **Save**.

The agent picks up the change within about 30 seconds and updates the Collector and the log sink for you. There's no Collector config to edit.

### Step 2: Turn on the optional data in GCP

Most data starts flowing with no extra work. Two kinds of data need a setting on the GCP side first:

- **Query execution time panels** need <a href="https://cloud.google.com/sql/docs/postgres/using-query-insights" target="_blank" rel="noopener noreferrer nofollow">Query Insights</a> turned on for the instance. It's off by default and has no extra charge.
- **pgAudit logs**, which record the SQL statements run on your database, need pgAudit set up on the instance and Data Access audit logs turned on for the project. See <a href="https://cloud.google.com/sql/docs/postgres/pg-audit" target="_blank" rel="noopener noreferrer nofollow">Audit a Cloud SQL instance with pgAudit</a>.

Skip this step if you don't need these.

### Validate

1. Wait about 10 minutes for the first metrics to arrive.
2. In SigNoz, go to **Dashboards** and open **GCP Cloud SQL for PostgreSQL Overview**. Panels should start filling in.
3. If you turned on **Log Collection**, open **Logs** in SigNoz and start with this filter to find your project's logs:

   ```text
   gcp.project = '<deployment-project-id>' AND gcp.resource_type = 'cloudsql_database'
   ```

   New PostgreSQL log lines from your instances appear within a few minutes.

   **Verify these values:**

   - `<deployment-project-id>`: the GCP project you connected with One-Click Integration.

## Manual Setup

You run the OpenTelemetry Collector in your own GCP project and add Cloud SQL metrics to its configuration. You control which metrics are pulled and how often. Collects **metrics only**.

Complete the [GCP integration setup](https://signoz.io/docs/integrations/gcp/manual-setup/) once, then follow the steps below for each Cloud SQL instance you want to monitor.

### Prerequisites

Before configuring this service, complete the shared GCP integration setup:

- Your [GCP account is connected in SigNoz](https://signoz.io/docs/integrations/gcp/connect-gcp-account/), and the project running your Cloud SQL instances is in [**Projects to Monitor**](https://signoz.io/docs/integrations/gcp/manual-setup/#connection-fields).
- The [OpenTelemetry Collector is deployed and running](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/).
- The `signoz-integration` service account has `roles/monitoring.viewer` on the project that hosts the instances. See [Create a service account](https://signoz.io/docs/integrations/gcp/create-service-account/#step-3-grant-metrics-permission-on-each-monitored-project).
- The **Cloud Monitoring API** is enabled in that project.

### Step 1: Enable the service in SigNoz

1. In SigNoz, go to **Integrations** > **Google Cloud Platform**.
2. Select **GCP Cloud SQL for PostgreSQL** from the service list.
3. Toggle **Metric Collection** on to activate the pre-built dashboard.
4. Open the **Data Collected** tab and note the metrics listed there. These are the metrics the dashboard's panels query.

<Admonition type="warning">
Enabling the toggle does not start collection on its own. The metrics that reach SigNoz are exactly the ones in your Collector's `metrics_list`. If you skip a metric in step 2, its dashboard panel stays empty.
</Admonition>

### Step 2: Add the metrics to your Collector config

Open the `otel-collector-config.yaml` you created in [Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-1-prepare-the-collector-configuration) and add the Cloud SQL metric names to the `metrics_list` of the `googlecloudmonitoring` receiver for the project your instances run in. Only the `metrics_list` shown below changes; leave the rest of the file as is:

```yaml:otel-collector-config.yaml defaultCollapsed
receivers:
  googlecloudmonitoring:
    project_id: "<monitored-project-id>"
    collection_interval: 300s   # 5 minutes; minimum is 60s
    metrics_list:
      # Availability
      - metric_name: "cloudsql.googleapis.com/database/up"
      # Compute
      - metric_name: "cloudsql.googleapis.com/database/cpu/utilization"
      - metric_name: "cloudsql.googleapis.com/database/memory/utilization"
      - metric_name: "cloudsql.googleapis.com/database/memory/usage"
      # Storage
      - metric_name: "cloudsql.googleapis.com/database/disk/bytes_used"
      # PostgreSQL engine
      - metric_name: "cloudsql.googleapis.com/database/postgresql/num_backends"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/num_backends_by_state"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/transaction_count"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/deadlock_count"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/vacuum/oldest_transaction_age"
      # Query insights
      - metric_name: "cloudsql.googleapis.com/database/postgresql/insights/aggregate/execution_time"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/insights/aggregate/io_time"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/insights/perquery/execution_time"
      # Replication
      - metric_name: "cloudsql.googleapis.com/database/postgresql/replication/replica_byte_lag"
```

**Verify these values:**

- `<monitored-project-id>`: The GCP project that hosts your Cloud SQL instances. It must be one of the entries in your **Projects to Monitor** list.

<Admonition type="info">
If your instances span several projects, add one **named** receiver per project (`googlecloudmonitoring/<name>`) and list them all in the metrics pipeline. See [Configure multiple projects](https://signoz.io/docs/integrations/gcp/collect-metrics/#step-3-configure-multiple-projects).
</Admonition>

The three `insights/` metrics need <a href="https://cloud.google.com/sql/docs/postgres/using-query-insights" target="_blank" rel="noopener noreferrer nofollow">Query Insights</a> enabled on the instance (off by default, no extra charge) or their panels stay empty; drop them from the list if you don't need query timing.

The receiver polls every metric in the list once per `collection_interval`, and the Monitoring API bills per read call, so keep the list to the metrics your dashboards and alerts actually use. See [Cost and tuning](https://signoz.io/docs/integrations/gcp/collect-metrics/#cost-and-tuning).

### Step 3: Apply the configuration

The Collector loads its config from the `signoz-collector-config` secret, so a config change needs a new secret version and a redeploy:

1. Save your updated `otel-collector-config.yaml`.
2. Add a new secret version ([step 2 of Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-2-store-the-config-in-secret-manager)).
3. Redeploy the Cloud Run service ([step 3](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-3-deploy-to-cloud-run)).

### Validate

1. Wait one or two collection intervals (up to about 5 minutes with the default `300s`).
2. In SigNoz, go to **Dashboards** and open the Cloud SQL for PostgreSQL dashboard. Panels should start filling in.
3. To check a single metric, open **Metrics Explorer** and query `cloudsql.googleapis.com/database/cpu/utilization`.

<details>
<summary>Logs (One-Click Integration only)</summary>

With **Log Collection** turned on, SigNoz collects these logs from your Cloud SQL for PostgreSQL instances:

| Log | What it contains | GCP setup needed |
| --- | --- | --- |
| PostgreSQL logs (`cloudsql.googleapis.com/postgres.log`) | Messages from the PostgreSQL server, such as errors, warnings, and slow queries | None. Use <a href="https://cloud.google.com/sql/docs/postgres/flags" target="_blank" rel="noopener noreferrer nofollow">database flags</a> such as `log_min_duration_statement` to choose what PostgreSQL writes. |
| pgAudit logs (`cloudaudit.googleapis.com/data_access`) | The SQL statements run on your database, for auditing | Set up <a href="https://cloud.google.com/sql/docs/postgres/pg-audit" target="_blank" rel="noopener noreferrer nofollow">pgAudit</a> and turn on Data Access audit logs |

SigNoz uses this log sink filter:

```text
resource.type="cloudsql_database" AND (
  logName:"/logs/cloudsql.googleapis.com%2Fpostgres"
  OR (log_id("cloudaudit.googleapis.com/data_access")
    AND protoPayload.request.@type="type.googleapis.com/google.cloud.sql.audit.v1.PgAuditEntry")
)
```

## Troubleshooting
</ToggleHeading>

**Query execution time panels are empty.** The `insights/` metrics only report once Query Insights is enabled on the instance. Enabling it is a change on the Cloud SQL instance, not in SigNoz or the Collector.

**No logs after turning on Log Collection (One-Click).** SigNoz can only forward logs that Cloud SQL writes to Cloud Logging. Open **Logs Explorer** in the GCP Console and filter on `resource.type="cloudsql_database"`. If nothing shows there, check your database logging flags. For pgAudit logs, confirm pgAudit is set up and Data Access audit logs are on for the project.

**No metrics at all (One-Click).** Confirm the instances run in the project the agent is deployed in, and that **Metric Collection** is on and saved. See the [One-Click troubleshooting](https://signoz.io/docs/integrations/gcp/one-click-gcp-integrations/#troubleshooting) for agent and Collector checks.

**A dashboard panel is empty (Manual).** The metric backing that panel is missing from your `metrics_list`. Compare the **Data Collected** tab against your `otel-collector-config.yaml`, add what's missing, and repeat step 3.

**No Cloud SQL metrics at all (Manual).** Confirm the `signoz-integration` service account holds `roles/monitoring.viewer` on the project in `project_id`, and that the Cloud Monitoring API is enabled there. Then check the Cloud Run logs for `googlecloudmonitoring` receiver errors.

**Metrics appear but are stale (Manual).** The receiver polls on `collection_interval` (default `300s`) and Cloud SQL itself samples most metrics no faster than every 60 seconds. Lower the interval only if you need the resolution, and expect a higher Monitoring API bill.
