The **Cloud SQL for PostgreSQL** integration brings instance metrics (availability, CPU, memory, disk, connections, transactions, vacuum age, query execution time, and replication lag) and PostgreSQL server logs into SigNoz, with a pre-built dashboard for the service.

Cloud SQL publishes its metrics to **Cloud Monitoring** and its server logs to **Cloud Logging**. SigNoz reads both through the OpenTelemetry Collector running in your GCP project.

## Prerequisites

Before configuring this service, complete the shared GCP integration setup:

- Your [GCP account is connected in SigNoz](https://signoz.io/docs/integrations/gcp/connect-gcp-account/), and the project running your Cloud SQL instances is in [**Projects to Monitor**](https://signoz.io/docs/integrations/gcp/manual-setup/#connection-fields).
- The [OpenTelemetry Collector is deployed and running](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/).
- The `signoz-integration` service account has `roles/monitoring.viewer` on the project that hosts the instances. See [Create a service account](https://signoz.io/docs/integrations/gcp/create-service-account/#step-3-grant-metrics-permission-on-each-monitored-project).
- The **Cloud Monitoring API** is enabled in that project. For logs, the **Cloud Logging API**, the **Pub/Sub API**, and a working [log pipeline](https://signoz.io/docs/integrations/gcp/collect-logs/) are also required.

<Admonition type="info">
Metrics and logs are independent. You can enable metrics only, and add logs later.
</Admonition>

## Step 1: Enable the service in SigNoz

1. In SigNoz, go to **Integrations** > **Google Cloud Platform**.
2. Select **GCP Cloud SQL for PostgreSQL** from the service list.
3. Toggle **Metric Collection** on to activate the pre-built dashboard. Toggle **Log Collection** on if you also route Postgres logs.
4. Open the **Data Collected** tab and note the metrics listed there. These are the metrics the dashboard's panels query.

<Admonition type="warning">
Enabling the toggle does not start collection on its own. The metrics that reach SigNoz are exactly the ones in your Collector's `metrics_list`. If you skip a metric in step 2, its dashboard panel stays empty.
</Admonition>

## Step 2: Add the metrics to your Collector config

Open the `otel-collector-config.yaml` you created in [Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-1-prepare-the-collector-configuration) and add the Cloud SQL metric names to the `metrics_list` of the `googlecloudmonitoring` receiver for the project your instances run in. Only the `metrics_list` shown below changes; leave the rest of the file as is:

```yaml:otel-collector-config.yaml
receivers:
  googlecloudmonitoring:
    project_id: "<monitored-project-id>"
    collection_interval: 300s   # 5 minutes; minimum is 60s
    metrics_list:
      # Availability
      - metric_name: "cloudsql.googleapis.com/database/up"
      # Compute
      - metric_name: "cloudsql.googleapis.com/database/cpu/utilization"
      - metric_name: "cloudsql.googleapis.com/database/memory/utilization"
      - metric_name: "cloudsql.googleapis.com/database/memory/usage"
      # Storage
      - metric_name: "cloudsql.googleapis.com/database/disk/bytes_used"
      # PostgreSQL engine
      - metric_name: "cloudsql.googleapis.com/database/postgresql/num_backends"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/num_backends_by_state"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/transaction_count"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/deadlock_count"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/vacuum/oldest_transaction_age"
      # Query insights
      - metric_name: "cloudsql.googleapis.com/database/postgresql/insights/aggregate/execution_time"
      - metric_name: "cloudsql.googleapis.com/database/postgresql/insights/perquery/execution_time"
      # Replication
      - metric_name: "cloudsql.googleapis.com/database/postgresql/replication/replica_byte_lag"
```

**Verify these values:**

- `<monitored-project-id>`: The GCP project that hosts your Cloud SQL instances. It must be one of the entries in your **Projects to Monitor** list.

<Admonition type="info">
If your instances span several projects, add one **named** receiver per project (`googlecloudmonitoring/<name>`) and list them all in the metrics pipeline. See [Configure multiple projects](https://signoz.io/docs/integrations/gcp/collect-metrics/#step-3-configure-multiple-projects).
</Admonition>

The two `insights/` metrics need <a href="https://cloud.google.com/sql/docs/postgres/using-query-insights" target="_blank" rel="noopener noreferrer nofollow">Query Insights</a> enabled on the instance (off by default, no extra charge) or their panels stay empty; drop them from the list if you don't need per-query timing.

The receiver polls every metric in the list once per `collection_interval`, and the Monitoring API bills per read call, so keep the list to the metrics your dashboards and alerts actually use. See [Cost and tuning](https://signoz.io/docs/integrations/gcp/collect-metrics/#cost-and-tuning).

## Step 3: Apply the configuration

The Collector loads its config from the `signoz-collector-config` secret, so a config change needs a new secret version and a redeploy:

1. Save your updated `otel-collector-config.yaml`.
2. Add a new secret version ([step 2 of Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-2-store-the-config-in-secret-manager)).
3. Redeploy the Cloud Run service ([step 3](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-3-deploy-to-cloud-run)).

## Step 4: Route Cloud SQL logs

Cloud SQL writes PostgreSQL server logs to Cloud Logging. To get them into SigNoz, follow [Collect logs](https://signoz.io/docs/integrations/gcp/collect-logs/) to create the Pub/Sub topic and the push subscription. When you reach [step 4, Create a log sink](https://signoz.io/docs/integrations/gcp/collect-logs/#step-4-create-a-log-sink-per-monitored-project), use this as the sink's **Build inclusion filter** value so it routes only Cloud SQL logs:

```
resource.type="cloudsql_database"
```

To narrow it to a single instance, add the instance's `database_id` (formatted as `<project-id>:<instance-id>`):

```
resource.type="cloudsql_database"
resource.labels.database_id="<monitored-project-id>:<instance-id>"
```

<Admonition type="warning">
Add a matching **exclusion filter** on the project's `_Default` sink, or you pay to store the same logs in both Cloud Logging and SigNoz. See [Avoid duplicate log costs](https://signoz.io/docs/integrations/gcp/collect-logs/#step-6-avoid-duplicate-log-costs).
</Admonition>

Which logs Cloud SQL emits depends on the instance's PostgreSQL flags. Statement logging (`log_statement`), slow-query logging (`log_min_duration_statement`), and connection logging (`log_connections`) are off or restrictive by default. See <a href="https://cloud.google.com/sql/docs/postgres/flags" target="_blank" rel="noopener noreferrer nofollow">Configure database flags</a> to turn on the logs you need.

## Validate

1. Wait one or two collection intervals (up to about 5 minutes with the default `300s`).
2. In SigNoz, go to **Dashboards** and open the Cloud SQL for PostgreSQL dashboard. Panels should start filling in.
3. To check a single metric, open **Metrics Explorer** and query `cloudsql.googleapis.com/database/cpu/utilization`.
4. For logs, open **Logs** and filter where `gcp.resource_type` = `cloudsql_database`.

## Troubleshooting
</ToggleHeading>

**A dashboard panel is empty.** The metric backing that panel is missing from your `metrics_list`. Compare the **Data Collected** tab against your `otel-collector-config.yaml`, add what's missing, and repeat step 3.

**Query execution time panels are empty.** The `insights/` metrics only report once Query Insights is enabled on the instance. Enabling it is a change on the Cloud SQL instance, not in the Collector. See step 2.

**No Cloud SQL metrics at all.** Confirm the `signoz-integration` service account holds `roles/monitoring.viewer` on the project in `project_id`, and that the Cloud Monitoring API is enabled there. Then check the Cloud Run logs for `googlecloudmonitoring` receiver errors.

**Metrics appear but are stale.** The receiver polls on `collection_interval` (default `300s`) and Cloud SQL itself samples most metrics no faster than every 60 seconds. Lower the interval only if you need the resolution, and expect a higher Monitoring API bill.

**Logs don't arrive.** Work back through the log pipeline: the sink's writer identity needs `roles/pubsub.publisher` on the topic, and the push subscription must reach the Collector. See [Verify logs in SigNoz](https://signoz.io/docs/integrations/gcp/collect-logs/#step-7-verify-logs-in-signoz).

**Logs arrive but contain no queries.** Statement and slow-query logging are controlled by PostgreSQL flags on the instance, not by SigNoz. Enable `log_statement` or `log_min_duration_statement` on the instance.

</details>
