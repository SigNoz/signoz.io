The **Google Kubernetes Engine (GKE)** integration brings cluster metrics into SigNoz, with a pre-built dashboard for the service. With One-Click Integration, it also brings in your cluster logs.

GKE publishes its system metrics to **Cloud Monitoring** and its logs to **Cloud Logging**. SigNoz reads them through the OpenTelemetry Collector running in your GCP project.

<Admonition type="info">
This page reads what GKE already sends to Cloud Monitoring and Cloud Logging, so nothing gets installed in your cluster. If you want finer-grained metrics scraped from inside the cluster, or traces from your workloads, use [Kubernetes monitoring with the SigNoz k8s-infra chart](https://signoz.io/docs/opentelemetry-collection-agents/k8s/k8s-infra/overview/). The two approaches work well together.
</Admonition>

## One-Click Integration

SigNoz deploys and manages the Collector for you. You turn the service on in SigNoz, and the SigNoz agent sets up metrics and logs collection in the background. Collects **metrics and logs**.

### Prerequisites

- Your GCP project is connected with [One-Click Integration](https://signoz.io/docs/integrations/gcp/one-click-gcp-integrations/).
- Your GKE clusters run in that same project. The agent monitors only the project it's deployed in.
- **System metrics collection is enabled on the cluster.** It's on by default. If it was turned off, turn it back on under the cluster's **Observability** settings. See <a href="https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-metrics" target="_blank" rel="noopener noreferrer nofollow">Configure metrics collection</a>.
- **For logs, Cloud Logging is enabled on the cluster.** It's on by default, but Standard clusters can turn it off, and workload logs can be turned off on any cluster. Check the logging components under the cluster's **Observability** settings: **System** is needed for system logs and events, and **Workloads** for your application logs. See <a href="https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs#available-logs" target="_blank" rel="noopener noreferrer nofollow">Available logs</a>.

### Step 1: Turn on the service in SigNoz

1. In SigNoz, go to **Integrations** > **Google Cloud Platform**.
2. Select **GCP Kubernetes Engine** from the service list.
3. Turn on **Metric Collection**, **Log Collection**, or both.
4. Click **Save**.

The agent picks up the change within about 30 seconds and updates the Collector and the log sink for you. There's no Collector config to edit.

<Admonition type="warning">
**Log Collection** forwards every log line your clusters write to Cloud Logging, including the stdout and stderr of all your workloads. Busy clusters can produce a lot of logs, which raises your Pub/Sub and SigNoz ingestion costs. If you only need metrics, leave **Log Collection** off.
</Admonition>

### Step 2: Turn on the optional logs in GCP

With the default logging settings, system logs, workload logs, Kubernetes events, and audit logs flow with no extra work. Control plane logs from the API server, scheduler, and controller manager are off by default. To collect them, turn them on in the cluster's **Observability** settings. See <a href="https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs" target="_blank" rel="noopener noreferrer nofollow">About GKE logs</a>.

Skip this step if you don't need control plane logs.

### Validate

1. Wait about 10 minutes for the first metrics to arrive.
2. In SigNoz, go to **Dashboards** and open **GCP Kubernetes Engine Overview**. Panels should start filling in.
3. If you turned on **Log Collection**, open **Logs** in SigNoz and start with this filter to find your project's logs:

   ```text
   gcp.project = '<deployment-project-id>' AND gcp.resource_type = 'k8s_container'
   ```

   This shows your application logs. New log lines appear within a few minutes. Drop the `gcp.resource_type` part to see every GKE log, including node, cluster, and audit logs.

   **Verify these values:**

   - `<deployment-project-id>`: the GCP project you connected with One-Click Integration.

</TabItem>

## Manual Setup

You run the OpenTelemetry Collector in your own GCP project and add the GKE metrics to its configuration. You control which metrics are pulled and how often. Collects **metrics only**.

Complete the [GCP integration setup](https://signoz.io/docs/integrations/gcp/manual-setup/) once, then follow the steps below for each project that hosts the clusters you want to monitor.

### Prerequisites

Before configuring this service, complete the shared GCP integration setup:

- Your [GCP account is connected in SigNoz](https://signoz.io/docs/integrations/gcp/connect-gcp-account/), and the project running your GKE clusters is in [**Projects to Monitor**](https://signoz.io/docs/integrations/gcp/manual-setup/#connection-fields).
- The [OpenTelemetry Collector is deployed and running](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/).
- The `signoz-integration` service account has `roles/monitoring.viewer` on the project that hosts the clusters. See [Create a service account](https://signoz.io/docs/integrations/gcp/create-service-account/#step-3-grant-metrics-permission-on-each-monitored-project).
- The **Cloud Monitoring API** is enabled in that project.
- **System metrics collection is enabled on the cluster.** It is on by default. If it was turned off, re-enable it under the cluster's **Observability** settings, or the `kubernetes.io/*` metrics never reach Cloud Monitoring for the Collector to read. See <a href="https://docs.cloud.google.com/kubernetes-engine/docs/how-to/configure-metrics" target="_blank" rel="noopener noreferrer nofollow">Configure metrics collection</a>.

### Step 1: Enable the service in SigNoz

1. In SigNoz, go to **Integrations** > **Google Cloud Platform**.
2. Select **GCP Kubernetes Engine** from the service list.
3. Toggle **Metric Collection** on to activate the pre-built dashboard.
4. Open the **Data Collected** tab and note the metrics listed there. These are the metrics the dashboard's panels query.

<Admonition type="warning">
Enabling the toggle does not start collection on its own. The metrics that reach SigNoz are exactly the ones in your Collector's `metrics_list`. If you skip a metric in step 2, its dashboard panel stays empty.
</Admonition>

### Step 2: Add the metrics to your Collector config

Open the `otel-collector-config.yaml` you created in [Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-1-prepare-the-collector-configuration) and add the GKE metric names to the `metrics_list` of the `googlecloudmonitoring` receiver for the project your clusters run in. Only the `metrics_list` shown below changes; leave the rest of the file as is:

```yaml:otel-collector-config.yaml defaultCollapsed
receivers:
  googlecloudmonitoring:
    project_id: "<monitored-project-id>"
    collection_interval: 300s   # 5 minutes; minimum is 60s
    metrics_list:
      # Container CPU and memory
      - metric_name: "kubernetes.io/container/cpu/limit_utilization"
      - metric_name: "kubernetes.io/container/cpu/request_utilization"
      - metric_name: "kubernetes.io/container/memory/limit_utilization"
      - metric_name: "kubernetes.io/container/memory/request_utilization"
      # Workload health
      - metric_name: "kubernetes.io/container/restart_count"
      - metric_name: "kubernetes.io/pod/latencies/pod_first_ready"
      # Pod network
      - metric_name: "kubernetes.io/pod/network/received_bytes_count"
      - metric_name: "kubernetes.io/pod/network/sent_bytes_count"
      # Storage
      - metric_name: "kubernetes.io/pod/volume/utilization"
      # Nodes
      - metric_name: "kubernetes.io/node/cpu/allocatable_utilization"
      - metric_name: "kubernetes.io/node/memory/allocatable_utilization"
      - metric_name: "kubernetes.io/node/ephemeral_storage/used_bytes"
      - metric_name: "kubernetes.io/node/ephemeral_storage/allocatable_bytes"
      - metric_name: "kubernetes.io/node/network/received_bytes_count"
      - metric_name: "kubernetes.io/node/network/sent_bytes_count"
      - metric_name: "kubernetes.io/node/status_condition"
```

**Verify these values:**

- `<monitored-project-id>`: The GCP project that hosts your GKE clusters. It must be one of the entries in your **Projects to Monitor** list.

<Admonition type="info">
If your clusters span several projects, add one **named** receiver per project (`googlecloudmonitoring/<name>`) and list them all in the metrics pipeline. See [Configure multiple projects](https://signoz.io/docs/integrations/gcp/collect-metrics/#step-3-configure-multiple-projects).
</Admonition>

The receiver polls every metric in the list once per `collection_interval`, and the Monitoring API bills per read call, so keep the list to the metrics your dashboards and alerts actually use. This list is longer than most services, so it is the one to trim first if your Monitoring API bill matters. See [Cost and tuning](https://signoz.io/docs/integrations/gcp/collect-metrics/#cost-and-tuning).

<Admonition type="info">
These metrics carry a series per container, pod, or node, so a large cluster produces many more series than a single database instance does. Start at the default `300s` and lower it only if you need the resolution.
</Admonition>

### Step 3: Apply the configuration

The Collector loads its config from the `signoz-collector-config` secret, so a config change needs a new secret version and a redeploy:

1. Save your updated `otel-collector-config.yaml`.
2. Add a new secret version ([step 2 of Deploy the Collector](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-2-store-the-config-in-secret-manager)).
3. Redeploy the Cloud Run service ([step 3](https://signoz.io/docs/integrations/gcp/deploy-otel-collector/#step-3-deploy-to-cloud-run)).

### Validate

1. Wait one or two collection intervals (up to about 5 minutes with the default `300s`).
2. In SigNoz, go to **Dashboards** and open the Kubernetes Engine dashboard. Panels should start filling in.
3. To check a single metric, open **Metrics Explorer** and query `kubernetes.io/container/cpu/limit_utilization`.

</TabItem>

## What's collected

<details>
<summary>Metrics</summary>

See the **Data Collected** tab in the SigNoz integration for the definitive list the dashboard uses, and the <a href="https://docs.cloud.google.com/monitoring/api/metrics_kubernetes" target="_blank" rel="noopener noreferrer nofollow">GKE system metrics list</a> for full definitions.

| Metric name | Unit | Type |
|-------------|------|------|
| `kubernetes.io/container/cpu/limit_utilization` | Ratio | Gauge |
| `kubernetes.io/container/cpu/request_utilization` | Ratio | Gauge |
| `kubernetes.io/container/memory/limit_utilization` | Ratio | Gauge |
| `kubernetes.io/container/memory/request_utilization` | Ratio | Gauge |
| `kubernetes.io/container/restart_count` | Count | Sum |
| `kubernetes.io/pod/latencies/pod_first_ready` | Seconds | Gauge |
| `kubernetes.io/pod/network/received_bytes_count` | Bytes | Sum |
| `kubernetes.io/pod/network/sent_bytes_count` | Bytes | Sum |
| `kubernetes.io/pod/volume/utilization` | Ratio | Gauge |
| `kubernetes.io/node/cpu/allocatable_utilization` | Ratio | Gauge |
| `kubernetes.io/node/memory/allocatable_utilization` | Ratio | Gauge |
| `kubernetes.io/node/ephemeral_storage/used_bytes` | Bytes | Gauge |
| `kubernetes.io/node/ephemeral_storage/allocatable_bytes` | Bytes | Gauge |
| `kubernetes.io/node/network/received_bytes_count` | Bytes | Sum |
| `kubernetes.io/node/network/sent_bytes_count` | Bytes | Sum |
| `kubernetes.io/node/status_condition` | Bool | Gauge |

</details>

<details>
<summary>Dashboard panels</summary>

The pre-built dashboard has 15 panels in five sections:

**CPU and memory.** Container resource pressure, each as a time series: **% Container CPU Limit Utilization**, **% Container CPU Request Utilization**, **% Container Memory Limit Utilization**, and **% Container Memory Request Utilization**. Usage against *limit* shows how close a container is to being throttled or OOM killed; usage against *request* shows how well the request is sized.

**Workload health.** Two tables: **Container Restarts (total)**, which lists only containers that have restarted, and **Pod First-Ready Latency**, the time from pod creation to first Ready state.

**Network.** **Pod Network Receive Throughput** and **Pod Network Sent Throughput**, in bytes per second per pod.

**Storage.** **% PVC Volume Utilization**, PersistentVolumeClaim usage as a percentage of capacity.

**Nodes (namespace agnostic).** Six node-level panels: **% Node CPU Allocatable Utilization**, **% Node Memory Allocatable Utilization**, **Node status conditions** (a table filtered to unhealthy states), **% Node Ephemeral Storage Utilization**, **Node Network Receive Throughput**, and **Node Network Sent Throughput**.

Three single-select variables scope the panels: **project_id**, **cluster_name**, and **namespace_name**.

Pre-built dashboards are read-only. To customize one, use **Export JSON** from the dashboard menu and import it as a new dashboard.

</details>

<Admonition type="info">
Node metrics have no namespace dimension, so the **Nodes (namespace agnostic)** section ignores the **namespace_name** variable. Those six panels always show every node in the selected cluster.
</Admonition>

<details>
<summary>Logs (One-Click Integration only)</summary>

With **Log Collection** turned on, SigNoz collects the <a href="https://docs.cloud.google.com/kubernetes-engine/docs/concepts/about-logs" target="_blank" rel="noopener noreferrer nofollow">GKE logs</a> that your clusters write to Cloud Logging:

| Log | What it contains | GCP setup needed |
| --- | --- | --- |
| Workload logs | stdout and stderr from your application containers | None by default. Workload logging is optional and can be turned off on any cluster. |
| System logs | Logs from system components such as kubelet, the container runtime, and `kube-system` pods | None by default. Standard clusters can turn off Cloud Logging entirely. Autopilot clusters always send them. |
| Kubernetes events | Events such as pod scheduling, image pulls, and restarts | Collected with system logs, on a best-effort basis |
| Audit logs | Calls to the Kubernetes API and GKE cluster and node pool operations | None. Always on. |
| Control plane logs | Logs from the API server, scheduler, and controller manager | Turn them on in the cluster's **Observability** settings |

SigNoz uses this log sink filter:

```text
resource.type=("k8s_container" OR "k8s_pod" OR "k8s_node" OR "k8s_cluster"
  OR "k8s_control_plane_component" OR "gke_cluster" OR "gke_nodepool")
```

</details>

## Troubleshooting
</ToggleHeading>

**No logs after turning on Log Collection (One-Click).** SigNoz can only forward logs that GKE writes to Cloud Logging. Open **Logs Explorer** in the GCP Console and filter on `resource.type="k8s_container"`. If nothing shows there, check the cluster's **Observability** settings: Cloud Logging must be on, with **System** selected for system logs and **Workloads** for application logs.

**No metrics at all (One-Click).** Confirm the clusters run in the project the agent is deployed in, that system metrics collection is on for each cluster, and that **Metric Collection** is on and saved. See the [One-Click troubleshooting](https://signoz.io/docs/integrations/gcp/one-click-gcp-integrations/#troubleshooting) for agent and Collector checks.

**A dashboard panel is empty (Manual).** The metric backing that panel is missing from your `metrics_list`. Compare the **Data Collected** tab against your `otel-collector-config.yaml`, add what's missing, and repeat step 3.

**No GKE metrics at all (Manual).** Confirm the `signoz-integration` service account holds `roles/monitoring.viewer` on the project in `project_id`, and that the Cloud Monitoring API is enabled there. Then confirm system metrics collection is still enabled on the cluster, and check the Cloud Run logs for `googlecloudmonitoring` receiver errors.

**The Container Restarts table is empty.** That is the healthy state. The panel excludes containers with no restarts, so an empty table means nothing has restarted in the selected window.

**Node panels ignore the namespace filter.** Expected. Node metrics are not namespaced, so the filter cannot apply to them.

**% PVC Volume Utilization is empty.** `pod/volume/utilization` only reports for pods with a PersistentVolumeClaim. Workloads using only ephemeral storage produce no series here.

**Limit utilization panels are empty for some workloads.** `limit_utilization` is only reported for containers that set a CPU or memory limit. Containers with no limit set have nothing to divide by, so they are absent from those panels. The request panels behave the same way for containers with no request.

</details>
