The OpenTelemetry Collector is the engine of the GCP integration: it pulls metrics from Cloud Monitoring, receives logs pushed from Pub/Sub, and exports both to SigNoz over OTLP. This guide deploys it as a **Cloud Run** service in your deployment project. This is step 3 of the [GCP integration](https://signoz.io/docs/integrations/gcp/gcp-integration/).

<Admonition type="info">
**Cloud Run is optional.** It's the quickest managed way to run the Collector, so these steps use it, but you can run the Collector on any compute you prefer (a Compute Engine VM, GKE, or an existing Kubernetes cluster). The only hard requirement is that the Collector's log endpoint is **reachable by the Pub/Sub push subscription** and that the Collector can authenticate to the Monitoring API (for example, via a service account with `roles/monitoring.viewer`). If you use different compute, apply the config and networking ideas below to your platform and skip the Cloud Run-specific commands.
</Admonition>

## Prerequisites

- You have [created the `signoz-integration` service account](https://signoz.io/docs/integrations/gcp/create-service-account/) and granted it `roles/monitoring.viewer` on your monitored projects.
- You have [connected your GCP account in SigNoz](https://signoz.io/docs/integrations/gcp/connect-gcp-account/) and noted your SigNoz Cloud region (from the **Ingestion URL**) and copied the **Ingestion Key**.
- The Cloud Run Admin API and the Secret Manager API are enabled in your `<deployment-project-id>`.
- The <a href="https://cloud.google.com/sdk/docs/install" target="_blank" rel="noopener noreferrer nofollow">`gcloud` CLI</a> is installed and authenticated, or use <a href="https://cloud.google.com/shell" target="_blank" rel="noopener noreferrer nofollow">Cloud Shell</a>.

<Admonition type="info">
`<deployment-project-id>` and `<deployment-region>` below are the **Deployment Project ID** and **Deployment Region** you entered when connecting the account.
</Admonition>

## Why the SigNoz Collector image

Deploy the <a href="https://hub.docker.com/r/signoz/signoz-otel-collector" target="_blank" rel="noopener noreferrer nofollow">`signoz/signoz-otel-collector`</a> image. It bundles the **`googlecloudpubsubpush`** receiver, which receives logs pushed from a Pub/Sub subscription and preserves GCP labels and resource attributes as structured fields.

Use a recent tag such as `signoz/signoz-otel-collector:0.144.5`. Check the <a href="https://hub.docker.com/r/signoz/signoz-otel-collector/tags" target="_blank" rel="noopener noreferrer nofollow">tags list</a> for the latest version and avoid `latest` in production so deployments are reproducible.

## Step 1: Prepare the Collector configuration

Create a file named `config.yaml`. The starter below wires up both signals. You fill in the receiver details in the next two guides, [Collect metrics](https://signoz.io/docs/integrations/gcp/collect-metrics/) and [Collect logs](https://signoz.io/docs/integrations/gcp/collect-logs/), so it's normal for parts to be placeholders now.

```yaml
receivers:
  # Logs: receives messages pushed from a Pub/Sub push subscription.
  # See "Collect logs" for the matching Pub/Sub topic and subscription.
  googlecloudpubsubpush:
    endpoint: :8090
    encoding: googlecloudlogentry_encoding

  # Metrics: one block per monitored project.
  # See "Collect metrics" for the metrics_list per service.
  googlecloudmonitoring/<monitored-project-id>:
    project_id: "<monitored-project-id>"
    collection_interval: 300s
    metrics_list:
      - metric_name: "compute.googleapis.com/instance/cpu/utilization"

processors:
  batch:
    timeout: 10s
    send_batch_size: 1024
  memory_limiter:
    check_interval: 5s
    limit_percentage: 80
    spike_limit_percentage: 25

exporters:
  otlphttp:
    endpoint: "https://ingest.<region>.signoz.cloud:443"
    headers:
      "signoz-ingestion-key": "<ingestion-key>"
    tls:
      insecure: false

extensions:
  googlecloudlogentry_encoding:

service:
  extensions: [googlecloudlogentry_encoding]
  pipelines:
    logs:
      receivers: [googlecloudpubsubpush]
      processors: [memory_limiter, batch]
      exporters: [otlphttp]
    metrics:
      receivers: [googlecloudmonitoring/<monitored-project-id>]
      processors: [memory_limiter, batch]
      exporters: [otlphttp]
```

**Verify these values:**

- `<region>`: Your [SigNoz Cloud region](https://signoz.io/docs/ingestion/signoz-cloud/overview/#endpoint) (for example, `us`, `eu`, or `in`). This is the region in the **Ingestion URL** shown on the SigNoz connection panel; use the region only, not the full URL.
- `<ingestion-key>`: Your SigNoz [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/), copied from the connection panel.

<Admonition type="info">
**Cloud Run requires a listening port.** Cloud Run health-checks a service by connecting to the port named in `--port` and considers the revision ready only once the container listens on it. The `googlecloudpubsubpush` receiver listens on `:8090`, so this config also serves as the container's HTTP port. Keep the receiver `endpoint` port and the Cloud Run `--port` the same value (`8090` here).
</Admonition>

## Step 2: Store the config in Secret Manager

Rather than baking a custom image, keep your `config.yaml` in <a href="https://cloud.google.com/secret-manager/docs" target="_blank" rel="noopener noreferrer nofollow">Secret Manager</a> and run the stock `signoz/signoz-otel-collector` image directly. Cloud Run injects the secret as an environment variable, and the Collector reads its config from that variable at startup. Your config (and the ingestion key inside it) stays out of any image.

Create the secret from your `config.yaml`, then grant the `signoz-integration` service account permission to read it.

<Tabs>
<TabItem value="cli" label="gcloud CLI" default>

Create the secret:

```bash
gcloud secrets create signoz-collector-config \
  --data-file=config.yaml \
  --project=<deployment-project-id>
```

Grant the service account read access:

```bash
gcloud secrets add-iam-policy-binding signoz-collector-config \
  --member="serviceAccount:signoz-integration@<deployment-project-id>.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor" \
  --project=<deployment-project-id>
```

</TabItem>
<TabItem value="console" label="Console">

1. In the deployment project, go to **Security** > **Secret Manager** > **+ Create secret**.
2. Set **Name** to `signoz-collector-config`.
3. Under **Secret value**, choose **Upload file** and select your `config.yaml` (or paste its contents into the value box).
4. Click **Create secret**.
5. Open the new secret, go to the **Permissions** tab, and click **Grant access**.
6. In **New principals**, paste `signoz-integration@<deployment-project-id>.iam.gserviceaccount.com`.
7. In **Role**, select **Secret Manager** > **Secret Manager Secret Accessor**, then click **Save**.

</TabItem>
</Tabs>

<Admonition type="info">
When you change the config later, add a new secret version (`gcloud secrets versions add signoz-collector-config --data-file=config.yaml`, or **Add new version** in the Console) and redeploy the service to pick it up.
</Admonition>

## Step 3: Deploy to Cloud Run

Deploy the stock `signoz/signoz-otel-collector` image as a Cloud Run service. Attach the `signoz-integration` service account, mount the config secret as the `COLLECTOR_CONFIG` environment variable, and point the Collector at it with `--config=env:COLLECTOR_CONFIG`.

<Tabs>
<TabItem value="cli" label="gcloud CLI" default>

```bash
gcloud run deploy signoz-otel-collector \
  --image=signoz/signoz-otel-collector:0.144.5 \
  --region=<deployment-region> \
  --project=<deployment-project-id> \
  --service-account=signoz-integration@<deployment-project-id>.iam.gserviceaccount.com \
  --set-secrets=COLLECTOR_CONFIG=signoz-collector-config:latest \
  --args=--config=env:COLLECTOR_CONFIG \
  --port=8090 \
  --ingress=internal \
  --no-allow-unauthenticated \
  --min-instances=1 \
  --cpu=2 \
  --memory=4Gi
```

</TabItem>
<TabItem value="console" label="Console">

1. In the deployment project, go to **Cloud Run** > **Deploy container** > **Service**.
2. Set the **Container image URL** to `signoz/signoz-otel-collector:0.144.5`.
3. Set **Region** to your `<deployment-region>`.
4. Under **Authentication**, choose **Require authentication** (do not allow unauthenticated invocations).
5. Under **Ingress control**, choose **Internal**.
6. Expand **Container(s), Volumes, Networking, Security**:
   - **Container port**: `8090`.
   - **Resources**: 2 vCPU, 4 GiB memory.
   - **Security** > **Service account**: `signoz-integration@<deployment-project-id>.iam.gserviceaccount.com`.
   - **Variables & Secrets** > **Reference a secret**: select `signoz-collector-config`, expose it as the environment variable `COLLECTOR_CONFIG`, and use the `latest` version.
   - **Container** > **Container arguments**: add `--config=env:COLLECTOR_CONFIG`.
   - **Autoscaling**: set **Minimum number of instances** to `1` so the Collector always runs.
7. Click **Create**.

</TabItem>
</Tabs>

**Why these flags:**

- `--ingress=internal` and `--no-allow-unauthenticated` keep the Collector off the public internet. It is reachable only from within your GCP project and VPC, including the authenticated Pub/Sub push you configure for logs. This is the recommended posture from the integration design.
- `--min-instances=1` keeps one instance warm. A Collector that scales to zero misses pushed logs and pauses metric scrapes, so keep at least one instance running.
- `--cpu=2 --memory=4Gi` matches the ~$110/month sizing in the [cost estimate](https://signoz.io/docs/integrations/gcp/gcp-integration/#costs-to-expect). Adjust to your volume. If you ingest low volumes, a smaller configuration such as `--cpu=1 --memory=2Gi` costs less; scale up only if the Collector shows memory pressure or dropped data.

## Step 4: Note the service URL

The deploy command prints a **Service URL** like `https://signoz-otel-collector-xxxxxxxxxx-uc.a.run.app`. Save it: the Pub/Sub push subscription in [Collect logs](https://signoz.io/docs/integrations/gcp/collect-logs/) delivers to `<service-url>/`.

Retrieve it any time:

<Tabs>
<TabItem value="cli" label="gcloud CLI" default>

```bash
gcloud run services describe signoz-otel-collector \
  --region=<deployment-region> \
  --project=<deployment-project-id> \
  --format='value(status.url)'
```

</TabItem>
<TabItem value="console" label="Console">

1. In the deployment project, go to **Cloud Run** and open the **signoz-otel-collector** service.
2. The **URL** is shown at the top of the service details page. Click the copy icon next to it.

</TabItem>
</Tabs>

## Step 5: Verify the Collector is running

1. In the Console, open **Cloud Run** > **signoz-otel-collector** > **Logs**.
2. Confirm the Collector started without configuration errors. Look for `Everything is ready. Begin running and processing data.`
3. If the revision fails to become ready, the most common cause is a port mismatch. Confirm the `googlecloudpubsubpush` receiver `endpoint` port matches the Cloud Run container port (`8090`).

The Collector does not yet have anything to do until you configure metrics or logs. Continue to the next step.
