The OpenTelemetry Collector is the engine of the GCP integration: it pulls metrics from Cloud Monitoring and exports them to SigNoz over OTLP. This guide deploys it as a **Cloud Run** service in your deployment project. This is step 3 of the [GCP integration](https://signoz.io/docs/integrations/gcp/gcp-integration/).

<Admonition type="info">
**Cloud Run is optional.** It's the quickest managed way to run the Collector, so these steps use it, but you can run the Collector on any compute you prefer (a Compute Engine VM, GKE, an existing Kubernetes cluster, or a <a href="https://cloud.google.com/run/docs/resource-model" target="_blank" rel="noopener noreferrer nofollow">Cloud Run worker pool</a>). The only hard requirement is that the Collector can authenticate to the Monitoring API, for example via a service account with `roles/monitoring.viewer`. If you use different compute, apply the config ideas below to your platform and skip the Cloud Run-specific commands.
</Admonition>

## Prerequisites

- You have [created the `signoz-integration` service account](https://signoz.io/docs/integrations/gcp/create-service-account/) and granted it `roles/monitoring.viewer` on your monitored projects.
- You have [connected your GCP account in SigNoz](https://signoz.io/docs/integrations/gcp/connect-gcp-account/) and noted your SigNoz Cloud region (from the **Ingestion URL**) and copied the **Ingestion Key**.
- The Cloud Run Admin API and the Secret Manager API are enabled in your `<deployment-project-id>`.
- The <a href="https://cloud.google.com/sdk/docs/install" target="_blank" rel="noopener noreferrer nofollow">`gcloud` CLI</a> is installed and authenticated, or use <a href="https://cloud.google.com/shell" target="_blank" rel="noopener noreferrer nofollow">Cloud Shell</a>.

<Admonition type="info">
`<deployment-project-id>` and `<deployment-region>` below are the **Deployment Project ID** and **Deployment Region** from the [connection fields](https://signoz.io/docs/integrations/gcp/manual-setup/#connection-fields) you entered when connecting the account.
</Admonition>

## Which Collector image to use

Deploy the <a href="https://hub.docker.com/r/otel/opentelemetry-collector-contrib" target="_blank" rel="noopener noreferrer nofollow">`otel/opentelemetry-collector-contrib`</a> image. It bundles the **`googlecloudmonitoring`** receiver, which pulls metrics from the Cloud Monitoring API, and the **`health_check`** extension used in the deployment below.

Check the <a href="https://hub.docker.com/r/otel/opentelemetry-collector-contrib/tags" target="_blank" rel="noopener noreferrer nofollow">tags list</a> for the latest version and use that tag (for example, `otel/opentelemetry-collector-contrib:0.158.0`) instead of `latest`, so deployments stay reproducible.

<Admonition type="warning">
Use **0.158.0 or later**. Earlier versions report cumulative GCP metrics as non-monotonic sums, which stops SigNoz from offering rate functions on counter metrics. Note that this image's tags have no `v` prefix.
</Admonition>

## Step 1: Prepare the Collector configuration

Create a file named `otel-collector-config.yaml`. The starter below is complete except for the metrics you want. You fill those in next, in [Collect metrics](https://signoz.io/docs/integrations/gcp/collect-metrics/), so it's normal for the `metrics_list` to be a placeholder now.

```yaml:otel-collector-config.yaml
receivers:
  # Metrics: one block per monitored project.
  # See "Collect metrics" for the metrics_list per service.
  googlecloudmonitoring:
    project_id: "<monitored-project-id>"
    collection_interval: 300s
    metrics_list:
      - metric_name: "compute.googleapis.com/instance/cpu/utilization"

processors:
  batch:
    timeout: 10s
    send_batch_size: 1024
  memory_limiter:
    check_interval: 5s
    limit_percentage: 80
    spike_limit_percentage: 25

exporters:
  otlphttp:
    endpoint: "https://ingest.<region>.signoz.cloud:443"
    headers:
      "signoz-ingestion-key": "<ingestion-key>"
    tls:
      insecure: false

extensions:
  # Serves the port Cloud Run health-checks. See the note below.
  health_check:
    endpoint: 0.0.0.0:8090

service:
  extensions: [health_check]
  pipelines:
    metrics:
      receivers: [googlecloudmonitoring]
      processors: [memory_limiter, batch]
      exporters: [otlphttp]
```

**Verify these values:**

- `<region>`: Your [SigNoz Cloud region](https://signoz.io/docs/ingestion/signoz-cloud/overview/#endpoint) (for example, `us`, `eu`, or `in`). This is the region in the **Ingestion URL** shown on the SigNoz connection panel; use the region only, not the full URL.
- `<ingestion-key>`: Your SigNoz [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/), copied from the connection panel.

<Admonition type="info">
**Self-Hosted Enterprise:** point `otlphttp.endpoint` at your SigNoz OTel Collector's OTLP HTTP address (for example, `http://<signoz-otel-collector-host>:4318`) instead of the Cloud endpoint, and omit the `signoz-ingestion-key` header — it's not required for self-hosted.
</Admonition>

<Admonition type="info">
**Why the `health_check` extension is here.** This Collector only makes outbound calls: it polls the Monitoring API and exports to SigNoz, so nothing else in the config listens on a port. A Cloud Run *service* considers a revision ready only once the container accepts connections on `--port`, so without a listener the deployment never becomes healthy. The `health_check` extension provides that endpoint, and it earns its place: a config error surfaces as a failed deployment rather than a service that looks healthy while collecting nothing. Keep the extension's `endpoint` port and the Cloud Run `--port` the same value (`8090` here).

If you'd rather not run a health endpoint, deploy to a <a href="https://cloud.google.com/run/docs/resource-model" target="_blank" rel="noopener noreferrer nofollow">Cloud Run worker pool</a> instead. Worker pools are built for non-request workloads and don't require the container to listen on a port, so you can drop the extension — at the cost of losing the readiness signal.
</Admonition>

## Step 2: Store the config in Secret Manager

Rather than baking a custom image, keep your `otel-collector-config.yaml` in <a href="https://cloud.google.com/secret-manager/docs" target="_blank" rel="noopener noreferrer nofollow">Secret Manager</a> and run the stock `otel/opentelemetry-collector-contrib` image directly. Cloud Run injects the secret as an environment variable, and the Collector reads its config from that variable at startup. Your config (and the ingestion key inside it) stays out of any image.

Create the secret from your `otel-collector-config.yaml`, then grant the `signoz-integration` service account permission to read it.

<Tabs entityName="method">
<TabItem value="console" label="Console" default>

1. In the deployment project, go to **Security** > **Secret Manager** > **+ Create secret**.
2. Set **Name** to `signoz-collector-config`.
3. Under **Secret value**, choose **Upload file** and select your `otel-collector-config.yaml` (or paste its contents into the value box).
4. Click **Create secret**.
5. Open the new secret, go to the **Permissions** tab, and click **Grant access**.
6. In **New principals**, paste `signoz-integration@<deployment-project-id>.iam.gserviceaccount.com`.
7. In **Role**, select **Secret Manager** > **Secret Manager Secret Accessor**, then click **Save**.

</TabItem>
<TabItem value="cli" label="gcloud CLI">

Create the secret:

```bash
gcloud secrets create signoz-collector-config \
  --data-file=otel-collector-config.yaml \
  --project=<deployment-project-id>
```

Grant the service account read access:

```bash
gcloud secrets add-iam-policy-binding signoz-collector-config \
  --member="serviceAccount:signoz-integration@<deployment-project-id>.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor" \
  --project=<deployment-project-id>
```

</TabItem>
</Tabs>

<Admonition type="info">
When you change the config later, add a new secret version (`gcloud secrets versions add signoz-collector-config --data-file=otel-collector-config.yaml`, or **Add new version** in the Console) and redeploy the service to pick it up.
</Admonition>

## Step 3: Deploy to Cloud Run

Deploy the stock `otel/opentelemetry-collector-contrib` image as a Cloud Run service. Attach the `signoz-integration` service account, mount the config secret as the `COLLECTOR_CONFIG` environment variable, and point the Collector at it with `--config=env:COLLECTOR_CONFIG`.

<Tabs entityName="method">
<TabItem value="console" label="Console" default>

1. In the deployment project, go to **Cloud Run** > **Deploy container** > **Service**.
2. Set the **Container image URL** to `otel/opentelemetry-collector-contrib:<tag>`, using a tag from the <a href="https://hub.docker.com/r/otel/opentelemetry-collector-contrib/tags" target="_blank" rel="noopener noreferrer nofollow">tags list</a> (0.158.0 or later).
3. Set **Region** to your `<deployment-region>`.
4. Under **Authentication**, choose **Require authentication** (do not allow unauthenticated invocations).
5. Under **Ingress control**, choose **Internal**.
6. Expand **Container(s), Volumes, Networking, Security**:
   - **Container port**: `8090`.
   - **Resources**: 2 vCPU, 4 GiB memory.
   - **Security** > **Service account**: `signoz-integration@<deployment-project-id>.iam.gserviceaccount.com`.
   - **Variables & Secrets** > **Reference a secret**: select `signoz-collector-config`, expose it as the environment variable `COLLECTOR_CONFIG`, and use the `latest` version.
   - **Container** > **Container arguments**: add `--config=env:COLLECTOR_CONFIG`.
   - **Autoscaling**: set both **Minimum number of instances** and **Maximum number of instances** to `1`, so the Collector always runs and never scales to a second scraping replica.
   - **Billing**: choose **Instance-based billing** so CPU stays allocated between requests. With the default request-based billing, the metrics receiver's polling loop is throttled while the instance is idle.
7. Click **Create**.

</TabItem>
<TabItem value="cli" label="gcloud CLI">

```bash
gcloud run deploy signoz-otel-collector \
  --image=otel/opentelemetry-collector-contrib:<tag> \
  --region=<deployment-region> \
  --project=<deployment-project-id> \
  --service-account=signoz-integration@<deployment-project-id>.iam.gserviceaccount.com \
  --set-secrets=COLLECTOR_CONFIG=signoz-collector-config:latest \
  --args=--config=env:COLLECTOR_CONFIG \
  --port=8090 \
  --ingress=internal \
  --no-allow-unauthenticated \
  --min-instances=1 \
  --max-instances=1 \
  --no-cpu-throttling \
  --cpu=2 \
  --memory=4Gi
```

</TabItem>
</Tabs>

**Why these flags:**

- `--ingress=internal` and `--no-allow-unauthenticated` keep the Collector off the public internet. Nothing needs to reach it from outside — it only makes outbound calls — so the health endpoint stays reachable from within your GCP project and VPC and nowhere else.
- `--min-instances=1` keeps one instance warm. A Collector that scales to zero pauses metric scrapes, so keep at least one instance running.
- `--no-cpu-throttling` keeps CPU allocated between requests (this is Cloud Run's **instance-based billing**). It is required alongside `--min-instances=1`: by default, Cloud Run throttles CPU whenever an instance isn't serving a request, which stalls the `googlecloudmonitoring` receiver's polling loop and leaves metrics stale. The warm instance only does useful background work with CPU always on.
- `--max-instances=1` pins the service to a single instance. The metrics receiver polls Cloud Monitoring on a timer, independently of incoming requests, so every extra replica would scrape the same metrics again and duplicate the data points SigNoz receives. Keep one instance and scale it up (`--cpu`/`--memory`) rather than out.
- `--cpu=2 --memory=4Gi` matches the ~$110/month sizing in the [cost estimate](https://signoz.io/docs/integrations/gcp/gcp-integration/#costs-to-expect). Adjust to your volume. If you ingest low volumes, a smaller configuration such as `--cpu=1 --memory=2Gi` costs less; scale up only if the Collector shows memory pressure or dropped data.

## Step 4: Verify the Collector is running

1. In the Console, open **Cloud Run** > **signoz-otel-collector** > **Logs**.
2. Confirm the Collector started without configuration errors. Look for `Everything is ready. Begin running and processing data.`
3. If the revision fails to become ready, the most common cause is a port mismatch. Confirm the `health_check` extension's `endpoint` port matches the Cloud Run container port (`8090`).

The Collector has nothing to do until you tell it which metrics to pull. Continue to the next step.
