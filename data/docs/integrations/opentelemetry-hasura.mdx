Monitor your Hasura GraphQL Engine by exporting traces, metrics, and logs to SigNoz using Hasura's native OpenTelemetry integration.

## Overview

Hasura provides built-in OpenTelemetry support for distributed tracing, metrics, and logs on Hasura Cloud and Enterprise editions. Starting from version v2.18.0, you can configure Hasura to export telemetry data directly to SigNoz without requiring an intermediate OpenTelemetry Collector.

<KeyPointCallout title="Using self-hosted SigNoz?" defaultCollapsed={true}>
  Most steps are identical. To adapt this guide, update the endpoint and remove the ingestion key
  header as shown in [Cloud →
  Self-Hosted](https://signoz.io/docs/ingestion/cloud-vs-self-hosted/#cloud-to-self-hosted).
</KeyPointCallout>

## Prerequisites

- Hasura Cloud, or Hasura Self-Hosted Enterprise Edition
- Hasura GraphQL Engine v2.18.0 or later (traces), v2.31.0 or later (metrics), v2.35.0 or later (logs)
- A SigNoz Cloud account with an active project
- Your SigNoz [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/)

## Configure OpenTelemetry Export

You can configure OpenTelemetry export for Hasura using either the Console UI or the CLI.

### Option 1: Configure via Console

1. Log into your Hasura Console and navigate to the **Settings** tab (⚙).
2. Click on **OpenTelemetry Exporter**.
3. Configure the following parameters:
   - **Endpoint**: `https://ingest.<region>.signoz.cloud:443/v1/traces` (and similar for metrics/logs)
   - **Connection Type**: HTTP/Protobuf
   - **Data Types**: Select `traces`, `metrics`, and/or `logs` as needed
4. Under **Headers**, add:
   - **Name**: `signoz-ingestion-key`
   - **Value**: Your SigNoz ingestion key
5. Optionally, under **Attributes**, set `service.name` to identify your Hasura instance (e.g., `hasura-prod`).
6. Click **Update**, then toggle the **Status** button to enable the integration.

### Option 2: Configure via CLI

Create or update the `metadata/opentelemetry.yaml` file:

```yaml
status: enabled
data_types:
  - traces
  - metrics
  - logs
exporter_otlp:
  headers:
    - name: signoz-ingestion-key
      value: <your-ingestion-key>
  resource_attributes:
    - name: service.name
      value: hasura-prod
  otlp_traces_endpoint: https://ingest.<region>.signoz.cloud:443/v1/traces
  otlp_metrics_endpoint: https://ingest.<region>.signoz.cloud:443/v1/metrics
  otlp_logs_endpoint: https://ingest.<region>.signoz.cloud:443/v1/logs
  protocol: http/protobuf
  traces_propagators:
    - tracecontext
batch_span_processor:
  max_export_batch_size: 512
```

Apply the metadata:

```bash
hasura metadata apply
```

Verify these values:

- `<region>`: Your SigNoz Cloud [region](https://signoz.io/docs/ingestion/signoz-cloud/overview/#endpoint)
- `<your-ingestion-key>`: Your SigNoz [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/)

## Available Telemetry

Hasura exports the following telemetry data to SigNoz:

### Traces

Hasura traces operations across:

- Metadata APIs (`/v1/metadata`)
- Schema APIs (`/v2/query`)
- GraphQL API (`/v1/graphql`)
- Event triggers
- Scheduled triggers

Multiple operations are linked together with the same trace ID, enabling end-to-end request tracing.

### Metrics

Hasura exports OpenTelemetry metrics covering:

- API request rates and latencies
- Query execution times
- Event trigger performance
- Connection pool statistics

The available metrics are the same as those available via Prometheus. See [Hasura Metrics Documentation](https://hasura.io/docs/2.0/observability/enterprise-edition/prometheus/metrics/).

### Logs

All logs printed to the output stream are exported to SigNoz. Log structure follows the OpenTelemetry Logs Data Model:

- `body` contains the log message
- `severity` contains the log level
- `attributes.type` contains the Hasura log type

## Validate

Verify data is appearing in SigNoz:

1. Go to the **Services** section in SigNoz to see your Hasura service listed.
2. Navigate to **Traces** to view distributed traces for your GraphQL operations.
3. Use **Dashboards** > **Metrics Explorer** to query Hasura metrics.
4. Check the **Logs** tab and filter by `service.name` to see Hasura logs.

Data should start appearing within a few minutes of enabling the integration.

## Troubleshooting

</ToggleHeading>

### Data is not appearing in SigNoz

- **Check endpoint format**: Ensure the endpoint URL includes the correct path suffix (`/v1/traces`, `/v1/metrics`, `/v1/logs`). Hasura does not auto-append these.
- **Verify ingestion key**: Confirm your `signoz-ingestion-key` header value is correct and active.
- **Check region**: Ensure the region in your endpoint matches your SigNoz Cloud region.
- **Verify Hasura version**: OpenTelemetry traces require Hasura v2.18.0+, metrics require v2.31.0+, and logs require v2.35.0+.

### Connection errors

- If using Hasura Cloud, ensure your SigNoz endpoint uses HTTPS with port 443.
- If running Hasura as a Docker container, you may need to use `http://host.docker.internal:4318` for local collectors.

### Trace context not propagating

Hasura supports W3C Trace Context for trace propagation (from v2.35.0+). If upstream services aren't receiving trace context, ensure they also support W3C Trace Context headers.

## Setup OpenTelemetry Collector (Optional)
</ToggleHeading>

### What is the OpenTelemetry Collector?

Think of the OTel Collector as a middleman between your app and SigNoz. Instead of your application sending data directly to SigNoz, it sends everything to the Collector first, which then forwards it along.

### Why use it?

- **Cleaning up data** — Filter out noisy traces you don't care about, or remove sensitive info before it leaves your servers.
- **Keeping your app lightweight** — Let the Collector handle batching, retries, and compression instead of your application code.
- **Adding context automatically** — The Collector can tag your data with useful info like which Kubernetes pod or cloud region it came from.
- **Future flexibility** — Want to send data to multiple backends later? The Collector makes that easy without changing your app.

See [Switch from direct export to Collector](https://signoz.io/docs/opentelemetry-collection-agents/opentelemetry-collector/switch-to-collector/) for step-by-step instructions to convert your setup.

Configure your existing Collector to accept data and forward it. Ensure your `otel-collector-config.yaml` has the `otlp` HTTP receiver enabled and is present in your pipelines.
We can configure Hasura to point to your collector endpoint (e.g., `http://host.docker.internal:4318/v1/traces`) instead of SigNoz directly.

For more details, see [Why use the OpenTelemetry Collector?](https://signoz.io/docs/opentelemetry-collection-agents/opentelemetry-collector/why-to-use-collector/) and the [Collector configuration guide](https://signoz.io/docs/opentelemetry-collection-agents/opentelemetry-collector/configuration/).
