## Overview

This page lists the transactions available for each resource in SigNoz. Each table shows the supported relations, what they mean for that resource, and which managed roles have access.

A transaction is a single relation on a resource, optionally scoped to specific instances with a selector. When you configure a custom role, the transactions you grant are shown together as the role's **Transaction Groups**.

For an explanation of relations and how access control works, see the [Authorization Overview](https://signoz.io/docs/manage/administrator-guide/iam/overview/).

<Admonition type="info">
This page currently covers roles, service accounts, API keys, dashboards, field resources (logs, traces), and telemetry resources (logs, traces, metrics, meter metrics). Transactions for other observability resources such as alerts and pipelines will be documented as they become available for fine-grained access control.
</Admonition>

## Resources

### Role

**Resource:** `role` · **Kind:** `role` · **Selector:** role name (for example, `my-custom-role`)

| Relation | Description | Managed Role Access |
|----------|-------------|---------------------|
| `create` | Create a new custom role. | signoz-admin |
| `list` | List all roles (managed and custom). | signoz-admin |
| `read` | View a role's details and its configured transactions. | signoz-admin |
| `update` | Modify a custom role's description or change its transactions. | signoz-admin |
| `delete` | Delete a custom role (the role must have no assigned principals). | signoz-admin |
| `attach` | Create a relationship with the role — assign this role to a principal. | signoz-admin |
| `detach` | Remove a relationship from the role — unassign this role from a principal. | signoz-admin |

### Service Account

**Resource:** `serviceaccount` · **Kind:** `serviceaccount` · **Selector:** service account ID

| Relation | Description | Managed Role Access |
|----------|-------------|---------------------|
| `create` | Create a new service account. | signoz-admin |
| `list` | List all service accounts in the organization. | signoz-admin |
| `read` | View a service account's details and its assigned roles. | signoz-admin |
| `update` | Modify a service account (for example, rename it). | signoz-admin |
| `delete` | Delete a service account and revoke all its API keys. | signoz-admin |
| `attach` | Create a relationship with the service account — assign a role to it, or add an API key to it. | signoz-admin |
| `detach` | Remove a relationship from the service account — unassign a role from it, or revoke an API key from it. | signoz-admin |

### API Key

**Resource:** `metaresource` · **Kind:** `factor-api-key` · **Selector:** API key ID

| Relation | Description | Managed Role Access |
|----------|-------------|---------------------|
| `create` | Generate a new API key for a service account. | signoz-admin |

| `delete` | Permanently revoke an API key. | signoz-admin |

### Dashboard

**Resource:** `metaresource` · **Kind:** `dashboard` · **Selector:** dashboard ID (the UUID in the dashboard URL, `/dashboard/<dashboard-id>`)

| Relation | Description | Managed Role Access |
|----------|-------------|---------------------|
| `create` | Create a dashboard, import one from JSON, or clone an existing one. | signoz-admin, signoz-editor |
| `list` | Open the dashboards list, and manage the saved views and pins on it. | signoz-admin, signoz-editor, signoz-viewer |
| `read` | Open a dashboard, view its panels, and view its public sharing configuration. | signoz-admin, signoz-editor, signoz-viewer |
| `update` | Edit a dashboard's panels, sections, variables and settings, lock or unlock it, and publish or unpublish its public link. | signoz-admin, signoz-editor |
| `delete` | Delete a dashboard. | signoz-admin, signoz-editor |

`create` and `list` cover the workspace rather than an instance, so both can only be granted as **All** or **None**. `read`, `update`, and `delete` accept **Only selected**, with the dashboard ID as the selector.

The list is not filtered by `read`. A principal holding `list` sees every dashboard in the workspace, and a dashboard they cannot `read` reports the denial when they open it. `read` controls what a dashboard shows; its row appears either way.

<Admonition type="info">
Publishing a dashboard requires `update` on it. Readers who open the resulting public link are anonymous and are authorized against the `public-dashboard` resource, which is not configurable in custom roles. See [Public Sharing](https://signoz.io/docs/dashboards/public-sharing/).
</Admonition>

### Logs Field

**Resource:** `metaresource` · **Kind:** `logs-field` · **Selector:** not instance-scoped — the grant covers all log fields, so set the selector to `*` (**All**)

| Relation | Description | Managed Role Access |
|----------|-------------|---------------------|
| `read` | View log fields, including which attribute paths are promoted. | signoz-admin, signoz-editor, signoz-viewer |
| `list` | List promoted log paths (`GET /api/v1/promoted_paths`). | signoz-admin, signoz-editor, signoz-viewer |
| `update` | Promote or unpromote log attribute paths (`POST /api/v1/promoted_paths`). | signoz-admin, signoz-editor |

### Traces Field

**Resource:** `metaresource` · **Kind:** `traces-field` · **Selector:** not instance-scoped — the grant covers all trace fields, so set the selector to `*` (**All**)

| Relation | Description | Managed Role Access |
|----------|-------------|---------------------|
| `read` | View trace fields, including which attribute paths are promoted. | signoz-admin, signoz-editor, signoz-viewer |
| `list` | List promoted trace paths (`GET /api/v1/promoted_paths`). | signoz-admin, signoz-editor, signoz-viewer |
| `update` | Promote or unpromote trace attribute paths (`POST /api/v1/promoted_paths`). | signoz-admin, signoz-editor |

The field resources gate the **Promoted Paths** feature per signal. Each request is authorized against the field resource of every signal it touches:

| Operation | Signals in request | Transactions Required |
|-----------|--------------------|-----------------------|
| List promoted paths (`GET`) | Logs only | `logs-field:list` |
| List promoted paths (`GET`) | Traces only | `traces-field:list` |
| List promoted paths (`GET`) | No filter, or both | `logs-field:list` AND `traces-field:list` |
| Promote paths (`POST`) | Logs entries | `logs-field:update` |
| Promote paths (`POST`) | Traces entries | `traces-field:update` |
| Promote paths (`POST`) | Mixed logs and traces | `logs-field:update` AND `traces-field:update` |

A `GET` request narrows the signals it checks using the `signal` and `context` query parameters. With no filter, or a filter that matches no signal, it checks every signal and so requires `list` on both field resources. A `POST` request checks every signal named in its request body.

<Admonition type="warning" title="Breaking change for custom roles">
Promoted Paths previously relied on a general Editor grant (to promote) or Viewer grant (to list). It now requires `update` or `list` on the `logs-field` and `traces-field` resources.

Managed roles (Admin, Editor, Viewer) keep their access automatically through a migration that backfills these grants, so organizations using only managed roles need to do nothing.

**Custom roles that previously accessed Promoted Paths through an Editor or Viewer grant lose access** until you add the field-resource transactions. Edit the role in [JSON mode](https://signoz.io/docs/manage/administrator-guide/iam/roles/#json-mode) and add the grants the role needs:

```json
[
  { "objectGroup": { "resource": { "kind": "metaresource", "type": "logs-field" }, "selectors": ["*"] }, "relation": "list" },
  { "objectGroup": { "resource": { "kind": "metaresource", "type": "logs-field" }, "selectors": ["*"] }, "relation": "update" },
  { "objectGroup": { "resource": { "kind": "metaresource", "type": "traces-field" }, "selectors": ["*"] }, "relation": "list" },
  { "objectGroup": { "resource": { "kind": "metaresource", "type": "traces-field" }, "selectors": ["*"] }, "relation": "update" }
]
```
</Admonition>

## Selectors

Roles, service accounts, API keys, and dashboards are scoped by instance names or IDs, shown in each resource's metadata line above. Telemetry resources (logs, traces, metrics, meter metrics) support only the `read` relation and use a query-scoped selector format instead.

### Telemetry Selectors

A telemetry selector scopes the transaction by **query type** and, optionally, by **ingestion key ID**:

| Selector | Meaning |
|----------|---------|
| `*` | Every query on that signal, regardless of query type. |
| `<query_type>/*` | Every query of that query type. |
| `<query_type>/signoz.workspace.key.id/*` | Queries of that query type that filter on `signoz.workspace.key.id`, for any ingestion key. |
| `<query_type>/signoz.workspace.key.id/<key-id>` | Queries of that query type that filter on the specified ingestion key ID. |

The supported query types are:

| Query Type | Description | Supports Ingestion Key Scoping |
|------------|-------------|-------------------------------|
| `builder_query` | Queries built with the query builder (Builder Query in the UI). | Yes |
| `promql` | PromQL queries. | No (wildcard only) |
| `clickhouse_sql` | ClickHouse SQL queries. | No (wildcard only) |

<Admonition type="warning">
`signoz.workspace.key.id` is the only key that telemetry transactions can be scoped by. Its value is the ingestion key ID, which you can find on the Ingestion Settings page.
</Admonition>

For transaction evaluation rules and how queries are authorized, see the [Telemetry Access Reference](https://signoz.io/docs/manage/administrator-guide/iam/reference/telemetry/).

## Compound Transactions

Some operations require transactions on multiple resources. Both transactions must be satisfied for the operation to succeed.

| Operation | Transactions Required |
|-----------|----------------------|
| Clone a dashboard | `dashboard:read` on the source dashboard AND `dashboard:create` |
| Assign a role to a service account | `serviceaccount:attach` AND `role:attach` |
| Unassign a role from a service account | `serviceaccount:detach` AND `role:detach` |
| Create an API key for a service account | `factor-api-key:create` AND `serviceaccount:attach` |
| Revoke an API key from a service account | `factor-api-key:delete` AND `serviceaccount:detach` |
| Promote logs and traces paths in one request | `logs-field:update` AND `traces-field:update` |
| List promoted paths without a signal filter | `logs-field:list` AND `traces-field:list` |
