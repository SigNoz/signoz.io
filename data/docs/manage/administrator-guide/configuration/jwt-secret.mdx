SigNoz signs and verifies user session tokens with the provider set by `tokenizer.provider`. The default provider is `opaque` and needs no JWT secret. When you set `tokenizer.provider: jwt`, SigNoz uses a JWT secret to sign and verify every session token, and that secret is required.

<Admonition type="warning" title="A JWT secret is required when the provider is jwt">
Starting with SigNoz v0.143.0, if `tokenizer.provider` is `jwt` and no secret is set, SigNoz refuses to start and exits with:
```bash
jwt::secret must be set when provider is jwt
```
Earlier versions logged a warning and kept running with an empty secret, which let anyone forge valid tokens with an empty string. Set the secret before you upgrade. See [Upgrade to v0.143](https://signoz.io/docs/operate/migration/upgrade-0-143/).
</Admonition>

## Set the JWT secret

This applies only when `tokenizer.provider` is set to `jwt`. Deployments on the default `opaque` provider need no changes.

1. **Choose a strong secret.** Use a long, random string. Avoid simple or guessable values. Generate one with `openssl rand -hex 32`.

2. **Set the environment variable.** Add it to your environment configuration:

   ```bash
   SIGNOZ_TOKENIZER_JWT_SECRET=<your-random-secret>
   ```

   Prefer `SIGNOZ_TOKENIZER_JWT_SECRET`. The older `SIGNOZ_JWT_SECRET` still works as a fallback but is deprecated and scheduled for removal in a future release. When both are set, `SIGNOZ_JWT_SECRET` takes precedence and logs a deprecation warning.

3. **Restart SigNoz.** Restart your services to apply the change.

## Best Practices

- **Never share your JWT secret publicly.**
- **Rotate the secret periodically** and update your environment configuration accordingly.
- **Store the secret in a secret manager** rather than in plain text.
