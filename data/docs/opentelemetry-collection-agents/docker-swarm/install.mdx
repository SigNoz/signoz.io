This guide explains how to install the Docker Swarm Collection Agent on a Docker Swarm, with Foundry, or with `docker stack deploy` or `docker service create`.

## Prerequisites

- A <a href="https://docs.docker.com/engine/swarm/" target="_blank" rel="noopener noreferrer nofollow">Docker Swarm</a> of Linux nodes, each with <a href="https://docs.docker.com/engine/install/" target="_blank" rel="noopener noreferrer nofollow">Docker Engine</a> 25.0 or newer.
- A shell on a manager node of the Swarm, where you run the commands in this guide.
- Ports `4317` and `4318` free on every node. To run the agent on a Swarm that runs self-hosted SigNoz, see [Run on the same Swarm as self-hosted SigNoz](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/configure/#run-on-the-same-swarm-as-self-hosted-signoz).
- A SigNoz to send data to: [SigNoz Cloud](https://signoz.io/teams/) or a [self-hosted SigNoz](https://signoz.io/docs/install/self-host/).

## Install with Foundry

<Admonition type="info" title="What is Foundry?" defaultCollapsed="true">
Foundry is an open-source CLI that runs your self-hosted observability stack as code. One declarative config provisions the infrastructure, installs the SigNoz backend, and sets up OpenTelemetry collection on bare metal, containers, or Kubernetes. Learn more about <a href="https://github.com/SigNoz/foundry" target="_blank" rel="noopener noreferrer nofollow">Foundry</a>.
</Admonition>

### Step 1: Install foundryctl

Run this on a manager node:

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
```

For manual install (Windows PowerShell, air-gapped, etc.) or PATH setup, see the <a href="https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md" target="_blank" rel="noopener noreferrer nofollow">foundry getting-started guide</a>.

### Step 2: Create casting.yaml

Create a file named `casting.yaml` on the manager node, with one document for the agent described in [How it works](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/overview/#how-it-works-the-agent-service):

<Admonition type="info" title="Using Self-Hosted SigNoz?" defaultCollapsed="true">
Most steps are identical. To adapt this guide, update the endpoint and remove the ingestion key as shown in [Cloud → Self-Hosted](https://signoz.io/docs/ingestion/cloud-vs-self-hosted/?ingestion-client=collection-agent&collection-agent=foundry#cloud-to-self-hosted).
</Admonition>

```yaml:casting.yaml defaultCollapsed
apiVersion: v1alpha1
kind: CollectionAgent
metadata:
  name: signoz
spec:
  deployment:
    mode: docker
    flavor: swarm
  collector:
    spec:
      env:
        SIGNOZ_INGESTION_ENDPOINT: https://ingest.<region>.signoz.cloud:443
        SIGNOZ_INGESTION_KEY: <your-ingestion-key>
        OTEL_RESOURCE_ATTRIBUTES: deployment.environment=<your-environment>
      config:
        data:
          collector/agent/agent.yaml: |
            exporters:
              otlphttp/signoz:
                headers:
                  signoz-ingestion-key: ${env:SIGNOZ_INGESTION_KEY}
```

**Verify these values:**

- `<region>`: Your SigNoz Cloud [region](https://signoz.io/docs/ingestion/signoz-cloud/overview/#endpoint).
- `<your-ingestion-key>`: Your SigNoz Cloud [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/).
- `<your-environment>`: Your deployment environment, for example `staging` or `production`.

For every option of this casting, see the <a href="https://github.com/SigNoz/foundry/tree/main/docs/examples/collectionagent/docker/swarm" target="_blank" rel="noopener noreferrer nofollow">Docker Swarm example</a>.

### Step 3: Deploy

Run this from the directory that contains `casting.yaml`:

```bash
foundryctl cast -f casting.yaml
```

This command:

- writes the stack file `compose.yaml` to `pours/collectionagent/` and the collector config `agent.yaml` to `pours/collectionagent/collector/agent/`;
- deploys `compose.yaml` with `docker stack deploy`, as the stack `signoz`;
- runs the agent as the service `signoz_collector-agent`, with one task on every node.

Run the same command again after editing `casting.yaml`. A changed collector config becomes a new Swarm config, and Swarm replaces the agent's tasks to use it.

<Admonition type="tip" title="Run docker stack deploy yourself" defaultCollapsed="true">
To run `docker stack deploy` directly, generate the files and deploy them. Run this from the directory that contains `casting.yaml`:

```bash
foundryctl forge -f casting.yaml   # writes compose.yaml and agent.yaml under pours/collectionagent
docker stack deploy -c pours/collectionagent/compose.yaml signoz
```
</Admonition>

### Step 4: Verify the Collection Agent

Run this on the manager node to check that the agent started:

```bash
docker service logs signoz_collector-agent
```

The logs should include a line similar to the following from each node, where task IDs and node names vary:

```output
signoz_collector-agent.0.qij0plduzksw@node-1    | ... Everything is ready. Begin running and processing data.
```

`docker service ps signoz_collector-agent` lists one `Running` task per node. In SigNoz, open **Infrastructure Monitoring** > **Hosts**: each node appears under its host name as data arrives. Check **Logs Explorer** to confirm container logs are flowing.

## Customize the Collection Agent

Every change follows the same loop: edit `casting.yaml`, then run `foundryctl cast -f casting.yaml` again.

- **Collector settings** (image, environment): set them in the collector's `spec` (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#spec-fields" target="_blank" rel="noopener noreferrer nofollow">spec fields</a>). For example, to pin the collector image:

  ```yaml
  spec:
    collector:
      spec:
        image: otel/opentelemetry-collector-contrib:0.147.0
  ```

- **Collector config** (receivers, processors, pipelines): add it under `spec.collector.spec.config.data`, keyed `collector/agent/agent.yaml`. It merges into the generated config (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#custom-config-files" target="_blank" rel="noopener noreferrer nofollow">custom config files</a>). For example, to collect host metrics every 30s:

  ```yaml
  spec:
    collector:
      spec:
        config:
          data:
            collector/agent/agent.yaml: |
              receivers:
                hostmetrics:
                  collection_interval: 30s
  ```

- **Stack file** (mounts, placement, memory limit): add <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/patches.md" target="_blank" rel="noopener noreferrer nofollow">patches</a> under `spec.patches` against `collectionagent/compose.yaml`. For example, to mount the node's `/var/log` into the agent:

  ```yaml
  spec:
    patches:
      - target: collectionagent/compose.yaml
        operations:
          - op: add
            path: /services/collector-agent/volumes/-
            value:
              type: bind
              source: /var/log
              target: /var/log
              read_only: true
  ```

  Take the target and paths from the files under `pours/`. Each run regenerates them, so keep every change in `casting.yaml`.

## Troubleshooting
</ToggleHeading>

### foundryctl cast stops with `tools are not available`

In Step 3, `foundryctl cast -f casting.yaml` stops with `tools are not available, please install them and try again: docker-swarm`.

**Cause:** the machine is not a manager node of an active Swarm. Run the command with `--debug` to see which: `docker swarm is not active` or `current node is a swarm worker, not a manager`.

**Fix:** run Step 3 on a manager node. To create a Swarm on this machine, run <a href="https://docs.docker.com/reference/cli/docker/swarm/init/" target="_blank" rel="noopener noreferrer nofollow">`docker swarm init`</a> first.

After the fix, `foundryctl cast -f casting.yaml` deploys the stack, and `docker service logs signoz_collector-agent` shows `Everything is ready`.

### A port conflict stops the agent

In Step 3, `foundryctl cast -f casting.yaml` stops with `port '4317' is already in use by service '<service>' (<id>) as an ingress port`. Or in Step 4, `docker service logs signoz_collector-agent` stays empty, and `docker service ps --no-trunc signoz_collector-agent` shows tasks `Pending` with `host-mode port already in use on 1 node`, or `Failed` with `failed to bind host port 0.0.0.0:4317/tcp: address already in use` or `Bind for 0.0.0.0:4317 failed: port is already allocated`.

**Cause:** something else holds port `4317` or `4318`:

- `as an ingress port`: another service publishes it through the Swarm routing mesh, such as the ingester of self-hosted SigNoz.
- `host-mode port already in use`: another Swarm service publishes it in host mode on that node.
- `address already in use` or `port is already allocated`: a container or process outside the Swarm holds it on that node, such as the Docker Collection Agent or a self-hosted SigNoz run with Docker Compose.

**Fix:** for self-hosted SigNoz on the Swarm, give the agent its own name and ports as [Run on the same Swarm as self-hosted SigNoz](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/configure/#run-on-the-same-swarm-as-self-hosted-signoz) shows, then run Step 3 again. Otherwise, stop what holds the port on that node. Swarm then starts the waiting tasks on its own.

After the fix, `docker service logs signoz_collector-agent` shows `Everything is ready`.

### The agent logs `at least one endpoint must be specified`

In Step 4, `docker service logs signoz_collector-agent` shows `exporters::otlphttp/signoz: at least one endpoint must be specified`, and the agent's tasks keep restarting.

**Cause:** the casting sets no `SIGNOZ_INGESTION_ENDPOINT` under `spec.collector.spec.env`.

**Fix:** add it as in Step 2, then run `foundryctl cast -f casting.yaml` again from the directory that contains it.

After the fix, `docker service logs signoz_collector-agent` shows `Everything is ready`.

### The agent logs `context canceled` from docker_stats

In Step 4, `docker service logs signoz_collector-agent` shows `Could not parse docker containerStats for container id` and `"error": "context canceled"` from `docker_stats`, and some container metrics are missing.

**Cause:** a bug in the `docker_stats` receiver of OpenTelemetry Collector 0.139.0, the image Foundry sets by default, <a href="https://github.com/open-telemetry/opentelemetry-collector-contrib/pull/45655" target="_blank" rel="noopener noreferrer nofollow">fixed in 0.147.0</a>.

**Fix:** set `spec.collector.spec.image` to `otel/opentelemetry-collector-contrib:0.147.0` or newer, as [Customize the Collection Agent](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/install/?setup=foundry#customize-the-collection-agent) shows. Then run `foundryctl cast -f casting.yaml` again from the directory that contains it.

After the fix, `docker service logs signoz_collector-agent` shows no new `context canceled` errors.

### foundryctl cast rejects a patch

`foundryctl cast -f casting.yaml` stops before it deploys the agent, with `failed to apply patch for target "<target>"` followed by one of these:

- `patch target "<target>" did not match any generated material`
- `doc is missing path: <path>: missing value`
- `doc is missing key: <path>: missing value`
- `unable to remove nonexistent key: <key>: missing value`

**Cause:** the patch's target or path does not exist in what Foundry generates.

**Fix:** remove the patch, then run this from the directory that contains `casting.yaml`:

```bash
foundryctl forge -f casting.yaml
```

Take the target and path from the files under `pours/collectionagent/`, add the patch back, then run `foundryctl cast -f casting.yaml` again.

After the fix, `docker service logs signoz_collector-agent` shows `Everything is ready`.

## Install with Docker

### Step 1: Create config.yaml

Create a file named `config.yaml` on a manager node, with the config of the agent described in [How it works](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/overview/#how-it-works-the-agent-service):

<Admonition type="info" title="Using Self-Hosted SigNoz?" defaultCollapsed="true">
Most steps are identical. To adapt this guide, update the endpoint and remove the ingestion key as shown in [Cloud → Self-Hosted](https://signoz.io/docs/ingestion/cloud-vs-self-hosted/?ingestion-client=collector#cloud-to-self-hosted).
</Admonition>

```yaml:config.yaml minimap defaultCollapsed
receivers:
  # OTLP: accept traces, metrics, and logs from instrumented apps (SDKs, agents)
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318
  # Host metrics: CPU, disk, memory, network, etc. (root_path for container)
  hostmetrics:
    collection_interval: 60s
    root_path: /hostfs
    scrapers:
      cpu: {}
      disk:
        exclude:
          match_type: regexp
          devices:
            - ^ram\d+$
            - ^zram\d+$
            - ^loop\d+$
            - ^fd\d+$
            - ^hd[a-z]\d+$
            - ^sd[a-z]\d+$
            - ^vd[a-z]\d+$
            - ^xvd[a-z]\d+$
            - ^nvme\d+n\d+p\d+$
      load: {}
      filesystem:
        exclude_fs_types:
          match_type: strict
          fs_types:
            - autofs
            - binfmt_misc
            - bpf
            - cgroup2
            - configfs
            - debugfs
            - devpts
            - devtmpfs
            - fusectl
            - hugetlbfs
            - iso9660
            - mqueue
            - nsfs
            - overlay
            - proc
            - procfs
            - pstore
            - rpc_pipefs
            - securityfs
            - selinuxfs
            - squashfs
            - sysfs
            - tracefs
        exclude_mount_points:
          match_type: regexp
          mount_points:
            - /dev/*
            - /proc/*
            - /sys/*
            - /run/*
            - /run/credentials/*
            - /run/k3s/containerd/*
            - /var/lib/docker/*
            - /var/lib/containers/storage/*
            - /var/lib/kubelet/*
            - /snap/*
      memory: {}
      network:
        exclude:
          match_type: regexp
          interfaces:
            - ^veth.*$
            - ^docker.*$
            - ^br-.*$
            - ^flannel.*$
            - ^cali.*$
            - ^cbr.*$
            - ^cni.*$
            - ^dummy.*$
            - ^tailscale.*$
            - ^lo$
      paging: {}
      process:
        mute_process_name_error: true
        mute_process_exe_error: true
        mute_process_io_error: true
        mute_process_user_error: true
      processes: {}
  # Container metrics from Docker daemon, with Swarm labels as resource attributes
  docker_stats:
    endpoint: unix:///var/run/docker.sock
    collection_interval: 10s
    timeout: 20s
    container_labels_to_metric_labels:
      com.docker.stack.namespace: docker.stack.name
      com.docker.swarm.node.id: docker.node.id
      com.docker.swarm.service.name: docker.service.name
      com.docker.swarm.task.name: docker.task.name
  # Container logs: Docker JSON log files
  filelog:
    include: [/var/lib/docker/containers/*/*-json.log]
    start_at: end  # Collect only logs written after the agent starts
    include_file_name: false
    include_file_path: true
    operators:
      - id: container-parser
        type: container
        format: docker
        add_metadata_from_filepath: false
      # Set container.id from the log file's directory
      - type: regex_parser
        parse_from: attributes["log.file.path"]
        regex: /var/lib/docker/containers/(?P<container_id>[a-f0-9]{64})/
        on_error: send
      - type: move
        from: attributes.container_id
        to: resource["container.id"]
        on_error: send_quiet

processors:
  batch:
    send_batch_size: 1000
    timeout: 10s
  resourcedetection:
    detectors: [env, ec2, gcp, azure, system, docker]
    override: false
    timeout: 2s
    system:
      hostname_sources: [os]
  memory_limiter:
    check_interval: 5s
    limit_mib: 4000
    spike_limit_mib: 800

exporters:
  otlphttp:
    endpoint: 'https://ingest.<region>.signoz.cloud:443'
    headers:
      'signoz-ingestion-key': '<your-ingestion-key>'

extensions:
  health_check:
    endpoint: 0.0.0.0:13133

service:
  extensions: [health_check]
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, resourcedetection, batch]
      exporters: [otlphttp]
    metrics:
      receivers: [otlp, hostmetrics, docker_stats]
      processors: [memory_limiter, resourcedetection, batch]
      exporters: [otlphttp]
    logs:
      receivers: [otlp, filelog]
      processors: [memory_limiter, resourcedetection, batch]
      exporters: [otlphttp]
```

**Verify these values:**

- `<region>`: Your SigNoz Cloud [region](https://signoz.io/docs/ingestion/signoz-cloud/overview/#endpoint).
- `<your-ingestion-key>`: Your SigNoz Cloud [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/).

### Step 2: Deploy the Collection Agent

Both methods run the agent as a global service with Docker's `local` log driver, which keeps the agent's own logs out of the container logs it collects. They store `config.yaml` as the Swarm config `signoz-collection-agent-config-v1`; the version at the end of its name lets each later change go into a new config.

<Tabs entityName="method">
<TabItem value="docker-stack" label="Docker Stack" default>

In the directory that contains `config.yaml`, create a file named `docker-stack.yaml`:

```yaml:docker-stack.yaml minimap defaultCollapsed
services:
  signoz-collection-agent:
    image: otel/opentelemetry-collector-contrib:0.162.0
    user: "0:0"
    hostname: "{{.Node.Hostname}}"
    logging:
      driver: local
    environment:
      - OTEL_RESOURCE_ATTRIBUTES=deployment.environment=<your-environment>
    configs:
      - source: otelcol_config
        target: /etc/otelcol-contrib/config.yaml
        mode: 0444
    volumes:
      - type: bind
        source: /var/run/docker.sock
        target: /var/run/docker.sock
        read_only: true
      - type: bind
        source: /var/lib/docker/containers
        target: /var/lib/docker/containers
        read_only: true
      - type: bind
        source: /
        target: /hostfs
        read_only: true
    ports:
      - target: 4317
        published: 4317
        protocol: tcp
        mode: host
      - target: 4318
        published: 4318
        protocol: tcp
        mode: host
    deploy:
      mode: global
      restart_policy:
        condition: any

configs:
  otelcol_config:
    name: signoz-collection-agent-config-v1
    file: ./config.yaml
```

Run this from the same directory to deploy it as the stack `signoz`:

```bash
docker stack deploy -c docker-stack.yaml signoz
```

The agent's service is `signoz_signoz-collection-agent`.

</TabItem>
<TabItem value="docker-service" label="Docker Service">

Run this from the directory that contains `config.yaml`, to store it as a Swarm config and create the agent's service `signoz-collection-agent`:

```bash
docker config create signoz-collection-agent-config-v1 ./config.yaml
docker service create \
  --name signoz-collection-agent \
  --mode global \
  --detach \
  --restart-condition any \
  --user 0:0 \
  --hostname '{{.Node.Hostname}}' \
  --log-driver local \
  --env OTEL_RESOURCE_ATTRIBUTES=deployment.environment=<your-environment> \
  --config source=signoz-collection-agent-config-v1,target=/etc/otelcol-contrib/config.yaml,mode=0444 \
  --mount type=bind,source=/var/run/docker.sock,target=/var/run/docker.sock,readonly \
  --mount type=bind,source=/var/lib/docker/containers,target=/var/lib/docker/containers,readonly \
  --mount type=bind,source=/,target=/hostfs,readonly \
  --publish target=4317,published=4317,protocol=tcp,mode=host \
  --publish target=4318,published=4318,protocol=tcp,mode=host \
  otel/opentelemetry-collector-contrib:0.162.0
```

</TabItem>
</Tabs>

**Verify these values:**

- `<your-environment>`: Your deployment environment, for example `staging` or `production`.

## Customize the Collection Agent

Every change to `config.yaml` follows the same loop: edit `config.yaml`, then store it as a new Swarm config and point the agent at it, as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/configure/?setup=docker#apply-changes) shows.

- **Collector config** (receivers, processors, pipelines): see [Configure the Docker Swarm Collection Agent](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/configure/?setup=docker).
- **Collector version**: change the image tag in `docker-stack.yaml` and run `docker stack deploy -c docker-stack.yaml signoz` again from its directory, or run `docker service update --image otel/opentelemetry-collector-contrib:<version> signoz-collection-agent`. Versions are listed in the <a href="https://github.com/open-telemetry/opentelemetry-collector-releases/releases" target="_blank" rel="noopener noreferrer nofollow">OpenTelemetry Collector releases</a>.

## Troubleshooting
</ToggleHeading>

### Step 2 fails with `only updates to Labels are allowed`

After an edit to `config.yaml`, running `docker stack deploy -c docker-stack.yaml signoz` again stops with `failed to update config signoz-collection-agent-config-v1: Error response from daemon: rpc error: code = InvalidArgument desc = only updates to Labels are allowed`.

**Cause:** a Swarm config keeps the content it was created with, and `docker-stack.yaml` still names the config that holds the earlier `config.yaml`.

**Fix:** raise the version in the config's name and deploy again, as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/configure/?setup=docker#apply-changes) shows.

After the fix, `docker stack deploy` prints `Creating config signoz-collection-agent-config-v2` and `Updating service signoz_signoz-collection-agent`.

### A port conflict stops the agent

In Step 2, `docker stack deploy` or `docker service create` stops with `port '4317' is already in use by service '<service>' (<id>) as an ingress port`. Or in Step 3, the agent's logs stay empty, and `docker service ps --no-trunc signoz_signoz-collection-agent` (or `signoz-collection-agent` for `docker service create`) shows tasks `Pending` with `host-mode port already in use on 1 node`, or `Failed` with `failed to bind host port 0.0.0.0:4317/tcp: address already in use` or `Bind for 0.0.0.0:4317 failed: port is already allocated`.

**Cause:** something else holds port `4317` or `4318`:

- `as an ingress port`: another service publishes it through the Swarm routing mesh, such as the ingester of self-hosted SigNoz.
- `host-mode port already in use`: another Swarm service publishes it in host mode on that node.
- `address already in use` or `port is already allocated`: a container or process outside the Swarm holds it on that node, such as the Docker Collection Agent or a self-hosted SigNoz run with Docker Compose.

**Fix:** for self-hosted SigNoz on the Swarm, change the agent as [Run on the same Swarm as self-hosted SigNoz](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/configure/?setup=docker#run-on-the-same-swarm-as-self-hosted-signoz) shows, and store `config.yaml` under a new config name as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/configure/?setup=docker#apply-changes) shows. Otherwise, stop what holds the port on that node. Swarm then starts the waiting tasks on its own.

After the fix, the agent's logs show `Everything is ready`.

### The agent logs `permission denied` on the Docker socket

In Step 3, the agent's logs show `permission denied while trying to connect to the docker API at unix:///var/run/docker.sock`, and its tasks keep restarting.

**Cause:** the agent runs as a user that cannot access the Docker socket.

**Fix:** run the agent as root, with `user: "0:0"` in `docker-stack.yaml` as in Step 2, then run `docker stack deploy -c docker-stack.yaml signoz` again. For the service from `docker service create`, run `docker service update --user 0:0 signoz-collection-agent`.

After the fix, the agent's logs show `Everything is ready`.

### The agent logs `invalid root_path`

In Step 3, the agent's logs show `receivers::hostmetrics: invalid root_path: stat /hostfs: no such file or directory`, and its tasks keep restarting.

**Cause:** the node's root filesystem is not mounted at `/hostfs`, the `root_path` of the `hostmetrics` receiver.

**Fix:** add the bind mount of `/` at `/hostfs` as in Step 2, then run `docker stack deploy -c docker-stack.yaml signoz` again. For the service from `docker service create`, run `docker service update --mount-add type=bind,source=/,target=/hostfs,readonly signoz-collection-agent`.

After the fix, the agent's logs show `Everything is ready`, and each node appears under **Infrastructure Monitoring** > **Hosts**.

### The agent exits with `failed to get config`

In Step 3, the agent's logs show an error that starts with `Error: failed to get config`, and its tasks keep restarting.

**Cause:** `config.yaml` is not valid YAML, names a component that the collector image does not include, or has a setting that a component does not accept.

**Fix:** correct `config.yaml` where the error points, then apply it as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/docker-swarm/configure/?setup=docker#apply-changes) shows.

After the fix, the agent's logs show `Everything is ready`.

### Agent tasks are rejected with `bind source path does not exist`

In Step 3, `docker service ps --no-trunc signoz_signoz-collection-agent` shows tasks `Rejected` on some nodes with `invalid mount config for type "bind": bind source path does not exist: <path>`.

**Cause:** those nodes lack a path the agent mounts, such as `/var/lib/docker/containers` on a node whose Docker data lives elsewhere.

**Fix:** keep the agent off those nodes. Add this to the agent's service in `docker-stack.yaml`, then run `docker stack deploy -c docker-stack.yaml signoz` again:

```yaml
services:
  signoz-collection-agent:
    deploy:
      placement:
        constraints:
          - node.hostname != <node-name>
```

For the service from `docker service create`, run `docker service update --constraint-add 'node.hostname != <node-name>' signoz-collection-agent`.

**Verify these values:**

- `<node-name>`: The node's hostname, as `docker node ls` shows it.

After the fix, `docker service ps signoz_signoz-collection-agent` lists a `Running` task on every other node.
