The [install guide](https://signoz.io/docs/opentelemetry-collection-agents/docker/install/) provides a working config: one agent container on each Docker host collects host metrics, container metrics, container logs, and data from instrumented applications. This page shows how to customize it, in `config.yaml` for Docker or in `casting.yaml` for Foundry.

## Prerequisites

- Docker Collection Agent installed with Docker Compose, `docker run`, or Foundry (see the [install guide](https://signoz.io/docs/opentelemetry-collection-agents/docker/install/))
- SigNoz Cloud account or self-hosted SigNoz instance
- A shell on the Docker host, and the files you installed from: `config.yaml` and `docker-compose.yaml` (or your `docker run` command) for Docker, or `casting.yaml` and `foundryctl` for Foundry

## Apply Changes

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

For each change:

1. Add the section's snippet to `config.yaml`, merging it into the keys the file already has.

2. Run this on the Docker host to apply the change:

   ```bash
   docker restart signoz-collection-agent
   ```

   The agent restarts and reads the new config. For a change to `docker-compose.yaml`, run `docker compose up -d` from its directory instead; with `docker run`, remove the container with `docker rm -f signoz-collection-agent` and run it again with the new flags.

3. View the agent's logs to confirm there are no configuration errors:

   ```bash
   docker logs --since 5m signoz-collection-agent
   ```

4. In SigNoz, confirm data in [Infrastructure Monitoring](https://signoz.io/docs/infrastructure-monitoring/overview/) for host metrics, the [Docker container metrics dashboard](https://signoz.io/docs/metrics-management/docker-container-metrics/) for container metrics, [Logs](https://signoz.io/docs/logs-management/overview/) for container logs, and [Traces](https://signoz.io/docs/instrumentation/overview/) for application traces.

</TabItem>
<TabItem value="foundry" label="Foundry">

For each change:

1. Add the section's snippet to `casting.yaml`. Foundry already generates the default receivers and processors, so add only what you change.

2. Run this from the directory that contains `casting.yaml` to apply the change:

   ```bash
   foundryctl cast -f casting.yaml
   docker restart signoz-collector-agent
   ```

   Foundry updates the agent's config, and the agent restarts with it.

3. View the agent's logs to confirm there are no configuration errors:

   ```bash
   docker logs --since 5m signoz-collector-agent
   ```

4. In SigNoz, confirm data in [Infrastructure Monitoring](https://signoz.io/docs/infrastructure-monitoring/overview/) for host metrics, the [Docker container metrics dashboard](https://signoz.io/docs/metrics-management/docker-container-metrics/) for container metrics, [Logs](https://signoz.io/docs/logs-management/overview/) for container logs, and [Traces](https://signoz.io/docs/instrumentation/overview/) for application traces.

</TabItem>
</Tabs>

## Send Data from Applications to the Collector

Host metrics, container metrics, and container logs flow as soon as the agent is running.

### Where and how to send data from your application

To send traces, metrics, and logs from an application, instrument it with OpenTelemetry ([language guides](https://signoz.io/docs/instrumentation/)), then point it at the agent. For an application in a container, add this to its service in its Compose file:

```yaml
services:
  <your-app>:
    environment:
      OTEL_EXPORTER_OTLP_ENDPOINT: http://host.docker.internal:4318
      OTEL_SERVICE_NAME: <service-name>
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

**Verify these values:**

- `<your-app>`: Your application's service in its Compose file.
- `<service-name>`: The name your application shows under in SigNoz.

The <a href="https://docs.docker.com/reference/cli/docker/container/run/#add-host" target="_blank" rel="noopener noreferrer nofollow">`host-gateway`</a> entry points `host.docker.internal` at the Docker host, where the agent listens. For an application on the host itself, use `http://localhost:4318`, and from another host, the Docker host's address. For OTLP over gRPC, set `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` and port `4317`.

Redeploy the application and send it some traffic. Within a minute it shows under **Services** in SigNoz.

## Collect Host Metrics

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To collect host metrics every 30s, add this to `config.yaml`:

```yaml
receivers:
  hostmetrics:
    collection_interval: 30s
```

To stop a scraper, delete its entry under `scrapers`.

</TabItem>
<TabItem value="foundry" label="Foundry">

To collect host metrics every 30s, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              hostmetrics:
                collection_interval: 30s
```

To stop a scraper, set it to `null` under `scrapers`, for example `paging: null`.

</TabItem>
</Tabs>

### Exclude filesystem mounts

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To stop reporting the filesystem mounted at `/mnt/backup`, add this to `config.yaml`:

```yaml
receivers:
  hostmetrics:
    scrapers:
      filesystem:
        exclude_mount_points:
          mount_points:
            - /dev/*
            - /proc/*
            - /sys/*
            - /run/credentials/*
            - /run/k3s/containerd/*
            - /var/lib/docker/*
            - /var/lib/containers/storage/*
            - /var/lib/kubelet/*
            - /snap/*
            - ^/mnt/backup$
```

Entries are unanchored regular expressions matched against each mount point.

</TabItem>
<TabItem value="foundry" label="Foundry">

To stop reporting the filesystem mounted at `/mnt/backup`, add this to `casting.yaml`:

```yaml defaultCollapsed
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              hostmetrics:
                scrapers:
                  filesystem:
                    exclude_mount_points:
                      mount_points:
                        - /dev/*
                        - /proc/*
                        - /sys/*
                        - /run/credentials/*
                        - /run/k3s/containerd/*
                        - /var/lib/docker/*
                        - /var/lib/containers/storage/*
                        - /var/lib/kubelet/*
                        - /snap/*
                        - ^/mnt/backup$
```

Lists replace, so restate Foundry's nine default entries, the ones above `^/mnt/backup$`.

</TabItem>
</Tabs>

### Map container labels to resource attributes

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To add container labels to container metrics as resource attributes, add this to `config.yaml`:

```yaml
receivers:
  docker_stats:
    container_labels_to_metric_labels:
      com.docker.compose.project: docker.compose.project
      com.docker.compose.service: docker.compose.service
      com.example.team: team
```

</TabItem>
<TabItem value="foundry" label="Foundry">

To add the `com.example.team` container label to container metrics as `team`, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              docker_stats:
                container_labels_to_metric_labels:
                  com.example.team: team
```

The map merges, so Foundry's default `com.docker.compose.project` and `com.docker.compose.service` mappings stay.

</TabItem>
</Tabs>

### Exclude containers from metrics

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To stop collecting metrics for containers by image, add this to `config.yaml`:

```yaml
receivers:
  docker_stats:
    excluded_images:
      - 'otel/opentelemetry-collector-contrib*'
      - /.*pause.*/
```

Entries match the image name exactly, as a glob, or as a regular expression between slashes.

</TabItem>

## Collect Container Logs

For Docker daemon logs and other log sources, see [Collecting Docker Logs](https://signoz.io/docs/userguide/collect_docker_logs/).

To keep a container's logs out of the agent's collection, add this to its service in its Compose file and redeploy it:

```yaml
services:
  <your-app>:
    logging:
      driver: local
```

**Verify these values:**

- `<your-app>`: The service whose logs you keep out.

The agent collects the logs of containers that use the `json-file` log driver, Docker's default.

### Disable Logs Collection

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To stop collecting container logs, add this to `config.yaml`:

```yaml
service:
  pipelines:
    logs:
      receivers: [otlp]
```

Logs that applications send over OTLP keep flowing.

</TabItem>
<TabItem value="foundry" label="Foundry">

To stop collecting container logs, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              filelog: null
            service:
              pipelines:
                logs:
                  receivers: [otlp/http, otlp/grpc]
```

Lists replace, so the `logs` pipeline is restated with Foundry's two OTLP receivers.

</TabItem>
</Tabs>

## Resource Detection

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To detect only host and Docker attributes on a host outside AWS, GCP, and Azure, add this to `config.yaml`:

```yaml
processors:
  resourcedetection:
    detectors: [env, system, docker]
```

The first detector to set an attribute wins.

</TabItem>
<TabItem value="foundry" label="Foundry">

To detect only host and Docker attributes on a host outside AWS, GCP, and Azure, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            processors:
              resourcedetection:
                detectors: [env, system, docker]
```

Lists replace, so `detectors` holds only the detectors you list.

</TabItem>
</Tabs>

### Custom resource attributes

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To add `team=backend` to all telemetry, set it in the agent's environment in `docker-compose.yaml`, or in the `-e` flag of `docker run`:

```yaml
services:
  signoz-collection-agent:
    environment:
      - OTEL_RESOURCE_ATTRIBUTES=deployment.environment=<your-environment>,team=backend
```

**Verify these values:**

- `<your-environment>`: Your deployment environment, for example `staging` or `production`.

</TabItem>
<TabItem value="foundry" label="Foundry">

```yaml
spec:

    spec:
      env:
        OTEL_RESOURCE_ATTRIBUTES: deployment.environment=<your-environment>,team=backend
```

**Verify these values:**

- `<your-environment>`: Your deployment environment, for example `staging` or `production`.

## Scrape Prometheus Metrics from Containers

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To scrape a Prometheus endpoint every 60s, add this to `config.yaml`:

```yaml
receivers:
  prometheus:
    config:
      scrape_configs:
        - job_name: my-app
          scrape_interval: 60s
          static_configs:
            - targets: [localhost:9090]
service:
  pipelines:
    metrics:
      receivers: [otlp, hostmetrics, docker_stats, prometheus]
```

The agent shares the host's network, so `localhost:9090` reaches port `9090` published by a container.

</TabItem>
<TabItem value="foundry" label="Foundry">

To scrape a Prometheus endpoint every 60s, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              prometheus:
                config:
                  scrape_configs:
                    - job_name: my-app
                      scrape_interval: 60s
                      static_configs:
                        - targets: [localhost:9090]
            service:
              pipelines:
                metrics:
                  receivers: [otlp/http, otlp/grpc, docker_stats, hostmetrics, prometheus]
```

Lists replace, so the `metrics` pipeline is restated with Foundry's default receivers.

</TabItem>
</Tabs>

## Tune Batch and Memory Limiter

For sizing guidance, see [Collector Configuration Best Practices](https://signoz.io/docs/opentelemetry-collection-agents/opentelemetry-collector/configuration/#best-practices).

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To send larger batches, add this to `config.yaml`:

```yaml
processors:
  batch:
    send_batch_size: 2000
    send_batch_max_size: 4000
```

</TabItem>
<TabItem value="foundry" label="Foundry">

To send larger batches, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            processors:
              batch:
                send_batch_size: 2000
                send_batch_max_size: 4000
```

Foundry's defaults are `send_batch_size: 1000`, `send_batch_max_size: 2048`, and `timeout: 10s`.

</TabItem>
</Tabs>

### Container Memory Limit

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To cap the agent's memory at 1 GiB, add this to its service in `docker-compose.yaml`, or pass `--memory 1g` to `docker run`:

```yaml
services:
  signoz-collection-agent:
    mem_limit: 1g
```

Then replace the `memory_limiter` block in `config.yaml` with this, which sizes it to that limit:

```yaml
processors:
  memory_limiter:
    check_interval: 5s
    limit_percentage: 80
    spike_limit_percentage: 25
```

</TabItem>
<TabItem value="foundry" label="Foundry">

To cap the agent's memory at 1 GiB, add this patch to `casting.yaml`:

```yaml
spec:
  patches:
    - target: collectionagent/collector/agent/compose.yaml
      operations:
        - op: add
          path: /services/signoz-collector-agent/mem_limit
          value: 1g
```

Foundry's `memory_limiter` processor uses a fixed `limit_mib: 4000`. Size it to the memory limit with percentages, in the same document:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            processors:
              memory_limiter:
                limit_mib: null
                spike_limit_mib: null
                limit_percentage: 80
                spike_limit_percentage: 25
```

</TabItem>
</Tabs>

## Add Custom Processors to Pipelines

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To add a processor to the `traces` pipeline, add this to `config.yaml`:

```yaml
processors:
  attributes/team:
    actions:
      - key: team
        value: platform
        action: insert
service:
  pipelines:
    traces:
      processors: [memory_limiter, resourcedetection, attributes/team, batch]
```

Processors run in the order listed, so put yours before `batch`.

</TabItem>
<TabItem value="foundry" label="Foundry">

To add a processor to the `traces` pipeline, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            processors:
              attributes/team:
                actions:
                  - key: team
                    value: platform
                    action: insert
            service:
              pipelines:
                traces:
                  processors: [memory_limiter, resourcedetection, attributes/team, batch]
```

Lists replace, so restate Foundry's processors `memory_limiter`, `resourcedetection`, and `batch`, with yours before `batch`.

</TabItem>
</Tabs>

## Common Deployment Scenarios

### Run on the same host as self-hosted SigNoz

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To run the agent on the host that runs self-hosted SigNoz, add this to `config.yaml`:

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:14317
      http:
        endpoint: 0.0.0.0:14318
exporters:
  otlphttp:
    endpoint: http://localhost:4318
```

Applications on the host then send to `localhost:14318`.

</TabItem>
<TabItem value="foundry" label="Foundry">

To run the agent on the host that runs self-hosted SigNoz, add this to `casting.yaml`:

```yaml
metadata:
  name: signoz-agent
spec:
  collector:
    spec:
      env:
        SIGNOZ_INGESTION_ENDPOINT: http://localhost:4318
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              otlp/grpc:
                protocols:
                  grpc:
                    endpoint: 0.0.0.0:14317
              otlp/http:
                protocols:
                  http:
                    endpoint: 0.0.0.0:14318
```

Remove the old agent with `docker rm -f signoz-collector-agent` before you apply this. The agent then runs as `signoz-agent-collector-agent` in its own Compose project, the name commands and patch paths use from then on, and applications on the host send to `localhost:14318`.

</TabItem>
</Tabs>

### Use bridge networking

<Tabs entityName="setup">
<TabItem value="docker" label="Docker" default>

To run the agent on a bridge network, remove `network_mode: host` from `docker-compose.yaml` and add this to the agent's service:

```yaml
services:
  signoz-collection-agent:
    hostname: <host-name>
    ports:
      - "4317:4317"
      - "4318:4318"
    networks:
      - monitoring
networks:
  monitoring:
    driver: bridge
```

**Verify these values:**

- `<host-name>`: The Docker host's name.

On a bridge network, host network metrics report the agent container's network interfaces.

</TabItem>
<TabItem value="foundry" label="Foundry">

To run the agent on a bridge network, add this patch to `casting.yaml`:

```yaml
spec:
  patches:
    - target: collectionagent/collector/agent/compose.yaml
      operations:
        - op: remove
          path: /services/signoz-collector-agent/network_mode
        - op: add
          path: /services/signoz-collector-agent/hostname
          value: <host-name>
        - op: add
          path: /services/signoz-collector-agent/ports
          value: ["4317:4317", "4318:4318"]
        - op: add
          path: /services/signoz-collector-agent/networks
          value: [monitoring]
        - op: add
          path: /networks
          value:
            monitoring:
              driver: bridge
```

**Verify these values:**

- `<host-name>`: The Docker host's name.

On a bridge network, host network metrics report the agent container's network interfaces.

</TabItem>
</Tabs>

## Troubleshooting
</ToggleHeading>

### Host or container metrics stop after adding a receiver

After a change that adds a receiver to the `metrics` pipeline, host or container metrics stop arriving in SigNoz.

**Cause:** the pipeline's `receivers` list replaces the whole list, so a list without `hostmetrics` and `docker_stats` drops them.

**Fix:** restate every receiver the pipeline still needs, as [Scrape Prometheus Metrics from Containers](https://signoz.io/docs/opentelemetry-collection-agents/docker/configure/#scrape-prometheus-metrics-from-containers) shows, then apply the change as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/docker/configure/#apply-changes) shows.

After the fix, host and container metrics arrive in SigNoz again.

### A custom processor has no effect

After a change that adds a processor, its attribute or transformation is missing from the data in SigNoz.

**Cause:** the processor is defined under `processors` but not listed in a pipeline's `processors`.

**Fix:** list it before `batch` as [Add Custom Processors to Pipelines](https://signoz.io/docs/opentelemetry-collection-agents/docker/configure/#add-custom-processors-to-pipelines) shows, then apply the change as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/docker/configure/#apply-changes) shows.

After the fix, the attribute or transformation appears on the signal in SigNoz Explorer.

</details>
