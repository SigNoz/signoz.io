This guide explains how to install the ECS EC2 Collection Agent on an Amazon ECS cluster with Foundry and Terraform.

## Prerequisites

- An Amazon ECS cluster with <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/launch_container_instance.html" target="_blank" rel="noopener noreferrer nofollow">EC2 container instances</a>, or with <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-anywhere.html" target="_blank" rel="noopener noreferrer nofollow">external instances registered through ECS Anywhere</a>. Every instance runs Docker Engine 25 or newer, as the current Amazon ECS-optimized AMIs do.
- <a href="https://developer.hashicorp.com/terraform/install" target="_blank" rel="noopener noreferrer nofollow">Terraform</a> 1.4 or newer and the AWS CLI, with AWS credentials on the same machine that can create AWS AppConfig applications, IAM roles, ECS task definitions, and ECS services.
- A SigNoz to send data to: [SigNoz Cloud](https://signoz.io/teams/) or a [self-hosted SigNoz](https://signoz.io/docs/install/self-host/).

## Install with Foundry and Terraform

<Admonition type="info" title="What is Foundry?" defaultCollapsed="true">
Foundry is an open-source CLI that runs your self-hosted observability stack as code. One declarative config provisions the infrastructure, installs the SigNoz backend, and sets up OpenTelemetry collection on bare metal, containers, or Kubernetes. Learn more about <a href="https://github.com/SigNoz/foundry" target="_blank" rel="noopener noreferrer nofollow">Foundry</a>.
</Admonition>

### Step 1: Install foundryctl

Run this on the machine where you run Terraform:

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
```

For manual install (Windows PowerShell, air-gapped, etc.) or PATH setup, see the <a href="https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md" target="_blank" rel="noopener noreferrer nofollow">foundry getting-started guide</a>.

### Step 2: Create casting.yaml

Create a file named `casting.yaml` with one document for the collector described in [How it works](https://signoz.io/docs/opentelemetry-collection-agents/ecs/ec2/overview/#how-it-works). Pick the tab for the instances your cluster runs on:

<Tabs entityName="launch-type">
<TabItem value="ec2" label="EC2" default>

```yaml:casting.yaml defaultCollapsed
apiVersion: v1alpha1
kind: CollectionAgent
metadata:
  name: signoz
  annotations:
    foundry.signoz.io/ecs-region: <aws-region>
    foundry.signoz.io/ecs-cluster-arn: <ecs-cluster-arn>
spec:
  deployment:
    platform: aws
    mode: ecs
    flavor: terraform
  collector:
    kind: agent
    spec:
      env:
        SIGNOZ_INGESTION_ENDPOINT: https://ingest.<region>.signoz.cloud:443
        SIGNOZ_INGESTION_KEY: <your-ingestion-key>
        OTEL_RESOURCE_ATTRIBUTES: deployment.environment=<DEPLOYMENT_ENVIRONMENT>
      config:
        data:
          collector/agent/agent.yaml: |
            exporters:
              otlphttp/signoz:
                headers:
                  signoz-ingestion-key: ${env:SIGNOZ_INGESTION_KEY}
```

**Verify these values:**

- `<aws-region>`: The AWS region of your ECS cluster, for example `us-east-1`. Terraform creates every resource in this region.
- `<ecs-cluster-arn>`: The ARN of your ECS cluster, from the cluster's page in the <a href="https://console.aws.amazon.com/ecs/v2/clusters" target="_blank" rel="noopener noreferrer nofollow">Amazon ECS console</a> or from `aws ecs list-clusters`. The collector runs on every container instance of this cluster.
- `<region>`: Your SigNoz Cloud [region](https://signoz.io/docs/ingestion/signoz-cloud/overview/#endpoint).
- `<your-ingestion-key>`: Your SigNoz Cloud [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/). It is set as a plain environment variable in the collector's task definition.
- `<DEPLOYMENT_ENVIRONMENT>`: Your deployment environment, for example `staging` or `production`. It becomes `deployment.environment` on every signal the collector sends.

For every option of this casting, see the <a href="https://github.com/SigNoz/foundry/tree/main/docs/examples/collectionagent/aws/ecs/terraform" target="_blank" rel="noopener noreferrer nofollow">ECS EC2 Terraform example</a>.

</TabItem>
<TabItem value="external" label="External">

<Admonition type="warning" title="Before you install on external instances">
Each external instance needs:

- Docker Engine 25 or newer. The `docker_stats` receiver uses Docker Engine API version 1.44.
- Outbound access to AWS AppConfig, `public.ecr.aws`, Docker Hub, and your SigNoz endpoint. The task pulls its images from `public.ecr.aws` and Docker Hub, and the AppConfig agent container fetches the collector config from AWS AppConfig.
- Task IAM roles enabled for the `host` network mode, since the AppConfig agent container reads the config with the task role. The `ecs-init` package that the ECS Anywhere install script installs enables them. For an ECS agent you run another way, see <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html#enable_task_iam_roles" target="_blank" rel="noopener noreferrer nofollow">External instance additional configuration</a>.

Tasks on external instances use the `bridge`, `host`, or `none` network mode. The `awsvpc` network mode is not available on them.
</Admonition>

This casting sets the launch type to `EXTERNAL` with two patches on the generated Terraform. It detects the host with the `system` detector, since external instances have no EC2 instance metadata, and it adds the `/var/log/syslog` and `/var/log/auth.log` files that Ubuntu writes:

```yaml:casting.yaml minimap defaultCollapsed
apiVersion: v1alpha1
kind: CollectionAgent
metadata:
  name: signoz
  annotations:
    foundry.signoz.io/ecs-region: <aws-region>
    foundry.signoz.io/ecs-cluster-arn: <ecs-cluster-arn>
spec:
  deployment:
    platform: aws
    mode: ecs
    flavor: terraform
  collector:
    kind: agent
    spec:
      env:
        SIGNOZ_INGESTION_ENDPOINT: https://ingest.<region>.signoz.cloud:443
        SIGNOZ_INGESTION_KEY: <your-ingestion-key>
        OTEL_RESOURCE_ATTRIBUTES: deployment.environment=<DEPLOYMENT_ENVIRONMENT>
      config:
        data:
          collector/agent/agent.yaml: |
            exporters:
              otlphttp/signoz:
                headers:
                  signoz-ingestion-key: ${env:SIGNOZ_INGESTION_KEY}
            processors:
              resourcedetection:
                detectors: [env, system]
            receivers:
              filelog/host:
                include:
                  - /hostfs/var/log/messages
                  - /hostfs/var/log/secure
                  - /hostfs/var/log/syslog
                  - /hostfs/var/log/auth.log
                  - /hostfs/var/log/ecs/*.log
  patches:
    - target: collectionagent/collector/agent/collector.tf.json
      operations:
        - op: replace
          path: /resource/aws_ecs_task_definition/collector_agent/requires_compatibilities/0
          value: EXTERNAL
        - op: replace
          path: /resource/aws_ecs_service/collector_agent/launch_type
          value: EXTERNAL
```

**Verify these values:**

- `<aws-region>`: The AWS region of your ECS cluster, for example `us-east-1`. Terraform creates every resource in this region.
- `<ecs-cluster-arn>`: The ARN of the ECS cluster your external instances are registered to, from the cluster's page in the <a href="https://console.aws.amazon.com/ecs/v2/clusters" target="_blank" rel="noopener noreferrer nofollow">Amazon ECS console</a> or from `aws ecs list-clusters`. The collector runs on every external instance of this cluster.
- `<region>`: Your SigNoz Cloud [region](https://signoz.io/docs/ingestion/signoz-cloud/overview/#endpoint).
- `<your-ingestion-key>`: Your SigNoz Cloud [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/). It is set as a plain environment variable in the collector's task definition.
- `<DEPLOYMENT_ENVIRONMENT>`: Your deployment environment, for example `staging` or `production`. It becomes `deployment.environment` on every signal the collector sends.

For every option of the casting this one patches, see the <a href="https://github.com/SigNoz/foundry/tree/main/docs/examples/collectionagent/aws/ecs/terraform" target="_blank" rel="noopener noreferrer nofollow">ECS EC2 Terraform example</a>.

</TabItem>
</Tabs>

<Admonition type="info" title="Use your own IAM roles" defaultCollapsed="true">
By default, Terraform creates two IAM roles: the task role `signoz-collectionagent-iam-task`, with read access to the collector's AWS AppConfig configuration, and the task execution role `signoz-collectionagent-iam-exec`. To use roles you manage instead, add either or both annotations under `metadata`:

```yaml
metadata:
  name: signoz
  annotations:
    foundry.signoz.io/ecs-region: <aws-region>
    foundry.signoz.io/ecs-cluster-arn: <ecs-cluster-arn>
    foundry.signoz.io/ecs-task-role-arn: <task-role-arn>
    foundry.signoz.io/ecs-task-execution-role-arn: <task-execution-role-arn>
```

**Verify these values:**

- `<task-role-arn>`: The ARN of an IAM role that `ecs-tasks.amazonaws.com` can assume, with the `appconfig:StartConfigurationSession` and `appconfig:GetLatestConfiguration` actions. The AppConfig agent container uses it to fetch the collector config. See <a href="https://docs.aws.amazon.com/appconfig/latest/userguide/appconfig-integration-containers-agent.html" target="_blank" rel="noopener noreferrer nofollow">AWS AppConfig Agent with Amazon ECS</a>.
- `<task-execution-role-arn>`: The ARN of an IAM role that `ecs-tasks.amazonaws.com` can assume to pull the images and start the task, for example one with the `AmazonECSTaskExecutionRolePolicy` managed policy.

The role names Terraform creates start with `metadata.name`.
</Admonition>

### Step 3: Deploy

Run this from the directory that contains `casting.yaml`:

```bash
foundryctl cast -f casting.yaml
```

This command:

- checks that `terraform` is on your `PATH`, then writes the Terraform root `pours/collectionagent/collector/agent`;
- runs `terraform init`, `terraform plan -out=tfplan`, and `terraform apply tfplan` in that root, with the AWS credentials Terraform finds on this machine, and applies the plan without a confirmation prompt;
- creates the AWS AppConfig application that holds the collector config, the `signoz-collector-agent` task definition, and the `signoz-collector-agent` daemon service on your cluster, plus the IAM roles you did not state.

Terraform keeps its state in `pours/collectionagent/collector/agent/terraform.tfstate`. Keep that file, and run every later command from the same directory: later casts and the removal read it.

Run the same command again after editing `casting.yaml` to apply the change.

<Admonition type="tip" title="Run Terraform yourself" defaultCollapsed="true">
To run Terraform directly, generate the Terraform root and apply it. Run this from the directory that contains `casting.yaml`:

```bash
foundryctl forge -f casting.yaml   # writes the Terraform root under pours/collectionagent/collector/agent
terraform -chdir=pours/collectionagent/collector/agent init
terraform -chdir=pours/collectionagent/collector/agent plan -out=tfplan
terraform -chdir=pours/collectionagent/collector/agent apply tfplan
```

The plan lists every resource before you apply it.
</Admonition>

### Step 4: Verify the Collection Agent

Run this on the machine where you use the AWS CLI to check that the daemon service runs one collector task on every instance:

```bash
aws ecs describe-services --region <aws-region> --cluster <ecs-cluster-arn> \
  --services signoz-collector-agent \
  --query 'services[0].{status:status,launchType:launchType,schedulingStrategy:schedulingStrategy,desiredCount:desiredCount,runningCount:runningCount}'
```

**Verify these values:**

- `<aws-region>`: The region you set in `casting.yaml`.
- `<ecs-cluster-arn>`: The cluster ARN you set in `casting.yaml`.

The output should look similar to the following, with `runningCount` equal to `desiredCount`, the number of instances in the cluster. `launchType` is `EXTERNAL` on external instances, and the counts vary:

```output
{
    "status": "ACTIVE",
    "launchType": "EC2",
    "schedulingStrategy": "DAEMON",
    "desiredCount": 3,
    "runningCount": 3
}
```

Then run this on a container instance to check the collector's health endpoint:

```bash
curl -fsS localhost:13133/healthz
```

The output should look similar to the following. The timestamps vary:

```output
{"status":"Server available","upSince":"2026-10-16T06:39:18.210100752Z","uptime":"2m3.51s"}
```

In SigNoz, open **Infrastructure Monitoring** and its [Hosts](https://signoz.io/docs/infrastructure-monitoring/host-monitoring/) view. Each instance shows under its `host.name`: the instance's private DNS name on EC2, or its hostname on an external instance. Then open [Logs](https://signoz.io/docs/logs-management/overview/) and filter by `service.name`: the instance's own logs show as `ecs-host`, and container logs show under their task family once the task definition sets the log labels in [Collect Container Logs](https://signoz.io/docs/opentelemetry-collection-agents/ecs/ec2/configure/#collect-container-logs).

## Customize the Collection Agent

Every change follows the same loop: edit `casting.yaml`, then run `foundryctl cast -f casting.yaml` again.

- **Collector settings** (image, environment): set them in the collector's `spec` (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#spec-fields" target="_blank" rel="noopener noreferrer nofollow">spec fields</a>). For example, to pin the collector image:

  ```yaml
  spec:
    collector:
      spec:
        image: otel/opentelemetry-collector-contrib:0.139.0
  ```

- **Collector config** (receivers, processors, pipelines): add it under `spec.collector.spec.config.data`, keyed `collector/agent/agent.yaml`, in the same block that holds the `otlphttp/signoz` header. It merges into the generated config (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#custom-config-files" target="_blank" rel="noopener noreferrer nofollow">custom config files</a>), and a changed config registers a new task revision that the daemon service rolls out to every instance. For example, to collect host metrics every 30s:

  ```yaml
  spec:
    collector:
      spec:
        config:
          data:
            collector/agent/agent.yaml: |
              receivers:
                hostmetrics:
                  collection_interval: 30s
  ```

- **Terraform** (task definition, service): add <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/patches.md" target="_blank" rel="noopener noreferrer nofollow">patches</a> under `spec.patches` against `collectionagent/collector/agent/collector.tf.json`. The collector container is `/locals/containers_collector_agent/1`, the AppConfig agent container is `/locals/containers_collector_agent/0`, and the daemon service is `/resource/aws_ecs_service/collector_agent`. For example, to reserve more memory for the collector:

  ```yaml
  spec:
    patches:
      - target: collectionagent/collector/agent/collector.tf.json
        operations:
          - op: replace
            path: /locals/containers_collector_agent/1/memoryReservation
            value: 1024
  ```

  Collector config changes go through `config.data`, which records the config's digest in the task definition so that every change rolls out. Keep patches to the Terraform files.

Each run regenerates the files under `pours/` and keeps `terraform.tfstate`, so keep every change in `casting.yaml`.

## Remove the Collection Agent

Run this from the directory that contains `casting.yaml`:

```bash
terraform -chdir=pours/collectionagent/collector/agent destroy
```

Terraform lists what it removes and asks you to confirm with `yes`. It removes the daemon service, which stops the collector on every instance, its task definition, the AWS AppConfig application, and the IAM roles it created. Roles you stated through annotations stay. Terraform reads `terraform.tfstate` in that directory and uses the same AWS credentials as `foundryctl cast`.

## Troubleshooting
</ToggleHeading>

### The collector task is not placed on an instance

Run this on the machine where you use the AWS CLI to read the service's latest events:

```bash
aws ecs describe-services --region <aws-region> --cluster <ecs-cluster-arn> \
  --services signoz-collector-agent --query 'services[0].events[:5].message'
```

Replace `<aws-region>` and `<ecs-cluster-arn>` with the values in `casting.yaml`. The events include `service signoz-collector-agent was unable to place a task because no container instance met all of its requirements. The closest matching container-instance <container-instance-id> is already using a port required by your task.`

**Cause:** another task on that instance holds host port 4317 or 4318, for example another OpenTelemetry Collector running as a daemon service.

**Fix:** list the cluster's services with `aws ecs list-services --region <aws-region> --cluster <ecs-cluster-arn>`, then delete the service that holds the ports or move its ports. The daemon service places its task on that instance again on its own.

After the fix, the Step 4 command shows `runningCount` equal to `desiredCount`.

### The AppConfig agent container never turns healthy

In the Step 4 command, `runningCount` stays below `desiredCount`. Run this on a container instance to see the AppConfig agent container's status:

```bash
docker ps -a --filter label=com.amazonaws.ecs.container-name=signoz-collector-appconfig-agent --format '{{.Status}}'
```

The status shows `(unhealthy)`. The collector starts only once this container is healthy, that is once it has written the collector config. To see the error it gets from AWS AppConfig, read its logs:

```bash
docker logs --since 10m $(docker ps -aq --filter label=com.amazonaws.ecs.container-name=signoz-collector-appconfig-agent | head -n 1)
```

**Cause:** the container has no AWS credentials that can read the config. Either the task role you stated with `foundry.signoz.io/ecs-task-role-arn` lacks `appconfig:StartConfigurationSession` and `appconfig:GetLatestConfiguration`, or the instance hands no task-role credentials to tasks in the `host` network mode. The second happens when the instance's ECS agent runs without the `ecs-init` package that the Amazon ECS-optimized AMIs and the ECS Anywhere install script set up.

**Fix:** add both actions to the task role, or enable task IAM roles for the `host` network mode as <a href="https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html#enable_task_iam_roles" target="_blank" rel="noopener noreferrer nofollow">External instance additional configuration</a> describes; the same settings apply to EC2 instances. The daemon service replaces the unhealthy task on its own.

After the fix, the Step 4 command shows `runningCount` equal to `desiredCount`, and the health endpoint answers on the instance.

### terraform plan rejects the region or the cluster ARN

`foundryctl cast -f casting.yaml` stops at `terraform plan` with `Error: Invalid value for variable` and one of these messages:

```output
aws_region must be a region identifier such as us-east-1.
cluster_arn must be the ARN of an ECS cluster.
```

**Cause:** the `foundry.signoz.io/ecs-region` or `foundry.signoz.io/ecs-cluster-arn` annotation is missing or malformed. The region must look like `us-east-1`, and the cluster ARN must start with `arn:aws:ecs:`. A role annotation that is not an IAM role ARN fails the same way, with `task_role_arn must be the ARN of an IAM role.` or `execution_role_arn must be the ARN of an IAM role.`

**Fix:** set the annotation under `metadata.annotations` in `casting.yaml`, as in Step 2, then run `foundryctl cast -f casting.yaml` again from the directory that contains it.

After the fix, `terraform plan` lists the resources to create, and the apply creates them.

### terraform plan finds no AWS credentials

`foundryctl cast -f casting.yaml` stops at `terraform plan` with `Error: No valid credential sources found`.

**Cause:** Terraform's AWS provider found no credentials on the machine where you run `foundryctl`.

**Fix:** sign in with the AWS CLI or select a profile, for example `export AWS_PROFILE=<profile-name>`, in the shell you run `foundryctl` from. Replace `<profile-name>` with a profile from `aws configure list-profiles`. For every way to pass credentials, see the <a href="https://registry.terraform.io/providers/hashicorp/aws/latest/docs#authentication-and-configuration" target="_blank" rel="noopener noreferrer nofollow">AWS provider authentication docs</a>. Then run this on the machine where you run Terraform to check which identity it resolves:

```bash
aws sts get-caller-identity
```

After the fix, the command prints your account and role, and `foundryctl cast -f casting.yaml` gets past `terraform plan`.
