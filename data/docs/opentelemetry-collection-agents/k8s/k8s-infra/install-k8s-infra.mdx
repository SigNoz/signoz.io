This guide explains how to install the K8s Infra collection agent on a Kubernetes cluster, with the `k8s-infra` Helm chart, or with Foundry through Helm or Kustomize.

## Prerequisites

- A Kubernetes cluster.
- `kubectl` configured to reach the cluster.
- For a Helm-based setup, Helm 3 installed on the same machine.
- A SigNoz to send data to: [SigNoz Cloud](https://signoz.io/teams/) or a [self-hosted SigNoz](https://signoz.io/docs/install/self-host/).

## Install with the Helm CLI

### Step 1: Add the Helm repository

Run this on the machine where you use `kubectl`:

```bash
helm repo add signoz https://charts.signoz.io
helm repo update
```

### Step 2: Create override-values.yaml

Create a file named `override-values.yaml` with the values for your Kubernetes platform:

<Admonition type="info" title="Using Self-Hosted SigNoz?" defaultCollapsed="true">
Most steps are identical. To adapt this guide, update the endpoint and remove the ingestion key as shown in [Cloud → Self-Hosted](https://signoz.io/docs/ingestion/cloud-vs-self-hosted/?ingestion-client=collection-agent&collection-agent=k8s-infra#cloud-to-self-hosted).
</Admonition>

### Step 3: Install the chart

Run this from the directory that contains `override-values.yaml`:

```bash
helm install my-release signoz/k8s-infra -f override-values.yaml
```

Helm installs the release `my-release` into the namespace of your current `kubectl` context, `default` unless you set another.

### Step 4: Verify the Collection Agent

Run this on the machine where you use `kubectl` to check that the pods are running:

```bash
kubectl get pods
```

The output should look similar to the following, with one `my-release-k8s-infra-otel-agent` pod per node. Pod suffixes vary, and if SigNoz runs in the same namespace its pods are listed too:

```output
NAME                                                    READY   STATUS    RESTARTS   AGE
my-release-k8s-infra-otel-agent-7xk2p                   1/1     Running   0          2m
my-release-k8s-infra-otel-agent-q9m4d                   1/1     Running   0          2m
my-release-k8s-infra-otel-deployment-6d9c7b8f5c-k2x9p   1/1     Running   0          2m
```

In SigNoz, open the [Kubernetes Monitoring](https://signoz.io/docs/infrastructure-monitoring/kubernetes-monitoring/) views under **Infrastructure Monitoring**. The **Clusters** view lists your cluster under the name you set as `<CLUSTER_NAME>`, and the **Pods** and **Nodes** views fill in as data arrives. Check **Logs Explorer** to confirm container logs and Kubernetes events are flowing.

## Customize the Collection Agent

Every change follows the same loop: edit `override-values.yaml`, then run this from the directory that contains it:

```bash
helm upgrade my-release signoz/k8s-infra -f override-values.yaml
```

- **Collector config** (presets, receivers, pipelines): see [Configure K8s Infra](https://signoz.io/docs/opentelemetry-collection-agents/k8s/k8s-infra/configure-k8s-infra/).
- **Chart values**: see the <a href="https://github.com/SigNoz/charts/tree/main/charts/k8s-infra" target="_blank" rel="noopener noreferrer nofollow">k8s-infra chart</a> for every setting.
- **Chart version**: add `--version <chart-version>` to `helm install` and `helm upgrade`. Versions are listed in the <a href="https://github.com/SigNoz/charts/releases" target="_blank" rel="noopener noreferrer nofollow">SigNoz charts releases</a>.

**Verify these values:**

- `<chart-version>`: A `k8s-infra` chart version from the SigNoz charts releases, for example `0.17.1`.

## Troubleshooting
</ToggleHeading>

### helm install fails with `cannot re-use a name that is still in use`

Run this on the machine where you use `kubectl` to list the releases in the current namespace:

```bash
helm list
```

**Cause:** the release `my-release` already exists.

**Fix:** apply your changes with `helm upgrade`, as shown under Customize the Collection Agent.

After the fix, `kubectl get pods` shows the agent pods as `Running`.

### Agent pod stays Pending

Run this on the machine where you use `kubectl` to see why the pod is unscheduled:

```bash
kubectl describe pod <pod-name>
```

Replace `<pod-name>` with the agent pod's name from `kubectl get pods`.

**Cause:** another collector holds host ports `4317`, `4318`, `8888`, and `13133` on the node, for example an agent installed with Foundry. This happens on every platform except GKE Autopilot, where the agent binds no host ports.

**Fix:** keep one of the two agents and remove the other.

After the fix, `kubectl get pods` shows one agent pod per node as `Running`.

### On GKE Autopilot the agent DaemonSet has no pods

Run this on the machine where you use `kubectl` to see the DaemonSet's events:

```bash
kubectl describe daemonset my-release-k8s-infra-otel-agent
```

The events show the pods denied by an Autopilot policy (`denied by autogke-`).

**Cause:** the values ask for host ports and host paths that GKE Autopilot denies.

**Fix:** use the **GKE (Autopilot)** values from Step 2, which set `global.cloud: gcp/autogke`, and run the `helm upgrade` command under Customize the Collection Agent.

After the fix, `kubectl get pods` shows one agent pod per node.

### Agent logs a `root_path` warning on GKE Autopilot

Run this on the machine where you use `kubectl` to see the agent's logs:

```bash
kubectl logs <pod-name>
```

Replace `<pod-name>` with the agent pod's name from `kubectl get pods`. The logs show a warning that starts with ``No `root_path` config set when running in docker environment``.

**Cause:** on GKE Autopilot the agent has no host root to read, so the `hostmetrics` receiver runs without `root_path` and reports the agent container's filesystem.

**Fix:** none needed. Node disk and network metrics come from the `kubeletstats` receiver as `k8s.node.filesystem.*` and `k8s.node.network.*`.

The agent keeps running: `kubectl get pods` shows its pods as `Running`.

### Agent pods stay in ErrImagePull

Run this on the machine where you use `kubectl` to see the pull error:

```bash
kubectl describe pod <pod-name>
```

Replace `<pod-name>` with the agent pod's name from `kubectl get pods`. The events show `ErrImagePull` or `ImagePullBackOff` with `no match for platform in manifest`.

**Cause:** the collector image's OS does not match the node's OS, for example the Windows image on a Linux node.

**Fix:** keep each agent on nodes of its OS: set `nodeSelector` under `otelAgent` and `otelDeployment` in `override-values.yaml`, for example `kubernetes.io/os: windows` for the Windows agent, then run the `helm upgrade` command under Customize the Collection Agent.

After the fix, `kubectl get pods` shows the agent pods as `Running`.

## Install with Foundry and Helm

<Admonition type="info" title="What is Foundry?" defaultCollapsed="true">
Foundry is an open-source CLI that runs your self-hosted observability stack as code. One declarative config provisions the infrastructure, installs the SigNoz backend, and sets up OpenTelemetry collection on bare metal, containers, or Kubernetes. Learn more about <a href="https://github.com/SigNoz/foundry" target="_blank" rel="noopener noreferrer nofollow">Foundry</a>.
</Admonition>

### Step 1: Install foundryctl

Run this on the machine where you use `kubectl`:

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
```

For manual install (Windows PowerShell, air-gapped, etc.) or PATH setup, see the <a href="https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md" target="_blank" rel="noopener noreferrer nofollow">foundry getting-started guide</a>.

### Step 2: Create casting.yaml

Create a file named `casting.yaml` for your Kubernetes platform, with one document for each collector described in [How it works](https://signoz.io/docs/opentelemetry-collection-agents/k8s/k8s-infra/overview/#how-it-works-the-otelagent-and-oteldeployment):

<Admonition type="info" title="Using Self-Hosted SigNoz?" defaultCollapsed="true">
Most steps are identical. To adapt this guide, update the endpoint and remove the ingestion key as shown in [Cloud → Self-Hosted](https://signoz.io/docs/ingestion/cloud-vs-self-hosted/?ingestion-client=collection-agent&collection-agent=foundry#cloud-to-self-hosted).
</Admonition>

## Customize the Collection Agent

Every change follows the same loop: edit `casting.yaml`, then run `foundryctl cast -f casting.yaml` again.

- **Collector settings** (image, environment): set them in the collector's `spec` (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#spec-fields" target="_blank" rel="noopener noreferrer nofollow">spec fields</a>). For example, to pin the collector image:

  ```yaml
  spec:
    collector:
      spec:
        image: otel/opentelemetry-collector-contrib:0.139.0
  ```

- **Collector config** (receivers, processors, pipelines): add it under `spec.collector.spec.config.data`, keyed `collector/agent/agent.yaml` or `collector/deployment/deployment.yaml`. It merges into the generated config (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#custom-config-files" target="_blank" rel="noopener noreferrer nofollow">custom config files</a>). For example, to scrape kubelet metrics every 60s:

  ```yaml
  spec:
    collector:
      spec:
        config:
          data:
            collector/agent/agent.yaml: |
              receivers:
                kubeletstats:
                  collection_interval: 60s
  ```

- **Chart values** (resources, tolerations, node selector): add <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/patches.md" target="_blank" rel="noopener noreferrer nofollow">patches</a> under `spec.patches` against `collectionagent/collector/agent/values.yaml` or `collectionagent/collector/deployment/values.yaml`. For example, to set the agent's resource requests:

  ```yaml
  spec:
    patches:
      - target: collectionagent/collector/agent/values.yaml
        operations:
          - op: add
            path: /otelAgent/resources
            value:
              requests:
                cpu: 200m
                memory: 256Mi
  ```

  Each run regenerates the files under `pours/`, so keep every change in `casting.yaml`.

## Troubleshooting
</ToggleHeading>

### Agent pod stays Pending

Run this on the machine where you use `kubectl` to see why the pod is unscheduled:

```bash
kubectl describe pod -n signoz <pod-name>
```

Replace `<pod-name>` with the agent pod's name from `kubectl get pods -n signoz`.

**Cause:** another collector holds host ports `4317`, `4318`, `8888`, and `13133` on the node, for example a `k8s-infra` release installed with Helm. This happens on every platform except GKE Autopilot, where the agent binds no host ports.

**Fix:** keep one of the two agents and remove the other.

After the fix, `kubectl get pods -n signoz` shows one agent pod per node as `Running`.

### On GKE Autopilot the agent DaemonSet has no pods

Run this on the machine where you use `kubectl` to see the DaemonSet's events:

```bash
kubectl describe daemonset -n signoz signoz-collector-agent
```

The events show the pods denied by an Autopilot policy (`denied by autogke-`).

**Cause:** the casting asks for host ports and host paths that GKE Autopilot denies.

**Fix:** use the **GKE (Autopilot)** casting from Step 2 and run `foundryctl cast -f casting.yaml` again from the directory that contains it.

After the fix, `kubectl get pods -n signoz` shows one agent pod per node.

### Agent logs a `root_path` warning on GKE Autopilot

Run this on the machine where you use `kubectl` to see the agent's logs:

```bash
kubectl logs -n signoz <pod-name>
```

Replace `<pod-name>` with the agent pod's name from `kubectl get pods -n signoz`. The logs show a warning that starts with ``No `root_path` config set when running in docker environment``.

**Cause:** on GKE Autopilot the agent has no host root to read, so the `hostmetrics` receiver runs without `root_path` and reports the agent container's filesystem.

**Fix:** none needed. Node disk and network metrics come from the `kubeletstats` receiver as `k8s.node.filesystem.*` and `k8s.node.network.*`.

The agent keeps running: `kubectl get pods -n signoz` shows its pods as `Running`.

### Agent pods stay in ErrImagePull

Run this on the machine where you use `kubectl` to see the pull error:

```bash
kubectl describe pod -n signoz <pod-name>
```

Replace `<pod-name>` with the agent pod's name from `kubectl get pods -n signoz`. The events show `ErrImagePull` or `ImagePullBackOff` with `no match for platform in manifest`.

**Cause:** the collector image's OS does not match the node's OS, for example the Windows image on a Linux node.

**Fix:** keep each agent on nodes of its OS: add a patch on `collectionagent/collector/agent/values.yaml` that adds `/otelAgent/nodeSelector`, and one on `collectionagent/collector/deployment/values.yaml` that adds `/otelDeployment/nodeSelector`, for example `kubernetes.io/os: windows`. Then run `foundryctl cast -f casting.yaml` again from the directory that contains it.

After the fix, `kubectl get pods -n signoz` shows the agent pods as `Running`.

### foundryctl cast reaches the wrong cluster or none

Run this on the machine where you run `foundryctl` to see which cluster it uses:

```bash
kubectl config current-context
```

**Cause:** `foundryctl cast` applies to the cluster of your current `kubectl` context.

**Fix:** switch to the right context with `kubectl config use-context <context-name>`, then run `foundryctl cast -f casting.yaml` again from the directory that contains it. Replace `<context-name>` with a context from `kubectl config get-contexts`.

After the fix, `kubectl get pods -n signoz` shows the collector pods on that cluster.

### Step 3: Deploy

Run this from the directory that contains `casting.yaml`:

```bash
foundryctl cast -f casting.yaml
```

This command:

- writes one kustomize root per collector, `pours/collectionagent/collector/agent` and `pours/collectionagent/collector/deployment`;
- applies each root with `kubectl apply -k` to the cluster of your current `kubectl` context;
- creates the `signoz` namespace on the first apply, since each root holds the namespace, the collector's service account, RBAC, Service, workload, and config.

Run the same command again after editing `casting.yaml` to apply the change.

<Admonition type="tip" title="Run kubectl yourself" defaultCollapsed="true">
To run kubectl directly, generate the kustomize roots and apply each one:

```bash
foundryctl forge -f casting.yaml   # writes one kustomize root per collector under pours/collectionagent/collector/
kubectl apply -k pours/collectionagent/collector/agent
kubectl apply -k pours/collectionagent/collector/deployment
```

To see the manifests before you apply them, run `kubectl kustomize` on a root, for example `kubectl kustomize pours/collectionagent/collector/agent`.
</Admonition>

## Customize the Collection Agent

Every change follows the same loop: edit `casting.yaml`, then run `foundryctl cast -f casting.yaml` again.

- **Collector settings** (image, environment): set them in the collector's `spec` (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#spec-fields" target="_blank" rel="noopener noreferrer nofollow">spec fields</a>). For example, to pin the collector image:

  ```yaml
  spec:
    collector:
      spec:
        image: otel/opentelemetry-collector-contrib:0.139.0
  ```

- **Collector config** (receivers, processors, pipelines): add it under `spec.collector.spec.config.data`, keyed `collector/agent/agent.yaml` or `collector/deployment/deployment.yaml`. It merges into the generated config (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#custom-config-files" target="_blank" rel="noopener noreferrer nofollow">custom config files</a>). For example, to scrape kubelet metrics every 60s:

  ```yaml
  spec:
    collector:
      spec:
        config:
          data:
            collector/agent/agent.yaml: |
              receivers:
                kubeletstats:
                  collection_interval: 60s
  ```

- **Manifests** (resources, tolerations, node selector): add <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/patches.md" target="_blank" rel="noopener noreferrer nofollow">patches</a> under `spec.patches` against `collectionagent/collector/agent/workload.yaml` or `collectionagent/collector/deployment/workload.yaml`. For example, to set the agent's resource requests:

  ```yaml
  spec:
    patches:
      - target: collectionagent/collector/agent/workload.yaml
        operations:
          - op: replace
            path: /spec/template/spec/containers/0/resources
            value:
              requests:
                cpu: 200m
                memory: 256Mi
  ```

  Each run regenerates the files under `pours/`, so keep every change in `casting.yaml`.

## Troubleshooting
</ToggleHeading>

### Agent pod stays Pending

Run this on the machine where you use `kubectl` to see why the pod is unscheduled:

```bash
kubectl describe pod -n signoz <pod-name>
```

Replace `<pod-name>` with the agent pod's name from `kubectl get pods -n signoz`.

**Cause:** another collector holds host ports `4317`, `4318`, `8888`, and `13133` on the node, for example a `k8s-infra` release installed with Helm. This happens on every platform except GKE Autopilot, where the agent binds no host ports.

**Fix:** keep one of the two agents and remove the other.

After the fix, `kubectl get pods -n signoz` shows one agent pod per node as `Running`.

### On GKE Autopilot the agent DaemonSet has no pods

Run this on the machine where you use `kubectl` to see the DaemonSet's events:

```bash
kubectl describe daemonset -n signoz signoz-collector-agent
```

The events show the pods denied by an Autopilot policy (`denied by autogke-`).

**Cause:** the casting asks for host ports and host paths that GKE Autopilot denies.

**Fix:** use the **GKE (Autopilot)** casting from Step 2 and run `foundryctl cast -f casting.yaml` again from the directory that contains it.

After the fix, `kubectl get pods -n signoz` shows one agent pod per node.

### Agent logs a `root_path` warning on GKE Autopilot

Run this on the machine where you use `kubectl` to see the agent's logs:

```bash
kubectl logs -n signoz <pod-name>
```

Replace `<pod-name>` with the agent pod's name from `kubectl get pods -n signoz`. The logs show a warning that starts with ``No `root_path` config set when running in docker environment``.

**Cause:** on GKE Autopilot the agent has no host root to read, so the `hostmetrics` receiver runs without `root_path` and reports the agent container's filesystem.

**Fix:** none needed. Node disk and network metrics come from the `kubeletstats` receiver as `k8s.node.filesystem.*` and `k8s.node.network.*`.

The agent keeps running: `kubectl get pods -n signoz` shows its pods as `Running`.

### Agent pods stay in ErrImagePull

Run this on the machine where you use `kubectl` to see the pull error:

```bash
kubectl describe pod -n signoz <pod-name>
```

Replace `<pod-name>` with the agent pod's name from `kubectl get pods -n signoz`. The events show `ErrImagePull` or `ImagePullBackOff` with `no match for platform in manifest`.

**Cause:** the collector image's OS does not match the node's OS, for example the Windows image on a Linux node.

**Fix:** keep each agent on nodes of its OS: add a patch with `op: add` at `/spec/template/spec/nodeSelector` on each collector's workload, `collectionagent/collector/agent/workload.yaml` and `collectionagent/collector/deployment/workload.yaml`, for example `kubernetes.io/os: windows`. Then run `foundryctl cast -f casting.yaml` again from the directory that contains it.

After the fix, `kubectl get pods -n signoz` shows the agent pods as `Running`.

### foundryctl cast reaches the wrong cluster or none

Run this on the machine where you run `foundryctl` to see which cluster it uses:

```bash
kubectl config current-context
```

**Cause:** `foundryctl cast` applies to the cluster of your current `kubectl` context.

**Fix:** switch to the right context with `kubectl config use-context <context-name>`, then run `foundryctl cast -f casting.yaml` again from the directory that contains it. Replace `<context-name>` with a context from `kubectl config get-contexts`.

After the fix, `kubectl get pods -n signoz` shows the collector pods on that cluster.
