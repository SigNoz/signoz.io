The <a href="https://github.com/open-telemetry/opentelemetry-operator" target="_blank" rel="noopener noreferrer nofollow">OpenTelemetry Operator</a> manages OpenTelemetry Collectors and auto-instrumentation in a Kubernetes cluster through custom resources. As a SigNoz collection agent, it runs the two pre-configured collectors described below, which Foundry declares as `OpenTelemetryCollector` resources.

[Install the operator](https://signoz.io/docs/opentelemetry-collection-agents/k8s/otel-operator/install/#install-the-opentelemetry-operator), then [install the collectors](https://signoz.io/docs/opentelemetry-collection-agents/k8s/otel-operator/install/) with Foundry through Helm or Kustomize.

## Architecture

The OpenTelemetry Operator follows a Kubernetes-native approach by leveraging Custom Resources and Controllers. Here's a breakdown of its architecture:

![OpenTelemetry Operator Architecture](/img/docs/otel-operator-arch.webp)

*   **Custom Resources (CRs):** The operator defines Custom Resource Definitions (CRDs) for managing OpenTelemetry components, such as `OpenTelemetryCollector`. These CRs allow you to declare the desired state of your telemetry collection infrastructure.
*   **Controller:** The operator's controller watches for changes in these Custom Resources. When a change is detected, it reconciles the current state of the cluster with the desired state defined in the CRs.
*   **OpenTelemetry Collector:** The controller manages the deployment and configuration of the OpenTelemetry Collector instances based on the information provided in the `OpenTelemetryCollector` CRs.
*   **Auto-instrumentation:** The operator can also manage auto-instrumentation for your applications, ensuring that telemetry data is automatically collected without manual code changes.

For a deeper dive into the architecture, you can explore the <a href="https://github.com/open-telemetry/opentelemetry-operator" target="_blank" rel="noopener noreferrer nofollow">OpenTelemetry Operator GitHub repository</a>.

## Benefits of using the OpenTelemetry Operator

- **Simplified Deployment:** Automates the deployment and scaling of the OpenTelemetry Collector.
- **Centralized Configuration:** Manages Collector configurations through Custom Resources (CRs).
- **Automated Lifecycle Management:** Upgrades the `OpenTelemetryCollector` resources when the operator itself is upgraded, and handles health checks of the Collector.
- **Auto-Instrumentation:** Supports Auto-Instrumentation of the workloads using OpenTelemetry instrumentation libraries.

## OpenTelemetry Operator Deployment Modes

The OpenTelemetry Operator supports four deployment modes through the `OpenTelemetryCollector` Custom Resource, which specifies how the Collector should be installed in your Kubernetes cluster. In every mode the operator owns the workload it creates, so change the Collector, including its version, through the `OpenTelemetryCollector` resource; the operator reverts edits made to the workload directly.

| Mode (`spec.mode`) | What the operator creates | Typical use |
|---|---|---|
| `sidecar` | A Collector container, injected into application pods annotated with `sidecar.opentelemetry.io/inject` | Collecting and processing telemetry inside each application's pod, with fewer network hops |
| `daemonset` | A DaemonSet: one Collector pod on each node | Node-level data, such as host metrics, local log collection, or network monitoring |
| `deployment` (default) | A Deployment | A gateway that receives OTLP data and scales with replicas, or a single Collector that pulls cluster-wide data. Every replica of a Collector that pulls data pulls the same data, so run one replica for it |
| `statefulset` | A StatefulSet: stable pod names and, through `volumeClaimTemplates`, a persistent volume per pod | Collectors that keep state. The operator's Target Allocator, which spreads Prometheus scrape targets across the Collector pods, works with this mode and with `daemonset` |

## How it works

The Collection Agent runs two collectors. Each is an `OpenTelemetryCollector` resource in one of the modes above, from which the operator creates the collector's workload and Services:

| Collector | `spec.mode` | Runs | Collects |
|---|---|---|---|
| Agent (`signoz-collector-agent`) | `daemonset` | One pod per node | Container logs (`filelog/k8s`), host metrics (`hostmetrics`), kubelet metrics (`kubeletstats`), and OTLP from your applications |
| Cluster collector (`signoz-collector-deployment`) | `deployment` | One pod | Cluster metrics (`k8s_cluster`) and Kubernetes events (`k8s_events`) |

Both collectors add Kubernetes and host resource attributes with the `k8sattributes` and `resourcedetection` processors. Cluster-level metrics come from the cluster collector alone, so each Kubernetes object is reported once.

## Auto-instrumentation

The OpenTelemetry Operator greatly simplifies the process of auto-instrumenting your applications. By defining an `Instrumentation` custom resource, you can automatically inject the OpenTelemetry SDK into your application's runtime. This eliminates the need for manual code modifications to collect traces, metrics, and logs.

The operator can inject and configure <a href="https://opentelemetry.io/docs/platforms/kubernetes/operator/automatic/" target="_blank" rel="noopener noreferrer nofollow">OpenTelemetry auto-instrumentation</a> libraries. Currently, Apache HTTPD, .NET, Go, Java, Nginx, Node.js and Python are supported.

To manage automatic instrumentation, the Operator must be configured to identify which pods to instrument and select the appropriate automatic instrumentation for those pods. This configuration is done through the <a href="https://github.com/open-telemetry/opentelemetry-operator/blob/main/docs/api/instrumentations.md" target="_blank" rel="noopener noreferrer nofollow">Instrumentation CRD</a> and adding [Annotations](https://signoz.io/docs/opentelemetry-collection-agents/k8s/otel-operator/configure/#auto-instrumentation-with-opentelemetry-operator) to the workloads.

## K8s-Infra vs OpenTelemetry Operator

When deciding between SigNoz’s **K8s Infra** Collection Agent and the **OpenTelemetry Operator**, the choice often comes down to setup simplicity versus auto-instrumentation. K8s Infra is installed with the `k8s-infra` Helm chart or with Foundry. With Foundry, both Collection Agents run the same SigNoz collector config; the operator manages the collectors through `OpenTelemetryCollector` resources and adds auto-instrumentation.

### Why and When k8s-infra

- **Fast Setup**: Install it with the `k8s-infra` Helm chart or with Foundry, and it collects metrics, traces, logs, and Kubernetes events.
- **SigNoz-Ready**: Pre-configured for SigNoz (dashboards, alerts, integrations work out of the box).
- **Minimal Overhead**: The collectors run as a DaemonSet and a Deployment, with no operator, CRDs, or cert-manager to install.

Use **K8s Infra** when you want a quick, production-ready way to start sending Kubernetes telemetry to SigNoz without learning OTel Collector internals. For more information, refer to the [K8s Infra Collection Agent](https://signoz.io/docs/opentelemetry-collection-agents/k8s/k8s-infra/overview/).

### Why and When OpenTelemetry Operator

- **Auto-Instrumentation**: Injects OpenTelemetry auto-instrumentation (SDKs and language agents) into application pods.
- **K8s-Native Management**: Manages the collectors through `OpenTelemetryCollector` resources.

Use the **Operator** when you require features like auto-instrumentation.

### Recommended Approach

Begin with **K8s Infra** for cluster and infrastructure monitoring: it’s optimized for SigNoz and minimizes operational overhead. Gradually introduce the **Operator** for workloads that require auto-instrumentation, and point its `Instrumentation` resource at the K8s Infra agent (see [Send Data from Applications to the Collector](https://signoz.io/docs/opentelemetry-collection-agents/k8s/k8s-infra/configure-k8s-infra/#send-data-from-applications-to-the-collector)).
