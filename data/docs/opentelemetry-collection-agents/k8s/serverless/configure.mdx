The [install guide](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/install/) provides a working config: the deployment collector collects kubelet metrics from every Fargate node, cluster metrics, Kubernetes events, and data from instrumented applications. The optional sidecar receives an application's telemetry inside its own pod. This page explains what each component in that config does and how to customize it through Foundry's `casting.yaml`.

## Prerequisites

- EKS Fargate Collection Agent installed with Foundry, with or without the OpenTelemetry Operator (see the [install guide](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/install/))
- SigNoz Cloud account or self-hosted SigNoz instance
- Access to the cluster with `kubectl`
- The `casting.yaml` and `foundryctl` you installed with

## Send Data from Applications to the Collector

Kubelet and cluster metrics and Kubernetes events flow as soon as the deployment collector is running.

### Where and how to send data from your application

To send traces, metrics, and logs from an application, instrument it with OpenTelemetry ([language guides](https://signoz.io/docs/instrumentation/)), then set its endpoint on the application's container in its manifest.

In a pod that runs the sidecar, send to the sidecar on `localhost`:

```yaml
env:
  - name: OTEL_EXPORTER_OTLP_ENDPOINT
    value: http://localhost:4318
  - name: OTEL_SERVICE_NAME
    value: <service-name>
```

**Verify these values:**

- `<service-name>`: The name your application shows under in SigNoz.

The sidecar adds the pod's Kubernetes resource attributes. Use port `4317` for OTLP over gRPC.

In any other pod, send to the deployment collector's Service:

<Tabs entityName="controller">
<TabItem value="default" label="K8s Infra" default>

```yaml
env:
  - name: K8S_POD_IP
    valueFrom:
      fieldRef:
        fieldPath: status.podIP
  - name: K8S_POD_UID
    valueFrom:
      fieldRef:
        fieldPath: metadata.uid
  - name: OTEL_EXPORTER_OTLP_ENDPOINT
    value: http://signoz-collector-deployment.signoz.svc.cluster.local:4318
  - name: OTEL_SERVICE_NAME
    value: <service-name>
  - name: OTEL_RESOURCE_ATTRIBUTES
    value: k8s.pod.ip=$(K8S_POD_IP),k8s.pod.uid=$(K8S_POD_UID)
```

</TabItem>
<TabItem value="opentelemetry-operator" label="OpenTelemetry Operator">


- `<service-name>`: The name your application shows under in SigNoz.
- `signoz` in the address: `metadata.name`, which is also the namespace unless the `foundry.signoz.io/kubernetes-namespace` annotation sets another.

With `k8s.pod.ip` and `k8s.pod.uid` set, the deployment collector adds the pod's Kubernetes resource attributes. Use port `4317` for OTLP over gRPC.

Redeploy the application and send it some traffic. Within a minute it shows under **Services** in SigNoz, and its traces carry `k8s.namespace.name` and `k8s.pod.name`.

## Export to SigNoz

Both collectors send every signal to `SIGNOZ_INGESTION_ENDPOINT` over OTLP/HTTP.

For SigNoz Cloud, the install guide's documents add the ingestion key as a header.

## Collect Kubelet Metrics

The deployment collector collects node, pod, container, and volume metrics from the kubelet of each Fargate node, through the Kubernetes API server.

It scrapes every 30s, with the metrics in the table below enabled. To change the interval and enable one more metric, add this under `receivers.receiver_creator.receivers.kubeletstats.config` in the deployment collector's document:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/deployment/deployment.yaml: |
            receivers:
              receiver_creator:
                receivers:
                  kubeletstats:
                    config:
                      collection_interval: 60s
                      metrics:
                        k8s.pod.memory.node.utilization:
                          enabled: true
```

`metrics` is a map, so the metrics you add join Foundry's defaults.

These container-level metrics are off by default upstream and on in Foundry's config. Keep them enabled to retain full container visibility on the [Containers](https://signoz.io/docs/infrastructure-monitoring/kubernetes/containers/) view:

| Metric | Powers |
|---|---|
| `k8s.container.cpu_request_utilization` | CPU request utilization column |
| `k8s.container.cpu_limit_utilization` | CPU limit utilization column |
| `k8s.container.memory_request_utilization` | Memory request utilization column |
| `k8s.container.memory_limit_utilization` | Memory limit utilization column |
| `container.uptime` | Uptime chart |
| `k8s.container.cpu.node.utilization` | Node-utilization chart (CPU) |
| `k8s.container.memory.node.utilization` | Node-utilization chart (memory) |

Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes).

## Collect Cluster Metrics

The deployment collector collects cluster-level metrics from the Kubernetes API server, every 30s.

To change the interval and report ephemeral storage too, add this under `receivers.k8s_cluster` in the deployment collector's document:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/deployment/deployment.yaml: |
            receivers:
              k8s_cluster:
                collection_interval: 60s
                allocatable_types_to_report: [cpu, memory, ephemeral-storage]
```

Lists replace, so `allocatable_types_to_report` holds only the types you list. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes).

## Collect Kubernetes Events

The deployment collector collects Kubernetes events as logs, for all namespaces.

To watch specific namespaces, add this under `receivers.k8s_events` in the deployment collector's document:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/deployment/deployment.yaml: |
            receivers:
              k8s_events:
                namespaces: [default, production]
```

Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes).

## Resource Detection and Kubernetes Attributes

Foundry adds these resource attributes by default, in the deployment collector and the sidecar, so you can filter and group by namespace, workload, or pod in SigNoz. They are the namespace, pod name and UID, node, and owning workload of the pod that sent the data, plus `k8s.cluster.name` from `K8S_CLUSTER_NAME`, `cloud.provider`, `cloud.platform`, and the attributes in the collector's `OTEL_RESOURCE_ATTRIBUTES`. Workloads that run the sidecar under service accounts of their own need `signoz-rolebinding.yaml`, as [Sidecar](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/collector-sidecar/#step-4-add-the-sidecar-to-your-workloads) shows.

To add a pod label as a resource attribute, add this under `processors.k8sattributes` in the deployment collector's document:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/deployment/deployment.yaml: |
            processors:
              k8sattributes:
                extract:
                  labels:
                    - tag_name: service.name
                      key: app.kubernetes.io/name
                      from: pod
```

For the sidecar, add the same block to its document, keyed `collector/sidecar/sidecar.yaml`. Lists replace, so restating `extract.metadata` or `pod_association` drops Foundry's defaults: include every entry you keep, as the warning below describes. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes).

<Admonition type="info" title="Note: extracting labels and annotations from other Kubernetes objects" defaultCollapsed="true">

The `from:` field selects which Kubernetes object the processor reads the label or annotation from. The example above uses `pod`, but other workload kinds are supported as well, and each reads from its own metadata.

Refer to the processor's <a href="https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/k8sattributesprocessor/README.md" target="_blank" rel="noopener noreferrer nofollow">OpenTelemetry documentation</a> for the full list of supported sources and the exact behavior of each.

</Admonition>

<Admonition type="info" title="Warning: customizing pod_association replaces all defaults" defaultCollapsed="true">

If telemetry suddenly stops getting Kubernetes attributes (`k8s.pod.name`, `k8s.namespace.name`, etc.) after a config change, a change to `pod_association` is the most likely cause.

A `pod_association` list that drops Foundry's default rules leaves the collector unable to associate telemetry with a pod, and `extract.labels` / `extract.annotations` stop producing attributes.

If you customize `pod_association`, restate the default rules alongside your additions. Run `foundryctl forge -f casting.yaml` and copy them from the generated files under `pours/collectionagent/collector/`.

</Admonition>

## Scrape Prometheus Metrics from pods

The deployment collector can scrape metrics from pods that expose a Prometheus endpoint. In `casting.yaml`, add this to the deployment collector's document to scrape pods annotated `signoz.io/scrape: "true"` every 60s, at the path in `signoz.io/path` and the port in `signoz.io/port`:

```yaml defaultCollapsed
spec:
  collector:
    spec:
      config:
        data:
          collector/deployment/deployment.yaml: |
            receivers:
              prometheus/scraper:
                config:
                  scrape_configs:
                    - job_name: signoz-scraper
                      scrape_interval: 60s
                      kubernetes_sd_configs:
                        - role: pod
                      relabel_configs:
                        - source_labels: [__meta_kubernetes_pod_annotation_signoz_io_scrape]
                          action: keep
                          regex: "true"
                        - source_labels: [__meta_kubernetes_pod_annotation_signoz_io_path]
                          action: replace
                          regex: (.+)
                          target_label: __metrics_path__
                        - source_labels: [__meta_kubernetes_pod_ip, __meta_kubernetes_pod_annotation_signoz_io_port]
                          action: replace
                          separator: ":"
                          target_label: __address__
            service:
              pipelines:
                metrics:
                  receivers: [otlp/http, otlp/grpc, k8s_cluster, receiver_creator, prometheus/scraper]
```

Lists replace, so the snippet restates the `metrics` pipeline's default receivers. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes).

## Tune Batch and Memory Limiter

Foundry batches telemetry before export, in the deployment collector and the sidecar, with `send_batch_size: 1000`, `send_batch_max_size: 2048`, and `timeout: 10s`. For sizing guidance, see [Collector Configuration Best Practices](https://signoz.io/docs/opentelemetry-collection-agents/opentelemetry-collector/configuration/#best-practices). To change the batch sizes, add this under `processors.batch` in the deployment collector's document:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/deployment/deployment.yaml: |
            processors:
              batch:
                send_batch_size: 15000
                send_batch_max_size: 20000
```

For the sidecar, add the same block to its document, keyed `collector/sidecar/sidecar.yaml`. Keys you leave out keep Foundry's values. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes).

Each collector limits its memory use to 80% of its container's memory limit, with a spike allowance of 20%, so it follows the limits in the next section.

### Resource Requests and Limits

Fargate sizes each pod from the CPU and memory requests of its containers, rounded up to one of the Fargate configurations. For the configurations, see <a href="https://docs.aws.amazon.com/eks/latest/userguide/fargate-pod-configuration.html" target="_blank" rel="noopener noreferrer nofollow">Fargate pod configuration</a>.

Foundry's defaults set requests and limits to the same values:

- The deployment collector requests 250m CPU and 512Mi memory, so its pod runs in the 0.25 vCPU / 1 GB Fargate configuration.
- The sidecar requests 200m CPU and 256Mi memory in each pod that runs it. A pod whose containers request 0.25 vCPU and 512 MiB runs in the 0.5 vCPU / 1 GB configuration with the sidecar.

In `casting.yaml`, add a patch to the deployment collector's document to raise its requests and limits:

<Tabs entityName="controller">
<TabItem value="default" label="K8s Infra" default>

```yaml
spec:
  patches:
    - target: collectionagent/collector/deployment/workload.yaml
      operations:
        - op: replace
          path: /spec/template/spec/containers/0/resources
          value:
            requests:
              cpu: 500m
              memory: 1Gi
            limits:
              cpu: 500m
              memory: 1Gi
```

For the sidecar, add a patch to its document that sets the resources of its container in `patch.yaml`, and in `patch-cronjob.yaml` if a CronJob takes the sidecar:

```yaml defaultCollapsed
spec:
  patches:
    - target: collectionagent/collector/sidecar/patch.yaml
      operations:
        - op: replace
          path: /spec/template/spec/initContainers/0/resources
          value:
            requests:
              cpu: 250m
              memory: 512Mi
            limits:
              cpu: 250m
              memory: 512Mi
    - target: collectionagent/collector/sidecar/patch-cronjob.yaml
      operations:
        - op: replace
          path: /spec/jobTemplate/spec/template/spec/initContainers/0/resources
          value:
            requests:
              cpu: 250m
              memory: 512Mi
            limits:
              cpu: 250m
              memory: 512Mi
```

</TabItem>
<TabItem value="opentelemetry-operator" label="OpenTelemetry Operator">

```yaml
spec:
  patches:
    - target: collectionagent/collector/deployment/opentelemetrycollector.yaml
      operations:
        - op: replace

            requests:
              cpu: 500m

              cpu: 500m
```

## Add Custom Processors to Pipelines

A processor transforms or enriches telemetry once a pipeline lists it under `processors`.

Foundry's pipelines are `traces`, `metrics` and `logs`, in the deployment collector and the sidecar. In `casting.yaml`, add this to the deployment collector's document to define a processor and add it to the `traces` pipeline:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/deployment/deployment.yaml: |
            processors:
              attributes/team:
                actions:
                  - key: team
                    value: platform
                    action: insert
            service:
              pipelines:
                traces:
                  processors: [memory_limiter, resourcedetection, resource/identity, k8sattributes, attributes/team, batch]
```

For the sidecar, add the same block to its document, keyed `collector/sidecar/sidecar.yaml`. Lists replace, so restate Foundry's default processors in the order the snippet shows, with yours before `batch`. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes).

## Exposing Ports for Custom Receivers

A receiver that listens on a port needs that port reachable from your applications. This example adds one on port 8125.

In `casting.yaml`, add the `statsd` receiver to the deployment collector's document and list it in the `metrics` pipeline:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/deployment/deployment.yaml: |
            receivers:
              statsd:
                endpoint: 0.0.0.0:8125
            service:
              pipelines:
                metrics:
                  receivers: [otlp/http, otlp/grpc, k8s_cluster, receiver_creator, statsd]
```

Lists replace, so the snippet restates the `metrics` pipeline's default receivers. Then open the port on the collector with a patch in the same document:

<Tabs entityName="controller">
<TabItem value="default" label="K8s Infra" default>

```yaml
spec:
  patches:
    - target: collectionagent/collector/deployment/workload.yaml
      operations:
        - op: add
          path: /spec/template/spec/containers/0/ports/-
          value: {name: statsd, containerPort: 8125, protocol: UDP}
    - target: collectionagent/collector/deployment/service.yaml
      operations:
        - op: add
          path: /spec/ports/-
          value: {name: statsd, port: 8125, targetPort: statsd, protocol: UDP}
```

Your applications reach the receiver on the deployment collector's Service, at `signoz-collector-deployment.signoz.svc.cluster.local:8125`, where `signoz` is the namespace from `metadata.name`.

</TabItem>
<TabItem value="opentelemetry-operator" label="OpenTelemetry Operator">

```yaml
spec:
  patches:
    - target: collectionagent/collector/deployment/opentelemetrycollector.yaml
      operations:
        - op: add
          path: /spec/ports/-
          value: {name: statsd, port: 8125, protocol: UDP}
```

The operator opens the port on the collector's Service, as the <a href="https://github.com/open-telemetry/opentelemetry-operator/blob/v0.139.0/docs/api/opentelemetrycollectors.md" target="_blank" rel="noopener noreferrer nofollow">OpenTelemetryCollector API reference</a> describes for `ports`. Your applications reach the receiver at `signoz-collector-deployment-collector.signoz.svc.cluster.local:8125`, where `signoz` is the namespace from `metadata.name`.

</TabItem>
</Tabs>

In a pod that runs the sidecar, your application reaches the sidecar on `localhost`, so a receiver needs only its config, in the sidecar's document:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/sidecar/sidecar.yaml: |
            receivers:
              statsd:
                endpoint: localhost:8125
            service:
              pipelines:
                metrics:
                  receivers: [otlp/http, otlp/grpc, statsd]
```

Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes).

## Disable Metrics Collection

To turn off kubelet and cluster metrics, add this to the deployment collector's document. It removes `receivers.receiver_creator` and `receivers.k8s_cluster`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/deployment/deployment.yaml: |
            receivers:
              receiver_creator: null
              k8s_cluster: null
            service:
              pipelines:
                metrics:
                  receivers: [otlp/http, otlp/grpc]
```

Lists replace, so the snippet restates the `metrics` pipeline with its two OTLP receivers. Kubernetes events keep flowing. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes).

## Add the Sidecar to More Workloads

Each workload takes the sidecar as [Sidecar](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/collector-sidecar/#step-4-add-the-sidecar-to-your-workloads) shows. To add it to one more workload:

<Tabs entityName="controller">
<TabItem value="default" label="K8s Infra" default>

With a Kustomize patch, add a `target` for the workload under `patches:` in your application's `kustomization.yaml`. A CronJob takes `pours/collectionagent/collector/sidecar/patch-cronjob.yaml` with `kind: CronJob`:

```diff
 patches:
+  - path: pours/collectionagent/collector/sidecar/patch.yaml
+    target:
+      kind: <your-workload-kind>
+      name: <your-workload>
```

**Verify these values:**

- `<your-workload-kind>`: The workload's kind: `Deployment`, `StatefulSet`, `DaemonSet`, or `Job`.
- `<your-workload>`: The workload's name, from its manifest.

If the workload runs under a service account of its own, add the account to the `subjects` of `signoz-rolebinding.yaml`. Then apply your application again.

With the pod template, add the `initContainers` entry and the `volumes` entry of `pours/collectionagent/collector/sidecar/patch.yaml` to the workload's pod template. In a CronJob, the pod template sits under `spec.jobTemplate`. Then apply the workload.

</TabItem>
<TabItem value="opentelemetry-operator" label="OpenTelemetry Operator">

Add the annotation to the workload's pod template:

```diff
 spec:
   template:
     metadata:
+      annotations:
+        sidecar.opentelemetry.io/inject: "signoz-collector-sidecar"
```

A CronJob takes the annotation under `spec.jobTemplate.spec.template.metadata.annotations`. If the workload runs under a service account of its own, add the account to the `subjects` of `signoz-rolebinding.yaml`. Then apply your application again, and the operator injects the sidecar into the workload's new pods.

</TabItem>

## Migrate to Foundry

If you already run the manual sidecar collector from the Manual tab of [Sidecar](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/collector-sidecar/?sidecar-setup=manual), move it to Foundry with these steps.

1. Install foundryctl and create `casting.yaml`, as [Step 1](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/install/#step-1-install-foundryctl) and [Step 2](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/install/#step-2-create-castingyaml) of the install guide show.

2. Add your customizations to `casting.yaml` under `spec.collector.spec.config.data`, keyed `collector/deployment/deployment.yaml` for the deployment collector and `collector/sidecar/sidecar.yaml` for the sidecar, as [Customize the Collection Agent](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/install/#customize-the-collection-agent) shows.

3. Remove the `my-release` chart release. Run this on the machine where you use `kubectl`:

   ```bash
   helm uninstall my-release --namespace <release-namespace>
   ```

   **Verify these values:**

   - `<release-namespace>`: The namespace of the `my-release` release, as `helm list -A` shows.

4. Deploy the deployment collector with Foundry. Run this from the directory that contains `casting.yaml`:

   ```bash
   foundryctl cast -f casting.yaml
   ```

5. Remove the old sidecar from each of your application's Deployments: the `opentelemetry-collector-contrib` container, the `otel-agent-config-vol` volume, and `serviceAccountName: otel-agent-sidecar`.

6. Add Foundry's sidecar as [Sidecar](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/collector-sidecar/#install-the-collection-agent) shows, or point the application at the deployment collector's Service as [Send Data from Applications to the Collector](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#send-data-from-applications-to-the-collector) shows. Then apply your application.

7. Remove the old ConfigMap, service account, and RBAC. Run this on the machine where you use `kubectl`:

   ```bash
   kubectl -n <your-namespace> delete configmap otel-agent-sidecar-config
   kubectl -n <your-namespace> delete serviceaccount otel-agent-sidecar
   kubectl delete clusterrolebinding otel-kubeletstats-proxy
   kubectl delete clusterrole otel-kubeletstats-proxy
   ```

   **Verify these values:**

   - `<your-namespace>`: The namespace of your application pods that ran the old sidecar.

8. Verify the Collection Agent as [Step 4 of the install guide](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/install/#step-4-verify-the-collection-agent) shows.

## Troubleshooting
</ToggleHeading>

### A custom processor does not appear to run

Defining a processor under `processors` renders it into the collector configuration but does not attach it to any pipeline. Confirm the processor is referenced in the relevant pipeline's `processors` list. `config.data` replaces lists, so restate every processor the pipeline still needs. See [Add Custom Processors to Pipelines](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#add-custom-processors-to-pipelines). After applying the change as shown in [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#apply-changes), verify in SigNoz Explorer that the attribute or transformation introduced by the processor is present on the relevant signal.

### Telemetry stopped getting Kubernetes attributes after customizing `pod_association`

A `pod_association` list that drops the default rules leaves the processor unable to associate telemetry with a pod. See the warning under [Resource Detection and Kubernetes Attributes](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#resource-detection-and-kubernetes-attributes) for the rules to keep. After restoring the rules and applying the change, confirm in SigNoz Explorer that resource attributes such as `k8s.pod.name` and `k8s.namespace.name` are populated on traces, metrics, or logs from your workloads.
