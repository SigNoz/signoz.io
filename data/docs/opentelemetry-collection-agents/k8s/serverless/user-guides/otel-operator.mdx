This guide runs the EKS Fargate Collection Agent through the OpenTelemetry Operator. Foundry generates each collector as an `OpenTelemetryCollector` resource, and the operator creates the deployment collector's workload and Service from it. For the sidecar, the operator's webhook injects the collector into each new pod whose template carries the `sidecar.opentelemetry.io/inject` annotation.

## Prerequisites

- An EKS cluster with a <a href="https://docs.aws.amazon.com/eks/latest/userguide/fargate-profile.html" target="_blank" rel="noopener noreferrer nofollow">Fargate profile</a> that selects the collector's namespace and your applications' namespaces.
- `kubectl` configured to reach the cluster, with the AWS CLI and Helm 3 installed on the same machine for the Fargate profile and cert-manager.
- A SigNoz to send data to: [SigNoz Cloud](https://signoz.io/teams/) or a [self-hosted SigNoz](https://signoz.io/docs/install/self-host/).

## Install the Collection Agent

<Admonition type="info" title="What is Foundry?" defaultCollapsed="true">
Foundry is an open-source CLI that runs your self-hosted observability stack as code. One declarative config provisions the infrastructure, installs the SigNoz backend, and sets up OpenTelemetry collection on bare metal, containers, or Kubernetes. Learn more about <a href="https://github.com/SigNoz/foundry" target="_blank" rel="noopener noreferrer nofollow">Foundry</a>.
</Admonition>

### Step 1: Install the OpenTelemetry Operator

Install the OpenTelemetry Operator, which reconciles the `OpenTelemetryCollector` resources Foundry generates for the collectors, and cert-manager, which issues the certificate of the operator's admission webhook. Run these on the machine where you use `kubectl`, with the AWS CLI and Helm 3 installed:

1. Add a Fargate profile that selects the `cert-manager` and `opentelemetry-operator-system` namespaces:

   ```bash
   aws eks create-fargate-profile --cluster-name <cluster-name> \
     --fargate-profile-name opentelemetry-operator \
     --pod-execution-role-arn <pod-execution-role-arn> \
     --selectors namespace=cert-manager namespace=opentelemetry-operator-system
   ```

   **Verify these values:**

   - `<cluster-name>`: Your EKS cluster's name.
   - `<pod-execution-role-arn>`: The ARN of the pod execution role your other Fargate profiles use.

2. Install cert-manager with its webhook on port 10260, since on Fargate the kubelet holds the default port 10250, as cert-manager's <a href="https://cert-manager.io/docs/installation/compatibility/#aws-fargate" target="_blank" rel="noopener noreferrer nofollow">AWS Fargate notes</a> describe:

   ```bash
   helm install cert-manager oci://quay.io/jetstack/charts/cert-manager \
     --version v1.21.2 \
     --namespace cert-manager \
     --create-namespace \
     --set crds.enabled=true \
     --set webhook.securePort=10260
   ```

3. Wait until cert-manager's webhook is ready, so that it accepts the operator's certificate:

   ```bash
   kubectl -n cert-manager rollout status deploy/cert-manager-webhook
   ```

4. Install operator v0.139.0, which matches the OpenTelemetry Collector 0.139.0 that Foundry pins, and its CRDs:

   ```bash
   kubectl apply -f https://github.com/open-telemetry/opentelemetry-operator/releases/download/v0.139.0/opentelemetry-operator.yaml
   ```

5. Check the operator. It is ready when `READY` shows `1/1`:

   ```bash
   kubectl get deployment opentelemetry-operator-controller-manager -n opentelemetry-operator-system
   ```

### Step 2: Install foundryctl

Run this on the machine where you use `kubectl`:

```bash
curl -fsSL https://signoz.io/foundry.sh | bash
```

For manual install (Windows PowerShell, air-gapped, etc.) or PATH setup, see the <a href="https://github.com/SigNoz/foundry/blob/main/docs/getting-started.md" target="_blank" rel="noopener noreferrer nofollow">Foundry getting-started guide</a>.

### Step 3: Create casting.yaml

Create a file named `casting.yaml` with one document for the deployment collector described in [How it works](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/overview/#how-it-works). `collector.kind: deployment` selects it:

<Admonition type="info" title="Required on every document: the controller annotation">
`foundry.signoz.io/kubernetes-collector-controller: opentelemetry-operator` sets the OpenTelemetry Operator as the controller of the collector's workload. Foundry then generates an `OpenTelemetryCollector` resource for the operator to reconcile, instead of the plain Deployment and sidecar container it generates without the annotation. See the <a href="https://github.com/SigNoz/foundry/blob/main/docs/examples/collectionagent/aws/kubernetes-serverless/kustomize/README.md#annotations" target="_blank" rel="noopener noreferrer nofollow">annotations table in the Foundry example</a>.
</Admonition>

<Admonition type="info" title="Using Self-Hosted SigNoz?" defaultCollapsed="true">
Most steps are identical. To adapt this guide, update the endpoint and remove the ingestion key as shown in [Cloud → Self-Hosted](https://signoz.io/docs/ingestion/cloud-vs-self-hosted/?ingestion-client=collection-agent&collection-agent=foundry#cloud-to-self-hosted).
</Admonition>

```yaml:casting.yaml defaultCollapsed
apiVersion: v1alpha1
kind: CollectionAgent
metadata:
  name: signoz
  annotations:
    foundry.signoz.io/kubernetes-collector-controller: opentelemetry-operator
spec:
  deployment:
    platform: aws
    mode: kubernetes-serverless
    flavor: kustomize
  collector:
    kind: deployment
    spec:
      env:
        SIGNOZ_INGESTION_ENDPOINT: https://ingest.<region>.signoz.cloud:443
        SIGNOZ_INGESTION_KEY: <your-ingestion-key>
        K8S_CLUSTER_NAME: <CLUSTER_NAME>
        OTEL_RESOURCE_ATTRIBUTES: deployment.environment=<DEPLOYMENT_ENVIRONMENT>
      config:
        data:
          collector/deployment/deployment.yaml: |
            exporters:
              otlphttp/signoz:
                headers:
                  signoz-ingestion-key: ${env:SIGNOZ_INGESTION_KEY}
```

**Verify these values:**

- `<region>`: Your SigNoz Cloud [region](https://signoz.io/docs/ingestion/signoz-cloud/overview/#endpoint).
- `<your-ingestion-key>`: Your SigNoz Cloud [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/).
- `<CLUSTER_NAME>`: A name for this cluster, unique across the clusters that send to the same SigNoz, which becomes `k8s.cluster.name` and names the cluster in the SigNoz Kubernetes views.
- `<DEPLOYMENT_ENVIRONMENT>`: Your deployment environment, for example `staging` or `production`, which becomes `deployment.environment` on the collected telemetry.

For every option of this casting, see the <a href="https://github.com/SigNoz/foundry/tree/main/docs/examples/collectionagent/aws/kubernetes-serverless/kustomize" target="_blank" rel="noopener noreferrer nofollow">EKS Fargate Kustomize example</a>.

<Admonition type="info" title="Change the namespace" defaultCollapsed="true">
The `foundry.signoz.io/kubernetes-namespace` annotation under `metadata` sets the namespace the deployment collector is applied to. A Fargate profile must select that namespace, or the deployment collector's pod stays `Pending`. The default is:

```yaml
metadata:
  name: signoz
  annotations:
    foundry.signoz.io/kubernetes-collector-controller: opentelemetry-operator
    foundry.signoz.io/kubernetes-namespace: signoz   # namespace to apply into, created by the apply
```

The namespace defaults to `metadata.name`. The <a href="https://github.com/SigNoz/foundry/blob/main/docs/examples/collectionagent/aws/kubernetes-serverless/kustomize/README.md#annotations" target="_blank" rel="noopener noreferrer nofollow">example's annotations table</a> describes it.
</Admonition>

### Step 4: Deploy

Run this from the directory that contains `casting.yaml`:

```bash
foundryctl cast -f casting.yaml
```

This command:

- writes the kustomize root `pours/collectionagent/collector/deployment`;
- applies it with `kubectl apply -k` to the cluster of your current `kubectl` context;
- creates the collector's namespace on the first apply, `signoz` from `metadata.name` in this casting. The root holds the namespace, the collector's service account and RBAC, and the `OpenTelemetryCollector` resource `signoz-collector-deployment`.

The operator then creates the collector's workload and Service, `signoz-collector-deployment-collector`, from the resource. Run the same command again after editing `casting.yaml` to apply the change.

<Admonition type="tip" title="Run kubectl yourself" defaultCollapsed="true">
To run kubectl directly, generate the kustomize root and apply it. Run this from the directory that contains `casting.yaml`:

```bash
foundryctl forge -f casting.yaml   # writes the kustomize root under pours/collectionagent/collector/deployment
kubectl apply -k pours/collectionagent/collector/deployment
```

To see the manifests before you apply them, run `kubectl kustomize pours/collectionagent/collector/deployment`.
</Admonition>

### Step 5: Verify the Collection Agent

Run this on the machine where you use `kubectl` to check that the deployment collector's pod is running on a Fargate node, in the namespace from `metadata.name`:

```bash
kubectl get pods -n signoz -o wide
```

The output should look similar to the following, with one `signoz-collector-deployment-collector` pod on a node whose name starts with `fargate-`. The operator names the workload after its `OpenTelemetryCollector` resource with a `-collector` suffix. Pod suffixes, IP addresses, and node names vary:

```output
NAME                                                     READY   STATUS    RESTARTS   AGE   IP           NODE                                 NOMINATED NODE   READINESS GATES
signoz-collector-deployment-collector-6d9c7b8f5c-k2x9p   1/1     Running   0          2m    10.0.12.34   fargate-ip-10-0-12-34.ec2.internal   <none>           <none>
```

In SigNoz, open the **[Kubernetes Monitoring](https://signoz.io/docs/infrastructure-monitoring/kubernetes-monitoring/)** views under **[Infrastructure Monitoring](https://signoz.io/docs/infrastructure-monitoring/overview/)**. The **Clusters** view lists your cluster under the name you set as `<CLUSTER_NAME>`, and the **Pods** and **Nodes** views fill in as data arrives. Check **[Logs Explorer](https://signoz.io/docs/userguide/logs_query_builder/)** to confirm Kubernetes events are flowing.

## Add the sidecar to your workloads

The sidecar has its own `casting.yaml`, kept in your application's kustomization directory.

### Step 1: Create casting.yaml

The sidecar's document carries the same `foundry.signoz.io/kubernetes-collector-controller: opentelemetry-operator` annotation as the deployment collector's.

Create a file named `casting.yaml` with this content:

<Admonition type="info" title="Using Self-Hosted SigNoz?" defaultCollapsed="true">
Most steps are identical. To adapt this guide, update the endpoint and remove the ingestion key as shown in [Cloud → Self-Hosted](https://signoz.io/docs/ingestion/cloud-vs-self-hosted/?ingestion-client=collection-agent&collection-agent=foundry#cloud-to-self-hosted).
</Admonition>

```yaml:casting.yaml defaultCollapsed
apiVersion: v1alpha1
kind: CollectionAgent
metadata:
  name: signoz
  annotations:
    foundry.signoz.io/kubernetes-collector-controller: opentelemetry-operator
spec:
  deployment:
    platform: aws
    mode: kubernetes-serverless
    flavor: kustomize
  collector:
    kind: sidecar
    spec:
      env:
        SIGNOZ_INGESTION_ENDPOINT: https://ingest.<region>.signoz.cloud:443
        SIGNOZ_INGESTION_KEY: <your-ingestion-key>
        K8S_CLUSTER_NAME: <CLUSTER_NAME>
        OTEL_RESOURCE_ATTRIBUTES: deployment.environment=<DEPLOYMENT_ENVIRONMENT>
      config:
        data:
          collector/sidecar/sidecar.yaml: |
            exporters:
              otlphttp/signoz:
                headers:
                  signoz-ingestion-key: ${env:SIGNOZ_INGESTION_KEY}
```

**Verify these values:**

- `<region>`: Your SigNoz Cloud [region](https://signoz.io/docs/ingestion/signoz-cloud/overview/#endpoint).
- `<your-ingestion-key>`: Your SigNoz Cloud [ingestion key](https://signoz.io/docs/ingestion/signoz-cloud/keys/).
- `<CLUSTER_NAME>`: The same value as in the deployment collector's `casting.yaml`, which becomes `k8s.cluster.name` on every signal.
- `<DEPLOYMENT_ENVIRONMENT>`: Your deployment environment, for example `staging` or `production`, which becomes `deployment.environment` on the collected telemetry.

### Step 2: Generate the sidecar files

Keep `casting.yaml` in your application's kustomization directory, the one that holds its `kustomization.yaml`, so `pours/` lands beside `kustomization.yaml`. Run this there to write the sidecar's files:

```bash
foundryctl forge -f casting.yaml
```

Foundry generates the `OpenTelemetryCollector` resource `signoz-collector-sidecar` in sidecar mode. The operator injects the sidecar into each new pod whose template carries the `sidecar.opentelemetry.io/inject` annotation.

### Step 3: Add the sidecar to your workloads

Add the sidecar's files to your application's `kustomization.yaml`, then annotate each workload that takes the sidecar.

The sidecar's permissions go to the namespace's `default` service account. If your workloads run under service accounts of their own, create `signoz-rolebinding.yaml` beside `kustomization.yaml`:

```yaml:signoz-rolebinding.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: signoz-collector-sidecar
subjects:
  - kind: ServiceAccount
    name: <your-service-account>
  - kind: ServiceAccount
    name: default
```

**Verify these values:**

- `<your-service-account>`: The service account of a workload that takes the sidecar, from `serviceAccountName` in its pod template; add one subject per account, and keep `default` while any such workload runs under it.

Edit your application's `kustomization.yaml` to add the sidecar's directory and the rolebinding file:

```diff
 namespace: <your-namespace>
 resources:
+  - pours/collectionagent/collector/sidecar
 patches:
+  - path: signoz-rolebinding.yaml
```

**Verify these values:**

- `<your-namespace>`: Your application's namespace.

Leave out the `signoz-rolebinding.yaml` entry if you did not create that file. The kustomization's `namespace:` places the sidecar's resource and permissions in your application's namespace.

Add the annotation to the pod template of each workload that takes the sidecar, whichever way you manage the template:

```diff
 spec:
   template:
     metadata:
+      annotations:
+        sidecar.opentelemetry.io/inject: "signoz-collector-sidecar"
```

A CronJob takes the annotation under `spec.jobTemplate.spec.template.metadata.annotations`.

The sidecar's resource must exist before your workloads' pods are created. On the first deploy, apply the sidecar's files on their own and check that the resource is listed. Run this from the directory that contains `casting.yaml`, with the same `<your-namespace>`:

```bash
kubectl -n <your-namespace> apply -k pours/collectionagent/collector/sidecar
kubectl -n <your-namespace> get opentelemetrycollector signoz-collector-sidecar
```

Then run this on the machine where you use `kubectl` to apply your application:

```bash
kubectl apply -k <overlay>
```

**Verify these values:**

- `<overlay>`: The directory that holds your application's `kustomization.yaml`, relative to where you run the command.

The operator injects the sidecar into each new pod, so restart the workloads whose pods were already running, for example a Deployment:

```bash
kubectl -n <your-namespace> rollout restart deployment/<your-workload>
```

**Verify these values:**

- `<your-workload>`: The name of the workload, from its manifest.

Jobs and CronJob runs created before the resource ran without the sidecar; delete them and create them again.

### Step 4: Verify the sidecar

Run this on the machine where you use `kubectl` to check that a workload's pods run the sidecar:

```bash
kubectl -n <your-namespace> get pods -l <your-pod-selector> -o jsonpath='{.items[*].spec.initContainers[*].name}'
```

**Verify these values:**

- `<your-namespace>`: Your application's namespace.
- `<your-pod-selector>`: A label selector for the workload's pods, from `spec.selector.matchLabels` in its manifest.

The output lists `otc-container`, the sidecar the operator injected, once per pod.

Once your application sends to the sidecar, as [Send Data from Applications to the Collector](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/configure/#send-data-from-applications-to-the-collector) shows, its traces, metrics, and logs appear in SigNoz with the `k8s.pod.name` and `k8s.namespace.name` resource attributes.

### Apply Changes

After a change to the sidecar's `casting.yaml`, forge again, apply your application again, and restart the workloads that take the sidecar.

## Customize the Collection Agent

Every change follows the same loop: edit `casting.yaml`, then run `foundryctl cast -f casting.yaml` again. For the sidecar, forge and apply as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#apply-changes) shows, then restart the workloads that run it.

- **Collector settings** (image, environment): set them in the collector's `spec` (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#spec-fields" target="_blank" rel="noopener noreferrer nofollow">spec fields</a>). For example, to pin the collector image:

  ```yaml
  spec:
    collector:
      spec:
        image: otel/opentelemetry-collector-contrib:0.139.0
  ```

- **Collector config** (receivers, processors, pipelines): add it under `spec.collector.spec.config.data`, keyed `collector/deployment/deployment.yaml` in the deployment collector's document or `collector/sidecar/sidecar.yaml` in the sidecar's. It merges into the generated config, which becomes the resource's `spec.config` (see <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/moldings.md#custom-config-files" target="_blank" rel="noopener noreferrer nofollow">custom config files</a>). For example, to scrape kubelet metrics every 60s:

  ```yaml
  spec:
    collector:
      spec:
        config:
          data:
            collector/deployment/deployment.yaml: |
              receivers:
                receiver_creator:
                  receivers:
                    kubeletstats:
                      config:
                        collection_interval: 60s
  ```

- **Manifests** (resources, annotations): add <a href="https://github.com/SigNoz/foundry/blob/main/docs/concepts/patches.md" target="_blank" rel="noopener noreferrer nofollow">patches</a> under `spec.patches` against `collectionagent/collector/deployment/opentelemetrycollector.yaml` or `collectionagent/collector/sidecar/opentelemetrycollector.yaml`, the collectors' `OpenTelemetryCollector` resources, with paths under `/spec`. For example, to give the deployment collector more CPU and memory:

  ```yaml
  spec:
    patches:
      - target: collectionagent/collector/deployment/opentelemetrycollector.yaml
        operations:
          - op: replace
            path: /spec/resources
            value:
              requests:
                cpu: 500m
                memory: 1Gi
              limits:
                cpu: 500m
                memory: 1Gi
  ```

  For every field of the resource, see the <a href="https://github.com/open-telemetry/opentelemetry-operator/blob/v0.139.0/docs/api/opentelemetrycollectors.md" target="_blank" rel="noopener noreferrer nofollow">OpenTelemetryCollector API reference</a>. Each run regenerates the files under `pours/`, so keep every change in `casting.yaml`.

## Troubleshooting
</ToggleHeading>

### Collector pod stays Pending

In [Step 5: Verify the Collection Agent](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-5-verify-the-collection-agent), the deployment collector's pod stays `Pending`. Run this on the machine where you use `kubectl` to see why the pod is unscheduled:

```bash
kubectl describe pod -n signoz <pod-name>
```

Replace `<pod-name>` with the pod's name from `kubectl get pods -n signoz`. The events show `FailedScheduling`.

**Cause:** no Fargate profile selects the collector's namespace, so no Fargate node is started for the pod.

**Fix:** add a <a href="https://docs.aws.amazon.com/eks/latest/userguide/fargate-profile.html" target="_blank" rel="noopener noreferrer nofollow">Fargate profile</a> that selects the namespace, then run this on the machine where you use `kubectl` to recreate the pod:

```bash
kubectl rollout restart -n signoz deployment/signoz-collector-deployment-collector
```

After the fix, `kubectl get pods -n signoz -o wide` shows the pod as `Running` on a `fargate-` node.

### The pods view stays empty

In [Step 5: Verify the Collection Agent](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-5-verify-the-collection-agent), the **Pods** view in SigNoz stays empty. Run this on the machine where you use `kubectl` to read the deployment collector's logs:

```bash
kubectl logs -n signoz deployment/signoz-collector-deployment-collector --since=10m
```

The logs show errors from the kubelet scrapes: a `403`, or a `404` on `/api/v1/nodes/<node-name>/proxy/stats/summary`.

**Cause:** with a `403`, the collector's service account is not allowed through the Kubernetes API server's node proxy. With a `404`, the kubelet on that node does not serve its stats through the proxy.

**Fix:** for a `403`, run this on the machine where you use `kubectl`. It prints `yes` once the ClusterRole Foundry generates is in place:

```bash
kubectl auth can-i get nodes/proxy --as=system:serviceaccount:signoz:signoz-collector-deployment
```

If it prints `no`, run [Step 4: Deploy](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-4-deploy) again. For a `404`, scrape the kubelets directly, as the example's <a href="https://github.com/SigNoz/foundry/blob/main/docs/examples/collectionagent/aws/kubernetes-serverless/kustomize/README.md#when-the-api-server-proxy-does-not-serve-kubelet-stats" target="_blank" rel="noopener noreferrer nofollow">API-server proxy section</a> shows.

After the fix, the **Pods** view in SigNoz lists your pods.

### foundryctl cast stops with `unsupported collector kind "agent"`

In [Step 4: Deploy](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-4-deploy), `foundryctl cast -f casting.yaml` stops before it applies anything, with the message `unsupported collector kind "agent"`.

**Cause:** the document has no `collector.kind`, so the collector kind defaults to `agent`, and on EKS Fargate the collector kinds are `deployment` and `sidecar`.

**Fix:** add `kind: deployment` under `spec.collector`, as in [Step 3: Create casting.yaml](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-3-create-castingyaml), or `kind: sidecar` in the sidecar's document, then run [Step 4: Deploy](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-4-deploy) again.

After the fix, `kubectl get pods -n signoz` shows the deployment collector's pod.

### foundryctl cast rejects a patch

In [Step 4: Deploy](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-4-deploy), `foundryctl cast -f casting.yaml` stops before it applies anything, with `failed to apply patch for target "<target>"` and one of these causes:

- `doc is missing key: <path>: missing value`
- `doc is missing path: <path>: missing value`
- `patch target "<target>" did not match any generated material`

**Cause:** the patch's target or path does not exist in what Foundry generates for the OpenTelemetry Operator.

**Fix:** remove the patch from `casting.yaml`, then run this from the directory that contains it:

```bash
foundryctl forge -f casting.yaml
```

Take the target from the files under `pours/collectionagent/collector/` and the path from the resource under `/spec`, add the patch back, and run [Step 4: Deploy](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-4-deploy) again.

After the fix, `kubectl get pods -n signoz` shows the deployment collector's pod.

### foundryctl cast reaches the wrong cluster or none

In [Step 4: Deploy](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-4-deploy), `foundryctl cast -f casting.yaml` applies to another cluster or cannot reach one. Run this on the machine where you run `foundryctl` to see which cluster it uses:

```bash
kubectl config current-context
```

**Cause:** `foundryctl cast` applies to the cluster of your current `kubectl` context.

**Fix:** switch to the right context with `kubectl config use-context <context-name>`, then run [Step 4: Deploy](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-4-deploy) again. Replace `<context-name>` with a context from `kubectl config get-contexts`.

After the fix, `kubectl get pods -n signoz` shows the deployment collector's pod on that cluster.

### A workload's pods have no sidecar

In [Step 4: Verify the sidecar](https://signoz.io/docs/opentelemetry-collection-agents/k8s/serverless/user-guides/otel-operator/#step-4-verify-the-sidecar), the `kubectl get pods` check prints nothing for a workload.

**Cause:** the workload's pods were created before the `signoz-collector-sidecar` resource existed, or its pod template lacks the annotation.

**Fix:** check that `kubectl -n <your-namespace> get opentelemetrycollector signoz-collector-sidecar` lists the resource and that the pod template carries the annotation, then restart the workload, for example with `kubectl -n <your-namespace> rollout restart deployment/<your-workload>`. Delete a Job and create it again.

After the fix, the check prints `otc-container` once per pod.
