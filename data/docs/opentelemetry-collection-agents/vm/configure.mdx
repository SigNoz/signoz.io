The [install guide](https://signoz.io/docs/opentelemetry-collection-agents/vm/install/) provides a working config: one agent on each host collects host metrics and data from instrumented applications, and on Linux the warnings and errors in the systemd journal. This page explains what each component in that config does and how to customize it.

## Prerequisites

- The VM Collection Agent installed as the [install guide](https://signoz.io/docs/opentelemetry-collection-agents/vm/install/) shows: with Foundry on Linux, or as a service on macOS or Windows
- SigNoz Cloud account or self-hosted SigNoz instance
- A shell on the host with `sudo`, or Windows PowerShell as Administrator
- On Linux, the `casting.yaml` and `foundryctl` you installed with

## Apply Changes

Each section shows its change as a `casting.yaml` snippet. The YAML under `collector/agent/agent.yaml` is collector config, and `spec.collector.spec.env` holds environment variables.

<Tabs entityName="os">
<TabItem value="linux" label="Linux" default>

1. Add the section's snippet to `casting.yaml`. Foundry already generates the default receivers and processors, so add only what you change. If `casting.yaml` already has a `collector/agent/agent.yaml` block, as the install guide's does, add the snippet's lines inside that block.

2. Run this from the directory that contains `casting.yaml` to apply the change:

   ```bash
   sudo foundryctl cast -f casting.yaml
   ```

   Foundry reinstalls the agent's files and restarts it.

3. [View the agent's logs](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#view-the-collectors-logs) to confirm there are no configuration errors:

   ```bash
   sudo journalctl -u signoz-collector-agent --since "5 min ago" --no-pager
   ```

4. In SigNoz, confirm data in [Infrastructure Monitoring](https://signoz.io/docs/infrastructure-monitoring/overview/) for host metrics, [Logs](https://signoz.io/docs/logs-management/overview/) for logs, and [Traces](https://signoz.io/docs/instrumentation/overview/) for application traces.

</TabItem>
<TabItem value="macos" label="macOS">

1. Add the YAML under the snippet's `collector/agent/agent.yaml: |` line to `/etc/signoz-collector-agent/custom.yaml`, starting at the left margin and combined with what the file already holds. For a variable under `spec.collector.spec.env`, set it in the environment file `/etc/signoz-collector-agent/signoz-collector-agent.conf` from [Step 3 of the install guide](https://signoz.io/docs/opentelemetry-collection-agents/vm/install/?os=macos#step-3-create-the-launchd-daemon) instead, one `NAME="value"` per line. 2. Restart the agent to apply the change:

   ```bash
   sudo tail -n 50 /Library/Logs/signoz-collector-agent/collector.log
   ```

4. In SigNoz, confirm data in [Infrastructure Monitoring](https://signoz.io/docs/infrastructure-monitoring/overview/) for host metrics, [Logs](https://signoz.io/docs/logs-management/overview/) for logs, and [Traces](https://signoz.io/docs/instrumentation/overview/) for application traces.

</TabItem>

## Send Data from Applications to Collector on VM

Host metrics, and on Linux the warnings and errors in the systemd journal, flow as soon as the agent is running.

### Where and how to send data from your application

To send traces, metrics, and logs from an application, instrument it with OpenTelemetry ([language guides](https://signoz.io/docs/instrumentation/)), then point it at the agent. For an application on the same host, set these in its environment, for example in the shell that starts it:

```bash
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_SERVICE_NAME=<service-name>
```

**Verify these values:**

- `<service-name>`: The name your application shows under in SigNoz.

From another host, use the agent host's address in place of `localhost`, with port `4318` open to it. For OTLP over gRPC, set `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` and port `4317`. On Windows, set the same variables in the application's environment.

Restart the application and send it some traffic. Within a minute it shows under **Services** in SigNoz.

## Collect Host Metrics

The agent's `hostmetrics` receiver collects CPU, memory, disk I/O, filesystem usage, network, load, paging, per-process usage, process counts, and uptime every 60s. For what each metric means, see [Host Metrics](https://signoz.io/docs/infrastructure-monitoring/user-guides/hostmetrics/).

To collect host metrics every 30s, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              hostmetrics:
                collection_interval: 30s
```

On Linux, to stop a scraper, set it to `null` under `scrapers`, for example `paging: null`. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

### Exclude filesystem mounts

To stop reporting the filesystem mounted at `/mnt/backup`, add this to `casting.yaml`:

```yaml defaultCollapsed
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              hostmetrics:
                scrapers:
                  filesystem:
                    exclude_mount_points:
                      match_type: regexp
                      mount_points:
                        - /dev/*
                        - /proc/*
                        - /sys/*
                        - /run/credentials/*
                        - /run/k3s/containerd/*
                        - /var/lib/docker/*
                        - /var/lib/containers/storage/*
                        - /var/lib/kubelet/*
                        - /snap/*
                        - ^/mnt/backup$
```

Lists replace, so restate the agent's default entries, the ones above `^/mnt/backup$`. On macOS, the only default entry is `/dev/*`. On Windows there is none, and mount points are drive letters, such as `^D:$`. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

## Collect Host Logs

On Linux, the agent's `journald` receiver reads new entries from the systemd journal and collects those at priority warning and above. It sets each record's `service.name` from its systemd unit or program name, and leaves out the agent's own entries. On macOS and Windows, the agent collects no host logs.

To also collect entries at priority info, which include a service's plain standard output and standard error, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              journald:
                priority: info
```

`priority` merges into the agent's `journald` receiver, so its other settings stay. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

To collect the journal of only some systemd units, list them:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              journald:
                units:
                  - nginx.service
                  - postgresql.service
```

Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

### Disable Logs Collection

To stop collecting the journal, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              journald: null
            service:
              pipelines:
                logs:
                  receivers: [otlp/http, otlp/grpc]
```

Lists replace, so the `logs` pipeline is restated with the agent's two OTLP receivers. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

## Collect Application Log Files

To collect the log files that an application writes, add a `filelog/app` receiver to `casting.yaml` and list it in the `logs` pipeline:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              filelog/app:
                include:
                  - /var/log/myapp/*.log
                start_at: end
                include_file_path: true
            service:
              pipelines:
                logs:
                  receivers: [otlp/http, otlp/grpc, journald, filelog/app]
```

Lists replace, so the `logs` pipeline restates the agent's receivers `otlp/http`, `otlp/grpc`, and `journald` with the new one. On macOS and Windows, leave `journald` out of the list. On Linux, the agent can read any file on the host outside `/tmp` and `/var/tmp`. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

For log files with one JSON object per line, parse each line into attributes:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              filelog/app:
                include:
                  - /var/log/myapp/*.json
                start_at: end
                include_file_path: true
                operators:
                  - type: json_parser
            service:
              pipelines:
                logs:
                  receivers: [otlp/http, otlp/grpc, journald, filelog/app]
```

Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes). For more `filelog` options, see [Collect Logs from a File](https://signoz.io/docs/userguide/collect_logs_from_file/).

### Other log sources

To receive syslog, or logs forwarded from [Fluent Bit](https://signoz.io/docs/userguide/fluentbit_to_signoz/), [Fluentd](https://signoz.io/docs/userguide/fluentd_to_signoz/), or [Logstash](https://signoz.io/docs/userguide/logstash_to_signoz/), take the receiver from its guide, add it under `collector/agent/agent.yaml`, and list it in the `logs` pipeline as above. For syslog, see [Collecting Syslogs](https://signoz.io/docs/userguide/collecting_syslogs/). On Linux, the agent can listen only on ports 1024 and above. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

## Resource Detection

The agent's `resourcedetection` processor sets `host.name`, `host.id`, and `os.type`, and on AWS, GCP, and Azure virtual machines the cloud provider, region, and instance. Values from `OTEL_RESOURCE_ATTRIBUTES` and attributes already on the data take precedence over detected ones.

To detect only host attributes on a host outside AWS, GCP, and Azure, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            processors:
              resourcedetection:
                detectors: [env, system]
```

Lists replace, so `detectors` holds only the detectors you list. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

### Custom resource attributes

To add `team=backend` to all telemetry, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      env:
        OTEL_RESOURCE_ATTRIBUTES: deployment.environment=<your-environment>,team=backend
```

**Verify these values:**

- `<your-environment>`: Your deployment environment, for example `staging` or `production`.

Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

## Scrape Prometheus Metrics

To scrape a Prometheus endpoint every 60s, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              prometheus:
                config:
                  scrape_configs:
                    - job_name: my-app
                      scrape_interval: 60s
                      static_configs:
                        - targets: [localhost:9090]
            service:
              pipelines:
                metrics:
                  receivers: [otlp/http, otlp/grpc, hostmetrics, prometheus]
```

Lists replace, so the `metrics` pipeline is restated with the agent's default receivers. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

## Tune Batch and Memory Limiter

For sizing guidance, see [Collector Configuration Best Practices](https://signoz.io/docs/opentelemetry-collection-agents/opentelemetry-collector/configuration/#best-practices).

To send larger batches, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            processors:
              batch:
                send_batch_size: 2000
                send_batch_max_size: 4000
```

The agent's defaults are `send_batch_size: 1000`, `send_batch_max_size: 2048`, and `timeout: 10s`. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

### Memory limit

On Linux, to cap the agent's memory at 1 GiB, add this patch to `casting.yaml`:

```yaml
spec:
  patches:
    - target: collectionagent/collector/agent/signoz-collector-agent.service
      operations:
        - op: add
          path: /Service/MemoryMax
          value: 1G
```

The agent's `memory_limiter` processor uses a fixed `limit_mib: 4000`. Size it to the memory limit with percentages, in the same document:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            processors:
              memory_limiter:
                limit_mib: null
                spike_limit_mib: null
                limit_percentage: 80
                spike_limit_percentage: 25
```

Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

## Add Custom Processors to Pipelines

To add a processor to the `traces` pipeline, add this to `casting.yaml`:

```yaml
spec:
  collector:
    spec:
      config:
        data:
          collector/agent/agent.yaml: |
            processors:
              attributes/team:
                actions:
                  - key: team
                    value: platform
                    action: insert
            service:
              pipelines:
                traces:
                  processors: [memory_limiter, resourcedetection, attributes/team, batch]
```

Lists replace, so restate the agent's processors `memory_limiter`, `resourcedetection`, and `batch`, with yours before `batch`. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

## Common Deployment Scenarios

### Run on the same host as self-hosted SigNoz

Self-hosted SigNoz can hold ports `4317`, `4318`, `8888`, and `13133` on its host, the ports the agent binds. To run the agent on that host, add this to `casting.yaml`:

```yaml defaultCollapsed
spec:
  collector:
    spec:
      env:
        SIGNOZ_INGESTION_ENDPOINT: http://localhost:4318
      config:
        data:
          collector/agent/agent.yaml: |
            receivers:
              otlp/grpc:
                protocols:
                  grpc:
                    endpoint: 0.0.0.0:14317
              otlp/http:
                protocols:
                  http:
                    endpoint: 0.0.0.0:14318
            extensions:
              health_check:
                endpoint: 0.0.0.0:13134
            service:
              telemetry:
                metrics:
                  readers:
                    - pull:
                        exporter:
                          prometheus:
                            host: localhost
                            port: 8889
```

The agent then receives OTLP on ports `14317` and `14318`, serves its health check on `13134` and its own metrics on `localhost:8889`, and sends to the SigNoz on the same host. Applications on the host send to `localhost:14318`. Then [apply the change](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

## Migrate to Foundry

If you run the agent on Linux as the `otelcol-contrib` service from the OpenTelemetry Collector package, or from the tarball, with your own `config.yaml`, move it to Foundry so that `casting.yaml` holds its whole setup and every change follows [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes).

1. To describe the agent in Foundry, [install foundryctl](https://signoz.io/docs/opentelemetry-collection-agents/vm/install/#step-1-install-foundryctl), [download the OpenTelemetry Collector](https://signoz.io/docs/opentelemetry-collection-agents/vm/install/#step-2-download-the-opentelemetry-collector), and [create casting.yaml](https://signoz.io/docs/opentelemetry-collection-agents/vm/install/#step-3-create-castingyaml) as the install guide shows. On a host that runs self-hosted SigNoz, also add the change in [Run on the same host as self-hosted SigNoz](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#run-on-the-same-host-as-self-hosted-signoz).

2. To keep your `config.yaml` customizations, add them to `casting.yaml` under `spec.collector.spec.config.data`, keyed `collector/agent/agent.yaml`, and your environment variables under `spec.collector.spec.env`. For example, for host metrics every 30s and a `team` resource attribute:

   ```yaml
   spec:
     collector:
       spec:
         env:
           OTEL_RESOURCE_ATTRIBUTES: deployment.environment=<your-environment>,team=backend
         config:
           data:
             collector/agent/agent.yaml: |
               receivers:
                 hostmetrics:
                   collection_interval: 30s
   ```

   **Verify these values:**

   - `<your-environment>`: Your deployment environment, for example `staging` or `production`.

   Foundry merges them over its own config: maps merge and lists replace, so restate whole lists, with Foundry's names `otlp/http` and `otlp/grpc` for your `otlp` receiver and `otlphttp/signoz` for your `otlphttp` exporter, and keep `journald` in the `logs` pipeline. Your exporter's endpoint and key go in `SIGNOZ_INGESTION_ENDPOINT` and `SIGNOZ_INGESTION_KEY`, as in the install guide.

3. To free the host ports the Foundry agent binds, remove the old collector. For the package on Debian and Ubuntu, run this on the host:

   ```bash
   sudo apt-get remove otelcol-contrib
   ```

   On RHEL and Fedora (`yum` on older releases):

   ```bash
   sudo dnf remove otelcol-contrib
   ```

   Remove the package rather than only stopping or disabling its service: the package's <a href="https://github.com/open-telemetry/opentelemetry-collector-releases/blob/v0.139.0/distributions/otelcol-contrib/postinstall.sh" target="_blank" rel="noopener noreferrer nofollow">install script</a> enables and restarts the service again on every upgrade. The agent runs its own binary from Step 2 of the install guide, so removing the package's `/usr/bin/otelcol-contrib` leaves it running. For a collector you started from the tarball, stop its process, for example with `kill "$(cat otel-pid)"` from the directory you started it in.

4. To start the agent with Foundry, run this from the directory that contains `casting.yaml`:

   ```bash
   sudo foundryctl cast -f casting.yaml
   ```

   Then verify the Collection Agent as [Step 5 of the install guide](https://signoz.io/docs/opentelemetry-collection-agents/vm/install/#step-5-verify-the-collection-agent) shows.

## Upgrade or Remove the Collection Agent

To replace the collector binary, for example when this guide moves to a newer collector version, stop the agent, download the binary again, then start the agent.

<Tabs entityName="os">
<TabItem value="linux" label="Linux" default>

To replace the collector binary:

1. Stop the agent. Run this on the host:

   ```bash
   sudo systemctl stop signoz-collector-agent
   ```

2. Download the binary as [Step 2 of the install guide](https://signoz.io/docs/opentelemetry-collection-agents/vm/install/#step-2-download-the-opentelemetry-collector) shows.

3. Start the agent. Run this from the directory that contains `casting.yaml`:

   ```bash
   sudo foundryctl cast -f casting.yaml
   ```

To remove the agent, run this on the host:

```bash
sudo systemctl disable --now signoz-collector-agent
sudo rm /etc/systemd/system/signoz-collector-agent.service /etc/sysusers.d/signoz-collector-agent.conf
sudo rm -r /etc/signoz-collector-agent /opt/signoz-collector-agent
sudo systemctl daemon-reload
sudo userdel signoz-collector-agent
```

With another `metadata.name`, the unit, its directory under `/etc`, and their files take that name in place of `signoz`. The user and `/opt/signoz-collector-agent` keep theirs.

```powershell
Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'signoz-collector-agent' } -MaxEvents 50 | Select-Object TimeCreated, LevelDisplayName, Message
```

## Troubleshooting
</ToggleHeading>

### Metrics or logs stop after adding a receiver

After a change that adds a receiver to the `metrics` or `logs` pipeline, host metrics or host logs stop arriving in SigNoz.

**Cause:** the pipeline's `receivers` list replaces the whole list, so a list without `hostmetrics` or `journald` drops them.

**Fix:** restate every receiver the pipeline still needs, as [Scrape Prometheus Metrics](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#scrape-prometheus-metrics) and [Collect Application Log Files](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#collect-application-log-files) show, then apply the change as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes) shows.

After the fix, host metrics and host logs arrive in SigNoz again.

### A custom processor has no effect

After a change that adds a processor, its attribute or transformation is missing from the data in SigNoz.

**Cause:** the processor is defined under `processors` but not listed in a pipeline's `processors`.

**Fix:** list it before `batch` as [Add Custom Processors to Pipelines](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#add-custom-processors-to-pipelines) shows, then apply the change as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes) shows.

After the fix, the attribute or transformation appears on the signal in SigNoz Explorer.

### A service's logs do not arrive

On Linux, a service's log lines are in its journal (`journalctl -u <unit>`) but not in the SigNoz Logs Explorer.

**Cause:** the agent collects journal entries at priority warning and above, and the service writes its lines at a lower priority. Plain standard output and standard error are stored at priority info.

**Fix:** collect entries at priority info as [Collect Host Logs](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#collect-host-logs) shows, then apply the change as [Apply Changes](https://signoz.io/docs/opentelemetry-collection-agents/vm/configure/#apply-changes) shows.

After the fix, new log lines from the service arrive in SigNoz.
