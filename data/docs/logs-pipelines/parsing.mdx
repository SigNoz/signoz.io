Log parsing transforms unstructured log messages into structured data, allowing you to filter, aggregate, and analyze your logs efficiently in SigNoz.

## Prerequisites

- You are sending logs to SigNoz.
- You have access to the **Logs Pipelines** section in SigNoz UI.

Learn more about SigNoz [Logs Pipelines](https://signoz.io/docs/logs-pipelines/introduction/).

## Choosing the Right Parser

SigNoz offers several processors to handle different types of logs. Choosing the right one depends on your log format:

| Log Format            | Recommended Parser                                                                                                                                        | Why?                                                                                             |
| :-------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------- |
| **JSON**              | [JSON Parser](https://signoz.io/docs/logs-pipelines/guides/json/)                                                                                         | **Fastest & Easiest.** If your logs are already in JSON format, this parser simply expands them. |
| **Unstructured Text** | [Regex Parser](#regex-parser)                                                                                                                             | **Flexible.** Best for custom log formats where you can define a specific pattern.               |
| **Common Formats**    | [Grok Parser](#grok-parser)                                                                                                                               | **Convenient.** Uses pre-defined patterns for common systems like Nginx, Apache, Syslog.         |
| **Specific Fields**   | [Timestamp](https://signoz.io/docs/logs-pipelines/guides/timestamp-parsing/) / [Severity](https://signoz.io/docs/logs-pipelines/guides/severity-parsing/) | Specialized processors to map these critical fields to the OpenTelemetry schema.                 |

<Admonition type="tip">
  For best performance, configure your applications to output logs in **JSON** format. This avoids
  the overhead of regex processing and is less brittle to format changes.
</Admonition>

## Regex Parser

The Regex processor uses [Regular Expressions](https://github.com/google/re2/wiki/Syntax) (based on Go's RE2 syntax) to extract information from unstructured logs. It uses **Named Capture Groups** to map parts of your log message to attribute names.

**The Concept:**
You define a pattern containing groups like `(?P<attribute_name>pattern)`. Whatever matches inside the parentheses becomes the value of `attribute_name`.

### Example Log

Suppose you have a legacy application producing this log:

```text
2025-12-27 10:00:00 [INFO] User 123 logged in from 192.168.1.5
```

### Desired Outcome

After parsing, we want to extract these attributes:

| Attribute | Value       |
| --------- | ----------- |
| `level`   | INFO        |
| `user_id` | 123         |
| `ip`      | 192.168.1.5 |

The final log should look like this:

```json
{
  "body": "2025-12-27 10:00:00 [INFO] User 123 logged in from 192.168.1.5",
  "attributes": {
    "level": "INFO",
    "user_id": "123",
    "ip": "192.168.1.5"
  }
}
```

### Step-by-Step Configuration

1. **Add a Processor**: Expand your pipeline and click the **"Add Processor"** button.

<Figure
  src="/img/docs/logs-management/logs-pipelines/logs-parsing-regex-step1.webp"
  alt="Expand Pipeline to access Processors"
  caption="Expand Pipeline to access Processors"
/>

<Figure
  src="/img/docs/logs-management/logs-pipelines/logs-parsing-regex-step2.webp"
  alt="Add Processors Button"
  caption="Add Processors Button"
/>

2. **Select Regex Parser** and configure the fields:

   - **Name**: `parse_app_log`
   - **Parse From**: `body` (This is where the raw message resides)
   - **Parse To**: `attributes` (We want to add these directly to log attributes)
   - **Pattern**:
     ```regex
     ^.*\[(?P<level>\w+)\].*User (?P<user_id>\d+) logged in from (?P<ip>[\d\.]+)
     ```

<Figure
  src="/img/docs/logs-management/logs-pipelines/logs-parsing-regex-step3.webp"
  alt="Regex Parser Configuration Example"
  caption="Configuring the Regex Parser"
/>

3. **Press "Create"** to add the processor.

## Grok Parser

Grok simplifies the creation of complex regular expressions by using pre-defined, reusable patterns. It allows you to use human-readable aliases for common data formats, making your parsing rules significantly easier to read and maintain.

**The Concept:**
Instead of writing complex regex for an IP address, you simply use `%{IP:ip_address}`. The syntax is `%{PATTERN_NAME:capture_name}`.

### Example Log

A standard web access log:

```text
127.0.0.1 - - [27/Dec/2025:10:00:00 +0000] "GET /api/v1/users HTTP/1.1" 200 1234
```

### Desired Outcome

After parsing, we want to extract these attributes:

| Attribute       | Value                      |
| --------------- | -------------------------- |
| `client_ip`     | 127.0.0.1                  |
| `timestamp`     | 27/Dec/2025:10:00:00 +0000 |
| `method`        | GET                        |
| `request`       | /api/v1/users              |
| `response_code` | 200                        |
| `bytes`         | 1234                       |

The final log should look like this:

```json
{
  "body": "127.0.0.1 - - [27/Dec/2025:10:00:00 +0000] \"GET /api/v1/users HTTP/1.1\" 200 1234",
  "attributes": {
    "client_ip": "127.0.0.1",
    "ident": "-",
    "auth": "-",
    "timestamp": "27/Dec/2025:10:00:00 +0000",
    "method": "GET",
    "request": "/api/v1/users",
    "http_version": "1.1",
    "response_code": "200",
    "bytes": "1234"
  }
}
```

### Step-by-Step Configuration

1. **Add a Processor**: In your pipeline, click **"Add Processor"** and select **Grok Parser**.

2. **Configure the fields**:

   - **Name**: `access_log_parser`
   - **Parse From**: `body`
   - **Parse To**: `attributes`
   - **Pattern**:
     ```grok
     %{IP:client_ip} %{USER:ident} %{USER:auth} \[%{HTTPDATE:timestamp}\] "%{WORD:method} %{URIPATHPARAM:request} HTTP/%{NUMBER:http_version}" %{NUMBER:response_code} %{NUMBER:bytes}
     ```

<Figure
  src="/img/docs/logs-management/logs-pipelines/grok-parser-config.webp"
  alt="Grok Parser Configuration Example"
  caption="Configuring the Grok Parser"
/>

3. **Press "Create"** to add the processor.

### Simulate and Validate

1. Click the **"eye" icon** to open the Pipeline Preview Dialog.
2. Press **"Simulate Processing"** to test with sample logs.
3. Verify that attributes like `client_ip`, `method`, `response_code` are extracted correctly.

<Figure
  src="/img/docs/logs-management/logs-pipelines/logs-after-grok-parser.webp"
  alt="Logs after Grok Parser"
  caption="Logs after Grok Parser with extracted attributes"
/>

<Admonition type="info">
  The `HTTPDATE` pattern captures timestamps in their raw format. To convert to ISO 8601 format for
  proper time-based querying, apply the [Timestamp
  Parser](https://signoz.io/docs/logs-pipelines/guides/timestamp-parsing/) after extracting the
  field.
</Admonition>

### Built-in Patterns

If you are using standard web servers like **Nginx** or **Apache**, you can use built-in patterns like `%{COMMONAPACHELOG}` or `%{COMBINEDAPACHELOG}` directly, instead of manually constructing the full pattern.

You can find the complete list of built-in patterns at [Grok patterns](https://github.com/vjeantet/grok/blob/master/patterns.go).

<Admonition type="tip">
  Verify and debug your Grok patterns using the [Grok Debugger](https://grokdebugger.com/).
</Admonition>

## Troubleshooting

### Parser not matching any logs

- Use the **Simulate** feature in the pipeline editor to test with real log entries.
- Check that `Parse From` points to the correct field (`body` vs `attributes.message`).
- Test patterns with [regex101](https://regex101.com/) (select Go flavor) or [Grok Debugger](https://grokdebugger.com/).

### Extracted attributes not appearing

- Ensure the pipeline is **deployed** after saving.
- Check pipeline order—parsers should run before processors that modify the same fields.
- Use unique attribute names to avoid conflicts.

### Performance issues with complex patterns

- Replace greedy `.*` with specific patterns like `[^\]]+`.
- Use `%{IP}` instead of `%{GREEDYDATA}` in Grok.
- Add filter conditions to apply parsers only to relevant logs.
