Use these recipes to alert on a silent service, a slow or failing endpoint, a host running out of memory, or a business flow that stopped. Each one lists the Query Builder fields, a PromQL or ClickHouse variant where one helps, and the settings that stop false alerts.

For the meaning of each condition field (operators, match type, evaluation window, threshold unit, no-data handling), see the per-signal references: [metrics](https://signoz.io/docs/alerts-management/metrics-based-alerts/), [logs](https://signoz.io/docs/alerts-management/log-based-alerts/), [traces](https://signoz.io/docs/alerts-management/trace-based-alerts/), and [exceptions](https://signoz.io/docs/alerts-management/exceptions-based-alerts/).

## Prerequisites

- [SigNoz Cloud](https://signoz.io/docs/cloud/) or [Self-Hosted SigNoz](https://signoz.io/docs/install/)
- At least one [notification channel](https://signoz.io/docs/setup-alerts-notification/) configured
- The signal you want to alert on is already flowing into SigNoz (metrics, logs, or traces)

## Settings that prevent false alerts

Configuration causes most false alerts. Get these settings right and you avoid alerts that fire on a single spike, alerts that stay silent when a service dies, and ratios that report 300%.

| Setting | Use it for | Why it matters |
| --- | --- | --- |
| **Match type** (`at least once`, `all the times`, `on average`) | Every alert | `at least once` catches brief spikes; `all the times` and `on average` require a sustained breach, which stops one transient data point from paging you. |
| **Y-axis unit**, then **Threshold Unit** | Latency and size alerts | Span duration is stored in nanoseconds. Set the query's y-axis unit to `Nanoseconds` first: the **Threshold Unit** list is filtered to that unit's category and stays disabled until you do. Then set **Threshold Unit** to `ms` so `500` means 500 ms. Setting neither compares `500` against raw nanoseconds and the alert fires constantly. |
| **Alert when data stops coming** (no-data) | Availability and dead-man alerts | A service that fully stops returns no series, so there is no value to compare against a threshold. Only no-data handling catches a total outage. |
| **Threshold ≠ 0 for no-data** | Availability alerts | A threshold of `0` collides with the literal value `0` that a no-data result reports. Use no-data handling instead of a zero threshold. |
| **Aligned aggregation on both sides of a ratio** | Percentage formulas | Summing the numerator across many series while the denominator covers one series produces values like 300% or 1300%. Group both queries by the same key and use the same space aggregation. |
| **Minimum data points in result group** | Sparse or low-traffic signals | Skips evaluation until enough points exist, which stops flapping. Set it below the number of points you expect in the window. See [evaluation patterns](https://signoz.io/docs/alerts-management/user-guides/understanding-alert-evaluation-patterns/). |
| **Having** clause (minimum traffic) | Error-rate and latency alerts | One error in 30 requests is a 3% error rate. Require a minimum request count so a quiet minute does not trip a percentage alert. |
| **Group alerts by** vs query group-by | Noise control | Grouping the *query* by `k8s.pod.name` creates one alert series per pod. Use **Group alerts by** in notification settings to control how many notifications you receive. |
| **Repeat notifications** | Ongoing incidents | An alert that is already firing does not re-notify by default. Enable repeat notifications if you want reminders while an incident stays open. |

<Admonition type="info">
Set evaluation windows wider than your collection interval plus any ingestion delay. A window narrower than the time between data points reads recent gaps as "no data" and can fire falsely. Read [time aggregation best practices](https://signoz.io/docs/alerts-management/user-guides/time-aggregation-best-practices/) before tightening a window.
</Admonition>

## Availability and no-data alerts

### Alert when a service's request rate drops

`signoz_calls_total` counts request spans, so its rate tracks traffic and not liveness. Use this recipe only for a service with guaranteed continuous traffic: a healthy service that receives less than one request per second trips `Below 1`. To alert on the process itself, use the next recipe.

Configure a metric alert on a metric the service emits on every request, such as `signoz_calls_total`:

- **Signal**: Metrics
- **Metric**: `signoz_calls_total`
- **Filter**: `service.name = '<your-service>' AND span.kind = 'SPAN_KIND_SERVER'`
- **Aggregate within time series**: Rate
- **Aggregate across time series**: Sum, grouped by `service.name`
- **Condition**: Below, **Threshold** `1`
- **Advanced Options → Alert when data stops coming**: enabled, with a "no data for" duration of 2 to 3 times your collection interval

`<your-service>` is the service name as it appears in SigNoz. The `span.kind` filter keeps the count to inbound requests the service served, so outbound client calls do not hold the rate up while the service serves nothing.

To watch every service with one rule, drop the `service.name` condition and keep the group-by. The rule then produces one alert series per service, and each is evaluated against the same threshold.

<Admonition type="warning">
The threshold path alone cannot detect a dead service: when the series disappears there is no data point to compare. **Alert when data stops coming** fires on a true outage. Do not set the threshold to `0` to approximate this, because `0` is also the value a no-data result reports.

No-data handling cannot tell an idle service from a stopped one, which is the other reason this recipe is not a liveness check.
</Admonition>

### Alert when a service process stops running

Telemetry silence and a dead process are different failures. Use this recipe for liveness itself, whether or not the service is handling traffic. It reads `process.uptime`, which ticks on a timer instead of moving with requests.

The OpenTelemetry Collector reports this metric through the `process` scraper of the `hostmetrics` receiver. The scraper is off by default, so add it to your existing collector config and keep the scrapers you already run:

```yaml defaultCollapsed
receivers:
  hostmetrics:
    scrapers:
      process:
        metrics:
          process.uptime:
            enabled: true
          # The scraper's four default metrics are off here to keep this to one
          # series per process. Enable them if you want per-process CPU and memory.
          process.cpu.time:
            enabled: false
          process.disk.io:
            enabled: false
          process.memory.usage:
            enabled: false
          process.memory.virtual:
            enabled: false

service:
  pipelines:
    metrics:
      receivers: [hostmetrics]
```

Add `hostmetrics` to the receivers your metrics pipeline already lists. A receiver that is defined but absent from a pipeline collects nothing.

When the Collector runs in a container, mount the host filesystem and point the receiver at it with `root_path: /hostfs`. A Collector installed directly on the host does not need `root_path`. Either way the Collector needs to run as root, because the scraper reads `/proc` entries owned by other users.

Then alert on it:

- **Signal**: Metrics
- **Metric**: `process.uptime`
- **Filter**: `process.executable.name = '<process-name>' AND host.name = '<host>'`
- **Aggregate within time series**: Latest
- **Aggregate across time series**: Max, grouped by `process.executable.name` and `host.name`
- **Condition**: Below, **Threshold** `1`
- **Evaluation window**: 2 to 3 times your collection interval
- **Advanced Options → Alert when data stops coming**: enabled, with a "no data for" duration of 2 to 3 times your collection interval

A live process reports an uptime far above `1`, so the threshold never fires on its own. The rule exists for its no-data setting, which is the part that detects the stopped process. Group by `process.executable.name` rather than `process.pid`: a restart gives the process a new pid, so a pid-keyed alert resolves and reopens on every restart.

<Admonition type="warning">
Pin the filter to one host. No-data detection covers the whole query, so a rule that matches the same executable on several hosts stays "present" while one host's process is gone. To watch the same process across a fleet with one rule, use the time-shift comparison in [Alert when one group stops reporting](#alert-when-one-group-stops-reporting) instead.
</Admonition>

<Admonition type="info">
The `process` scraper reads `/proc` entries owned by other users, so the collector needs to run as root to see anything but itself. It also emits one series per process per node, so leave the scraper's four default-on metrics disabled unless you want them, and scope it with the scraper's `include` filter on a busy host.

A .NET service running the release-candidate <a href="https://github.com/open-telemetry/opentelemetry-dotnet-contrib/tree/main/src/OpenTelemetry.Instrumentation.Process" target="_blank" rel="noopener noreferrer nofollow">Process instrumentation</a> reports the same metric from the SDK instead. Those series carry `service.name`, so filter and group on that rather than on `process.executable.name`. No other language's instrumentation emits `process.uptime` today.
</Admonition>

### Alert when one group stops reporting

Grouped entities need a different approach: one host in a fleet, one Kubernetes pod, one environment, or one Kafka cluster must keep reporting while its siblings stay healthy.

The built-in no-data toggle is global for the alert query. If one group still returns data, the query is still "present." Use a time-shift comparison instead:

- **Signal**: Metrics
- **Metric**: a metric every group emits, such as `system.cpu.utilization` or `kafka.brokers`
- **Query A**: Count, Sum, grouped by the entity key, for example `host.name` or `deployment.environment` and `kafka.cluster.name`
- **Query A function**: Time shift by the missing-data window, for example `600` seconds for 10 minutes
- **Query B**: same metric, aggregation, and group-by as Query A, without time shift
- **Formula F1**: `B / A`
- **Alert on**: F1, **Condition** Equal to `0`, **Match type** `all the times`
- **Evaluation window**: match the time shift duration

Query A shows groups that existed in the shifted window. If Query B has no current value for one of those groups, F1 evaluates to `0` for that group. For the full walkthrough, see [No Data Alerts for Groups](https://signoz.io/docs/alerts-management/no-data-alerts-for-groups/).

### Alert when request rate drops to zero

Use this for a service that should handle traffic throughout the day.

- **Signal**: Metrics
- **Metric**: `signoz_calls_total`
- **Filter**: `service.name = '<your-service>' AND span.kind = 'SPAN_KIND_SERVER'`
- **Aggregate within time series**: Rate
- **Aggregate across time series**: Sum, grouped by `service.name`
- **Condition**: Below, **Threshold** a small amount above the service's idle request rate
- **Advanced Options → Alert when data stops coming**: enabled

<Admonition type="info">
There is no PromQL variant for this recipe. SigNoz PromQL reads only metrics with cumulative or unspecified temporality, and `signoz_calls_total` uses delta temporality by default, so a PromQL rate over it returns no series and the alert never evaluates. Write this one in the Query Builder, which reads delta metrics. See [Calculating score from metrics](https://signoz.io/docs/alerts-management/apdex-alerts/#calculating-score-from-metrics).
</Admonition>

<Admonition type="info">
A rate-below-threshold alert needs **Alert when data stops coming** enabled. A down service emits no series, so the rate query returns no value instead of a low one. To detect the process itself rather than its traffic, use [Alert when a service process stops running](#alert-when-a-service-process-stops-running).
</Admonition>

### Alert when no business events occur

Set a dead man's switch on a flow that should happen on a schedule, such as orders, payments, or a recurring job. Resource metrics stay green while the flow stops, so alert on the event itself.

- **Signal**: Logs
- **Aggregation**: `count()`
- **Filter**: the log that marks the event, for example `body CONTAINS 'order placed'`
- **Group by**: a tenant or merchant attribute, if you track the flow per customer
- **Evaluation window**: `60m`
- **Condition**: Below, **Threshold** `1`, **Match type** `in total`
- **Advanced Options → Alert when data stops coming**: enabled

Set the window to at least the longest normal gap between events. A 60-minute window with `in total` fires when fewer than one matching log arrives in the last hour. For a scheduled job, widen the window past the job's interval, for example `25h` for a daily job.

## Error and latency alerts

### Alert on high error rate for an endpoint

Page when a specific endpoint fails for a rising share of its own traffic.

Build a trace alert with two queries and a formula:

- **Query A** (error spans): `count()`, filter `service.name = '<your-service>' AND hasError = true`, group by `service.name` and `http.route`
- **Query B** (all spans): `count()`, filter `service.name = '<your-service>'`, group by `service.name` and `http.route`
- **Query B → Having**: `count() > 100` to require a minimum request volume
- **Formula F1**: `(A / B) * 100`, with the y-axis unit set to `Percent (0 - 100)`
- **Alert on**: F1
- **Condition**: Above, **Threshold** `5`, **Match type** `on average` over a 5-minute window

<Admonition type="warning">
Without the **Having** minimum-traffic guard, a single error during a quiet minute (1 error in 30 requests) reads as a 3% error rate and pages you. Require a minimum request count, and prefer `on average` or `all the times` over `at least once` so one noisy data point does not fire the alert.
</Admonition>

To page only on server-side (5xx) failures instead of every error, swap the Query A filter for the status code range: `service.name = '<your-service>' AND http.status_code >= 500`. This excludes 4xx client errors (bad requests, auth failures) that `hasError = true` may also count, depending on your instrumentation.

### Alert when a success ratio drops after enough traffic

Evaluate ratios after the denominator has enough volume. This pattern fits cache hit rate, checkout success rate, payment authorization success rate, or test pass rate per customer.

Build a metric alert with two queries and a formula:

- **Query A** (successful events): count or increase the event metric, filter to success, and group by the entity key, for example `orgId`, `tenant.id`, or `service.name`
- **Query B** (all events): count or increase the same event metric without the success filter, grouped by the same entity key
- **Query B → Having**: require enough volume, for example `count() > 100` or `sum() > 100`
- **Formula F1**: `(A / B) * 100`, with the y-axis unit set to `Percent (0 - 100)`
- **Alert on**: F1
- **Condition**: Below, **Threshold** `90`, **Match type** `on average`

Keep the time aggregation and space aggregation identical for Query A and Query B. Put the Having clause on Query B, since Query B counts the total traffic the ratio needs before it means anything.

To alert on an SLO where a good call must be both successful and fast, add the response-time bound to Query A. This example pages when fewer than 90% of an endpoint's calls both succeed and finish in under 6 seconds:

- **Query A** (good calls): `count()`, filter `service.name = '<your-service>' AND name = '<endpoint>' AND hasError = false AND durationNano <= 6000000000`
- **Query B** (all calls): `count()`, filter `service.name = '<your-service>' AND name = '<endpoint>'`, **Having** `count() > 100`
- **Formula F1**: `(A / B) * 100`, with the y-axis unit set to `Percent (0 - 100)`
- **Condition**: Below, **Threshold** `90`, **Match type** `on average` over a 5-minute window

`durationNano` is the span duration in nanoseconds, so 6 seconds is `6000000000`. Replace `<endpoint>` with the operation name, such as `POST /payments/verify`.

### Alert on high latency for a service or endpoint

Alert on P95 or P99 when slowdowns matter more than averages.

- **Signal**: Traces
- **Aggregation**: P95 (or P99) of span duration
- **Filter**: `service.name = '<your-service>' AND name = '<operation-name>'`, or drop the `name` condition for a service-wide percentile
- **Y-axis unit**: `Nanoseconds`
- **Condition**: Above, **Threshold** `1200`, **Threshold Unit** `ms`
- **Match type**: `at least once` for spike detection, or `on average` for sustained slowness
- **Evaluation window**: `5m`

PromQL variant, against a histogram your application exports with **cumulative** temporality:

```promql
histogram_quantile(0.99, sum by (le, "service.name") (rate({"http.server.request.duration.bucket", "service.name"="<your-service>"}[5m]))) > 1.2
```

Add the histogram's own endpoint label inside the selector to scope it, or leave it out for a service-wide percentile. Match the threshold to the histogram's unit: OpenTelemetry HTTP duration histograms record seconds, so `1.2` means 1200 ms.

<Admonition type="warning">
Point this at a cumulative histogram, not at SigNoz's span metrics. SigNoz PromQL reads only cumulative and unspecified temporality, and `signoz_latency.bucket` is delta by default, so `histogram_quantile` over it returns no series and the alert never evaluates. Check a metric's temporality in [Metrics Explorer](https://signoz.io/docs/metrics-management/metrics-explorer/) before you write PromQL against it. See [Calculating score from metrics](https://signoz.io/docs/alerts-management/apdex-alerts/#calculating-score-from-metrics).
</Admonition>

<Admonition type="warning">
In the Query Builder recipe, set the y-axis unit to `Nanoseconds` before you set **Threshold Unit** to `ms`. The Query Builder returns span duration in nanoseconds and does not set the unit for you, and the **Threshold Unit** list is filtered to the y-axis unit's category, so it stays disabled until the y-axis unit is set. With both set, `1200` means 1200 ms. With neither, a bare threshold of `1200` is read as 1200 ns and the alert fires on almost every request.
</Admonition>

<Admonition type="info">
On self-hosted SigNoz with a sharded ClickHouse cluster, percentile values computed across shards can read higher than the raw data. Cross-check against the dashboard before you tune the threshold.
</Admonition>

### Alert on exception spikes

Alert when application exceptions appear or exceed a count. The exception type, message, and stack trace live on span events, which the traces Query Builder does not expose, so write this alert as a ClickHouse query. Reserve the Query Builder for span-level error conditions, such as the count of failed spans. See [Exceptions-based alerts](https://signoz.io/docs/alerts-management/exceptions-based-alerts/).

```sql
SELECT
    count() AS value,
    toStartOfInterval(timestamp, toIntervalMinute(1)) AS interval,
    serviceName
FROM signoz_traces.distributed_signoz_error_index_v2
WHERE exceptionType = 'ConnectionError'
  AND timestamp BETWEEN $start_datetime AND $end_datetime
GROUP BY serviceName, interval;
```

- **Condition**: Above, **Threshold** `0`, **Match type** `at least once`

The query must return a `value` column and an `interval` column for time-series evaluation. Drop the `exceptionType` filter to alert on all exceptions, or change it to the type you care about.

For more ClickHouse examples, including any exception, service-specific spikes, message matching, and escaped exceptions, see [Exceptions-based alerts](https://signoz.io/docs/alerts-management/exceptions-based-alerts/#examples).

## Resource usage alerts

### Alert on host or pod memory usage

Use a utilization metric when one exists, so you skip the byte math:

- **Signal**: Metrics
- **Metric**: `k8s.pod.memory_request_utilization` (ratio, 0.0 to 1.0)
- **Aggregate within time series**: Avg
- **Aggregate across time series**: Max, grouped by `k8s.pod.name`
- **Condition**: Above, **Threshold** `0.8`, **Match type** `all the times` over a 5-minute window

To derive a percentage from raw bytes instead, use a formula. For a host, query A is used memory (`system.memory.usage` filtered with `state != 'free'`) and query B is total memory, both grouped by `host.name`:

- **Formula F1**: `A / B`, with the y-axis unit set to Percent (0.0 - 1.0)
- **Alert on**: F1, Above `0.7`, `all the times`

<Admonition type="warning">
Group both query A and query B by the same key (`host.name` or `k8s.pod.name`) and use the same space aggregation. If the numerator sums memory across several pods while the denominator covers one, the formula reports impossible values like 300% and pages you while the pods sit idle.
</Admonition>

### Alert on container CPU usage

Container CPU is a ratio metric, so 80% maps to a threshold of `0.8`:

- **Signal**: Metrics
- **Metric**: `k8s.container.cpu_limit_utilization`
- **Aggregate within time series**: Avg (smooths short spikes over the window)
- **Aggregate across time series**: Max, grouped by `k8s.cluster.name`, `k8s.namespace.name`, `k8s.pod.name`, `k8s.container.name`
- **Condition**: Above, **Threshold** `0.8`, **Match type** `all the times`

For the full walkthrough, including the metric prerequisites, see [Create a CPU Usage Alert for Kubernetes Containers](https://signoz.io/docs/alerts-management/user-guides/k8s-cpu-usage-alert/).

<Admonition type="info">
If a resource alert fires but the graph looks below the threshold, compare the firing value in **Alert History** with the alert's evaluation window, match type, and threshold unit. Common mistakes include using `80` for a ratio metric that expects `0.8`, or using `in total` for CPU where `on average` or `all the times` fits better. See [Alerts Firing Without Visible Threshold Breach](https://signoz.io/docs/alerts-management/troubleshooting/alerts-firing-without-visible-threshold-breach/).
</Admonition>

## Log alerts

### Alert on a spike in error logs

Alert on a rising share of error logs for a service when a fixed count would page during normal traffic changes.

- **Query A** (error logs): `count()`, filter `service.name = '<your-service>' AND severity_text IN ('ERROR', 'FATAL')`
- **Query B** (all logs): `count()`, filter `service.name = '<your-service>'`
- **Formula F1**: `(A / B) * 100`, with the y-axis unit set to `Percent (0 - 100)`
- **Alert on**: F1, Above `5`, `on average` over `5m`

For an absolute count, drop Query B and alert on Query A with a count threshold. To write the same logic as a ClickHouse query, see the examples in [Log-based alerts](https://signoz.io/docs/alerts-management/log-based-alerts/).

### Alert when telemetry export errors appear

Your application or Collector logs must already reach SigNoz. Then export failures page you before they leave gaps in your data.

- **Signal**: Logs
- **Aggregation**: `count()`
- **Filter**: `body CONTAINS 'BatchSpanProcessor.ExportError' OR body CONTAINS 'DeadlineExceeded' OR body CONTAINS 'Exporting failed'`
- **Group by**: `service.name`, `host.name`, or `k8s.pod.name`, depending on where the exporter runs
- **Condition**: Above, **Threshold** `0`, **Match type** `at least once`
- **Evaluation window**: `5m`

The process producing exporter errors must send its logs to SigNoz. For persistent exporter failures, check endpoint, protocol, compression, timeout, and retry settings in [SigNoz Cloud ingestion troubleshooting](https://signoz.io/docs/ingestion/signoz-cloud/troubleshooting/troubleshooting/).

## Telemetry volume and cost alerts

### Alert when log ingestion spikes

A deploy, a batch job, a debug-logging change, or a runaway loop can multiply log volume overnight and move your bill.

- **Product area**: Cost Meter Alerts
- **Meter metric**: `signoz.meter.log.size` for bytes, or `signoz.meter.log.count` when you care about event volume
- **Filter**: optional, for example `service.name = '<your-service>'` or `signoz.workspace.key.id = '<ingestion-key-id>'`
- **Group by**: `service.name`, `deployment.environment`, or `signoz.workspace.key.id`
- **Aggregation**: Increase
- **Condition**: Above the normal daily or hourly baseline
- **Match type**: `in total` for cumulative windows, or `on average` for rolling windows

Use [Meter Explorer](https://signoz.io/docs/cost-meter/meter-explorer/) to find the normal baseline first, then configure the alert with [Cost Meter Alert Configuration Guide with Examples](https://signoz.io/docs/cost-meter/alert-configuration-guide/). To get notified before an ingestion key reaches its daily cap, use the bell icon on the ingestion key limit as described in the cost meter alert guide.

## Validate

Confirm a recipe works before you rely on it:

1. Run the query in the alert form. The chart preview must show at least one series against the threshold line.
2. Click **Test Notification**. Confirm the alert reaches every channel you selected.
3. Read the delivered message. Each attribute you referenced must show a real value, not the attribute name.
4. Wait for one evaluation window. Then open [alert history](https://signoz.io/docs/alerts-management/alerts-history/) and confirm the rule evaluated.

An empty chart preview means the query returns no data. Correct the query before you save the rule.
