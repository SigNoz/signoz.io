You can investigate an incident in [SigNoz Cloud](https://signoz.io/log-management/) by collecting application and cloud logs, then comparing records from the same time and resources in [Logs Explorer](https://signoz.io/docs/userguide/logs_query_builder/). If your application logs the provider request ID and the cloud record contains it too, that ID can help you find the corresponding call.

## Follow one failed upload

For example, a checkout service saves an order receipt in Amazon S3 after accepting payment. If S3 rejects the upload, the checkout can return a server error even though payment succeeded. We wrote example application logs and records in the format used by AWS CloudTrail, which can record AWS API activity, to show how to investigate this failure.

Our example records use an application request ID to identify the checkout request and an AWS request ID to identify the S3 call. We searched for both in Logs Explorer to find the application logs and corresponding cloud record, then ordered the results by time. Four records show the payment being accepted, an `AccessDenied` response, the application's upload error and its HTTP 500 response.

The records point to the rejected upload, but `AccessDenied` alone does not identify the permission or policy responsible. For your own incident, compare available details such as the account, region, bucket and object before treating records as related. If an ID is missing, those details and the time can help you find candidates, but a close timestamp alone does not establish a connection.

If you cannot find a record, check whether your filters include both sources. For example, a service or severity filter may exclude the cloud record, and account or environment fields may be missing or have different names or values. Check the timestamps too. CloudTrail's <a href="https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-record-contents.html" target="_blank" rel="noopener noreferrer nofollow">`eventTime`</a> records when AWS completed the request; the log can arrive later. Widen the time range if the stored timestamps or clocks differ.

A record can also be missing if it was not collected or has expired. See the [application log collection methods](https://signoz.io/docs/logs-management/send-logs/collection-methods/) to send application logs to SigNoz Cloud. For an S3 upload like this one, CloudTrail must capture the relevant <a href="https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html" target="_blank" rel="noopener noreferrer nofollow">S3 data events</a>, which AWS does not enable by default. You can then <a href="https://docs.aws.amazon.com/awscloudtrail/latest/userguide/send-cloudtrail-events-to-cloudwatch-logs.html" target="_blank" rel="noopener noreferrer nofollow">send those events to CloudWatch Logs</a> and follow the [CloudWatch collection guide](https://signoz.io/docs/userguide/send-cloudwatch-logs-to-signoz/).
