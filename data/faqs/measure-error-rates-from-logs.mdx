Compare the share of requests that return a server error with the total number of requests. If traffic rises while that share stays the same, the extra errors may reflect the extra traffic. If the share rises too, a greater proportion of requests is failing.

## Compare the counts and the percentage

For example, take a checkout service that records one log when each request completes, with its response status and request ID. We sent requests to the service in three separate one-minute periods. The first had 10 HTTP 500 responses out of 1,000 requests, a failure percentage of 1%. When traffic doubled to 2,000 requests, 20 returned HTTP 500, so the percentage stayed at 1%. In the third period, 100 of 2,000 requests returned HTTP 500, raising the percentage to 5%.

In SigNoz Cloud, the Logs Explorer table below groups these results by example phase. It shows the failed and total counts alongside the `100*A/B` percentage, where A counts HTTP 5xx responses and B counts all completed requests.

To make this comparison for your service, count the same set of completion records in both queries, with the HTTP 5xx filter only on A. Keep the service, route, time range, interval, and grouping aligned. The [multi-query guide](https://signoz.io/docs/querying/multi-query-analysis/) explains how to use the formula in Logs Explorer.

The total count needs one completion record for each successful and failed request. Counting every application log can inflate it because one request may write several messages. If B is zero, there is no meaningful percentage. Missing or duplicate completion records can also distort the result, and failures without a completion record need another recorded outcome.

## Keep the counts visible

Add the request count, server-error count, and percentage to a dashboard to see how failures change with traffic. If the percentage rises, filter the completion logs to HTTP 5xx and open a failed record to inspect its status and request ID.

You can also select the percentage formula as the target of a [log-based alert](https://signoz.io/docs/alerts-management/log-based-alerts/). For example, with one-minute points, **At least once** above 2% in a five-minute window checks whether any point exceeds that threshold.
