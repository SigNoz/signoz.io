Logs may be missing from SigNoz Cloud because they reached a different destination, fall outside your search, or were removed or rejected along the way. Start with the destination and search scope, then check the collection and export path if you still cannot find them.

An application may send logs directly to SigNoz Cloud or through an OpenTelemetry Collector. A Collector response reports the outcome at that hop; it does not confirm that the Collector delivered the logs to SigNoz Cloud.

## Check the destination and search scope

Check the exporter that sends to SigNoz Cloud, whether it runs in your application or in a Collector. Compare its endpoint and ingestion key with **Settings → Ingestion** in the workspace you are searching. For Self-Hosted SigNoz, check that you have opened the instance that receives the logs. The [ingestion guide](https://signoz.io/docs/ingestion/signoz-cloud/overview/) explains the Cloud settings.

Next, search for one log whose message and approximate time you know. For example, a checkout service called `checkout-api-delivery` writes a log when it receives an order. In [Logs Explorer](https://signoz.io/docs/userguide/logs_query_builder/), clear filters such as service and severity, choose a time range around the event, and search its message. Widen the range if you are unsure of the timestamp.

In this example, a search for `delivery-check-4821-86062494` returned the matching log. Filtering for `checkout-api-delivery-wrong` hid it, while filtering for `checkout-api-delivery` returned it again. If you find your log, inspect its timestamp and service fields before narrowing your search. An older timestamp or an unexpected service name can put it outside the original search.

## Check the path to SigNoz

If the search still returns no log, follow it from the source to SigNoz. Confirm that the application wrote it. If you use a Collector, check that it can read the source and that its processing rules do not change or drop the record. Then inspect the outgoing exporter’s errors and warnings. Receiver activity alone shows that data reached the Collector, not that it reached SigNoz Cloud.

For OpenTelemetry Protocol (OTLP) over HTTP, a `200` response can still report rejected records in a partial-success response. Check exporter warnings as well as errors; the <a href="https://opentelemetry.io/docs/specs/otlp/#otlphttp-response" target="_blank" rel="noopener noreferrer nofollow">OTLP specification</a> explains the response. The [missing-data guide](https://signoz.io/docs/ingestion/signoz-cloud/troubleshooting/data-not-appearing/) gives checks for each hop.

After a correction, send a new identifiable log and look for it in the intended workspace. If it is still missing, keep the message, UTC time, relevant configuration and exporter errors for further investigation. Redact ingestion keys and other secrets before sharing the configuration.
