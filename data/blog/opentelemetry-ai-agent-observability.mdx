AI agents don't just call a model and return its response. Instead, they orchestrate entire workflows that involve selecting tools for LLMs to use, evaluating guardrails, routing between LLM calls, and managing context across conversation turns. This means that a single user request can spawn dozens of internal steps, each one a potential point of failure, latency, or unexpected cost.

AI agent observability is the practice of capturing these agent execution flows so you can understand _what_ the agent did, _why_ it chose that path, and _how_ it performed. In terms of the implementation, it means tracing every step in an agent run, such as tool calls and model invocations, and correlating them with system-level signals like latency, token usage, and error rates.

Tracing builds the foundation for agent observability, as a single trace maps an agent's decision graph per-run, revealing which tools were called and what their output was, what the model returned, what input context was passed to the model, and so on.<br />
Without tracing, debugging an AI agent becomes a game of trying to guess which event triggered what decision in the agentic loop, and why.

## Why do AI agents need observability?

When building traditional software, engineers could start small with application observability, and reach for more comprehensive implementations once the application scaled up or the business asked.<br />
Consider a startup that found product-market fit and must now adhere to Service Level Agreements (SLAs) for enterprise clients. At this stage, they must observe their entire distributed system to maintain service uptime.

However, the same can't be said for agentic applications. Every request can trigger a different combination of tool calls, guardrail checks, and model invocations, meaning the resulting behaviour can vary significantly across runs.

### LLM non-determinism compounds across agent steps

A single LLM call is already non-deterministic: the same prompt can produce different outputs across runs. Agents amplify this because they chain multiple LLM calls together, where the output of one step determines the input of the next.

This means variance doesn't just exist at one point. Rather, it compounds across the workflow. A slightly different model response in step one can cause the agent to select a completely different tool in step two, which changes the context passed to step three, and so on. Reproducing a specific agent run becomes nearly impossible without capturing the full execution path.

### Agents can silently produce incorrect results

Traditional software either succeeds or throws an error. Very rarely do you have situations where application response quality degrades without notice. Agents introduce a failure mode that's harder to catch: the workflow completes without any error, but the agent selected the wrong tool, retrieved stale context, or returned a response that is confidently incorrect.

Without observability, these silent failures only surface when a user complains or when downstream systems consume bad output. Tracing each decision in the agentic loop, such as which tool was selected, what context was available, what the model actually returned, is the only reliable way to evaluate whether an agent's "successful" run was actually logically correct.

### Cost and latency are unpredictable by design

Agents decide at runtime how many tools to call and how many LLM roundtrips to make. A simple user query might resolve in one LLM call, while a similar query might trigger several tool calls and model invocations depending on the agent's reasoning.

This makes cost and latency inherently unpredictable. Observability lets engineers track token usage, tool call frequency, and per-step latency across runs to identify expensive patterns early. For example, if two models with different pricing tiers perform comparably for a given workload, engineers can switch to the cheaper option — but only if they have the data to make that comparison.

## How does OpenTelemetry enable AI agent observability?

[OpenTelemetry](https://signoz.io/opentelemetry/) (OTel) is a CNCF graduated project for instrumenting applications to emit telemetry data (primarily [traces, metrics, and logs](https://signoz.io/blog/three-pillars-of-observability/)) in a vendor-neutral format. What makes it uniquely suited for agentic applications is that your visibility extends beyond the AI agent to the entire request: what endpoint did the user call, what DB queries ran, were any background jobs enqueued, did the application make any downstream API calls?

Before we move ahead, let’s look at how the OpenTelemetry community is standardizing telemetry standards, capture, and export processes for agentic applications.

### Evolving GenAI standards

While early instrumentation discussions focused solely on "LLM tracing", OpenTelemetry standardizes AI telemetry under the broader umbrella of `Generative AI` (GenAI), using <a href="https://github.com/open-telemetry/semantic-conventions-genai/blob/4f85037ef86e92c510d2ef881a58f1076f6fc0e4/docs/gen-ai/README.md" rel="noopener noreferrer nofollow" target="_blank">semantic conventions prefixed with `gen_ai.*`</a>.

Because GenAI patterns and agentic harnesses evolve far more rapidly than traditional HTTP or database libraries, OpenTelemetry created a dedicated repository, <a href="https://github.com/open-telemetry/opentelemetry-python-genai" rel="noopener noreferrer nofollow" target="_blank">`open-telemetry/opentelemetry-python-genai`</a>, to enable maintainers to independently develop and publish these libraries.

This migration introduced a cleaner, **split-scope architecture**:

1. **`opentelemetry.instrumentation.genai.openai_agents`**: Instruments the agent orchestration harness, emitting spans for workflow execution (`invoke_workflow`) and agent routing (`invoke_agent`).
2. **`opentelemetry.instrumentation.genai.openai`**: A companion package that instruments the underlying model calls (`chat`), capturing token usage (`gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`), model parameters, and prompt context.

The <a href="https://github.com/open-telemetry/opentelemetry-python-contrib/tree/main/instrumentation-genai/opentelemetry-instrumentation-openai-agents-v2" rel="noopener noreferrer nofollow" target="_blank">earlier iteration of Agents instrumentation</a> attempted to capture both agent workflows and raw model invocations within a single package. Decoupling agent loops from raw model calls ensures each layer strictly follows OpenTelemetry GenAI semantic conventions.

Additionally, because `opentelemetry-bootstrap` has not yet added these dedicated GenAI packages to its automated discovery list, you must install and track them separately through your `requirements.txt` or `pyproject.toml` files.

<Figure src="/img/blog/2026/06/opentelemetry-llm-bootstrap-gap.webp" alt="Developers must install latest GenAI instrumentation libraries manually as they aren't yet registered with opentelemetry-bootstrap." caption="Developers must install latest GenAI instrumentation libraries manually as they aren't yet registered with opentelemetry-bootstrap." />

<KeyPointCallout title="Varying maturity across GenAI instrumentation packages">

Maturity currently varies across the OpenTelemetry GenAI instrumentation libraries:

- **Core provider SDKs**: Packages for underlying LLM clients (such as OpenAI, Anthropic, and Google GenAI) have solid coverage, reliably capturing model calls, token usage metrics, latency, and streaming chunks.
- **Agent frameworks**: Higher-level agentic libraries (such as OpenAI Agents, LangChain, and Agno) are in active beta and continuing to evolve rapidly. Agent-centric primitives—such as cross-agent handoffs and guardrail evaluations—are active areas of development as the broader GenAI semantic conventions expand.

We recommend that you pin your instrumentation packages explicitly and check their changelogs when upgrading dependencies.

</KeyPointCallout>

#### The core agentic setup

Our web application exposes an NBA Reporter agent that answers questions on NBA topics (e.g., `general` news or `finals`), performs web research, calculates team win percentages, and retains conversation history across turns via server-managed session persistence.

The <a href="https://github.com/SigNoz/examples/blob/main/python/otel-ai-agent-observability-demo/app/agent_service.py" rel="noopener noreferrer nofollow" target="_blank">`agent_service.py` file</a> defines the agent configuration and the execution function used by our FastAPI endpoint.

We initialize the agent with a system prompt, tools, input guardrails, and model selection. The application uses **`gpt-6-luna`** (`OPENAI_MODEL = "gpt-6-luna"` in `app/config.py`), which delivers consistent multi-turn reasoning and tool formatting:

```python
NBA_AGENT = Agent(
    name="NBA_Reporter",
    instructions=NBA_INTERACTIVE_PROMPT,
    tools=[WebSearchTool(), calculate_win_percentage],
    input_guardrails=[nba_content_guardrail],
    model=OPENAI_MODEL,
)
```

The `calculate_win_percentage` function tool gives the agent a deterministic way to calculate and display team win percentages without the risk of arithmetic hallucinations:

```python
@function_tool
def calculate_win_percentage(wins: int, losses: int) -> str:
    """Calculates the winning percentage for an NBA team given their wins and losses."""

    total_games = wins + losses
    if total_games == 0:
        return ".000"

    return f"{wins / total_games:.3f}".lstrip("0")
```

To prevent misuse or off-topic queries, we define an input guardrail. When a user prompt does not match relevant basketball keywords, the function returns a `GuardrailFunctionOutput` with `tripwire_triggered=True`:

```python
@input_guardrail()
def nba_content_guardrail(
    context: RunContextWrapper[None],
    agent: Agent,
    input_data: str | list,
) -> GuardrailFunctionOutput:
    """Ensures the user query is relevant to basketball/NBA."""

    keywords = [
        "nba",
        "basketball",
        "player",
        ... # truncated for brevity
    ]

    # extract the last user message from chat history
    if isinstance(input_data, list):
        latest_user_message = next(
            (
                item.get("content", "")
                for item in reversed(input_data)
                if isinstance(item, dict) and item.get("role") == "user"
            ),
            "",
        )
        input_query = latest_user_message
    else:
        input_query = input_data

    input_query = input_query.lower()
    is_relevant = any(keyword in input_query for keyword in keywords)

    if len(input_query) < 5 or is_relevant:
        return GuardrailFunctionOutput(tripwire_triggered=False, output_info=None)

    return GuardrailFunctionOutput(
        tripwire_triggered=True,
        output_info={
            "reason": "The request is off-topic. Please ask questions relevant to NBA or basketball."
        },
    )
```

Setting `tripwire_triggered=True` instructs the Agents SDK to abort execution and raise an `InputGuardrailTripwireTriggered` exception. We intercept this in a FastAPI exception handler to record the exception event directly on the active OpenTelemetry span before returning an HTTP 400 response:

```python
@app.exception_handler(InputGuardrailTripwireTriggered)
async def handle_guardrail_block(
    request: Request,
    exc: InputGuardrailTripwireTriggered,
) -> JSONResponse:
    guardrail_msg = exc.guardrail_result.output.output_info
    span = trace.get_current_span()

    span.record_exception(exc)
    return JSONResponse(status_code=400, content={"detail": guardrail_msg})
```

#### Managing session context across turns

The `run_agent_turn` function completes our implementation. The agent uses the `OpenAIConversationsSession` object to persist and gather conversation context across turns.

If no `session_id` was passed, the session object triggers the creation of a new conversation session. In a follow-up request, the user can attach this ID to ensure the agent has context of the conversation thus far.

```python
def run_agent_turn(
    topic: str,
    user_message: str | None,
    session_id: str | None,
) -> dict:
    nba_topic = _validate_topic(topic)
    prompt = build_nba_turn_prompt(nba_topic, user_message)

    # if no session ID was given, the sdk internally creates a session_id during the turn
    # subsequent calls which pass the ID maintain the conversation context
    session = OpenAIConversationsSession(conversation_id=session_id)
    result = Runner.run_sync(NBA_AGENT, prompt, session=session)

    message = sanitize_agent_message((result.final_output or "").strip())
    ... # truncated for brevity

    return {
        "topic": topic,
        "session_id": session.session_id,
        "message": message,
        "model": OPENAI_MODEL,
        "usage": usage,
    }
```

### Exploring the trace hierarchy in SigNoz

Now let's visualize in SigNoz the multi-step trace that invoked tool use:

<Figure src="/img/blog/2026/10/otel-ai-agent-trace-details.gif" alt="Walkthrough of the OpenTelemetry-instrumented multi-step AI agent trace." caption="Walkthrough of the OpenTelemetry-instrumented multi-step AI agent trace." />

Modern OpenTelemetry GenAI instrumentation structures the request into a clean, hierarchical span tree:

```plain
POST /agent/turn                                     [fastapi]              Server   26.00s
├─ POST /agent/turn http receive                     [asgi]                 Internal
├─ POST /v1/conversations                            [httpx]                Client
├─ GET  /v1/conversations/{id}/items?order=asc       [httpx]                Client
├─ invoke_workflow Agent workflow                    [genai.openai_agents]  Internal 24.41s
│  ├─ POST /v1/conversations/{id}/items              [httpx]                Client
│  └─ invoke_agent NBA_Reporter                      [genai.openai_agents]  Internal 23.71s
│     ├─ chat gpt-6-luna                             [genai.openai]         Client    3.94s
│     │  └─ POST /v1/responses                       [httpx]                Client    3.84s
│     ├─ execute_tool calculate_win_percentage       [genai.openai_agents]  Internal
│     ├─ execute_tool calculate_win_percentage       [genai.openai_agents]  Internal
│     ├─ POST /v1/conversations/{id}/items           [httpx]                Client
│     ├─ chat gpt-6-luna                             [genai.openai]         Client   18.21s
│     │  └─ POST /v1/responses                       [httpx]                Client   17.90s
│     └─ POST /v1/conversations/{id}/items           [httpx]                Client
├─ POST /v1/traces/ingest  ×3                         [httpx]                Client
└─ POST /agent/turn http send  ×2                    [asgi]                 Internal
```

This trace highlights several key structural details of the agentic loop:

1. **Full-stack request lifecycle**: The trace begins at the FastAPI boundary (`POST /agent/turn`). Before the agent workflow executes, child HTTP spans show the session layer fetching conversation history (`GET /v1/conversations/{id}/items`).
2. **Dedicated agentic scopes**: The agent orchestration harness is captured under `opentelemetry.instrumentation.genai.openai_agents` via the `invoke_workflow` and `invoke_agent` spans, defining the agent's decision boundary.
3. **Iterative tool execution loop**: Rather than a single model completion, the trace maps the full multi-step loop:
   - **Initial model call (`chat gpt-6-luna`, 3.94s)**: The model processes the turn, detects the win percentage query, and emits tool call instructions.
   - **Tool execution (`execute_tool calculate_win_percentage` ×2)**: The agent loop executes our tools, followed by an HTTP span persisting the tool results to the conversation session.
   - **Final synthesis call (`chat gpt-6-luna`, 18.21s)**: The model receives the tool outputs and generates the comprehensive user-facing response.
4. **Standardized semantic convention attributes**: Selecting either `chat gpt-6-luna` span reveals a set of standardized GenAI attributes:
   - `gen_ai.provider.name = "openai"`
   - `gen_ai.request.model = "gpt-6-luna"` and `gen_ai.response.model = "gpt-6-luna"`
   - `gen_ai.operation.name = "chat"`
   - `gen_ai.response.finish_reasons = "["tool_calls"]"` or `gen_ai.response.finish_reasons = "["stop"]"`
   - `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens`
   - `gen_ai.system_instructions` and `gen_ai.tool.definitions`

<KeyPointCallout title="Clarifying the duplicate tool calls">

You must have noticed the duplicate `calculate_win_percentage` tool calls. Several previous runs with the same prompt only triggered a single tool call, as expected given the trivial workload. In this run, the agent loop triggered a second tool call, and its input arguments tell the story: `gen_ai.tool.call.arguments: "{"wins":0,"losses":0}"`.

The tool call was made with technically valid but impractical input and received an equally impractical result: `gen_ai.tool.call.result:".000"`.
Although this didn't affect the final result, this further goes to show the non-deterministic nature of AI agents, and underlines why we need observability for AI workloads.

</KeyPointCallout>

#### Inspecting message content and privacy controls

Because we set `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=span_only`, the instrumentation populates `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, and `gen_ai.tool.definitions` directly as span attributes. This allows engineers to inspect the exact prompts, system instructions, and model completions for each turn during debugging.

In environments with sensitive data or strict PII compliance, prompt content capture can be turned off entirely by setting:

```bash
export OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=no_content
```

This retains model timing, token counts, and span hierarchies while omitting raw message payloads and input/output values from the exported telemetry.

When an off-topic query triggers the input guardrail tripwire, the agent stops execution before calling the model. 

In our FastAPI exception handler, intercepting `InputGuardrailTripwireTriggered` and invoking `span.record_exception(exc)` marks the root span as an error. Clicking into the span's Events tab on the right reveals the recorded exception event.
