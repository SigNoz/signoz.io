Datadog Kubernetes monitoring is the bundle of components Datadog ships to pull metrics, logs, traces, and events out of a Kubernetes cluster and into the Datadog backend. It usually consists of three moving parts - the `Datadog Agent` running as a DaemonSet on every node, the `Datadog Cluster Agent` running as a singleton that talks to the Kubernetes API server, and the `Datadog Operator` (or the older Helm chart) that manages those deployments through a Kubernetes-native interface. Once installed, the Agent auto-discovers workloads through pod annotations, scrapes `kubelet` and `kube-state-metrics`, tails container stdout for logs, and forwards everything to Datadog over a proprietary HTTP API.

The setup is straightforward and the Kubernetes dashboards in Datadog look good in a demo, but the friction shows up at month-end when Datadog APM is billed at `\$31` per host per month on the Pro plan, infrastructure monitoring adds another per-host charge on top, and Datadog's auto-tagging on Kubernetes (`pod_name`, `container_id`, `kube_namespace`, `kube_deployment`, and friends) drives custom metrics cardinality to numbers that turn into surprise invoice lines. Most teams running Datadog on Kubernetes report that the K8s side of the bill grows faster than the cluster itself.

This article walks through how Datadog actually monitors Kubernetes, where the costs and operational pain points compound, and how teams replace the Datadog stack with OpenTelemetry and SigNoz.

## What Datadog Drops Into Your Cluster

A Datadog install on Kubernetes is four moving parts that ship together. Each one is does a different job, and each one is a separate Datadog-specific component you'll have to remove if you ever migrate.

- Datadog Agent: Runs as a DaemonSet, putting one Agent pod on every node to scrape `kubelet`, tail container stdout, forward APM traces from `dd-trace`-instrumented apps, and collect node-local events, all sent to Datadog over a proprietary HTTP API.
- Datadog Cluster Agent: Runs as a singleton, watches the Kubernetes API, runs cluster-level integrations like `kube-state-metrics`, and exposes the External Metrics API for HPA-driven autoscaling.
- Datadog Operator (or Helm chart): Deploys and reconciles both Agents via a `DatadogAgent` Custom Resource, with the older `datadog/datadog` Helm chart as the alternative path on legacy installs.
- Pod annotations: Workload discovery happens through `ad.datadoghq.com/*` annotations that pin each monitoring config to the workload's deployment YAML and need a pod restart to change.

Every piece of that stack is Datadog-specific. The wire protocol, the Operator, the Cluster Agent, and the annotation schema all stop working the moment you point at another backend, which is what makes moving off this stack an operational change rather than a code one.

## The Compounding Meters That Drive Your Datadog Bill on Kubernetes

Datadog doesn't have one Kubernetes pricing problem. It has several that multiply, because every meter on the invoice tracks something Kubernetes naturally produces a lot of. Host count grows when the cluster autoscales. Container count grows when pods spin up. Custom metrics cardinality grows every time a pod restarts. Log volume grows with every sidecar and init container the team adds. The bill is the product of all of them.

### Per-host pricing scales with node count, not load

Datadog APM and Infrastructure are both priced per host. On Kubernetes, "host" means "node," so a cluster that auto-scales from 20 nodes to 200 during peak load is also auto-scaling your Datadog bill. The pricing model rewards you for keeping workloads tightly packed on fewer larger nodes and penalises clusters that scale horizontally, which is the opposite of how most Kubernetes-native architectures are built.

### Per-container pricing on top

Datadog's container monitoring tier adds a separate per-container fee on top of the node price. The bill ends up structured as host count × per-host APM + container count × per-container + log volume + custom metrics, all of which scale independently with cluster growth.

### Custom metrics cardinality from Kubernetes' default tag set

Datadog auto-attaches `pod_name`, `container_id`, `kube_namespace`, `kube_deployment`, `kube_replica_set`, and several other tags to every Kubernetes metric. Pod names rotate every deploy, container IDs rotate every restart, and replica set names rotate every rolling update. Each rotation creates new time series Datadog counts as separate custom metrics. A team that emits one cleanly-named application metric can easily be billed for tens of thousands of unique series after Datadog's auto-tagging is applied.

### Log indexing cost on top of ingestion

Datadog Logs charges `\$0.10/GB` for ingestion and an additional `\$1.06–\$2.50` per million events for indexing, with retention adding further multipliers. Kubernetes log volume tends to be high because every sidecar, init container, and ambient platform component emits its own stream, so the indexing line on the invoice is usually larger than teams estimate going in.

### DaemonSet resource overhead

The Agent runs on every node, and the Cluster Agent runs centrally. On a busy cluster, the Agent's CPU and memory footprint becomes visible in the resource budget, which means the cluster is also paying its cloud provider for the compute that runs the monitoring stack itself.

## DaemonSet, Sidecar, or Gateway: The Footprint Choice Datadog Doesn't Give You

Most observability tools on Kubernetes give you a single deployment pattern and ask you to live with the trade-offs. Datadog's collection pattern is fixed: the `Datadog Agent` runs as a DaemonSet, one pod per node, and that's the only supported topology. If your cluster runs hundreds of small nodes, you get hundreds of Agent pods consuming CPU and memory on every node whether you need them or not.

OpenTelemetry gives you three patterns and lets you pick per workload:

- **DaemonSet** — same shape as the Datadog Agent. One Collector per node, scrapes local `kubelet` and `cAdvisor`, tails local container logs. Best when most data is node-local.
- **Sidecar** — a Collector container injected next to your application pod. Stronger isolation and zero noisy-neighbour risk between workloads, at the cost of a Collector container per pod. Rarely needed, but available.
- **Gateway** — a centralised Collector deployment that the cluster ships data to. Zero per-pod overhead and horizontally scalable, so your monitoring stack scales independently of cluster size. Best for high-traffic clusters or any team optimising the resource footprint of their observability layer.

The practical effect is that an OpenTelemetry deployment can be tuned for the cluster you actually run. A 500-node cluster running batch workloads doesn't need 500 Agent pods sitting idle most of the day; it needs a gateway with two or three replicas. Datadog's per-host pricing makes this distinction expensive twice over: the Agent is on every node by design, and you pay per node whether the Agent is doing useful work or not.

## Datadog vs OpenTelemetry for Kubernetes

The contrast comes down to one design choice: Datadog's Kubernetes stack is built around its own Agent, Cluster Agent, and Operator, while OpenTelemetry is an open standard that any backend can implement and any team can run without committing to a single vendor.

| Aspect | Datadog Kubernetes | OpenTelemetry on Kubernetes |
| --- | --- | --- |
| **Maintained by** | Datadog | The CNCF (Cloud Native Computing Foundation) |
| **Collection agent** | Datadog Agent (DaemonSet) | OpenTelemetry Collector (DaemonSet or sidecar) |
| **Cluster-level integrations** | Datadog Cluster Agent | OTel Collector + Kubernetes Receiver |
| **Install path** | Datadog Operator or Helm chart | OTel Operator or Helm chart (CNCF maintained) |
| **Auto-discovery** | `ad.datadoghq.com/*` pod annotations | OTel target allocator, Kubernetes attributes processor |
| **Wire protocol** | Proprietary Datadog HTTP API | OTLP (open standard) |
| **Pricing model** | Per-host, per-container, custom metrics by cardinality | Set by the backend you choose |
| **Backend** | Datadog only | Any OTLP-compatible backend (SigNoz, etc.) |

Most pieces of the Datadog Kubernetes stack have a direct OpenTelemetry equivalent that does the same job without binding the cluster to one vendor.

## Signals That Datadog Has Stopped Fitting Your Cluster

Three patterns push teams to pull the Datadog Agent off their cluster, and most teams that migrate hit two of them at once.

### The Bill Scales Faster Than the Cluster

Per-host charges multiply by node count, per-container charges multiply by pod count, and custom metrics charges multiply by the cardinality of Kubernetes' default tags. Each of those three meters tracks something a Kubernetes cluster naturally produces a lot of, and they compound rather than overlap. The result is that the K8s side of the Datadog bill tends to grow faster than the underlying cluster, especially on clusters that autoscale aggressively or run a lot of short-lived workloads.

### Portability Becomes a Platform Requirement

OpenTelemetry is the standard the broader Kubernetes ecosystem has settled on, with the OTel Collector and the OTel Operator both available as CNCF projects and every major cloud provider now publishing OTLP-native pipelines. Picking OpenTelemetry means the instrumentation work is reusable if you ever switch backends, while Datadog's Operator, Cluster Agent, and `dd-trace` SDKs only work with Datadog. Platform teams that have to justify lock-in to their org usually find the OTel argument easier to defend.

### Operational Footprint Stops Fitting

The Datadog Cluster Agent is a singleton, which becomes a scaling and reliability concern on large clusters. The OpenTelemetry Collector can act as both a DaemonSet and a centralised gateway, and the gateway path is horizontally scalable. Teams that have hit Cluster Agent throughput limits on large clusters or want monitoring infrastructure that scales independently of cluster size usually find the OTel architecture easier to operate.

If any of these apply, the swap itself is mechanical. You install the OpenTelemetry Operator, deploy a Collector DaemonSet (or use the Kubernetes Receiver pattern), point your existing applications at OTLP, and remove the Datadog Agent once data flow is validated. ## One OpenTelemetry Collector Replaces Four Datadog Components

Most teams that migrate aren't just changing where data lands, they're shrinking what their platform team has to operate. A single `OpenTelemetry Collector` deployment, configured once, handles node-local collection, cluster-level scraping via the `Kubernetes Cluster Receiver`, and OTLP forwarding to your backend. The `OpenTelemetry Operator` manages the Collector lifecycle the same way the Datadog Operator manages Datadog's stack, and auto-instrumentation injection happens through standard Kubernetes annotations rather than vendor-specific ones. The Datadog Cluster Agent singleton, which becomes a scaling bottleneck on large clusters, disappears entirely.

The replacement isn't more components, it's fewer. Teams that have done it usually report that the new monitoring stack is easier to reason about than the one they removed, which is rare for a migration of any kind.

## FAQs

**How does Datadog monitor Kubernetes?**

Through three components: the `Datadog Agent` as a DaemonSet on every node, the `Datadog Cluster Agent` as a singleton for cluster-level data and the Kubernetes API, and the `Datadog Operator` (or Helm chart) to manage both.

**Is the Datadog Agent open source?**

The Agent's source is on GitHub, but the wire protocol it speaks and the backend it sends to are Datadog's. You can read the code but you can't send Agent traffic anywhere other than Datadog without a translation layer.

**Datadog Operator or Helm chart, which one should I use?**

The Operator is the newer, Datadog-recommended path and uses a `DatadogAgent` Custom Resource. The Helm chart is older but still maintained. Both produce the same runtime; the choice is mostly about how your team prefers to manage configuration.

**Does Datadog charge per Kubernetes node?**

Yes. Datadog APM and Infrastructure are both priced per host, and on Kubernetes "host" means "node." Per-container charges sit on top, and custom metrics cardinality is billed separately.

**Why does my Datadog bill grow when my cluster auto-scales?**

Per-host pricing scales linearly with node count. Auto-scaling from 20 to 200 nodes during peak load multiplies the Datadog bill the same way. Volume-based pricing models like SigNoz's avoid this scaling.

**Can I move from the Datadog Agent to the OpenTelemetry Collector on Kubernetes?**

Yes. Install the OpenTelemetry Operator, deploy a Collector DaemonSet (and a gateway Collector for cluster-level data), point your applications at OTLP, and remove the Datadog Agent. Full steps are in our [Datadog to SigNoz migration guide](https://signoz.io/docs/migration/migrate-from-datadog/).

**Does SigNoz work with the Datadog Operator?**

Not directly. The Datadog Operator manages Datadog Agents only. The OpenTelemetry equivalent is the [OpenTelemetry Operator](https://github.com/open-telemetry/opentelemetry-operator), which manages OpenTelemetry Collectors and ships with the same Kubernetes-native experience.

**Can I keep dd-trace on Kubernetes and use SigNoz?**

Indirectly. The OpenTelemetry Collector's Datadog Receiver can accept traffic from existing Datadog Agents (and `dd-trace`-instrumented apps) and forward it to SigNoz over OTLP. This lets you stage a migration without swapping SDKs on day one.
