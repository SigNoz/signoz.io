`dd-trace` is the tracing library Datadog ships as part of Datadog APM. It runs inside your application and records what your services are doing like incoming requests, database queries, calls to downstream services and sends that data to the Datadog Agent, which forwards it to Datadog. The result is what you see in the Datadog UI as traces, service maps, and APM metrics. Datadog ships a separate `dd-trace` package for each supported language (Python, Node.js, Go, Java, Ruby, .NET, and PHP), and the exact package names differ slightly across ecosystems.

`dd-trace` gets your tracing data into Datadog, but it does so by locking your application into Datadog's ecosystem. The libraries talk to Datadog's Agent in a proprietary protocol, they require Datadog-specific configuration such as `DD_SERVICE`, `DD_ENV`, `DD_TRACE_AGENT_URL`, and similar env vars. Once your code is instrumented with `dd-trace`, moving to any other observability backend means swapping out the SDK entirely, not just redirecting traffic to a different endpoint.

This article walks through what `dd-trace` actually does, how it's set up across each language, the common setup issues, and how teams replace it with OpenTelemetry and SigNoz.

## How dd-trace Works

<Figure
  src="/img/blog/2026/06/datadog-dd-trace.webp"
  alt="dd-trace pipeline into Datadog"
  caption="dd-trace data flow"
/>

Conceptually, `dd-trace` produces the same kind of trace data as any other tracing system. What separates it from a generic tracing SDK is how spans get created, what gets attached to them, and where they're sent.

`dd-trace` works in two ways: 
- Automatic instrumentation kicks in as soon as the library loads, producing spans for popular frameworks like Flask, Express, and more without you writing any tracing code. 
- Manual instrumentation handles anything that isn't auto-covered, such as a custom function, a background job, or a third-party SDK call. You wrap the operation in `dd-trace` calls and add your own tags.

When requests cross service boundaries, `dd-trace` propagates context using Datadog-specific headers like `x-datadog-trace-id` and `x-datadog-parent-id`, so the receiving service knows the request is part of an existing trace. Sampling decisions about which traces actually get sent to Datadog are made by the SDK and the Agent together based on configured rules. Each span is also tagged with the service name, environment, and version from your `DD_SERVICE`, `DD_ENV`, and `DD_VERSION` settings, which is what populates the service entities you see in the Datadog APM UI.

Once spans are produced, they're sent to the Datadog Agent running locally or as a sidecar, and the Agent forwards them to Datadog's backend over a proprietary HTTP API. The application never talks to Datadog's backend directly.

Each language has its own `dd-trace` package:

| Language | Package name | Install path | Auto-instrumentation |
| --- | --- | --- | --- |
| **Python** | `ddtrace` | `pip install ddtrace` | `ddtrace-run python app.py` or `import ddtrace.auto` |
| **Node.js** | `dd-trace` | `npm install dd-trace` | `require('dd-trace').init()` as the first import |
| **Go** | `gopkg.in/DataDog/dd-trace-go.v1` (v1) or `github.com/DataDog/dd-trace-go/v2` (v2) | `go get` the module | Per-package imports plus `tracer.Start()` |
| **Java** | `dd-java-agent.jar` | Download JAR, add `-javaagent:` JVM argument | Automatic via the agent |
| **Ruby** | `datadog` gem (formerly `ddtrace`) | `gem install datadog` | `Datadog.configure` block |
| **.NET** | `Datadog.Trace` NuGet, or the `dd-trace` global CLI tool | `dotnet add package Datadog.Trace` | Automatic via Datadog .NET tracer agent |
| **PHP** | `datadog/dd-trace` Composer package plus the `ddtrace` PHP extension | `pecl install datadog_trace` for the extension, `composer require datadog/dd-trace` for the library | Automatic once the extension is loaded |

If your application is in a language not in the above list, `dd-trace` doesn't support it. In that case, your options are OpenTelemetry (which has broader language coverage) or a community-maintained library.

## How dd-trace Makes Tracing Harder Than It Should Be

Beyond the bill and the lock-in, `dd-trace` quietly costs engineering time and the root cause for this cost is structural - each language SDK was built around Datadog's pipeline rather than a shared open standard, so the same product behaves differently across your stack and the rules aren't always obvious until something breaks in production.

Each language has different problems with `dd-trace`, and Node.js has the most. There, `dd-trace` uses runtime patching to attach itself to imports and assumes the library loads before anything else, an assumption that modern Node setups (ESM imports, webpack, esbuild, Next.js, Nest.js) violate in different ways, with fixes scattered across fragmented docs. 

Python is mid-migration between the older `ddtrace-run` command and the newer `import ddtrace.auto` entry point, which produces duplicate spans if you happen to use both. PHP needs a system-level `ddtrace` extension on top of the Composer package or auto-instrumentation does nothing, .NET only auto-instruments when your process is launched under the `dd-trace` CLI tool, and Go has no auto-instrumentation at all, so every integration is a manual import plus a `tracer.Start()` call.

Cutting across all of this, `DD_*` environment variables silently override anything you configure in code, so the service name your application thinks it's emitting isn't always what shows up in Datadog.

These are small problems on their own, but they add up to engineers debugging the tracer instead of the application. OpenTelemetry doesn't escape complexity entirely, but its instrumentation model is shared across languages and maintained by an open community, so the friction lives somewhere you can find documentation for, not in one vendor's release notes.

## dd-trace vs OpenTelemetry

<Figure
  src="/img/blog/2026/06/datadog-dd-trace-vs-otel.webp"
  alt="dd-trace vs OpenTelemetry pipelines"
  caption="dd-trace vs OpenTelemetry"
/>

Every difference below clearly shows how `dd-trace` is built for Datadog's pipeline, while OpenTelemetry is built as an open standard that any backend can implement.

| Aspect | `dd-trace` | OpenTelemetry |
| --- | --- | --- |
| **Maintained by** | Datadog | The CNCF (Cloud Native Computing Foundation) |
| **Wire protocol** | Datadog Agent protocol (proprietary HTTP API) | OTLP (open standard) |
| **Context propagation** | `x-datadog-trace-id`, `x-datadog-parent-id`, etc. | W3C Trace Context (the cross-vendor standard) |
| **Configuration** | `DD_*` environment variables | `OTEL_*` environment variables |
| **Backend** | Datadog only | Any OTLP-compatible backend |
| **Auto-instrumentation** | Datadog-maintained for each library | Community and vendor-maintained instrumentations |
| **Language support** | Python, Node.js, Go, Java, Ruby, .NET, PHP | Broader, including languages `dd-trace` doesn't support |
| **Lock-in** | Tracing code is tied to Datadog | None. The same SDK works with any OTLP backend |

Whether you stay on `dd-trace` or move to OpenTelemetry comes down to portability. `dd-trace` works only with Datadog while OpenTelemetry works with any compatible backend, so teams that expect to stay on Datadog indefinitely can keep `dd-trace`, and teams that want flexibility, lower cost, or independence from a single vendor's roadmap end up moving to OpenTelemetry.

## When to Replace dd-trace with OpenTelemetry

The most common reason teams move off `dd-trace` is cost. Datadog APM is `\$31` per host per month on the Pro plan, before any custom metrics or log line items, and at 100 hosts that's already `\$3,100/month` for APM alone. Moving to an OpenTelemetry-native backend usually drops that bill noticeably, especially at higher host counts.

At scale, the remaining reasons start to matter as much as the bill itself. Once your tracing code uses OpenTelemetry instead of `dd-trace`, you can point traces at any backend by changing a single endpoint, which `dd-trace` simply doesn't allow. OpenTelemetry is also the open standard the industry has settled on, so most new instrumentation work goes into OTel rather than vendor-specific SDKs. And because Datadog charges based on time series and tag combinations, rich tagging that's actually useful for debugging (like `customer_id` or `request_id`) drives the bill up faster than data volume alone, while most OpenTelemetry backends don't impose that pricing model.

If any of these apply, the swap itself is straightforward. For each language, you uninstall the `dd-trace` package, install the equivalent OpenTelemetry SDK, swap the `DD_*` environment variables for `OTEL_*`, and point the OTLP exporter at your new backend. The detailed steps per language are in our [Datadog APM migration guide](https://signoz.io/docs/migration/migrate-from-datadog/traces/).

## FAQs

**What does `dd-trace` do?**

It's Datadog's tracing SDK. It produces spans from your application, propagates trace context, and sends data to the Datadog Agent for forwarding to Datadog.

**Is `ddtrace` the same as `dd-trace`?**

Yes, just spelled differently per ecosystem. Python uses `ddtrace`, Node.js uses `dd-trace`.

**Is `dd-trace` open source?**

The libraries are open source, but the wire protocol and backend are Datadog's. You can't send `dd-trace` traffic anywhere other than Datadog without a translation layer.

**Does `dd-trace` work with OpenTelemetry?**

Partially. It accepts OTel-instrumented spans and supports W3C Trace Context, but it isn't an OpenTelemetry SDK. Full OTel means replacing `dd-trace` with the OTel SDK for that language.

**Is there a free Datadog option?**

No free tier for Datadog APM. For free production tracing, use SigNoz Community Edition or OpenTelemetry with an OSS backend.

**Which package do I install for my language?**

Python: `ddtrace` on PyPI. Node.js: `dd-trace` on npm. Go: `gopkg.in/DataDog/dd-trace-go.v1`. Java: `dd-java-agent.jar`. Ruby: `datadog` gem. .NET: `Datadog.Trace` on NuGet. PHP: `datadog/dd-trace` plus the `ddtrace` extension.

**Can I run `dd-trace` without the Datadog Agent?**

No. `dd-trace` only talks to the Datadog Agent (or the Datadog OpenTelemetry Collector), not directly to Datadog's backend.

**How do I move my services off Datadog's `dd-trace` SDK to OpenTelemetry?**

Uninstall the `dd-trace` package, install the OpenTelemetry SDK for that language, swap `DD_*` env vars for `OTEL_*`, and point the OTLP exporter at SigNoz Cloud. Per-language steps are in our [Datadog APM migration guide](https://signoz.io/docs/migration/migrate-from-datadog/traces/).
