<a href="https://github.com/winstonjs/winston" rel="noopener noreferrer nofollow" target="_blank">Winston Logger</a> is the most widely-used [Node.js logging](/guides/nodejs-logging/) library, offering production-grade logging capabilities. This library for Node.js is designed as a universal tool for managing and routing logs to multiple destinations in your applications.

Using Winston logger, you can set up multiple transports in a single logger, where each Winston transport acts as a storage device for your logs. Each transport can be configured to handle specific [log levels](/blog/logging-levels/), allowing you to route different logs to different places. For example, you might configure transport so that error logs go to a database, while all logs just print to the console during development. Winston also gives you full control over log formatting and lets you define custom Winston log levels to suit your application's needs.

## Key Features of Winston Logger

Winston logger provides enterprise-grade features that make it the go-to choice for Node.js logging. Here are the key capabilities that set the Winston logger apart:

1. **Multiple Transports:** Send logs to different destinations (console, files, databases, HTTP endpoints) simultaneously from a single logger.

2. **Winston Log Levels:** Comes with built-in severity levels like `error`, `warn`, `info`, `debug`, etc. You can also define your own custom levels.

3. **Custom Winston Format**: Control how your log messages appear using built-in formatters like `json`, `simple`, `colorize`, `timestamp`, or combine them to build your own Winston logger format.

4. **Exception & Rejection Handling:** Automatically catch and log uncaught exceptions and unhandled promise rejections so your app doesn't silently crash.

5. **Querying Logs:** Supports querying and streaming logs from specific transports, useful for reviewing historical log data.

6. **Profiling:** Winston has built-in support for measuring how long operations take between two points of code. It is helpful in tracking performance.

7. **Child Loggers:** You can create child loggers that inherit the parent's configuration while adding extra metadata, useful for adding context such as a request ID or module name.

## Getting Started with Winston Logger for Node.js

In this section, we'll install NPM Winston and create a basic Winston logger that demonstrates core Winston logging patterns.

### Prerequisites

Before you proceed with the next steps, make sure you have <a href="https://nodejs.org/en/download" rel="noopener noreferrer nofollow" target="_blank">Node.js</a> installed on your machine. This guide assumes you're working with Node.js 14 or higher, which provides the best compatibility for Winston JS features.

### Step 1: Install NPM Winston Package

```bash
npm install winston
```

### Step 2: Create a Basic Logger

Create a file called `logger.js` to configure your Winston logger with a basic Winston format:

```jsx:logger.js
const winston = require('winston');

const logger = winston.createLogger({
  level: 'info',
  format: winston.format.simple(),
  transports: [
    new winston.transports.Console()
  ]
});

logger.info('This is an info message');
logger.warn('This is a warning message');
logger.error('This is an error message');
```

### Step 3: Run and verify output

```bash
node logger.js
```

```bash:Output
info: This is an info message
warn: This is a warning message
error: This is an error message
```

This basic Winston logger example demonstrates the default Winston format in action. Each log line shows the severity level followed by the message, a pattern you'll recognize throughout Winston logging implementations.

Now that we have a basic logger up and running, let's explore each of Winston's core features in detail, starting with Winston log levels.

## Winston Log Levels Explained

Winston log levels follow the severity ordering specified by <a href="https://tools.ietf.org/html/rfc5424" rel="noopener noreferrer nofollow" target="_blank">RFC5424</a>, where all levels are numerically ordered from most important to least important. This Winston logging standard ensures consistent priority handling across your application.

The Winston logger uses NPM-style log levels by default, prioritized from 0 to 6 (highest to lowest):

```jsx
{
  error: 0,    // Something broke
  warn: 1,     // Something might be wrong
  info: 2,     // General information
  http: 3,     // HTTP request logs
  verbose: 4,  // Detailed information
  debug: 5,    // Debugging details
  silly: 6     // Log absolutely everything
}
```

You can log a message in one of two ways: either call the level name directly as a method, or pass it as a string to `log()`:

```jsx
// Using the level as a method (preferred, cleaner)
logger.info('User signed up successfully');
logger.error('Failed to connect to database');

// Using log() with the level as a string
logger.log('info', 'User signed up successfully');
logger.log('error', 'Failed to connect to database');
```

Both approaches produce identical Winston logging output. The method-based syntax (`logger.info()`) is cleaner and preferred in most Winston logger implementations, while the string-based approach (`logger.log('info', ...)`) offers more programmatic flexibility.

Winston also allows you to configure log levels per transport, so the Winston logger will only record that level and all levels above it (lower-priority levels). This per-transport Winston logging configuration is one of Winston's most powerful features. Messages below that threshold are ignored. For example, if you set a transport's level to `warn`, it will log `warn (1)` and `error (0)`, but skip `info (2)`, `debug (5)`, and everything else. This lets you keep your console clean during production while still capturing detailed logs in a file.

## Custom Winston Log Levels

In addition to the predefined `npm`, `syslog`, and `cli` levels available in Winston JS, you can define custom Winston log levels that match your application's specific needs. Just pass an object mapping level names to numeric priorities:

```jsx:logger.js
const winston = require('winston');

const customLevels = {
  critical: 0,
  important: 1,
  normal: 2,
  trivial: 3
};

const logger = winston.createLogger({
  levels: customLevels,
  level: 'normal',
  transports: [
    new winston.transports.Console()
  ]
});

// Winston automatically creates methods for each custom level
logger.critical('System is on fire');
logger.normal('User updated their profile');
logger.trivial('Button hover event tracked');
```

```bash:Output
{"level":"critical","message":"System is on fire"}
{"level":"normal","message":"User updated their profile"}
```

Custom Winston log levels give you fine-grained control over your Winston logging strategy. This Winston logger configuration automatically generates methods for each custom level, making your logging code more semantic and domain-specific.

## Winston Logger Format Guide

The Winston logger format system (introduced in Winston 3.x) dictates how log messages are transformed, structured, and serialized before output. Understanding Winston format options is crucial for production Winston logging.

At its core, a Winston format is a function that takes an `info` object (which always contains at least `level` and `message` properties) and modifies it before the Winston logger sends it to a transport.

```jsx
{
  level: 'info',
  message: 'Server started on port 3000'
}
```

The transport then takes this modified `info` object and writes it to the destination.

Formatting in Winston can be categorized into three main types based on how they are constructed and applied:

1. **Built-in Formats**

    The Winston logger provides a standard library of pre-defined formatters accessible via `winston.format`. These built-in Winston format options handle common Winston logging requirements out of the box.

    Key built-in formats include:

    - **`winston.format.json()`:** Serializes the `info` object into a JSON string. Standard for production environments, parsing logs to systems like ELK or Datadog.
    - **`winston.format.simple()`:** Returns a basic string representation: `level: message`.
    - **`winston.format.colorize()`:** Adds ANSI colour codes to the `level` or `message` for terminal readability.
    - **`winston.format.timestamp()`:** Appends a timestamp property to the `info` object.
    - **`winston.format.printf()`:** Allows you to define a custom string layout using a callback function.
    - **`winston.format.errors({ stack: true })`:** Catches standard JavaScript `Error` objects and ensures their stack traces are included in the log output.

    These Winston format examples show the most commonly used formatters. You can apply any Winston logger format individually or combine multiple formats for complex Winston logging scenarios.

    For example:

    ```jsx:logger.js {4}
    const winston = require('winston');
    
    const jsonLogger = winston.createLogger({
      level: 'info',
      format: winston.format.json(),
      transports: [new winston.transports.Console()]
    });
    
    jsonLogger.info('Server started', { port: 8080 });
    // Output: {"port":8080,"level":"info","message":"Server started"}
    ```

2. **Combined Winston Format Patterns**

    The Winston logger allows you to chain multiple Winston format functions using `winston.format.combine()`. This creates a pipeline where each Winston format processes the log sequentially. The formats are executed in the order they are defined, operating on the `info` object sequentially like a pipeline.

    For example:

    ```jsx:winstonLoggerFormat.js {4-7,11-15}
    const winston = require('winston');
    const { combine, timestamp, printf, colorize } = winston.format;
    
    // Define a custom string format for the final output
    const myFormat = printf(({ level, message, timestamp }) => {
      return `${timestamp} [${level}]: ${message}`;
    });
    
    const pipelineLogger = winston.createLogger({
      level: 'debug',
      format: combine(
        colorize(),          // 1. Colorize the level
        timestamp(),         // 2. Add a timestamp property
        myFormat             // 3. Format the final string
      ),
      transports: [new winston.transports.Console()]
    });
    
    pipelineLogger.debug('Debugging database connection');
    // Output: 2026-04-21T06:16:41.000Z [\u001b[34mdebug\u001b[39m]: Debugging database connection
    ```

    This Winston format example demonstrates a common pattern: colorizing for readability, adding timestamps for debugging, and custom formatting for the final output. The Winston logger executes these Winston format functions in order, making complex Winston logging transformations maintainable.

3. **Custom Winston Format Functions**

    If the built-in formats do not meet your exact requirements, you can create a custom Winston format using `winston.format(transformFn)`. The transform function takes the `info` object and an optional `opts` object, modifies `info`, and returns it. If the function returns `false`, the log message is completely ignored (filtered out).

    For example:

    ```jsx:winstonLoggerFormat.js  {3-12}
    const winston = require('winston');
    
    // Create a custom format that redacts sensitive data
    const redactData = winston.format((info, opts) => {
      if (info.password) {
        info.password = '[REDACTED]';
      }
      if (info.creditCard) {
        info.creditCard = '**-**-****-' + info.creditCard.slice(-4);
      }
      return info; // Must return the modified info object
    });
    
    const customLogger = winston.createLogger({
      level: 'info',
      format: winston.format.combine(
        redactData(),
        winston.format.json()
      ),
      transports: [new winston.transports.Console()]
    });
    
    customLogger.info('User registration attempt', { 
      user: 'admin', 
      password: 'supersecretpassword123' 
    });
    
    //Output: {"level":"info","message":"User registration attempt","password":"[REDACTED]","user":"admin"}
    ```

    This custom Winston format demonstrates how to sanitize sensitive data in your Winston logging pipeline. The Winston logger applies this Winston format before any transport receives the log, ensuring consistent data redaction across all destinations.

## Winston Logger Transports Explained

In the Winston logger, a transport is the destination to which your logs are sent. Understanding Winston logging transports is fundamental to routing logs effectively in production. The most basic example is logging to the console, where you configure a single transport, and every log message flows to that one place. This is useful during development when you just want to see output in your terminal.

```jsx:logger.js
const winston = require('winston');

const logger = winston.createLogger({
  transports: [
    new winston.transports.Console()
  ]
});

logger.info('Hello from basic transport!');
```

This basic Winston logger configuration sends all Winston logging output to the console using a single transport. While this works for development, production Winston logger setups typically use multiple transports for different log levels.

A single Winston logger instance can utilize multiple transports simultaneously. This is one of the core strengths of Winston logging. This allows you to route logs of different severity levels to different destinations based on your Winston format preferences, or to apply different formats to each destination (e.g., colourized text for the console, pure JSON for a file). This is helpful in production where you want real-time visibility in the terminal while also persisting logs to disk for later analysis. Each transport can have its own log level, so you could send only errors to a file but all messages to the console.

```jsx:logger.js
const winston = require('winston');

const logger = winston.createLogger({
  transports: [
    new winston.transports.Console({ level: 'info' }),
    new winston.transports.File({ filename: 'app.log', level: 'error' })
  ]
});

logger.info('Shown only in console');
logger.error('Shown in console AND saved to app.log');

// Output: 
// {"level":"info","message":"Shown only in console"}
// {"level":"error","message":"Shown in console AND saved to app.log"}
```

This multi-transport Winston logger demonstrates a common production pattern: send all logs to the console for real-time monitoring, but persist only errors to disk. The Winston logging library efficiently handles concurrent writes to multiple destinations.

You can also build a custom Winston logger transport by extending the base `Transport` class, giving you complete control over where and how Winston logging occurs. You implement a `log()` method that defines exactly what happens when a message arrives. This is the go-to approach when built-in Winston transports don't fit your specific needs.

```jsx:logger.js
const Transport = require('winston-transport');
const winston = require('winston');

class MyCustomTransport extends Transport {
  log(info, callback) {
    console.log(`[CUSTOM] ${info.level}: ${info.message}`);
    callback();
  }
}

const logger = winston.createLogger({
  transports: [new MyCustomTransport()]
});

logger.info('Handled by my custom transport!');

//Output: [CUSTOM] info: Handled by my custom transport!
```

There are dozens of <a href="https://github.com/winstonjs/winston/blob/master/docs/transports.md#additional-transports" rel="noopener noreferrer nofollow" target="_blank">community-maintained external transports</a> for routing logs directly to databases (MongoDB, Redis), cloud services (AWS CloudWatch, Datadog), or message brokers.

## Exception Handling in Winston Logger

The Winston logger intercepts and logs unhandled errors that would otherwise crash your Node.js process. This Winston logging feature is critical for production diagnostics. By default, Winston only logs what you explicitly tell it to. However, these two features allow it to "listen" for global failures.

### Handling Uncaught Exceptions

An uncaught exception occurs when a synchronous error is thrown and not caught by a `try...catch` block. Normally, Node.js prints the stack trace to `stderr` and exits with code `1`. When you configure `exceptionHandlers` in Winston logger, it attaches a listener to the `process.on('uncaughtException')` event.

By default, Winston will exit the process after logging an exception. You can override this by setting `exitOnError: false`, though this is generally discouraged as the process state may be corrupted. You can also direct exceptions to a specific file or remote endpoint separate from your standard application logs.

```jsx:logger.js
const winston = require('winston');

const logger = winston.createLogger({
  transports: [
    new winston.transports.File({ filename: 'combined.log' })
  ],
  exceptionHandlers: [
    // This will catch any uncaught synchronous errors
    new winston.transports.File({ filename: 'exceptions.log' })
  ]
});

// Triggering an uncaught exception
throw new Error('This will be caught by the exceptionHandler');
```

This Winston logger configuration separates exception logs from application logs, making it easier to monitor critical failures. The Winston logging library writes exceptions to a dedicated file while continuing to handle normal logs through separate transports.

### Handling Unhandled Rejections

An unhandled rejection occurs when a Promise is rejected (e.g., an API call fails) and there is no `.catch()` block or `await` inside a `try...catch` to handle it.

For example:

```jsx:logger.js
const winston = require('winston');

const logger = winston.createLogger({
  transports: [
    new winston.transports.Console()
  ],
  rejectionHandlers: [
    // This will catch any unhandled promise rejections
    new winston.transports.File({ filename: 'rejections.log' })
  ]
});

// Triggering an unhandled rejection
Promise.reject(new Error('Async failure captured by rejectionHandler'));
```

This Winston logger example handles async errors that would otherwise go unnoticed. By configuring rejection handlers, your Winston logging captures promise failures before they terminate the process.

## Performance Profiling with Winston Logger

Profiling in the Winston logger is a lightweight mechanism for measuring execution time between code checkpoints. This Winston logging feature helps identify performance bottlenecks without external dependencies. It works by capturing a high-resolution timestamp when you `start` a profile, calculating the delta (duration) when you `stop` it, and then automatically emitting a log entry.

**How does it work?**

The Winston logger profiling system uses a stateful timer keyed by a unique string ID. This Winston logging approach requires minimal overhead while providing accurate duration measurements. The profiling can be split into two phases.

**Start Phase:** When `logger.profile(id)` is called for the first time with a specific ID, Winston stores the current timestamp in an internal map associated with that ID.

**End Phase:** When `logger.profile(id)` is called a second time with the same ID, Winston retrieves the stored timestamp, calculates the difference against the current time, deletes the ID from the internal map to free memory, and finally outputs a log message at the `info` level (by default) containing the duration in milliseconds.

The following example demonstrates how to profile a synchronous or asynchronous operation without using external hooks or abstractions.

```jsx:logger.js
const winston = require('winston');

// 1. Set up a basic logger
const logger = winston.createLogger({
  level: 'debug',
  format: winston.format.combine(
    winston.format.timestamp(),
    winston.format.json()
  ),
  transports: [new winston.transports.Console()]
});

async function heavyTask() {
  // 2. Start the timer for 'database-query'
  logger.profile('database-query');

  // Simulate an asynchronous operation (e.g., DB call)
  await new Promise(resolve => setTimeout(resolve, 1500));

  // 3. End the timer. 
  // Winston calculates the delta and logs it automatically.
  logger.profile('database-query', { 
    message: 'Completed fetching user records', 
    level: 'debug' // Optional: override default 'info' level
  });
}

heavyTask();
```

The output will include a `durationMs` field, which is injected automatically by the profiling logic.

```jsx:Output
{
  "level": "debug",
  "message": "Completed fetching user records",
  "timestamp": "2026-04-21T16:20:00.000Z",
  "durationMs": 1501
}
```

This Winston logger example shows how to measure the duration of an async operation. The Winston logging system automatically calculates elapsed time and includes it in the log output, making performance analysis straightforward.

## Centralizing Logs in a Log Management Tool

A running Node.js service emits logs from multiple sources: the application process, its dependencies, the runtime, and any sidecars or middleware in the request path. When these logs live only on the local filesystem or in container stdout, debugging a production incident requires SSH access to individual hosts or `kubectl logs` against short-lived pods whose output disappears upon recycling. This breaks down as soon as the deployment scales beyond a single instance.

This Winston logging integration enriches log records with `trace_id` and `span_id`, enabling you to jump from a trace to the exact Winston logger output that was produced during that request. Logs emitted inside a trace span are enriched with `trace_id` and `span_id`, so when you are looking at a slow request in the traces view, you can jump straight to the exact log lines that were produced during that request. You also get structured search over your log metadata, [log-based alerts](/docs/alerts-management/log-based-alerts/), and [dashboards](/metrics-and-dashboards/), all without touching your existing `logger.info()` and `logger.error()` calls.

## Conclusion

The Winston logger covers the full range of what Node.js applications need from a logging library: multiple transports, configurable Winston log levels, the flexible Winston logger format system, automatic exception handling, and built-in profiling. These features are enough to handle logging inside a single process, and the flexibility to plug in custom transports and formats means you can shape it to fit almost any workflow.
